Appendix E

Exploring Repo Context with graft

graft is a pre-built context graph of your repository. When you need to understand code, find where to make a change, or trace the blast radius of an edit, asking graft first — instead of grepping or opening files blind — gets you an exact file:line answer for far fewer tokens.

What this appendix covers
  • What graft is and why it exists
  • Why reach for graft before grep or reading files directly
  • The five core commands (ask, grep, skeleton, callers, map)
  • Using graft as MCP tools (in supported environments)
  • A real-world workflow example
  • Refreshing the graph after code changes

1. What is graft

graft scans a repository and produces a graph of small markdown nodes — one per file, each explaining what the file does, what symbols it defines, and who calls it. This graph lives in a graft/ directory and is kept in sync with the code through git as the codebase evolves.

grep only tells you where a string appears. graft is a pre-built map that already tells you where a concept is defined, how it behaves, and who uses it. It's the difference between wandering a new city block by block and being handed a map someone already drew.

graft can be used two ways:

  • CLI — run graft <subcommand> directly from the terminal
  • MCP tools — when the host (e.g. Claude Code) exposes tools like graft_find_code, graft_find_all, graft_trace_calls, graft_file_api, and graft_repo_map, the same graph is queried through tool calls instead
In this workspace, a SessionStart hook reminds you to use graft at the start of every session. In practice, that means: for any task involving understanding or changing code, reach for graft first — that is the baseline rule here.

2. Why graft instead of grep

Situation grep / reading files directly graft
"How does this feature work?" Have to guess which files are relevant and open several graft ask returns ranked results with code snippets inline, immediately
"Who calls this symbol?" String search plus manual cross-checking (lots of false positives) graft callers reads the exact call edges straight from the graph
"Find every occurrence of this pattern" Possible with grep -rn, but results are unorganized graft grep groups every hit by its enclosing symbol
"I want to skim this file's whole API" Have to read the entire file (expensive in tokens) graft skeleton gives every signature at roughly 10x lower cost
"New to this repo, where do I start?" Read the README and open folders one by one graft map summarizes directory clusters, hubs, and hotspots within a token budget
The core principle: pick the one tool that fits the task shape, and act on its answer. Calling the same tool over and over, or re-asking a slightly reworded question, wastes effort. If one call isn't enough, switch to the different tool that fits the next need.

3. Core Commands

3.1 graft map — orientation for an unfamiliar repo

Run this first when you're new to a repository. No LLM call involved (free), it shows directory structure, hub files, and hotspots within a token budget.

graft map

Note: map is the answer on its own. Following up by running skeleton on every subsystem it names is overuse.

3.2 graft ask — find where to understand or edit

For questions like "how does this work?" or "where is this defined?", it returns ranked results with code snippets inlined.

graft ask "how does the retry logic behave on login failure" --source
  • --source — shows each hit's crux code (8 lines by default) alongside the result
  • --full — when 8 lines isn't enough, shows the whole definition
  • For understanding or editing, the top result IS the answer. Cite the file:line from covers: and edit straight from the --source output.
Don't use ask for exhaustive tasks like "find every occurrence of this pattern." ask is ranked, top-N only — it does not guarantee completeness. Use graft grep for exhaustive searches.

3.3 graft grep — exhaustive search

Finds every occurrence of a literal string or symbol, grouped by the symbol that encloses each hit.

graft grep "processPayment"

Fall back to raw grep -rn only when you need to cover files that aren't indexed.

3.4 graft skeleton — a file's whole API at a glance

Shows every definition's signature and location without reading the whole file, at roughly 10x lower cost. Useful for skimming an API surface.

graft skeleton src/services/payment.ts

3.5 graft callers — trace exact call relationships

Before changing a symbol, find out exactly who calls it (or what it calls). Always run this before a refactor or rename.

# Who calls this symbol (default)
graft callers formatCurrency

# What this symbol calls
graft callers formatCurrency --direction out

# Full blast radius (every connected file)
graft callers formatCurrency --depth all
The classic mistake in refactors, renames, or multi-file changes is editing only the primary file and stopping there. Run graft callers <symbol> --depth all first to map every connected file, then edit.

4. Using It as MCP Tools

In host environments like Claude Code, the same graph can be queried through MCP tool calls instead of the CLI. The mapping is:

CLI command MCP tool
graft askgraft_find_code
graft grepgraft_find_all
graft callersgraft_trace_calls
graft skeletongraft_file_api
graft mapgraft_repo_map
Call edges — who calls what — live only in the graph, not in the node markdown files themselves. graft callers / graft_trace_calls is the only way to read them.

5. Real-World Workflow

Step 1: New repo? Start with map

If you're unfamiliar with a project, run graft map first to get the overall lay of the land.

Step 2: Pick the tool that fits the task

Understanding or editing → ask --source. Exhaustive search → grep. Skimming an API → skeleton. Mapping blast radius → callers.

Step 3: Edit straight from the result

Cite the file:line and snippet returned by ask --source and edit directly from it. If a span is truncated (+N more lines), open the file at that exact range to confirm before finalizing.

Step 4: Refresh the graph after big changes

After a significant code change, run graft build to bring the graph back up to date.

6. Refreshing the Graph (graft build)

The graft graph is generated deterministically and can be refreshed for free, with no LLM API key required. After a large code change — new files, a major refactor — rebuild the graph to keep it current.

graft build
You don't need to run build after every small edit. The graph is version-controlled alongside git; refreshing it once after a meaningful chunk of work is enough.
As of 2026-09-20: when you create a new project (new-project.ts), the graft graph is built automatically during scaffolding. It first uses the globally installed graft command and falls back to bunx if that is missing. In other words, a freshly scaffolded project can answer graft ask questions from day one.
In short: understand or edit → graft ask, find everything → graft grep, skim an API → graft skeleton, trace blast radius → graft callers, new to a repo → graft map. Those five are all you need to remember.
