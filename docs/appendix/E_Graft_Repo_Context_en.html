Appendix E

Exploring Repo Context with trail

trail is a pre-built context graph of your repository. When you need to understand code, find where to make a change, or trace the blast radius of an edit, asking trail first — instead of grepping or opening files blind — gets you an exact file:line answer for far fewer tokens.

What this appendix covers
  • What trail is and why it exists
  • Why reach for trail before grep or reading files directly
  • The five core commands (ask, grep, skeleton, callers, map)
  • Using trail as MCP tools (in supported environments)
  • A real-world workflow example
  • Refreshing the graph after code changes
What's new (2026-11): the tool was renamed. trail is the vendor rename of graft 0.28 (install: npm i -g @trailhq/trail-code; the graft-era package @nanonets/graft still resolves). Everything this appendix teaches carries over — the commands just say trail now: trail map, trail ask, trail grep, trail skeleton, trail callers, trail build. The MCP tool names keep the vendor's graft spelling (graft_find_code, graft_find_all, graft_trace_calls, graft_file_api, graft_repo_map) — vendor-internal surface, not ours to rename. Policy: ADR-0076; migration design: docs/designs/2026-10-31-graft-trail-migration-design.md in the upstream workspace.

1. What is trail

trail scans a repository and produces a graph of small markdown nodes — one per file, each explaining what the file does, what symbols it defines, and who calls it. This graph lives in a .trail/cache/ directory (graft-era checkouts that haven't run trail init yet still use graft/) and is kept in sync with the code through git as the codebase evolves.

grep only tells you where a string appears. trail is a pre-built map that already tells you where a concept is defined, how it behaves, and who uses it. It's the difference between wandering a new city block by block and being handed a map someone already drew.

trail can be used two ways:

  • CLI — run trail <subcommand> directly from the terminal
  • MCP tools — when the host (e.g. Claude Code) exposes tools like graft_find_code, graft_find_all, graft_trace_calls, graft_file_api, and graft_repo_map, the same graph is queried through tool calls instead (the tool names keep the vendor's graft spelling)
In this workspace, a SessionStart hook reminds you to use trail at the start of every session. In practice, that means: for any task involving understanding or changing code, reach for trail first — that is the baseline rule here.

2. Why trail instead of grep

Situation grep / reading files directly trail
"How does this feature work?" Have to guess which files are relevant and open several trail ask returns ranked results with code snippets inline, immediately
"Who calls this symbol?" String search plus manual cross-checking (lots of false positives) trail callers reads the exact call edges straight from the graph
"Find every occurrence of this pattern" Possible with grep -rn, but results are unorganized trail grep groups every hit by its enclosing symbol
"I want to skim this file's whole API" Have to read the entire file (expensive in tokens) trail skeleton gives every signature at roughly 10x lower cost
"New to this repo, where do I start?" Read the README and open folders one by one trail map summarizes directory clusters, hubs, and hotspots within a token budget
The core principle: pick the one tool that fits the task shape, and act on its answer. Calling the same tool over and over, or re-asking a slightly reworded question, wastes effort. If one call isn't enough, switch to the different tool that fits the next need.

3. Core Commands

3.1 trail map — orientation for an unfamiliar repo

Run this first when you're new to a repository. No LLM call involved (free, $0), it shows directory structure, hub files, and hotspots within a token budget.

trail map

Note: map is the answer on its own. Following up by running skeleton on every subsystem it names is overuse.

3.2 trail ask — find where to understand or edit

For questions like "how does this work?" or "where is this defined?", it returns ranked results with code snippets inlined.

trail ask "how does the retry logic behave on login failure" --source
  • --source — shows each hit's crux code (8 lines by default) alongside the result
  • --full — when 8 lines isn't enough, shows the whole definition
  • For understanding or editing, the top result IS the answer. Cite the file:line from covers: and edit straight from the --source output.
Don't use ask for exhaustive tasks like "find every occurrence of this pattern." ask is ranked, top-N only — it does not guarantee completeness. Use trail grep for exhaustive searches.

3.3 trail grep — exhaustive search

Finds every occurrence of a literal string or symbol, grouped by the symbol that encloses each hit.

trail grep "processPayment"

Fall back to raw grep -rn only when you need to cover files that aren't indexed.

3.4 trail skeleton — a file's whole API at a glance

Shows every definition's signature and location without reading the whole file, at roughly 10x lower cost. Useful for skimming an API surface.

trail skeleton src/services/payment.ts

3.5 trail callers — trace exact call relationships

Before changing a symbol, find out exactly who calls it (or what it calls). Always run this before a refactor or rename.

# Who calls this symbol (default)
trail callers formatCurrency

# What this symbol calls
trail callers formatCurrency --direction out

# Full blast radius (every connected file)
trail callers formatCurrency --depth all
The classic mistake in refactors, renames, or multi-file changes is editing only the primary file and stopping there. Run trail callers <symbol> --depth all first to map every connected file, then edit.

4. Using It as MCP Tools

In host environments like Claude Code, the same graph can be queried through MCP tool calls instead of the CLI. The mapping is:

CLI command MCP tool
trail askgraft_find_code
trail grepgraft_find_all
trail callersgraft_trace_calls
trail skeletongraft_file_api
trail mapgraft_repo_map
Call edges — who calls what — live only in the graph, not in the node markdown files themselves. trail callers / graft_trace_calls is the only way to read them.

5. Real-World Workflow

Step 1: New repo? Start with map

If you're unfamiliar with a project, run trail map first to get the overall lay of the land.

Step 2: Pick the tool that fits the task

Understanding or editing → ask --source. Exhaustive search → grep. Skimming an API → skeleton. Mapping blast radius → callers.

Step 3: Edit straight from the result

Cite the file:line and snippet returned by ask --source and edit directly from it. If a span is truncated (+N more lines), open the file at that exact range to confirm before finalizing.

Step 4: Refresh the graph after big changes

After a significant code change, run trail build to bring the graph back up to date.

6. Refreshing the Graph (trail build)

The trail graph is generated deterministically and can be refreshed for free, with no LLM API key required. After a large code change — new files, a major refactor — rebuild the graph to keep it current.

trail build
You don't need to run build after every small edit. The graph is version-controlled alongside git; refreshing it once after a meaningful chunk of work is enough. Two related commands: trail check reports index freshness, and on a repo migrated by trail init pass --dir .trail/cache to trail build — the binary still defaults its graph directory to the graft-era <repo>/graft.
As of 2026-09-20: when you create a new project (new-project.ts), the graph is built automatically during scaffolding. It first uses the globally installed command and falls back to bunx if that is missing. In other words, a freshly scaffolded project can answer trail ask questions from day one.

Update (2026-10): the workspace itself no longer carries graft’s integration files. The skill is marked mirror: false and l2_propagate: false in its frontmatter, and scaffolded AGENTS.md files no longer receive a pre-rendered graft block — graph surfaces are tool-owned, so run trail init once in a checkout to materialize them. The scaffold-time graph build described above still works the same way.

Update (2026-11): the skill itself was renamed with the vendor: skills/graft became skills/trail upstream, and trail init (which also runs inside trail upgrade) finishes the per-repo migration — it swaps the instruction-block markers, moves the graph index to .trail/cache/, replaces helper hooks with .trail/hook.cjs, and deletes the tracked .mcp.json seed. Verify a checkout with trail check and ls .trail/cache/INDEX.md.

In short: understand or edit → trail ask, find everything → trail grep, skim an API → trail skeleton, trace blast radius → trail callers, new to a repo → trail map. Those five are all you need to remember.
