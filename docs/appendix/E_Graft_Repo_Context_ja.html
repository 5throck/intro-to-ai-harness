付録E

trailでリポジトリコンテキストを探索する

trailはリポジトリをあらかじめインデックス化したコンテキストグラフです。コードを理解したり、どこを修正すべきか探したり、変更の影響範囲を把握したりするとき、grepやファイルを直接開く代わりに先にtrailへ尋ねると、はるかに少ないトークンで正確なfile:line位置が得られます。

この付録で扱う内容
  • trailとは何か、なぜ必要か
  • grep/ファイル直接読み込みより先にtrailを使うべき理由
  • 主要コマンド5つ (ask, grep, skeleton, callers, map)
  • MCPツールとしてtrailを使う方法（対応環境）
  • 実践ワークフローの例
  • コード変更後のグラフ更新
2026-11の新情報：ツールの名前が変わりました。trailはgraft 0.28のベンダーによるリネームです（インストール: npm i -g @trailhq/trail-code。graft時代のパッケージ@nanonets/graftも引き続き解決されます）。この付録の内容はそのまま有効で、コマンドの接頭辞がtrailに変わるだけです: trail map、trail ask、trail grep、trail skeleton、trail callers、trail build。MCPツール名はベンダーのgraft表記をそのまま維持します（graft_find_code、graft_find_all、graft_trace_calls、graft_file_api、graft_repo_map）— ベンダー内部のサーフェスであり、こちらでは改名しません。ポリシー: ADR-0076、移行設計: 上流ワークスペースのdocs/designs/2026-10-31-graft-trail-migration-design.md。

1. trailとは何か

trailはリポジトリをスキャンし、ファイルごとに「このファイルが何をするか、どのシンボルを定義しているか、誰が呼び出しているか」を整理した小さなMarkdownノードのグラフを作成します。このグラフは.trail/cache/ディレクトリに保存され（trail initをまだ実行していないgraft時代のチェックアウトはgraft/をそのまま使います）、コードが変わるたびにgitと共に更新されます。

grepは「この文字列がどこにあるか」だけを教えてくれます。trailは「この概念がどこで定義され、どう動作し、誰が使っているか」まであらかじめ整理された地図です。初めて訪れる街を路地ごとに歩き回るのと、すでに作られた地図を見るのとの違いです。

trailは2つの方法で使えます：

  • CLI — ターミナルでtrail <subcommand>の形式で直接実行
  • MCPツール — ホスト（Claude Codeなど）がgraft_find_code、graft_find_all、graft_trace_calls、graft_file_api、graft_repo_mapのようなツールを公開している場合、同じグラフをツール呼び出しで照会（ツール名はベンダーのgraft表記を維持）
このワークスペースでは、セッション開始時にSessionStartフックがtrailの利用を案内します。つまり、コードを理解したり修正したりする作業であれば、まずtrailを確認することがこのワークスペースの基本ルールです。

2. なぜgrepではなくtrailなのか

状況 grep / ファイル直接読み込み trail
「この機能はどう動作するか？」 関連ファイルを推測して複数開く必要がある trail askがコードスニペット付きのランキング結果を即座に返す
「このシンボルを誰が呼び出しているか？」 文字列検索＋手動照合（誤検出が多い） trail callersが正確な呼び出し関係をグラフから直接照会
「このパターンが出現する箇所を全部探したい」 grep -rnで可能だが結果が整理されない trail grepが包含するシンボルごとにグループ化して表示
「このファイルのAPI全体をざっと確認したい」 ファイル全体を読む必要がある（トークン消費が大きい） trail skeletonがシグネチャだけを約10倍安く提供
「初めて見るリポジトリ、どこから始める？」 READMEを読んでフォルダを一つずつ開いていく trail mapがディレクトリクラスター・ハブ・ホットスポットをトークン予算内で要約
核心原則は「作業の形に合ったツールを一つ選び、その答えで行動する」ことです。同じツールを繰り返し呼び出したり、質問を少し変えて再度尋ねたりするのは非効率です。一度で足りない場合は、次に必要な別のツールに切り替えましょう。

3. 主要コマンド

3.1 trail map — 初めてのリポジトリのオリエンテーション

初めて見るリポジトリでまず実行します。LLM呼び出しなし（無料、$0）で、ディレクトリ構造・ハブファイル・ホットスポットをトークン予算内で表示します。

trail map

注意：mapそのものがオリエンテーションの答えです。mapが言及したすべてのサブシステムをskeletonで追いかけるのは過剰使用です。

3.2 trail ask — 理解・修正すべき場所を探す

「これはどう動作するか？」「このコードはどこにあるか？」といった質問に、コードスニペット付きのランキング結果を返します。

trail ask "ログイン失敗時のリトライロジックはどう動作するか" --source
  • --source — 各結果に核心コード（デフォルト8行）を一緒に表示
  • --full — 8行で不十分な場合、定義全体を表示
  • 理解・修正作業であれば、1位の結果がそのまま答えです。covers:に明記されたfile:lineを引用し、--source結果からそのまま修正します。
「このパターンが出現するすべての箇所」のような網羅的な調査にはaskを使わないでください。askはランキング上位N件に過ぎず、全体を保証しません。網羅的な調査にはtrail grepを使いましょう。

3.3 trail grep — 網羅的検索

リテラル文字列やシンボルのすべての出現箇所を、それを包含するシンボル単位でグループ化して表示します。

trail grep "processPayment"

インデックスされていないファイルまで確認が必要な場合のみ、生のgrep -rnで補います。

3.4 trail skeleton — ファイルAPIを一目で確認

ファイル全体を読まずに、すべての定義のシグネチャと位置を約10倍安く確認できます。API全体をざっと見たいときに便利です。

trail skeleton src/services/payment.ts

3.5 trail callers — 正確な呼び出し関係を追跡

あるシンボルを変更する前に、それを誰が呼び出しているか（またはそれが何を呼び出しているか）を正確に把握します。リファクタリングや名前変更の前には必ず実行しましょう。

# このシンボルを呼び出している箇所（デフォルト）
trail callers formatCurrency

# このシンボルが呼び出しているもの
trail callers formatCurrency --direction out

# 全体の影響範囲（つながっているすべてのファイル）
trail callers formatCurrency --depth all
リファクタリング・名前変更・複数ファイル変更でよくあるミスは、主ファイルだけ修正して止まってしまうことです。trail callers <symbol> --depth allでつながっているすべてのファイルを先に地図化してから修正しましょう。

4. MCPツールとして使う

Claude Codeのようなホスト環境では、同じグラフをCLIの代わりにMCPツール呼び出しで照会できます。対応関係は次の通りです：

CLIコマンド MCPツール
trail askgraft_find_code
trail grepgraft_find_all
trail callersgraft_trace_calls
trail skeletongraft_file_api
trail mapgraft_repo_map
呼び出し関係（誰が何を呼んでいるか）のようなエッジ情報はグラフにのみ存在します — ノードのMarkdownファイルを直接読んでもわかりません。trail callers / graft_trace_callsがこのエッジを読む唯一の方法です。

5. 実践ワークフロー

ステップ1: 初めてのリポジトリならmapから

初めて触れるプロジェクトであれば、まずtrail mapで全体構造を把握します。

ステップ2: 作業の形に合ったツールを選ぶ

理解・修正ならask --source、網羅的調査ならgrep、API確認ならskeleton、影響範囲の把握ならcallersを使います。

ステップ3: 結果からそのまま修正

ask --sourceが返したfile:lineとコードスニペットをそのまま引用しながら修正します。結果が切り詰められている場合（+N more lines）は、その正確な範囲だけファイルで開いて確認します。

ステップ4: 大きな変更後にグラフを更新

コードを大きく変更した後は、trail buildでグラフを最新状態に合わせます。

6. グラフの更新 (trail build)

trailのグラフは決定論的に生成され、LLM APIキーなしで無料で更新できます。大規模なコード変更（新規ファイル追加、大規模リファクタリングなど）の後は、グラフを再ビルドして最新状態を保ちましょう。

trail build
小さな修正のたびにbuildを実行する必要はありません。グラフはgitと共にバージョン管理されており、意味のある単位の変更が終わった後に一度更新すれば十分です。一緒に覚えておくべきコマンド：trail checkはインデックスの鮮度を表示し、trail initで移行されたリポジトリではtrail buildに--dir .trail/cacheを渡す必要があります — バイナリは依然としてgraft時代のデフォルト<repo>/graftをグラフディレクトリとして使います。
2026-09-20から: 新しいプロジェクトを作るとき(new-project.ts)は、スキャフォールディングの過程でグラフが自動的にビルドされます。グローバルにインストールされたコマンドをまず使い、なければbunxで代替実行します。つまり、新しく作ったプロジェクトは最初からtrail askで質問できます。

2026-10アップデート：ワークスペース自体はgraftの統合ファイルをテンプレートとして同梱しなくなりました。スキルはfrontmatterにmirror: falseとl2_propagate: falseを持ち、スキャフォールドされたAGENTS.mdには事前レンダリングされたgraftブロックが入らなくなっています — グラフのサーフェスはツール所有のため、チェックアウトで一度trail initを実行すれば生成されます。上記のスキャフォールディング時のグラフビルドは以前と同じく動作します。

2026-11アップデート：スキルもベンダーのリネームに従い、skills/graftがskills/trailに変わりました。trail init（trail upgradeの中でも実行されます）がリポジトリ単位のマイグレーションを仕上げます — 命令ブロックのマーカー交換、グラフインデックスの.trail/cache/への移動、ヘルパーフックの.trail/hook.cjsへの置き換え、バージョン管理されていた.mcp.jsonシードの削除。チェックアウトの状態はtrail checkとls .trail/cache/INDEX.mdで確認できます。

まとめると：理解・修正するとき → trail ask、すべて探すとき → trail grep、APIをざっと見るとき → trail skeleton、影響範囲を見るとき → trail callers、初めてのリポジトリを見るとき → trail map。この5つだけ覚えれば十分です。
