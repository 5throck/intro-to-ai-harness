Chapter 4

Multi-Agent Harness Concepts

Learn the core concepts of the multi-agent harness: agents, skills, PM orchestration, the 3-Tier strategy, the PM Gateway, dispatch flow, and handoff contracts — in this chapter you will understand the entire skeleton of the harness.

What This Chapter Covers
  • Definitions of agents and skills
  • PM orchestration and the role of the PM Gateway
  • The 3-Tier strategy (High/Medium/Low)
  • Dispatch flow and handoff contracts
  • The complete harness architecture diagram

What Are Agents

Definition of an Agent

An agent is an AI assistant that is given a specific role and performs tasks according to defined behavioral instructions. Unlike an ordinary chatbot, an agent has its own name, role, and rules of behavior, and it is granted permission to read and write files and to use tools.

As Chapter 1 illustrated, an agent is like an employee of a company. The PM is the team leader, and specialist agents are the experts in each department. When the planning agent, the design agent, and the coding agent each do their part, the whole project moves forward efficiently.

Components of an Agent

Each agent consists of four core elements. Together, these four define a single agent.

In concrete terms:

  1. Identifier (name) — The unique name that distinguishes the agent. co-deck uses short English names such as research, design, storyline, and html-build. The file name becomes the agent's name (e.g. agents/research.md).
  2. Role (role) — A one-sentence summary of what this agent does. For example, the research agent's role is "to gather information from the web and organize it into research_notes.md." Only when the role is clear can the PM choose the right agent.
  3. Behavioral instructions — The detailed rules the agent must follow when performing a task. They include directions such as "write files in this format" or "check with the user in this situation." The more specific the behavioral instructions are, the more consistent and predictable the agent's output becomes.
  4. Tools (tools) — The list of tools available to the agent: reading files (Read), writing files (Write), editing (Edit), shell commands (Bash), web search (WebSearch), and so on. Not every agent can use every tool. The PM agent, for example, has its tools restricted so it cannot modify files directly.

Agent Types in the Harness

The co-deck harness defines several specialist agents, each responsible for a different stage of the presentation pipeline.

Orchestrator

  • PM Agent — The project manager. This agent never writes code or edits files directly. It reads configuration, plans execution, and deploys the specialist agents.

Content Agents

  • research — Gathers web sources and writes research_notes.md.
  • storyline — Writes the narrative structure and per-slide content.
  • source-verifier — Validates URLs and checks source trustworthiness.

Production Agents

  • design — Finalizes the visual theme (colors, fonts, layout).
  • html-build — Generates HTML slides from the deck spec.
  • pdf-export — Converts slides into PDF output.

Asset Agents

  • image-curator — Searches for and downloads slide images.
  • diagram-specialist — Generates SVG diagrams and charts.
  • measure — Measures layout coordinates for PDF.
There is also a version agent that takes a snapshot of files before every edit, acting as a safety net. Because this agent runs at every stage (0 through 6), you can always roll back to a previous version if something goes wrong.

Example Agent File

Below is a simplified example of what an agent definition file looks like. Real files contain far more detail, but this example gives you the overall idea.

# agents/research.md
---
name: research
tier: medium
phases: 1
role: >
  Gathers web sources and writes research_notes.md
  for storyline design.
dispatch_triggers:
  - "research the topic"
  - "collect sources"
  - "write research notes"
---
## Instructions
- Search both Korean and English sources.
- Write the findings to research_notes.md.
- Include URLs, key facts, and source credibility notes.
- Do NOT create slide content — that is the storyline agent's job.

Notice how clearly this file defines what the agent does (role), when it gets dispatched (dispatch_triggers), and what it must not do (the prohibitions under Instructions). This clarity is exactly what makes multi-agent collaboration work reliably.

What Are Skills

Definition of a Skill

A skill is a reusable workflow that an agent can perform. If an agent is the "who," then a skill defines "what that agent does." A skill is a work procedure made up of multiple steps, activated automatically by a specific trigger.

Put simply: if the agent is a cook, the skill is the recipe. A cook (agent) keeps many recipes (skills), and when an order comes in (trigger), they prepare the dish according to the corresponding recipe.

Components of a Skill

Each skill consists of the following four elements.

  1. Name (name) — The unique name identifying the skill. It is often related to an agent name, such as research, html-build, or pdf-export.
  2. Description (description) — Describes what the skill does and which steps it involves. The PM consults this description when deciding which skill to dispatch.
  3. Trigger (trigger) — The condition under which the skill activates automatically. For example, when the user says "do some research for me," the research skill fires. Triggers can be keywords, command patterns, or particular stages of the pipeline.
  4. Steps (steps) — The concrete procedure the skill executes, defined in sequence, e.g. "1. Confirm the topic with the user → 2. Search the web → 3. Write the results to research_notes.md."

Skill vs Agent

Agents and skills are often confused, but there is a clear difference.

Agent

  • "Who" performs the task
  • An AI assistant with a role, permissions, and tools
  • Made up of identifier (name), role, instructions, tools
  • A single agent can hold several skills
  • Analogy: the cook

Skill

  • "What" is performed
  • A reusable workflow procedure
  • Made up of name, description, trigger, steps
  • A single skill can be shared by several agents
  • Analogy: the recipe
If the agent is the cook, the skill is the recipe. One cook can have both a pasta recipe (skill) and a steak recipe (skill), and the same pasta recipe can be shared by several cooks.

Skill Hierarchy

In co-deck, skills can be defined in three locations, each with a different priority.

Priority Order

  • Priority 1 — Workspace skills (skills/)
  • Priority 2 — Platform skills (.claude/skills/, .gemini/skills/)
  • Priority 3 — Global plugin skills

Key Rules

  • If the same skill exists in several locations, priority 1 wins
  • Workspace skills live only in the skills/ folder
  • Platform skills are Claude/Gemini-specific hooks
  • Duplicate definitions should be avoided as a principle
Beginner tip: You don't need to understand the internal structure of skills at first. Just remember that a skill is "a recipe that enables an agent to do something." When you open real skill files in the hands-on chapters (6–8), everything will fall into place naturally.

PM Orchestration

The Role of the PM (Project Manager) Agent

The PM agent is the center and single point of entry of the multi-agent harness. Users send requests only to the PM, and the PM analyzes each request, selects the appropriate specialist agents, and assigns the work.

Step by step, the PM's core duties are as follows.

  1. Request analysis — Understands the user's request and determines what work is needed. When a request like "make me a new presentation" comes in, the PM recognizes that it breaks down into the sequence research → storyline → design → HTML build → PDF export.
  2. Selecting specialist agents — Decides which specialists fit the request. Research needs go to the research agent; design needs go to the design agent.
  3. Assigning work (dispatch) — Gives concrete task instructions to the selected specialists, running them in parallel or serially depending on whether the tasks read or write files.
  4. Collecting results — Gathers the results each specialist completed and prepares them to be handed to the next stage.
  5. Quality review — At major checkpoints, verifies whether outputs meet quality standards and requests revisions if they fall short.

PM Orchestration Flow Diagram

The PM Never Executes Directly

The PM's most important trait is that it never writes files or runs code itself. As orchestrator (conductor), the PM merely directs specialist agents; it never produces deliverables on its own.

Here is why this rule matters:

  • Clear accountability — When something is wrong with a deliverable, the specialist who owns that domain fixes it. If the PM had created the file itself, confusion would arise over whether "the PM or a specialist" should fix it.
  • Guaranteed expertise — Each domain is best known by its specialist agent. If the PM produced design files directly, quality would suffer.
  • Separation of governance — Separating coordination (management) from execution (work) makes the system run more stably. It is the same principle by which human organizations separate managers from practitioners.
The PM is the conductor of an orchestra. It never plays an instrument itself; it directs who plays which instrument, and when. The violinist plays the violin, the cellist plays the cello, and the conductor leads the whole into harmony.

Quality Gates

At certain points in the pipeline, the PM pauses and presents its output for review. These checkpoints are called gates. There are two types.

  • Mandatory gates — the pipeline cannot advance until approval is given explicitly. Gate 2 (after content preparation) and Gate 5 (after sample PDF generation) are mandatory.
  • Optional gates — the PM shows a summary and then continues automatically. Gate 1.5 (source verification), Gate 3 (design spec), and Gate 4 (HTML draft) are optional.
Why gates matter: Without gates the pipeline would charge straight from the research stage to the PDF with no chance to change course. Gates let you review the storyline before the design is locked and preview the layout before the full PDF is generated — saving time and preventing wasted effort.

3-Tier Strategy

Why Multiple AI Models?

The higher an AI model's performance, the higher its cost. Using a top-tier model for complex design work produces excellent results, but using one for simple file lookups or script runs is wasteful.

To balance cost against performance, the harness assigns AI models across three tiers. Just as a company has principal engineers, seniors, and juniors, it chooses the model that matches the complexity of each task.

The Three Tiers

High-Tier (High Performance)

  • Purpose: complex reasoning, architectural design, planning
  • Assigned to: PM agent (orchestration)
  • Cost: high
  • Analogy: principal engineer
  • Used for complex judgments that set the direction of the entire project

Medium-Tier (Balanced)

  • Purpose: code review, quality checks, QA
  • Assigned to: specialist agents (most of them)
  • Cost: medium
  • Analogy: senior engineer
  • Used for hands-on specialist work and quality reviews

Low-Tier (High Efficiency)

  • Purpose: simple repetitive tasks, script maintenance
  • Assigned to: lightweight jobs such as the version agent
  • Cost: low
  • Analogy: junior engineer
  • Used for repetitive work with well-established patterns

Tier Adjustment Rules

  • The PM may lower the tier on simple tasks to save cost
  • But may never raise it above the baseline tier
  • If a downgraded task fails, restore the tier
  • Beginners are advised to keep the default settings

3-Tier Comparison Table

Criterion High-Tier Medium-Tier Low-Tier
Role Design, planning, reasoning Review, quality checks, QA Simple coding, scripts
Cost High Medium Low
Analogy Principal engineer Senior engineer Junior engineer

Key Rules

Along with the comparison table above, remember these key rules of the 3-Tier strategy.

  • Tiers can be lowered but never raised. The PM may assign a lower-tier model to save cost on simple tasks, but it cannot assign a model above an agent's defined baseline tier. If a downgraded task fails, the agent's baseline tier must always be restored on retry.
  • The orchestrator always uses the High tier. Because the PM makes the most critical decisions — which agents to dispatch, in what order to run them — it always operates at the highest level of reasoning.
  • Reviewers must be independent. The agent that performed the work never reviews its own output. This separation follows the same principle as having a dedicated QA team, guaranteeing genuine quality control.
Beginner tip: The 3-Tier strategy is an advanced topic. Keeping the default settings as they are is perfectly fine at first. co-deck's default configuration already assigns an appropriate tier to each agent, so you never need to adjust anything yourself. Learn tier tuning when cost optimization actually becomes necessary.

PM Gateway

Definition of the PM Gateway

The PM Gateway is the rule that forces every specialist agent to be invoked only through the PM. Users send requests only to the PM, and the PM selects suitable specialist agents and delegates the work. Requesting a specialist agent (such as research or design) directly is not permitted.

Why is this rule needed? There are three core reasons.

  • Control — When every request passes through the PM, the entire workflow can be managed from one place. This prevents several specialist agents from editing the same file simultaneously or performing conflicting work.
  • Consistency — The PM sets the priority of requests and sequences agents appropriately. This keeps the whole project flowing consistently.
  • Quality — At each stage the PM reviews the results and decides whether to proceed to the next stage or request revisions. This guarantees the quality of the final output.

Why a Gateway?

Imagine a company where any employee could walk up to the CEO and give orders. Chaos would ensue. The same is true in the harness. If users could invoke specialist agents like design or research directly, the PM would lose its ability to plan the workflow, sequence it, and review quality. The gateway exists precisely to prevent this.

How the Gateway Works

The PM Gateway is enforced through four layers of defense. Defense in depth means the layers complement one another.

  1. Tool-Level — The agent tool itself rejects calls that bypass the PM. This is the strongest enforcement layer, like a locked door that opens only with the right key.
  2. System Prompt-Level — The platform (Claude Code or Antigravity CLI) loads the PM's rules first, so the AI knows from the very beginning that requests must route through the PM.
  3. Agent File-Level — Every specialist agent definition file includes a "PM-ONLY INVOCATION" section stating explicitly that only the PM may dispatch it.
  4. QA Gate-Level — During the Phase 6 quality audit, the auditor agent detects attempts to bypass the PM and reports them as violations.

The section immediately below shows these four enforcement layers as a diagram.

Four Enforcement Layers

The PM Gateway is enforced at four levels. If any one of them is violated, the specialist agent does not run.

  1. Tool-Level — The agent tool itself rejects calls not made by the PM. Technically the strongest enforcement level.
  2. System-Level — System configuration files such as CLAUDE.md and GEMINI.md state the PM Gateway rule explicitly, so the AI model is aware of it from the start.
  3. Agent-Level — Each specialist agent's definition file contains a "PM-ONLY INVOCATION" section, so the agent itself refuses direct invocation.
  4. QA-Level — Final-stage quality review audits for instances of bypassing the PM Gateway.
Do not call specialist agents directly. Asking research, design, html-build, and their peers for work directly violates the PM Gateway rule. Specialist agents must be invoked through the PM only.
The PM Gateway resembles a company's chain of command. Ordinary employees do not give assignments directly to members of another department; they pass requests through their own team leader. This prevents duplicated, missed, and conflicting work.

PM Direct Execution Scope

Even the PM itself faces restrictions on what it may do directly.

Always Allowed

  • Read files
  • Search (glob, grep)
  • Create tasks and update status
  • Ask the user questions
  • Run read-only bash commands (git status, ls)

Restricted

  • Write/Edit files — limited to memory/*.md and CHANGELOG.md
  • Bash write commands — must delegate to a specialist
  • Code implementation — must delegate to a specialist
  • Design work — must delegate to a specialist
Important: Never attempt to call specialist agents directly. Always go through the PM. If you submit a request without following the PM workflow, it is rejected at the tool level. This is by design. The gateway guarantees that every action is planned, tracked, and quality-checked.

Dispatch Flow

What Is Dispatch?

Dispatch means the process by which the PM assigns work to specialist agents. When a user request arrives, the PM triages it, selects suitable specialist agents, and issues instructions.

Parallel vs Serial Dispatch

Dispatch has two modes. The nature of the task determines which mode is chosen.

Parallel Dispatch

  • Target: read-only tasks
  • Runs multiple agents at the same time
  • Research, analysis, inspection — work that does not interfere with each other
  • Advantage: time savings
  • Example: research + source-verifier running simultaneously
  • Suited to tasks with no risk of file conflicts

Serial Dispatch

  • Target: write tasks
  • Agents run one at a time, in order
  • File creation, editing — work with conflict potential
  • Advantage: guaranteed safety
  • Example: html-build runs after design completes
  • Suited to pipelines where one stage's output is the next stage's input

Dispatch Flow Diagram

Dispatch Decision Flow

After receiving a request, the PM decides how to dispatch as follows.

1. Receive the request — The PM receives the user's request.
2. Classify the nature of the task — Determine whether the request is read-only or a write task.
3. Read-only → parallel dispatch — Run multiple agents at once. Example: research and source verification proceeding simultaneously.
4. Write task → serial dispatch — Run agents one at a time, in order. Because each agent's output becomes the next agent's input, order matters.
5. Collect results → QA Gate → finalization — Aggregate all agents' outputs, pass quality review, and deliver the final result to the user.
Parallel dispatch is like several teams conducting their own investigations at the same time — one team runs market research while another analyzes competitors. Serial dispatch, by contrast, is an assembly line: planning must finish before design starts, and design must finish before development begins.

Handoff Contracts

What Is a Handoff?

A handoff refers to how work results are passed between agents. In the multi-agent harness, the finished output of one agent becomes the input of the next. You must define in advance in what format, at what path, and satisfying what quality criteria the handover happens. These agreements are called handoff contracts.

The Three Elements of a Handoff Contract

A handoff contract consists of three core elements.

  1. Input format — The format and location of the input an agent needs to start working. For example, the storyline agent receives the research_notes.md file as input. Where the input file lives and how it is structured must be stated explicitly.
  2. Output format — The format and location of the result an agent produces after finishing its work. For example, the research agent creates research_notes.md, while the storyline agent creates storyline.md and slide_deck.md. File names, paths, and internal structure must be settled so the next agent can read them.
  3. Quality criteria — The minimum standards the output must meet. Examples include "research_notes.md must contain at least 10 sources" or "every slide in slide_deck.md must have a title and body." Output that fails to meet these criteria does not move on to the next stage.

Handoff Example: research → storyline

The most representative handoff in co-deck is the transfer from the research agent to the storyline agent.

As the diagram shows, when the research agent produces its output in the form of research_notes.md, the storyline agent receives that same file as input and carries out its own work. Here the path, file name, and internal structure (markdown format, section layout, etc.) of research_notes.md must have been defined in advance by the handoff contract.

Why Handoff Contracts Matter

  • Error prevention — If a file name is wrong or a path is broken, the next agent cannot find its input and the entire pipeline stalls. With a handoff contract in place, such mistakes can be prevented.
  • Guaranteed independence — Once dependencies between agents become explicit, each agent can be developed and tested independently. As long as everyone honors the promise "given input A, produce output B," internal implementations can change freely.
  • Replaceability — Honor the contract and any agent can be swapped out for another. Even if you replace the research agent with a more capable version, the storyline agent keeps working unchanged as long as the output format stays identical.
A handoff contract is the "handover manual" between agents. It is like a company defining the form and standards of handover documents in advance whenever work moves from one department to another. With the manual in place, handovers proceed smoothly and nothing gets lost along the way.

Chapter Summary
  • An agent is an AI assistant with a role, instructions, and tools. The PM is the orchestrator; specialist agents are the executors.
  • A skill is a reusable workflow performed by an agent. If the agent is the "who," the skill is the "what it does."
  • PM orchestration flows through request analysis → agent selection → task assignment → result collection → quality review.
  • The 3-Tier strategy layers models to balance cost and performance: High (design), Medium (hands-on work), Low (simple tasks).
  • The PM Gateway is the four-layer rule forcing every specialist agent to be invoked only through the PM.
  • Dispatch splits into read-only → parallel and write tasks → serial.
  • A handoff contract defines the input format, output format, and quality criteria for passing outputs between agents.
