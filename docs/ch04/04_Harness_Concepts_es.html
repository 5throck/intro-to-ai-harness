Multi-Agent Conceptos del Harness

Learn the core concepts of the harness multi-agente: agents, skills, PM orchestration, 3-Tier strategy, PM Gateway, dispatch flow, and handoff contracts. Este capítulo builds your understanding of the entire harness architecture.

Lo que cubre este capítulo
  • Definitions of agents and skills
  • PM orchestration and PM Gateway roles
  • 3-Tier strategy (High / Medium / Low)
  • Dispatch flow and handoff contracts
  • Complete harness architecture diagram

What Are Agents

In Capítulo 1 we compared a single AI to an entire team of specialists. Now let us look at the building blocks of that team. The first and most important concept is the agent.

Agent Definition

An agent is an AI entity that has a clearly defined role, a set of tools it may use, and a set of rules it must follow. Think of an agent as a digital employee in a company: it has a job title, knows which tools it is allowed to operate, and works within the boundaries set by company policy.

Each agent is described by a markdown file (for example, agents/research.md or agents/design.md). That file contains everything the AI needs to behave as the agent: its name, tier, phase assignments, detailed instructions, tool permissions, and the triggers that tell the PM when to dispatch it.

Agent Componentes

Every agent is built from four core components.

Agent Types in the Harness

The co-deck harness defines several specialist agents, each responsible for a different stage of the presentation pipeline.

Orchestrator

  • PM Agent — The project manager. It never writes code or edits files directly. It reads configurations, plans execution, and dispatches specialist agents.

Content Agents

  • research — Gathers web sources and writes research_notes.md
  • storyline — Writes the narrative structure and per-slide content
  • source-verifier — Validates URLs and checks source trustworthiness

Production Agents

  • design — Locks the visual theme (colors, fonts, layout)
  • html-build — Generates HTML slides from the deck spec
  • pdf-export — Converts slides to PDF output

Asset Agents

  • image-curator — Searches and downloads slide images
  • diagram-specialist — Generates SVG diagrams and charts
  • measure — Measures layout coordinates for PDF
There is also a version agent that takes snapshots of files before every edit, like a safety net. It runs at every stage (0 through 6) so you can always roll back to a previous version if something goes wrong.

Agent File Example

Below is a simplified example of what an agent definition file looks like. The real files contain much more detail, but this gives you the idea.

# agents/research.md
---
name: research
tier: medium
phases: 1
role: >
  Gathers web sources and writes research_notes.md
  for storyline design.
dispatch_triggers:
  - "research the topic"
  - "collect sources"
  - "write research notes"
---
## Instructions
- Search the web in both Korean and English.
- Write findings to research_notes.md.
- Include URLs, key facts, and source credibility notes.
- Do NOT create slide content — that is the storyline agent's job.

Notice how the file clearly defines what the agent does (role), when to dispatch it (triggers), and what it must not do (rules). This clarity is what makes multi-agent collaboration work reliably.

What Are Skills

If agents are the employees, then skills are the recipe books they follow. A skill is a reusable set of instructions that tells an agent how to perform a specific type of work.

Skill Definition

A skill is a packaged instruction document (stored as SKILL.md) that defines a repeatable workflow. Skills can be loaded by any agent that needs them. For example, the research agent loads the research skill to know exactly how to search the web and structure its findings.

Skill Componentes

Each skill contains the following parts.

  • Metadata — The skill's name, version, owner (maintainer), status, and trigger phrases stored in YAML frontmatter.
  • Triggers — Natural-language phrases that tell the system when to activate this skill (for example, "research topic" or "generate PDF").
  • Instructions — Step-by-step guidance the agent follows to complete the task.
  • Input / Resultado Contract — What files the skill reads and what files it produces, so the next agent in the pipeline knows where to pick up.
  • Quality Checks — Validation rules the agent applies before declaring the task done.

Agent vs Skill Comparison

Agent

  • What: A digital employee with a fixed identity
  • Analogy: The employee themselves
  • File: agents/<name>.md
  • Scope: Persistent role across the entire project
  • Lifecycle: Created once, updated over time
  • Example: The research agent always handles web research, no matter which project it works on

Skill

  • What: A reusable instruction recipe
  • Analogy: The recipe book the employee follows
  • File: skills/<name>/SKILL.md
  • Scope: Invoked on demand when a specific task is needed
  • Lifecycle: Versioned independently; multiple agents can share the same skill
  • Example: The "source-verification" skill can be loaded by the research agent or run as a standalone check
Analogy: Think of it this way — a chef (agent) uses different recipes (skills) depending on what dish the customer ordered. The chef's identity does not change, but the recipe tells them exactly how to prepare each dish. Similarly, the html-build agent always builds HTML slides, but the html-build skill tells it precisely how to read the slide deck file, apply the theme, and produce the output.

Skill Resolution Priority

When a user request matches a skill trigger, the system checks three locations in priority order.

  1. Workspace-level skills (skills/<name>/SKILL.md) — Core workspace functionality like scaffolding, validation, and audit. These have the highest priority.
  2. Platform config skills (.claude/skills/ or .gemini/skills/) — Platform-specific hooks, commands, and lifecycle management.
  3. Global plugin skills — General-purpose development workflows from external plugins. These have the lowest priority.
Tip: A single skill can be shared across multiple agents. The "version" skill, for example, is loaded by every agent because every agent needs to snapshot files before editing them. This reuse is what makes skills powerful — write the instructions once, use them everywhere.

PM Orchestration

We have introduced agents and skills. Now the question is: who decides which agent runs when, in what order, and with what resources? The answer is the PM (Project Manager) Agent, and the process it manages is called PM orchestration.

What the PM Does

The PM agent is the orchestrator of the entire multi-agent workflow. It sits at the top of the hierarchy and is responsible for the following tasks.

  • Triage user requests — When you type a command like "make a presentation about climate change," the PM analyzes what you need and determines which agents should be involved.
  • Create execution plans — The PM maps out a step-by-step plan: first dispatch the research agent, then the storyline agent, then the design agent, and so on.
  • Dispatch specialist agents — The PM sends the right agent to do each job. It never does the work itself — it only coordinates.
  • Enforce quality gates — At certain checkpoints (called "gates"), the PM pauses the pipeline and asks you to review the output before proceeding.
  • Track progress — The PM maintains project_state.json to record which stages are complete and which are still pending.
  • Manage rework — If you request changes after a stage is done, the PM identifies which downstream stages need to be re-run and dispatches the minimum set of agents to apply the fix.

What the PM Does NOT Do

This is equally important. The PM never directly edits project files (except memory logs and changelogs), never writes code, and never performs specialist work. If the PM tried to do the research agent's job, it would violate the separation of concerns that keeps the system reliable.

Analogy — The Conductor: Think of the PM agent as the conductor of an orchestra. The conductor does not play any instrument. Instead, they read the score (the execution plan), cue each section at the right moment (dispatch), and ensure the whole performance flows harmoniously. The musicians (specialist agents) are the ones who actually produce the music.

Quality Gates

At certain points in the pipeline, the PM pauses and presents the output for your review. These checkpoints are called gates. There are two types.

  • Mandatory gates — The pipeline cannot proceed until you explicitly approve. Gate 2 (after content is ready) and Gate 5 (after the sample PDF is generated) are mandatory.
  • Optional gates — The PM shows you a summary and then continues automatically. Gate 1.5 (source verification), Gate 3 (design spec), and Gate 4 (HTML draft) are optional.
Why gates matter: Without gates, the pipeline would run straight from research to PDF without giving you a chance to correct direction. Gates let you review the storyline before the design is locked, and preview the layout before the full PDF is generated — saving time and preventing wasted effort.

3-Tier Strategy

Not all tasks require the same level of AI reasoning. Some tasks need deep architectural thinking, while others are simple and repetitive. The harness uses a 3-Tier strategy to match the right model to each task, balancing quality against cost.

The Three Tiers

High Tier (Plan)

  • Models: Claude Opus 4, Gemini 3.1 Pro
  • Used for: Complex reasoning, architectural design, planning, writing precise agent prompts
  • Who uses it: The PM agent (orchestrator)
  • Cost: Highest
  • Example: Analyzing a user's request, determining which agents to dispatch, and creating a multi-step execution plan

Medium Tier (Review)

  • Models: Claude Sonnet 4, Gemini 3.5 Flash
  • Used for: Code review, testing, quality gates, compliance checks
  • Who uses it: Auditor and QA agents
  • Cost: Moderate
  • Example: Reviewing the storyline agent's output for factual accuracy, checking that design specs are internally consistent

Low Tier (Execute)

  • Models: Claude Haiku 4, Gemini 3.5 Flash
  • Used for: Fast repetitive coding, simple file operations, routine tasks
  • Who uses it: Execution agents (version snapshots, file edits)
  • Cost: Lowest
  • Example: Taking a snapshot of a file before an edit, performing a string replacement in a config file

Key Rules

  • Tier can be downgraded, never upgraded. The PM may assign a lower-tier model to a simple task to save cost, but it can never assign a model above an agent's defined baseline tier. If a downgraded task fails, the agent's baseline tier must be restored for the retry.
  • The orchestrator always uses the High tier. Since the PM makes the most critical decisions — which agents to dispatch, what order to run them in — it always operates at the highest reasoning level.
  • Reviewers must be independent. The agent that produced the work is never the same agent that reviews it. This separation ensures genuine quality control, just like having a separate QA team.
For beginners: You do not need to worry about selecting models yourself. The harness automatically assigns the right tier based on the task. When you gain more experience, you can tune tier assignments in the agent configuration files to optimize cost and quality for your specific projects.

PM Gateway

The PM Gateway is the single point of entry through which all user requests flow. It ensures that specialist agents are never called directly by the user — every interaction goes through the PM first.

Why a Gateway?

Imagine a company where any employee could walk up to the CEO and give orders. Chaos, right? The same principle applies here. If a user could directly invoke the design agent or the research agent, the PM would lose its ability to plan, sequence, and quality-check the workflow. The gateway prevents this.

How the Gateway Works

The PM Gateway is enforced at four layers, providing defense in depth.

  1. Tool-Level Enforcement — The agent tool itself rejects calls that bypass the PM. This is the hardest enforcement layer, like a locked door that only opens with the right key.
  2. System Prompt-Level Enforcement — The platform (Claude Code or Antigravity CLI) loads the PM's rules first, so the AI knows from the start that it must route through the PM.
  3. Agent File-Level Enforcement — Every specialist agent file contains a "PM-ONLY INVOCATION" section that explicitly states only the PM may dispatch it.
  4. QA Gate-Level Enforcement — The auditor agent detects any attempt to bypass the PM during the Phase 6 quality audit and reports it as a violation.

PM Direct Execution Scope

Even the PM itself has restrictions on what it can do directly.

Always Allowed

  • Read files
  • Search (glob, grep)
  • Create tasks and update status
  • Ask the user questions
  • Run read-only bash commands (git status, ls)

Restricted

  • Write/Edit files — only memory/*.md and CHANGELOG.md
  • Bash write commands — must delegate to a specialist
  • Code implementation — must delegate to a specialist
  • Design work — must delegate to a specialist
Important: Never attempt to call specialist agents directly. Always go through the PM. If you type "research topic X" instead of going through the PM workflow, the request will be rejected at the tool level. This is by design — the gateway ensures that every action is planned, tracked, and quality-checked.

Dispatch Flow

When the PM decides which agents to run and in what order, it follows a structured dispatch flow. The key decision is whether to run agents in parallel or in sequence.

Parallel vs Serial Dispatch

Parallel Dispatch

  • Multiple agents run at the same time
  • Used for read-only tasks (research, analysis, inspection)
  • Faster overall — no waiting for one agent to finish
  • Example: The image-curator and diagram-specialist both run in parallel at Stage 3.5 because they do not depend on each other's output

Serial Dispatch

  • Agents run one at a time, in order
  • Used for write tasks to prevent file conflicts
  • Slower but safer — each agent's output is available before the next one starts
  • Example: The research agent must finish research_notes.md before the storyline agent can use it

The Dispatch Decision

When the PM receives a request, it follows a simple decision tree.

1. Receive request — The user types a command or the pipeline advances to the next stage.
2. Classify deliverable type — The PM identifies what kind of output is needed (research notes, design spec, HTML slides, PDF, etc.) and maps it to the correct agent.
3. Determine parallel or serial — If the task involves writing files, dispatch serially (one agent at a time). If it involves only reading and analysis, dispatch all relevant agents in parallel.
4. Dispatch agents — Send the task to the specialist agent(s) with the appropriate tier model.
5. Collect and validate — Wait for all agents to complete, then run quality checks at the next gate.
Beginner tip: You do not need to memorize this decision tree. The PM handles it automatically. As you gain experience, you will start to recognize which stages run in parallel and which are serial, and you can predict the pipeline's behavior more accurately.

Handoff Contracts

In a sistema multi-agente, the work product of one agent becomes the input for the next. The mechanism that makes this transfer reliable is called a handoff contract.

What Is a Handoff Contract?

A handoff contract is an agreement between two agents that specifies three things.

  1. Resultado file — What file(s) the sending agent produces. For example, the research agent produces research_notes.md.
  2. File location — Where the file is placed so the receiving agent knows exactly where to find it. For example, presentations/<project>/research_notes.md.
  3. Format and structure — The expected format (markdown, JSON, etc.) and the sections or fields the file must contain, so the receiving agent can parse it reliably.

When these three elements are clearly defined, the handoff is contractual — the receiving agent knows exactly what to expect and how to consume the data. This eliminates guesswork and reduces errors.

Example: Research to Storyline

Here is a real handoff contract from the co-deck pipeline.

Sending Agent: Research

  • Produces: research_notes.md
  • Location: presentations/<name>/
  • Format: Markdown with sections for Sources, Key Facts, Credibility Notes
  • Trigger: "research the topic"

Receiving Agent: Storyline

  • Consumes: research_notes.md
  • Reads from: Same project directory
  • Expects: Structured markdown it can parse for key facts and source URLs
  • Produces: storyline.md + slide_deck.md

The contract is explicit in both agent files. The research agent's instructions say "write findings to research_notes.md" and the storyline agent's instructions say "read research_notes.md as input." Because the contract is written down in the agent definitions, there is no ambiguity.

Why Handoff Contracts Matter

Without handoff contracts, agents would need to guess where to find their input, what format it is in, and whether it is ready. This leads to three common failure modes.

  • File not found — The receiving agent looks for a file that was never created or was saved in a different location.
  • Format mismatch — The sending agent outputs JSON but the receiving agent expects markdown.
  • Premature consumption — The receiving agent starts before the sending agent has finished writing, resulting in incomplete or corrupted data.

Handoff contracts prevent all three of these issues by making the transfer expectations explicit, verifiable, and enforceable.

Analogy — The Handover Manual: Think of a handoff contract like the handover manual used in shift changes at a hospital or factory. When the day shift ends, the outgoing nurse fills out a structured form: which patients were treated, which medications were administered, what issues remain open. The incoming nurse reads this form and can pick up exactly where the previous shift left off. Without this manual, critical information could be lost. The same principle applies to AI agents.

Handoff Chain in the Full Pipeline

Here is the complete handoff chain for the co-deck presentation pipeline. Each arrow represents a handoff contract.

Stage 0: PM reads lecture-profile.md → initializes project_state.json
Stage 1: research → produces research_notes.md
Stage 1.5: source-verifier → reads research_notes.md, produces source-verification.md
Stage 2-3: storyline → reads research_notes.md, produces storyline.md + slide_deck.md
Stage 3: design → reads slide_deck.md, produces design_spec.md
Stage 3.5: image-curator → reads slide_deck.md, produces image-manifest.json + images
Stage 3.5: diagram-specialist → reads slide_deck.md, produces diagram-manifest.json + SVGs
Stage 5-8: html-build → reads slide_deck.md + design_spec.md + manifests, produces lecture_vN.html
Stage 9-10: measure → reads HTML, produces pdf_layout_spec.md
Stage 11: pdf-export → reads all specs, produces <project>.pdf

Notice how each agent only reads what it needs and produces a well-defined output. The chain forms a clear data flow from user request to final PDF, with every handoff point documented in the agent and skill definitions.
