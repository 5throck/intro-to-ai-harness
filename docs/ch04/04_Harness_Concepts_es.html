Capítulo 4

Conceptos del Harness Multi-Agente

Aprende los conceptos clave del harness multi-agente: agentes, skills, orquestación del PM, estrategia 3-Tier, PM Gateway, flujo de despacho y contratos de traspaso — en este capítulo comprenderás todo el esqueleto del harness.

Lo que cubre este capítulo
  • Definiciones de agente y skill
  • Orquestación del PM y el papel del PM Gateway
  • Estrategia 3-Tier (High/Medium/Low)
  • Flujo de despacho y contratos de traspaso
  • Diagrama completo de la arquitectura del harness

Qué son los agentes

Definición de agente

Un agente es un asistente de IA al que se le asigna un rol específico y que ejecuta tareas siguiendo instrucciones de comportamiento definidas. A diferencia de un chatbot común, un agente tiene su propio nombre, rol y reglas de comportamiento, y recibe permiso para leer y escribir archivos y usar herramientas.

Como vimos en el Capítulo 1, un agente es como un empleado de una empresa. El PM es el jefe de equipo y los agentes especialistas son los expertos de cada departamento. Cuando el agente de planificación, el de diseño y el de programación cumplen cada uno con su parte, todo el proyecto avanza con eficiencia.

Componentes de un agente

Cada agente se compone de cuatro elementos centrales. Esos cuatro elementos juntos definen un solo agente.

Dicho de forma concreta:

  1. Identificador (name) — El nombre único que distingue al agente. co-deck usa nombres cortos en inglés como research, design, storyline y html-build. El nombre del archivo se convierte en el nombre del agente (por ejemplo: agents/research.md).
  2. Rol (role) — Un resumen en una frase de lo que hace este agente. Por ejemplo, el rol del agente research es «recopilar información de la web y organizarla en research_notes.md». Solo cuando el rol está claro puede el PM elegir el agente adecuado.
  3. Instrucciones de conducta — Las reglas detalladas que el agente debe seguir al ejecutar una tarea. Incluyen indicaciones como «escribe los archivos en este formato» o «consulta al usuario en este caso». Cuanto más específicas sean las instrucciones, más consistentes y predecibles serán los resultados del agente.
  4. Herramientas (tools) — La lista de herramientas que el agente puede usar: lectura de archivos (Read), escritura de archivos (Write), edición (Edit), comandos de shell (Bash), búsqueda web (WebSearch), etc. No todos los agentes pueden usar todas las herramientas. El agente PM, por ejemplo, tiene las herramientas restringidas para que no pueda modificar archivos directamente.

Tipos de agentes en el harness

El harness de co-deck define varios agentes especialistas, cada uno responsable de una etapa distinta del pipeline de presentación.

Orquestador

  • Agente PM — El gestor de proyecto. Este agente nunca escribe código ni edita archivos directamente. Lee la configuración, planifica la ejecución y despliega a los agentes especialistas.

Agentes de contenido

  • research — Recopila fuentes web y escribe research_notes.md.
  • storyline — Escribe la estructura narrativa y el contenido por diapositiva.
  • source-verifier — Valida URLs y comprueba la fiabilidad de las fuentes.

Agentes de producción

  • design — Fija el tema visual (colores, tipografías, diseño).
  • html-build — Genera diapositivas HTML a partir de la especificación del deck.
  • pdf-export — Convierte las diapositivas en salida PDF.

Agentes de assets

  • image-curator — Busca y descarga imágenes para las diapositivas.
  • diagram-specialist — Genera diagramas SVG y gráficos.
  • measure — Mide coordenadas de disposición para el PDF.
También existe un agente version que toma una instantánea de los archivos antes de cada edición y actúa como red de seguridad. Como este agente se ejecuta en todas las etapas (de la 0 a la 6), siempre puedes volver a una versión anterior si algo sale mal.

Ejemplo de archivo de agente

A continuación tienes un ejemplo simplificado del aspecto de un archivo de definición de agente. Los archivos reales contienen muchos más detalles, pero con este ejemplo te harás una idea general.

# agents/research.md
---
name: research
tier: medium
phases: 1
role: >
  Recopila fuentes web y escribe research_notes.md
  para el diseño del storyline.
dispatch_triggers:
  - "investiga el tema"
  - "recopila fuentes"
  - "escribe las notas de investigación"
---
## Instructions
- Busca tanto fuentes en coreano como en inglés.
- Escribe los hallazgos en research_notes.md.
- Incluye URLs, hechos clave y notas sobre la fiabilidad de las fuentes.
- NO crees contenido de diapositivas — esa es tarea del agente storyline.

Fíjate en cómo este archivo define con claridad qué hace el agente (role), cuándo se despacha (dispatch_triggers) y qué no debe hacer (las prohibiciones de Instructions). Esa claridad es justo lo que hace que la colaboración multi-agente funcione de manera fiable.

Qué son las skills

Definición de skill

Una skill es un flujo de trabajo reutilizable que un agente puede ejecutar. Si el agente es el «quién», la skill define «qué hace» ese agente. Una skill es un procedimiento de trabajo compuesto por varios pasos, activado automáticamente por un trigger específico.

Dicho fácil: si el agente es un cocinero, la skill es la receta de cocina. El cocinero (agente) dispone de varias recetas (skills) y, cuando llega un pedido (trigger), prepara el plato siguiendo la receta correspondiente.

Componentes de una skill

Cada skill se compone de los siguientes cuatro elementos.

  1. Nombre (name) — El nombre único que identifica a la skill. Suele estar relacionado con un nombre de agente: research, html-build, pdf-export, etc.
  2. Descripción (description) — Describe qué hace esta skill y qué pasos sigue. El PM consulta esta descripción al decidir qué skill despachar.
  3. Trigger (trigger) — La condición bajo la cual la skill se activa automáticamente. Por ejemplo, si el usuario dice «hazme una investigación», se dispara la skill research. Los triggers pueden ser palabras clave, patrones de comando o etapas concretas del pipeline.
  4. Pasos (steps) — El procedimiento concreto que ejecuta la skill, definido en orden: «1. Confirmar el tema con el usuario → 2. Realizar la búsqueda web → 3. Escribir los resultados en research_notes.md».

Skill vs agente

Agentes y skills se confunden con frecuencia, pero hay una diferencia clara.

Agente (Agent)

  • El «quién» ejecuta la tarea
  • Un asistente de IA con rol, permisos y herramientas
  • Formado por identificador (name), rol, instrucciones y herramientas
  • Un solo agente puede tener varias skills
  • Analogía: el cocinero

Skill (Skill)

  • El «qué» se ejecuta
  • Un procedimiento de flujo de trabajo reutilizable
  • Formada por nombre, descripción, trigger y pasos
  • Una sola skill puede compartirse entre varios agentes
  • Analogía: la receta de cocina
Si el agente es el cocinero, la skill es la receta. Un mismo cocinero puede tener tanto la receta de la pasta (skill) como la del filete (skill), y la misma receta de pasta puede compartirla varios cocineros.

Jerarquía de las skills

En co-deck, las skills pueden definirse en tres ubicaciones, cada una con una prioridad distinta.

Orden de prioridad

  • Prioridad 1 — Skills del workspace (skills/)
  • Prioridad 2 — Skills de plataforma (.claude/skills/, .gemini/skills/)
  • Prioridad 3 — Skills globales de plugins

Reglas clave

  • Si la misma skill existe en varias ubicaciones, gana la de prioridad 1
  • Las skills del workspace viven solo en la carpeta skills/
  • Las skills de plataforma son hooks exclusivos de Claude/Gemini
  • Como principio, evita las definiciones duplicadas
Consejo para principiantes: Al principio no necesitas entender toda la estructura interna de las skills. Basta con recordar que una skill es «una receta que permite a un agente hacer algo». Cuando abras archivos de skill reales en los capítulos prácticos (6–8), lo comprenderás de forma natural.

Orquestación del PM

El papel del agente PM (Project Manager)

El agente PM es el centro y punto único de entrada (Single Point of Entry) del harness multi-agente. El usuario hace solicitudes solo al PM, y el PM analiza la solicitud, selecciona los agentes especialistas adecuados y asigna el trabajo.

Las funciones centrales del PM, paso a paso, son las siguientes.

  1. Análisis de la solicitud — Comprende la petición del usuario y determina qué trabajo hace falta. Ante una solicitud como «créame una nueva presentación», el PM identifica que se compone de una secuencia de etapas: investigación → storyline → diseño → construcción HTML → exportación a PDF.
  2. Selección de agentes especialistas — Decide qué especialistas encajan mejor con la solicitud. Para investigación elige al agente research; para diseño, al agente design.
  3. Asignación del trabajo (despacho) — Da instrucciones de trabajo concretas a los especialistas seleccionados, ejecutándolos en paralelo o en serie según las tareas lean o escriban archivos.
  4. Recogida de resultados — Reúne los resultados completados por cada especialista y los prepara para entregarlos a la siguiente etapa.
  5. Revisión de calidad — En los puntos clave comprueba si los entregables cumplen los criterios de calidad y pide correcciones cuando se quedan cortos.

Diagrama de flujo de la orquestación del PM

El PM no ejecuta directamente

La característica más importante del PM es que nunca escribe archivos ni ejecuta código por sí mismo. Como orquestador (director), el PM solo dirige a los agentes especialistas; nunca produce entregables por su cuenta.

Por qué importa esta regla:

  • Claridad en la responsabilidad — Si un entregable tiene algún problema, lo corrige el especialista de ese ámbito. Si el PM hubiera creado el archivo él mismo, habría confusión sobre si debe corregirlo «el PM o un especialista».
  • Garantía de especialización — Cada ámbito lo conocen mejor sus agentes especialistas. Si el PM creara archivos de diseño directamente, la calidad podría resentirse.
  • Separación de gobernanza — Separar la coordinación (gestión) de la ejecución (trabajo) hace que el sistema funcione de forma más estable. Es el mismo principio por el que las organizaciones humanas separan a gestores y operarios.
El PM es el director de una orquesta. No toca ningún instrumento; indica quién toca qué instrumento y cuándo. El violinista toca el violín, el violonchelista el violonchelo, y el director conduce el conjunto hacia la armonía.

Puertas de calidad (gates)

En ciertos puntos del pipeline, el PM hace una pausa y presenta el resultado para su revisión. Estos puntos de control se llaman gates. Hay dos tipos.

  • Gates obligatorios — el pipeline no puede avanzar hasta que se apruebe explícitamente. El Gate 2 (tras preparar el contenido) y el Gate 5 (tras generar el PDF de muestra) son obligatorios.
  • Gates opcionales — el PM muestra un resumen y continúa automáticamente. El Gate 1.5 (verificación de fuentes), el Gate 3 (especificación de diseño) y el Gate 4 (borrador HTML) son opcionales.
Por qué importan los gates: Sin gates, el pipeline correría directo desde la investigación hasta el PDF sin ninguna oportunidad de corregir el rumbo. Los gates permiten revisar el storyline antes de fijar el diseño y previsualizar la disposición antes de generar el PDF completo — ahorrando tiempo y esfuerzo innecesario.

Estrategia 3-Tier

¿Por qué hacen falta varios modelos de IA?

Cuanto mayor es el rendimiento de un modelo de IA, mayor es también su coste. Usar un modelo de gama alta para trabajos de diseño complejos da buenos resultados, pero usarlo para búsquedas sencillas de archivos o ejecuciones de scripts resulta ineficiente.

Para equilibrar coste y rendimiento, el harness reparte los modelos de IA en tres niveles (tiers). Igual que una empresa cuenta con ingenieros principales, sénior y júnior, elige el modelo que se ajusta a la complejidad de cada tarea.

Los tres tiers

High-Tier (alto rendimiento)

  • Propósito: razonamiento complejo, diseño de arquitectura, planificación
  • Asignado a: agente PM (orquestación)
  • Coste: alto
  • Analogía: ingeniero principal
  • Se usa para juicios complejos que marcan la dirección de todo el proyecto

Medium-Tier (equilibrado)

  • Propósito: revisión de código, controles de calidad, QA
  • Asignado a: agentes especialistas (la mayoría)
  • Coste: medio
  • Analogía: ingeniero sénior
  • Se usa para el trabajo práctico de cada especialidad y las revisiones de calidad

Low-Tier (alta eficiencia)

  • Propósito: tareas repetitivas simples, mantenimiento de scripts
  • Asignado a: trabajos ligeros como el agente version
  • Coste: bajo
  • Analogía: ingeniero júnior
  • Se usa para tareas repetitivas con patrones ya establecidos

Reglas de ajuste de tier

  • El PM puede bajar el tier en tareas simples para ahorrar coste
  • Pero nunca puede subirlo por encima del tier base
  • Si falla una tarea con el tier reducido, se restaura el tier
  • A los principiantes se recomienda mantener la configuración por defecto

Reglas clave

Junto con la tabla comparativa anterior, estas son las reglas clave de la estrategia 3-Tier que conviene recordar.

  • El tier puede bajarse, pero jamás subirse. El PM puede asignar un modelo de un tier inferior para ahorrar coste en tareas simples, pero no puede asignar un modelo superior al tier base definido para un agente. Si una tarea con el tier reducido falla, al reintentarla debe restaurarse siempre el tier base del agente.
  • El orquestador usa siempre el tier High. Como el PM toma las decisiones más críticas —a qué agentes despachar, en qué orden ejecutarlos—, opera siempre al máximo nivel de razonamiento.
  • Quien revisa debe ser independiente. El agente que realizó el trabajo nunca revisa su propio resultado. Esta separación sigue el mismo principio que contar con un equipo de QA aparte y garantiza un control de calidad real.
Consejo para principiantes: La estrategia 3-Tier es un tema avanzado. Al principio basta con mantener la configuración por defecto tal cual. La configuración básica de co-deck ya asigna a cada agente un tier apropiado, así que no necesitas ajustar nada tú mismo. Aprende a afinar los tiers cuando de verdad necesites optimizar costes.

PM Gateway

Definición del PM Gateway

El PM Gateway es la regla que obliga a que todos los agentes especialistas se invoquen únicamente a través del PM. El usuario solicita solo al PM, y el PM selecciona los agentes especialistas adecuados y les delega el trabajo. Solicitar directamente a un agente especialista (como research o design) no está permitido.

¿Por qué hace falta esta regla? Hay tres razones fundamentales.

  • Control — Cuando toda solicitud pasa por el PM, el flujo completo del trabajo se gestiona desde un solo lugar. Esto evita que varios agentes especialistas editen el mismo archivo a la vez o realicen tareas contradictorias.
  • Consistencia — El PM decide la prioridad de las solicitudes y ordena los agentes en la secuencia adecuada. Así, todo el proyecto mantiene un flujo consistente.
  • Calidad — En cada etapa el PM revisa los resultados y decide si avanzar a la siguiente etapa o pedir correcciones. Esto garantiza la calidad del resultado final.

¿Por qué un gateway?

Imagina una empresa donde cualquier empleado pudiera acercarse libremente al CEO y darle órdenes. Se produciría un enorme caos. En el harness ocurre igual. Si el usuario pudiera invocar directamente a agentes especialistas como design o research, el PM perdería su capacidad de planificar el flujo de trabajo, ordenarlo y revisar la calidad. El gateway existe precisamente para impedirlo.

Cómo funciona el gateway

El PM Gateway se aplica mediante cuatro líneas de defensa. La defensa en profundidad (defense in depth) hace que las capas se complementen entre sí.

  1. Nivel de herramienta (Tool-Level) — La propia herramienta de agentes rechaza las llamadas que se saltan al PM. Es la capa de aplicación más potente, como una puerta cerrada que solo se abre con la llave correcta.
  2. Nivel de prompt de sistema (System Prompt-Level) — La plataforma (Claude Code o Antigravity CLI) carga primero las reglas del PM, de modo que la IA sabe desde el principio que las solicitudes deben pasar por el PM.
  3. Nivel de archivo de agente (Agent File-Level) — Todos los archivos de definición de agentes especialistas incluyen una sección «PM-ONLY INVOCATION» que declara explícitamente que solo el PM puede despacharlos.
  4. Nivel de gate de QA (QA Gate-Level) — Durante la auditoría de calidad de la Fase 6, el agente auditor detecta los intentos de saltarse al PM y los reporta como infracciones.

En la sección inmediatamente siguiente puedes ver estos cuatro niveles de aplicación en forma de diagrama.

Los cuatro niveles de aplicación

El PM Gateway se aplica en cuatro niveles. Si se viola cualquiera de ellos, el agente especialista no llega a ejecutarse.

  1. Nivel de herramienta (Tool-Level) — La propia herramienta de agentes rechaza las llamadas que no provienen del PM. Técnicamente, es el nivel de aplicación más fuerte.
  2. Nivel de sistema (System-Level) — Archivos de configuración del sistema como CLAUDE.md y GEMINI.md declaran explícitamente la regla del PM Gateway, de modo que el modelo de IA la conoce desde el principio.
  3. Nivel de agente (Agent-Level) — Cada archivo de definición de agente especialista incluye una sección «PM-ONLY INVOCATION», de modo que el propio agente rechaza las invocaciones directas.
  4. Nivel de QA (QA-Level) — La revisión de calidad final audita si ha habido casos de saltarse el PM Gateway.
No debes invocar directamente a los agentes especiales. Pedir trabajo directamente a agentes especialistas como research, design o html-build vulnera la regla del PM Gateway. Los agentes especiales deben invocarse únicamente a través del PM.
El PM Gateway se parece al organigrama de una empresa. Un empleado corriente no da instrucciones de trabajo directamente a miembros de otro departamento; las transmite a través de su propio jefe de equipo. Así se evita el trabajo duplicado, omitido o en conflicto.

Ámbito de ejecución directa del PM

Incluso el propio PM tiene restricciones sobre lo que puede hacer directamente.

Siempre permitido

  • Leer archivos
  • Buscar (glob, grep)
  • Crear tareas y actualizar estados
  • Hacer preguntas al usuario
  • Ejecutar comandos bash de solo lectura (git status, ls)

Restringido

  • Escritura/edición de archivos — limitado a memory/*.md y CHANGELOG.md
  • Comandos bash de escritura — debe delegarse en un especialista
  • Implementación de código — debe delegarse en un especialista
  • Trabajo de diseño — debe delegarse en un especialista
Importante: No intentes llamar directamente a los agentes especialistas. Procede siempre a través del PM. Si envías una solicitud sin seguir el flujo de trabajo del PM, será rechazada en el nivel de herramienta. Esto es intencionado. El gateway garantiza que cada acción esté planificada, registrada y pase un control de calidad.

Flujo de despacho

¿Qué es el despacho?

El despacho (Dispatch) significa el proceso por el cual el PM asigna trabajo a los agentes especialistas. Cuando llega una solicitud del usuario, el PM analiza su naturaleza (triaje), selecciona los agentes especialistas adecuados y les da instrucciones.

Despacho paralelo vs despacho serie

El despacho tiene dos modos. Según la naturaleza de la tarea se elige el modo apropiado.

Despacho paralelo (Parallel)

  • Objetivo: tareas de solo lectura
  • Ejecuta varios agentes a la vez
  • Investigación, análisis, inspección: tareas que no interfieren entre sí
  • Ventaja: ahorro de tiempo
  • Ejemplo: research + source-verifier ejecutándose a la vez
  • Adecuado para tareas sin riesgo de conflictos de archivos

Despacho serie (Serial)

  • Objetivo: tareas de escritura
  • Ejecuta los agentes uno a uno, en orden
  • Creación y edición de archivos: tareas con riesgo de conflicto
  • Ventaja: seguridad garantizada
  • Ejemplo: html-build se ejecuta tras completarse design
  • Adecuado para flujos donde la salida de una etapa es la entrada de la siguiente

Diagrama de flujo del despacho

Flujo de decisión del despacho

Tras recibir una solicitud, el PM decide cómo despacharla de la siguiente manera.

1. Recepción de la solicitud — El PM recibe la solicitud del usuario.
2. Análisis de la naturaleza de la tarea — Determina si la solicitud es de solo lectura o de escritura.
3. Si es de solo lectura → despacho paralelo — Ejecuta varios agentes a la vez. Ejemplo: investigación y verificación de fuentes avanzando simultáneamente.
4. Si es tarea de escritura → despacho serie — Ejecuta los agentes uno a uno, en orden. Como la salida de cada agente es la entrada del siguiente, el orden importa.
5. Recogida de resultados → QA Gate → finalización — Reúne los entregables de todos los agentes, supera la revisión de calidad y entrega el resultado final al usuario.
El despacho paralelo es como varios equipos realizando sus propias investigaciones al mismo tiempo: uno hace el estudio de mercado mientras otro analiza a la competencia. El despacho serie, en cambio, es como una cadena de montaje: primero termina la planificación y luego empieza el diseño; primero el diseño y después el desarrollo.

Contratos de traspaso

¿Qué es un traspaso?

El traspaso (Handoff) se refiere a la forma en que se pasan los resultados del trabajo entre agentes. En el harness multi-agente, el entregable terminado por un agente se convierte en la entrada del siguiente. Hay que definir por adelantado en qué formato, en qué ruta y cumpliendo qué criterios de calidad se realiza la entrega. Estos acuerdos se llaman contratos de traspaso (Handoff Contract).

Los tres elementos del contrato de traspaso

Un contrato de traspaso se compone de tres elementos centrales.

  1. Formato de entrada (Input Format) — El formato y la ubicación de la entrada que un agente necesita para empezar a trabajar. Por ejemplo, el agente storyline recibe el archivo research_notes.md como entrada. Debe indicarse con claridad dónde está el archivo de entrada y qué estructura tiene.
  2. Formato de salida (Output Format) — El formato y la ubicación del resultado que produce el agente al terminar su trabajo. Por ejemplo, el agente research genera research_notes.md, y el agente storyline genera storyline.md y slide_deck.md. El nombre del archivo, la ruta y la estructura interna deben estar fijados para que el siguiente agente pueda leerlos.
  3. Criterios de calidad (Quality Criteria) — Los estándares mínimos que debe cumplir la salida. Por ejemplo: «research_notes.md debe incluir al menos 10 fuentes» o «cada diapositiva de slide_deck.md debe tener título y cuerpo». Una salida que no cumpla estos criterios no pasa a la etapa siguiente.

Ejemplo de traspaso: research → storyline

El traspaso más representativo de co-deck es la entrega del agente research al agente storyline.

Como muestra el diagrama, cuando el agente research produce su salida en forma de research_notes.md, el agente storyline toma ese mismo archivo como entrada y realiza su propio trabajo. Aquí la ruta, el nombre del archivo y la estructura interna (formato markdown, organización de secciones, etc.) de research_notes.md deben haber quedado definidos de antemano por el contrato de traspaso.

Por qué importan los contratos de traspaso

  • Prevención de errores — Si el nombre del archivo es incorrecto o la ruta está mal, el siguiente agente no encuentra su entrada y todo el pipeline se detiene. Con un contrato de traspaso, estos errores se pueden evitar.
  • Garantía de independencia — Cuando las dependencias entre agentes son explícitas, cada agente puede desarrollarse y probarse por separado. Basta cumplir la promesa «dada la entrada A, producir la salida B», y la implementación interna puede cambiar libremente.
  • Reemplazabilidad — Si se respeta el contrato, cualquier agente puede sustituirse por otro. Aunque cambies el agente research por una versión más potente, mientras el formato de salida sea idéntico el agente storyline seguirá funcionando sin ningún cambio.
Un contrato de traspaso es el «manual de relevo» entre agentes. Es como cuando una empresa fija por adelantado el formato y los criterios de los documentos de relevo para pasar el trabajo de un departamento a otro. Con este manual, las transiciones de trabajo son fluidas y no se pierde nada por el camino.

Vista completa de la arquitectura del harness

Resumamos todos los conceptos explicados en este capítulo en una sola imagen. El siguiente diagrama representa la arquitectura global del harness de co-deck.

Resumen del capítulo
  • Un agente es un asistente de IA con rol, instrucciones y herramientas. El PM es el orquestador; los agentes especialistas son los ejecutores.
  • Una skill es un flujo de trabajo reutilizable que ejecuta un agente. Si el agente es el «quién», la skill es el «qué hace».
  • La orquestación del PM sigue el flujo: análisis de la solicitud → selección de agentes → asignación del trabajo → recogida de resultados → revisión de calidad.
  • La estrategia 3-Tier estratifica los modelos para equilibrar coste y rendimiento: High (diseño), Medium (trabajo práctico), Low (tareas simples).
  • El PM Gateway es la regla de cuatro niveles que obliga a invocar a todos los agentes especialistas únicamente a través del PM.
  • El despacho se divide en: solo lectura → paralelo y tareas de escritura → serie.
  • Un contrato de traspaso define el formato de entrada, el formato de salida y los criterios de calidad para pasar resultados entre agentes.
Adelanto del próximo capítulo: En el Capítulo 5 veremos cómo se implementan estos conceptos en un repositorio de proyecto real (ai-workspace-standards). Abre el archivo AGENTS.md, la carpeta agents/ y la carpeta skills/ reales, y comprueba cómo los conceptos aprendidos en este capítulo se expresan como código.
