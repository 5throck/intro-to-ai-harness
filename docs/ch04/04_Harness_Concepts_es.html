Capítulo 4

Multi-Agent Conceptos del Harness

Aprende los conceptos clave del harness multi-agente: agents, skills, orquestación del PM, 3-Tier strategy, PM Gateway, flujo de despacho y handoff contracts. Este capítulo construye tu comprensión de toda la arquitectura del harness.

Lo que cubre este capítulo
  • Definitions of agents and skills
  • PM orchestration and PM Gateway roles
  • 3-Tier strategy (High / Medium / Low)
  • Dispatch flow and handoff contracts
  • Complete harness architecture diagram

What Are Agents

En el Capítulo 1 comparamos una única IA con un equipo entero de especialistas. Ahora veamos los bloques de construcción de ese equipo. El primer y más importante concepto es el agent.

Agent Definition

Un agent es una entidad de IA que tiene un role claramente definido, un conjunto de tools que puede usar y un conjunto de rules que debe seguir. Piensa en un agent como un empleado digital en una empresa: tiene un cargo, sabe qué herramientas tiene permitido operar y trabaja dentro de los límites establecidos por la política de la empresa.

Cada agent está descrito por un archivo markdown (por ejemplo, agents/research.md o agents/design.md). Ese archivo contiene todo lo que la IA necesita para comportarse como el agent: su nombre, tier, asignaciones de fase, instrucciones detalladas, permisos de herramientas y los triggers que le indican al PM cuándo despacharlo.

Agent Componentes

Cada agent se construye a partir de cuatro componentes fundamentales.

Agent Types in the Harness

El harness de co-deck define varios agents especializados, cada uno responsable de una etapa diferente del pipeline de presentación.

Orchestrator

  • PM Agent — El gestor de proyecto. Nunca escribe código ni edita archivos directamente. Lee configuraciones, planifica la ejecución y despacha a los agents especializados.

Content Agents

  • research — Gathers web sources and writes research_notes.md
  • storyline — Writes the narrative structure and per-slide content
  • source-verifier — Validates URLs and checks source trustworthiness

Production Agents

  • design — Locks the visual theme (colors, fonts, layout)
  • html-build — Generates HTML slides from the deck spec
  • pdf-export — Converts slides to PDF output

Asset Agents

  • image-curator — Searches and downloads slide images
  • diagram-specialist — Generates SVG diagrams and charts
  • measure — Measures layout coordinates for PDF
También hay un agent version que toma instantáneas de los archivos antes de cada edición, como una red de seguridad. Se ejecuta en cada etapa (de la 0 a la 6) para que siempre puedas revertir a una versión anterior si algo sale mal.

Agent File Example

A continuación tienes un ejemplo simplificado de cómo se ve un archivo de definición de agent. Los archivos reales contienen mucho más detalle, pero esto te da la idea.

# agents/research.md
---
name: research
tier: medium
phases: 1
role: >
  Gathers web sources and writes research_notes.md
  for storyline design.
dispatch_triggers:
  - "research the topic"
  - "collect sources"
  - "write research notes"
---
## Instructions
- Search the web in both Korean and English.
- Write findings to research_notes.md.
- Include URLs, key facts, and source credibility notes.
- Do NOT create slide content — that is the storyline agent's job.

Observa cómo el archivo define claramente qué hace el agent (rol), cuándo despacharlo (triggers) y lo que no debe hacer (reglas). Esta claridad es lo que hace que la colaboración multi-agent funcione de manera confiable.

What Are Skills

Si los agents son los empleados, entonces skills son los libros de recetas que siguen. Una skill es un conjunto reutilizable de instrucciones que le dice a un agent how realizar un tipo específico de trabajo.

Skill Definition

Una skill es un documento de instrucciones empaquetado (almacenado como SKILL.md) que define un flujo de trabajo repetible. Las skills pueden ser cargadas por cualquier agent que las necesite. Por ejemplo, el agent research carga la skill research para saber exactamente cómo buscar en la web y estructurar sus hallazgos.

Skill Componentes

Each skill contains the following parts.

  • Metadata — El nombre de la skill, su versión, propietario (mantenedor), estado y frases de trigger almacenadas en el frontmatter YAML.
  • Triggers — Frases en lenguaje natural que le indican al sistema cuándo activar esta skill (por ejemplo, "investigar tema" o "generar PDF").
  • Instructions — Guía paso a paso que el agent sigue para completar la tarea.
  • Input / Resultado Contract — Qué archivos lee la skill y qué archivos produce, para que el siguiente agent del pipeline sepa dónde continuar.
  • Quality Checks — Validation rules the agent applies before declaring the task done.

Agent vs Skill Comparison

Agent

  • What: A digital employee with a fixed identity
  • Analogía: The employee themselves
  • File: agents/<name>.md
  • Scope: Persistent role across the entire project
  • Lifecycle: Created once, updated over time
  • Example: El agent de investigación siempre maneja la investigación web, sin importar en qué proyecto trabaje

Skill

  • What: A reusable instruction recipe
  • Analogía: The recipe book the employee follows
  • File: skills/<name>/SKILL.md
  • Scope: Invocado bajo demanda cuando se necesita una tarea específica
  • Lifecycle: Versionado de forma independiente; múltiples agents pueden compartir la misma skill
  • Example: La skill "source-verification" puede ser cargada por el agent de investigación o ejecutarse como una comprobación independiente
Analogía: Piénsalo así — un chef (agent) usa diferentes recetas (skills) según el plato que haya pedido el cliente. La identidad del chef no cambia, pero la receta le dice exactamente cómo preparar cada plato. De manera similar, el agent html-build siempre construye diapositivas HTML, pero la skill html-build le indica con precisión cómo leer el archivo de la presentación, aplicar el tema y producir el resultado.

Skill Resolution Priority

Cuando una solicitud del usuario coincide con un trigger de skill, el sistema comprueba tres ubicaciones en orden de prioridad.

  1. Workspace-level skills (skills/<name>/SKILL.md) — Funcionalidad central del workspace como scaffolding, validación y audit. Estas tienen la prioridad highest.
  2. Platform config skills (.claude/skills/ or .gemini/skills/) — Platform-specific hooks, commands, and lifecycle management.
  3. Global plugin skills — Flujos de trabajo de desarrollo de propósito general provenientes de plugins externos. Estas tienen la prioridad lowest.
Tip: Una sola skill puede compartirse entre múltiples agents. La skill "version", por ejemplo, es cargada por every agent porque cada agent necesita tomar instantáneas de los archivos antes de editarlos. Este reúso es lo que hace poderosas a las skills — escribe las instrucciones una vez, úsalas en todas partes.

PM Orchestration

Hemos presentado los agents y las skills. Ahora la pregunta es: ¿quién decide qué agent se ejecuta cuándo, en qué orden y con qué recursos? La respuesta es el PM (Project Manager) Agent, y el proceso que gestiona se llama PM orchestration.

Lo que hace el PM

El agent PM es el orchestrator de todo el flujo de trabajo multi-agent. Se sitúa en la cima de la jerarquía y es responsable de las siguientes tareas.

  • Triage user requests — Cuando escribes un comando como "haz una presentación sobre el cambio climático", el PM analiza lo que necesitas y determina qué agents deben involucrarse.
  • Create execution plans — El PM traza un plan paso a paso: primero despacha al agent de investigación, luego al agent de storyline, luego al agent de diseño, y así sucesivamente.
  • Dispatch specialist agents — El PM envía al agent adecuado para cada trabajo. Nunca hace el trabajo él mismo — solo coordina.
  • Enforce quality gates — En ciertos puntos de control (llamados "gates"), el PM pausa el pipeline y te pide que revises el resultado antes de continuar.
  • Track progress — El PM mantiene project_state.json para registrar qué etapas están completas y cuáles siguen pendientes.
  • Manage rework — Si solicitas cambios después de que una etapa ha terminado, el PM identifica qué etapas posteriores deben re-ejecutarse y despacha el conjunto mínimo de agents para aplicar la corrección.

Lo que el PM NO hace

Esto es igualmente importante. El PM never edita directamente los archivos del proyecto (excepto logs de memoria y changelogs), nunca escribe código y nunca realiza trabajo especializado. Si el PM intentara hacer el trabajo del agent de investigación, violaría la separación de responsabilidades que mantiene el sistema confiable.

Analogía — El Director: Piensa en el agent PM como el director de una orquesta. El director no toca ningún instrumento. En cambio, lee la partitura (el plan de ejecución), marca la entrada de cada sección en el momento justo (despacho) y se asegura de que toda la actuación fluya armoniosamente. Los músicos (agents especializados) son quienes realmente producen la música.

Quality Gates

En ciertos puntos del pipeline, el PM hace una pausa y presenta el resultado para tu revisión. Estos puntos de control se llaman gates. Hay dos tipos.

  • Mandatory gates — El pipeline cannot proceed hasta que tú lo apruebes explícitamente. El Gate 2 (después de que el contenido esté listo) y el Gate 5 (después de que se genere el PDF de muestra) son obligatorios.
  • Optional gates — El PM te muestra un resumen y luego continúa automáticamente. El Gate 1.5 (verificación de fuentes), el Gate 3 (especificación de diseño) y el Gate 4 (borrador HTML) son opcionales.
Por qué importan los gates: Sin gates, el pipeline iría directo de la investigación al PDF sin darte la oportunidad de corregir el rumbo. Los gates te permiten revisar la storyline antes de que el diseño quede fijado y previsualizar la disposición antes de generar el PDF completo — ahorrando tiempo y evitando esfuerzo desperdiciado.

3-Tier Strategy

No todas las tareas requieren el mismo nivel de razonamiento de IA. Algunas tareas necesitan un pensamiento arquitectónico profundo, mientras que otras son simples y repetitivas. El harness usa una 3-Tier strategy para emparejar el modelo adecuado con cada tarea, equilibrando calidad y costo.

The Three Tiers

High Tier (Plan)

  • Models: Claude Opus 4, Gemini 3.1 Pro
  • Used for: Complex reasoning, architectural design, planning, writing precise agent prompts
  • Who uses it: El agent PM (orquestador)
  • Cost: Highest
  • Example: Analizar la solicitud de un usuario, determinar qué agents despachar y crear un plan de ejecución de múltiples pasos

Medium Tier (Review)

  • Models: Claude Sonnet 4, Gemini 3.5 Flash
  • Used for: Code review, testing, quality gates, compliance checks
  • Who uses it: Agents de auditoría y QA
  • Cost: Moderate
  • Example: Revisar el resultado del agent de storyline para verificar exactitud factual, comprobando que las especificaciones de diseño sean internamente consistentes

Low Tier (Execute)

  • Models: Claude Haiku 4, Gemini 3.5 Flash
  • Used for: Fast repetitive coding, simple file operations, routine tasks
  • Who uses it: Execution agents (version snapshots, file edits)
  • Cost: Lowest
  • Example: Tomar una instantánea de un archivo antes de una edición, realizar un reemplazo de texto en un archivo de configuración

Key Rules

  • El tier puede degradarse, nunca elevarse. El PM puede asignar un modelo de tier inferior a una tarea simple para ahorrar costos, pero nunca puede asignar un modelo por encima del tier base definido de un agent. Si una tarea degradada falla, el tier base del agent debe restaurarse para el reintento.
  • El orquestador siempre usa el tier High. Dado que el PM toma las decisiones más críticas — qué agents despachar, en qué orden ejecutarlos — siempre opera en el nivel de razonamiento más alto.
  • Los revisores deben ser independientes. El agent que produjo el trabajo nunca es el mismo agent que lo revisa. Esta separación garantiza un control de calidad genuino, igual que tener un equipo de QA separado.
Para principiantes: No necesitas preocuparte por seleccionar los modelos tú mismo. El harness asigna automáticamente el tier adecuado según la tarea. Cuando ganes más experiencia, podrás ajustar las asignaciones de tier en los archivos de configuración de los agents para optimizar costo y calidad en tus proyectos específicos.

PM Gateway

El PM Gateway es el punto único de entrada por donde fluyen todas las solicitudes del usuario. Garantiza que los agents especializados nunca sean llamados directamente por el usuario — cada interacción pasa primero por el PM.

Why a Gateway?

Imagina una empresa donde cualquier empleado pudiera acercarse al CEO y darle órdenes. Caos, ¿verdad? El mismo principio se aplica aquí. Si un usuario pudiera invocar directamente al agent de diseño o al agent de investigación, el PM perdería su capacidad de planificar, secuenciar y controlar la calidad del flujo de trabajo. El gateway evita esto.

How the Gateway Works

El PM Gateway se aplica en cuatro capas, proporcionando defensa en profundidad.

  1. Aplicación a Nivel de Herramienta — La propia herramienta del agent rechaza las llamadas que omiten al PM. Esta es la capa de aplicación más estricta, como una puerta cerrada que solo se abre con la llave correcta.
  2. Aplicación a Nivel de System Prompt — La plataforma (Claude Code o Antigravity CLI) carga primero las reglas del PM, para que la IA sepa desde el principio que debe enrutar a través del PM.
  3. Aplicación a Nivel de Archivo de Agent — Cada archivo de agent especializado contiene una sección "PM-ONLY INVOCATION" que establece explícitamente que solo el PM puede despacharlo.
  4. Aplicación a Nivel de QA Gate — El agent auditor detecta cualquier intento de eludir al PM durante la audit de calidad de la Phase 6 y lo reporta como una violación.

PM Direct Execution Scope

Incluso el propio PM tiene restricciones sobre lo que puede hacer directamente.

Always Allowed

  • Read files
  • Search (glob, grep)
  • Create tasks and update status
  • Ask the user questions
  • Run read-only bash commands (git status, ls)

Restricted

  • Write/Edit files — only memory/*.md and CHANGELOG.md
  • Bash write commands — must delegate to a specialist
  • Code implementation — must delegate to a specialist
  • Design work — must delegate to a specialist
Important: Nunca intentes llamar directamente a los agents especializados. Siempre pasa por el PM. Si escribes "investigar tema X" en lugar de seguir el flujo de trabajo del PM, la solicitud será rechazada a nivel de herramienta. Esto es intencional — el gateway garantiza que cada acción esté planificada, rastreada y controlada en calidad.

Dispatch Flow

Cuando el PM decide qué agents ejecutar y en qué orden, sigue un dispatch flow estructurado. La decisión clave es si ejecutar los agents in parallel o in sequence.

Parallel vs Serial Dispatch

Parallel Dispatch

  • Múltiples agents se ejecutan al mismo tiempo
  • Used for read-only tasks (research, analysis, inspection)
  • Faster overall — no waiting for one agent to finish
  • Ejemplo: El image-curator y el diagram-specialist se ejecutan en paralelo en el Stage 3.5 porque no dependen del resultado del otro

Serial Dispatch

  • Agents run one at a time, in order
  • Used for write tasks to prevent file conflicts
  • Más lento pero más seguro — el resultado de cada agent está disponible antes de que comience el siguiente
  • Ejemplo: El agent de investigación debe terminar research_notes.md antes de que el agent de storyline pueda usarlo

The Dispatch Decision

Cuando el PM recibe una solicitud, sigue un árbol de decisión simple.

1. Receive request — The user types a command or the pipeline advances to the next stage.
2. Classify deliverable type — El PM identifica qué tipo de resultado se necesita (notas de investigación, especificación de diseño, diapositivas HTML, PDF, etc.) y lo mapea al agent correcto.
3. Determine parallel or serial — Si la tarea implica escribir archivos, despacha en serie (un agent a la vez). Si implica solo lectura y análisis, despacha todos los agents relevantes en paralelo.
4. Dispatch agents — Envía la tarea al agent o agents especialistas con el modelo del tier apropiado.
5. Collect and validate — Espera a que todos los agents terminen, luego ejecuta las comprobaciones de calidad en el siguiente gate.
Consejo para principiantes: No necesitas memorizar este árbol de decisión. El PM lo maneja automáticamente. A medida que ganes experiencia, empezarás a reconocer qué etapas se ejecutan en paralelo y cuáles en serie, y podrás predecir el comportamiento del pipeline con mayor precisión.

Handoff Contracts

En un sistema multi-agente, el producto de trabajo de un agent se convierte en la entrada del siguiente. El mecanismo que hace confiable esta transferencia se llama handoff contract.

What Is a Handoff Contract?

Un handoff contract es un acuerdo entre dos agents que especifica tres cosas.

  1. Resultado file — Qué archivo(s) produce el agent emisor. Por ejemplo, el agent de investigación produce research_notes.md.
  2. File location — Dónde se coloca el archivo para que el agent receptor sepa exactamente dónde encontrarlo. Por ejemplo, presentations/<project>/research_notes.md.
  3. Format and structure — El formato esperado (markdown, JSON, etc.) y las secciones o campos que debe contener el archivo, para que el agent receptor pueda analizarlo de manera confiable.

Cuando estos tres elementos están claramente definidos, el traspaso es contractual — el agent receptor sabe exactamente qué esperar y cómo consumir los datos. Esto elimina las conjeturas y reduce los errores.

Example: Research to Storyline

Aquí tienes un handoff contract real del pipeline de co-deck.

Sending Agent: Research

  • Produces: research_notes.md
  • Location: presentations/<name>/
  • Format: Markdown with sections for Sources, Key Facts, Credibility Notes
  • Trigger: "research the topic"

Receiving Agent: Storyline

  • Consumes: research_notes.md
  • Reads from: Same project directory
  • Expects: Markdown estructurado que puede analizar para obtener hechos clave y URLs de fuentes
  • Produces: storyline.md + slide_deck.md

El contrato es explícito en ambos archivos de agent. Las instrucciones del agent de investigación dicen "escribe los hallazgos en research_notes.md" y las instrucciones del agent de storyline dicen "lee research_notes.md como entrada". Como el contrato está escrito en las definiciones de los agents, no hay ambigüedad.

Why Handoff Contracts Matter

Sin handoff contracts, los agents tendrían que adivinar dónde encontrar su entrada, en qué formato está y si está lista. Esto conduce a tres modos de fallo comunes.

  • Archivo no encontrado — El agent receptor busca un archivo que nunca fue creado o que se guardó en una ubicación diferente.
  • Format mismatch — The sending agent outputs JSON but the receiving agent expects markdown.
  • Premature consumption — El agent receptor comienza antes de que el agent emisor haya terminado de escribir, lo que resulta en datos incompletos o corruptos.

Los handoff contracts previenen estos tres problemas haciendo que las expectativas de transferencia sean explícitas, verificables y exigibles.

Analogía — El Manual de Relevo: Piensa en un handoff contract como el manual de relevo que se usa en los cambios de turno de un hospital o una fábrica. Cuando termina el turno de día, la enfermera saliente completa un formulario estructurado: qué pacientes fueron atendidos, qué medicamentos se administraron, qué asuntos quedan abiertos. La enfermera entrante lee este formulario y puede retomar exactamente donde dejó el turno anterior. Sin este manual, la información crítica podría perderse. El mismo principio se aplica a los agents de IA.

Handoff Chain in the Full Pipeline

Aquí tienes la cadena completa de traspasos del pipeline de presentación de co-deck. Cada flecha representa un handoff contract.

Stage 0: PM reads lecture-profile.md → initializes project_state.json
Stage 1: research → produces research_notes.md
Stage 1.5: source-verifier → reads research_notes.md, produces source-verification.md
Stage 2-3: storyline → reads research_notes.md, produces storyline.md + slide_deck.md
Stage 3: design → reads slide_deck.md, produces design_spec.md
Stage 3.5: image-curator → reads slide_deck.md, produces image-manifest.json + images
Stage 3.5: diagram-specialist → reads slide_deck.md, produces diagram-manifest.json + SVGs
Stage 5-8: html-build → reads slide_deck.md + design_spec.md + manifests, produces lecture_vN.html
Stage 9-10: measure → reads HTML, produces pdf_layout_spec.md
Stage 11: pdf-export → reads all specs, produces <project>.pdf

Observa cómo cada agent solo lee lo que necesita y produce un resultado bien definido. La cadena forma un flujo de datos claro desde la solicitud del usuario hasta el PDF final, con cada punto de traspaso documentado en las definiciones de los agents y skills.
