Exploring ai-workspace-standards

Learn the structure of the ai-workspace-standards repository and its core concepts: the 4-level layer structure (L0→L1→L2→L3), the variant concept, the roles of the key files (AGENTS.md, CLAUDE.md, GEMINI.md), and common contracts.

What This Chapter Covers
  • The structure of the ai-workspace-standards repository
  • Key files: the roles of AGENTS.md, CLAUDE.md, and GEMINI.md
  • The 4-level layer structure (L0 → L1 → L2 → L3)
  • The variant concept
  • Common contracts and template inheritance

What is ai-workspace-standards

Definition

ai-workspace-standards is an open-source standard template for building projects in which multiple AI agents cooperate using AI coding tools such as Claude Code and Antigravity CLI. It is publicly available on GitHub free of charge, and anyone can copy it and apply it to their own projects.

  • GitHub repository: github.com/5throck/ai-workspace-standards
  • License: Open source (anyone is free to use, modify, and distribute it)
  • Supported platforms: Claude Code, Antigravity CLI (both platforms use the same structure)

Why Is a Standard Needed?

If every project defines and manages its AI agents differently, all sorts of problems appear. The reasons a standard template is needed are as follows.

  • Consistency — When every project follows the same structure, even a teammate joining a new project understands it immediately, because file locations, the way agents are defined, and the rules are all identical.
  • Reusability — Agents or skills built once can be used as-is in other projects. There is no need to define similar work from scratch every time.
  • Collaboration — When several people work together, shared "language" and "rules" reduce communication errors and enable efficient cooperation.
  • Quality assurance — Automated verification scripts (audit, validate) operate on the standard structure, so rule violations can be caught early.

A Beginner's Analogy: Org Chart and Operations Manual Templates

To understand ai-workspace-standards, it helps to compare it to a company. To found a company you need an org chart (who does what) and an operations manual (how each person should work). ai-workspace-standards is precisely a template for that org chart and operations manual. Copy the template, adapt it to your own company (project), and you have a complete organizational system from day one.

In this handbook's exercises, both co-consult and co-deck were built on top of ai-workspace-standards. In other words, these two projects started from the same template and were customized for their respective purposes.

Directory Structure

The ai-workspace-standards repository has a regular directory structure. Because each folder has a clear role, the structure alone tells you at a glance how a project is organized.

Top-Level Directory Overview

The memory/ Folder

The top level also has a memory/ folder. This is where records of AI sessions, meeting minutes, work logs, and the like are stored. The PM agent leaves a record of each session's progress and decisions in a memory/YYYY-MM-DD.md file. That way, the next session can see what happened in previous ones.

Root Files

Besides folders, important files sit at the top level: AGENTS.md (the agent registry), CLAUDE.md (instructions for Claude Code), GEMINI.md (instructions for Antigravity CLI), and CHANGELOG.md (change history), all located in the project root. These files are covered in detail in the "Key Files" section of this chapter.

Tip: If you would like to explore it yourself, clone the repository in a terminal. After copying it to your computer with git clone https://github.com/5throck/ai-workspace-standards.git, opening each folder and file directly makes the understanding come much faster.

Key Files

The key files of ai-workspace-standards are located in the project root, and each has a clear role. This section explains the five most important files.

AGENTS.md — The Agent Registry

AGENTS.md is the "official roster" that registers every AI agent belonging to the project: definitions, roles, Tiers, and dispatch triggers. When you open the file you find a table listing all the agents, with links to each agent's detailed definition file (agents/pm.md, agents/research.md, etc.).

AGENTS.md contains the following information:

  • Agent roster — Every agent's name, file location, Tier (priority), and role
  • PM Gateway workflow — The rules for how the PM dispatches agents
  • Dispatch triggers — Which situations call for which agent
  • Execution plan templates — The standard format used when planning tasks

Beginner's analogy: AGENTS.md is the company's "employee roster." An employee roster lists each person's name, rank (Tier), and duties. Likewise, AGENTS.md clearly defines each AI agent's name, grade, and role.

CLAUDE.md — Behavioral Instructions for Claude Code

CLAUDE.md holds the behavioral instructions that Claude Code (Anthropic's AI coding tool) must follow when working in the project. It describes in detail which agent roles Claude may perform, which tools it may use, and which rules it must observe.

The core contents of CLAUDE.md are:

  • Agent dispatch rules — Which situations send which agent out from the PM
  • 3-Tier strategy — When High/Medium/Low models are used
  • Gate protocol — Which steps need user approval and which proceed automatically
  • Tool permissions — The scope of tools available to each agent

Beginner's analogy: CLAUDE.md is Claude's "job instruction sheet." It is like a manual that says things like "when work of this kind comes in, hand it to this person in charge," and "at this stage you must obtain manager approval."

GEMINI.md — Behavioral Instructions for Antigravity CLI

GEMINI.md contains the behavioral instructions for Antigravity CLI (Google's AI coding tool). Its content and structure play exactly the same role as CLAUDE.md; the only difference is that it applies when you use Antigravity CLI instead of Claude Code.

Why do the two files exist separately? Because Claude Code and Antigravity CLI are tools made by different companies, their model names, tool invocation styles, and system prompt formats differ. However, the agent structure, workflows, and gate rules are completely identical. So think of CLAUDE.md and GEMINI.md as "same rules, different tool settings."

CHANGELOG.md — Recording Change History

CHANGELOG.md records every change made to the project in chronological order. Whenever a new agent is added, a skill is revised, or a rule changes, it is recorded here. Unlike a version control system's (Git's) commit log, the CHANGELOG summarizes changes in a form humans can read.

context.md (in the docs/ Folder) — Advanced Settings for L2/L3 Projects

docs/context.md is an advanced settings file that exists only in L2 variant templates and L3 projects. It is absent at the workspace root (L0), where AGENTS.md is the SSOT. Its main contents are:

  • The concrete definition of the L0 → L1 → L2 → L3 layer structure
  • The frontmatter specification for agent files
  • Lifecycle management procedures
  • The structure of governance documents

Because this file is closer to "system configuration," beginners don't need to understand it fully at first. As you run projects, you will refer to it more and more deeply.

Comparing the Key Files

AGENTS.md

  • Role: Agent registry
  • Audience: All agents
  • Contents: Agent roster, roles, Tiers, dispatch triggers, workflow
  • Analogy: Employee roster
  • Location: Project root

CLAUDE.md / GEMINI.md

  • Role: Platform-specific behavioral instructions
  • Audience: Claude Code / Antigravity CLI
  • Contents: Dispatch rules, 3-Tier strategy, gate protocol, tool permissions
  • Analogy: Job instruction sheet
  • Location: Project root

4-Level Layer Structure

One of the most important design principles of ai-workspace-standards is the 4-level layer structure. It is a hierarchy in which workspace resources travel from the original source (L0) through common infrastructure (L1) and variant templates (L2) down to actual projects (L3).

Distribution Path vs Layer Structure
"L0 → L1 → L2" describes the distribution path: the direction in which original source is delivered to L1 and L2.
"L1 → L2 → L3" describes the layer structure: the static hierarchy in which each layer forms the foundation of the layer below.

L0 Source (Workspace Root) — The Original Source

L0 Source is the workspace root directory itself. It is the only place where edits are made, and the starting point from which changes are delivered to every other layer.

  • Common agents — Basic agents such as the PM agent that every project uses
  • Common skills — Basic skills reusable anywhere
  • Core scripts — Essential automation tools such as audit.ts and validate-templates.ts
  • AGENTS.md — The global agent registry

L1 (Common Template) — Common Infrastructure Layer

L1 is the common infrastructure layer located at templates/common/. Built from what is distributed by L0 Source, it provides the templates shared by every variant, including platform-specific configurations and the standardized directory structure.

  • The .claude/ directory — settings, commands, and skills for Claude Code
  • The .gemini/ directory — settings, commands, and skills for Antigravity CLI
  • Platform-specific agent configurations (CLAUDE.md, GEMINI.md)
  • Common agent templates, common skills, and scripts
  • propagation-map.json — Defines the L0→L1 distribution rules

Note: L1 is never edited directly. Changes are distributed automatically from L0 Source via bun run propagate:apply.

L2 (Variant Template) — Variant Template Layer

L2 is the variant template layer located at templates/co-*/. Each variant (co-deck, co-consult, etc.) is a template built on L1 that adds its own agents, skills, and settings.

  • Variant-specific agents (e.g., co-deck's image-curator, pdf-export)
  • Variant-specific skills (e.g., co-deck's html-build, storyline)
  • Variant configuration (variant.json, PM agent YAML overrides)
  • Inheritance of the L1 common template (inherits_common: "templates/common" in variant.json)

There are currently 11 variant templates: co-abap, co-consult, co-deck, co-design, co-develop, co-export, co-game, co-hr, co-news, co-security, and co-work.

L3 (Project) — Actual Project Layer

L3 is the actual project layer located at Projects/*/. Each L3 project is scaffolded from an L2 variant template. Each project operates independently and allows local customization.

  • docs/context.md — The project's advanced settings (immutable after project creation)
  • Project-specific agents, skills, and scripts
  • variant.json — Metadata copied from L2
  • The space where real work output is produced

Distribution Path and Layer Structure

In this system it is important to distinguish two directions.

  • Distribution path (L0 → L1 → L2): Changes from the original source (L0) reach the L1 common template via propagate:apply, and then each L2 variant template. This is the direction code flows.
  • Layer structure (L1 → L2 → L3): The static hierarchical relationship in which each layer builds upon the template of the layer above. L3 projects are scaffolded from L2 variant templates, and L2 inherits the L1 common template.

L2 → L3: Actually Creating a Project

The "scaffold" arrows in the diagram above amount, in practice, to running one script from the workspace root. The new-project.ts script reads the chosen L2 variant template (templates/co-*/) and generates a fully working L3 project under Projects/<project-name>/.

bun scripts/new-project.ts "my-project" --variant co-consult

Running this command makes the script automatically perform the following steps:

  • Copies templates/co-consult/'s (L2) agents, skills, and settings into Projects/my-project/
  • Also applies the common infrastructure from templates/common/ (L1)
  • Places variant.json at the project root and updates it with the project name
  • Creates project-specific setting files such as docs/context.md

For --variant you can specify any of the 11 variants that exist today, including co-consult and co-deck. The co-consult and co-deck examples used in the exercises of Chapters 6 and 7 are not separate cloned repositories but the result of scaffolding templates/co-consult/ and templates/co-deck/ (L2) directly from the public ai-workspace-standards repository with the command above.

Override Rules

A lower layer may override the settings of higher layers, but never influences them in the reverse direction. This is the same principle as class inheritance in object-oriented programming.

  • Rules set at L3 take priority over rules from L2, L1, and L0.
  • Rules set at L2 take priority over rules from L1 and L0 (unless overridden at L3).
  • Rules set at L1 take priority over rules from L0 (unless overridden at L2 or L3).
  • Rules from L0 apply everywhere if no layer overrides them.
Anything in L0 Source applies commonly to all projects. That is why core L0 scripts (audit.ts, validate-templates.ts) behave identically in every project. Fixing something at L0 delivers the change through the distribution path to L1 and L2, ultimately reaching L3 projects too. This is the heart of the standard — decide once, apply consistently everywhere.

The Variant Concept

What Is a Variant?

A variant is a template customized for a specific purpose, built on ai-workspace-standards' L0 + L1 templates. The L2 described in the 4-level layer structure section is precisely the variant-template layer, while L3 refers to actual projects scaffolded from those L2 templates.

All variants share the same "skeleton" (L0 + L1), but each adds different agents, skills, and settings according to its own purpose. It is like various models — sedans, SUVs, sports cars — being built on the same automobile platform.

Examples of Variants

The ai-workspace-standards ecosystem currently includes the following variants.

  • co-consult — A variant for practicing AI consulting. It provides an agent team that automates company analysis, strategy development, and report writing. Practiced in Chapter 6 of this handbook.
  • co-deck — A variant for presentation automation. It automates the entire pipeline, from research → storyline → design → HTML build → PDF output. Provides an 11-stage workflow.

variant.json — A Variant's Metadata

Each variant defines its metadata through a variant.json file. This file contains the following information:

  • Name — the variant's identifier (e.g., "co-deck", "co-consult")
  • Version — the variant's current version (e.g., "1.0.0")
  • Status — current development stage, such as draft, beta, stable
  • Dependencies — dependency relationships on the upper levels (L0, L1)
  • Description — the variant's purpose and characteristics
{
  "name": "co-deck",
  "description": "Presentation and lecture material production variant",
  "variant_type": "lecture",
  "status": "beta",
  "version": "0.2.0",
  "inherits_common": "templates/common",
  "agents": [
    { "name": "pm",              "file": "agents/pm.md" },
    { "name": "research",         "file": "agents/research.md" },
    { "name": "storyline",       "file": "agents/storyline.md" },
    { "name": "html-build",      "file": "agents/html-build.md" }
  ]
}

variant.json acts like an "identity card" referenced when installing and managing a variant. Only with this file can the system know which variant it is, which version, and which dependencies it carries.

The Variant Lifecycle

Variants pass through the following lifecycle stages:

  • draft — Initial development stage; only the basic structure exists yet
  • beta — Testing stage; major features implemented but stability still needs verification
  • stable — Stable stage; fit for actual use
  • deprecated — Discontinued; no longer maintained

This lifecycle is managed centrally in docs/VERSION_MANIFEST.md. A new variant starts as draft and, after sufficient testing, is promoted to stable.

Creating a New Project From a Variant

In the Chapter 6 and 7 exercises, pre-built example projects (co-consult, co-deck) are cloned to save time. But in real daily work you never clone anything — from the workspace root, a single command scaffolds a brand-new L3 project from an L2 variant template.

bun scripts/new-project.ts "my-market-report" --variant co-consult

This command creates Projects/my-market-report/ as an independent new Git repository, copies in co-consult's agents, skills, and settings, and renders an empty docs/context.md skeleton ready to be filled in with this project's goals. The full syntax is:

bun scripts/new-project.ts "<project-name>" --variant <variant> [--platform claude|antigravity|both] [--version X.Y.Z] [--country <CODE>]
  • <project-name> — Required. Becomes the folder name under Projects/.
  • --variant <variant> — Required. Specifies which L2 template to scaffold from (co-consult, co-deck, co-develop, etc.).
  • --platform — Optional. Restricts which platform configurations (.claude/, .gemini/) get copied. Defaults to both.
  • --version — Optional. Pins a specific template version instead of the source variant's current one.
  • --country <CODE> — Optional. For a Korea-focused project, pass --country KR. The country profile injects Korea-only skills such as k-dart, k-law, and k-kosis together with KR API key setup into your project (see Appendix D for details).
Do not confuse this with creating a new variant, covered next. new-project.ts is an everyday command you will run constantly — it scaffolds an L3 project from an already existing L2 template. Creating the L2 template itself (a brand-new variant like co-legal or co-hr) is a separate, far rarer job that uses create-l3-scaffold.ts — covered in Chapter 11.
Tip: You can also make your own variant! Copy ai-workspace-standards' templates and add the agents and skills you need. Chapter 11 covers how to build a variant in detail.

Common Contracts

What Is a Contract?

A contract is a common set of rules that agents, skills, and scripts must all observe. It is the same idea as an "interface" or "protocol" in programming: every participant is compelled to follow the same formats and rules.

Beginner's analogy: a contract is a "common language." When multilingual people meet and agree to use the same language (say, English), communication flows smoothly. Likewise, when all agents follow the same contract, they can cooperate without conflicts.

Governance Contracts — Where Are They Defined?

Governance contracts (the common rules) are not a single JSON file; they are defined across the workspace's core governance documents.

  • CONSTITUTION.md — The master shared standard for the entire workspace: governance rules, PR workflows, multi-agent architecture principles, etc.
  • AGENTS.md — The SSOT at L0 (workspace root): the agent registry, PM Gateway workflow, skill roster, etc.
  • docs/context.md (L2/L3 projects only) — Each variant's and project's advanced settings: project type, status, architecture, key files, etc.

These documents define the common rules that agents, skills, and scripts must all observe. Like an "interface" or "protocol" in programming, they compel every participant to follow the same formats and rules.

The Three Roles of Contracts

Governance contracts perform three core roles.

  • Consistency guarantee — Because every project uses the same format, a file from one project can be understood instantly in another. You know where agent files live and which fields are required.
  • Compatibility maintenance — When creating a new variant, simply following the contract keeps you automatically compatible with the existing tools (audit, validate). No extra setup or conversion needed.
  • Automatic verification — Scripts like bun scripts/audit.ts inspect files automatically and detect rule violations. Nobody needs to check everything by hand.

Applying a Contract

When creating a new agent or skill, applying the contract works like this:

Check the contract — Open CONSTITUTION.md and AGENTS.md and review the rules for the kind of file you plan to create (agent, skill, script). Identify which fields are required and which optional.
Write the frontmatter — Write YAML frontmatter at the top of the file, filling in every field defined in the governance documents (name, tier, phase, etc.) without omission.
Write the body — Write the body of the file following the structure guide: naming conventions, section layout, required descriptions.
Run automatic verification — Run bun scripts/audit.ts to check contract compliance automatically. Fix any errors and verify again.
Contracts are the "common language" between agents. Following the same rules enables smooth collaboration — just as drivers who follow the same traffic laws share roads safely and accident-free. Thanks to contracts, every project in the ai-workspace-standards ecosystem stays mutually compatible and behaves consistently.
