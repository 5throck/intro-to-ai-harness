Exploring ai-workspace-standards

Learn the structure and core concepts of the ai-workspace-standards repository: 4-level layer structure (L0→L1→L2→L3), the variant concept, key files (AGENTS.md, CLAUDE.md, GEMINI.md), and common contracts. This chapter gives you a guided tour of the workspace that underpins every multi-agent project.

What This Chapter Covers

What is ai-workspace-standards

In the previous chapter we explored the conceptual building blocks of a multi-agent harness — agents, skills, the PM Gateway, and handoff contracts. Now it is time to look at the actual codebase that puts all those ideas into practice. That codebase is called ai-workspace-standards.

Definition

ai-workspace-standards is an open-source GitHub repository that defines a standardized workspace structure for multi-agent AI projects. It provides a shared set of conventions, file layouts, agent definitions, skill templates, and automation scripts that any AI-assisted project can adopt. Think of it as the foundational blueprint that makes agent teamwork possible.

The repository is hosted at github.com/5throck/ai-workspace-standards and is maintained as a living standard that evolves alongside AI tooling capabilities.

Why Standards Matter

You might wonder: why do we need a "standard" workspace at all? Can't each project just organize its files however it wants?

The answer comes down to interoperability. When multiple AI agents need to collaborate on the same project, they must all agree on where files live, what format they use, and what conventions to follow. Without a shared standard, every project would invent its own structure, and agents trained for one project could not work on another. Standards make it possible to:

  • Reuse agents across projects — A research agent written for one project can work on any project that follows the same layout conventions.
  • Share skills as plugins — Skills are packaged as portable instruction sets that any workspace can load, just like browser extensions.
  • Automate quality checks — Audit scripts can validate any workspace that follows the standard structure, catching errors before they propagate.
  • Onboard new team members quickly — Whether human or AI, anyone joining the project immediately knows where to find what they need.

The Org Chart Analogy

Think of ai-workspace-standards as an "org chart and employee manual template" for a company. When you start a new business, you do not invent the concept of "departments" from scratch — you adopt a standard structure (HR, Finance, Engineering, Marketing) and customize it to your needs. In the same way, ai-workspace-standards provides a proven organizational template for AI projects:

Company Org Chart

  • Departments → agents/, skills/, scripts/
  • Employee handbooks → CLAUDE.md, GEMINI.md
  • Company policies → AGENTS.md
  • Project files → presentations/, docs/
  • Meeting minutes → memory/

ai-workspace-standards

  • Directories give each function its own workspace
  • Agent files define each AI's role and permissions
  • Governance files enforce consistency across the project
  • Output directories store the project's deliverables
  • Session logs record every decision and change
co-consult and co-deck are built on top of this standard. Every variant project — whether it produces slide decks (co-deck), consulting analyses (co-consult), or something else entirely — inherits its base structure from ai-workspace-standards. The variant adds its own specialized agents, skills, and scripts on top of the common foundation, just as a franchise restaurant adds its own menu items to a standard kitchen layout.

Directory Structure

Let us take a tour of the top-level directories in a typical ai-workspace-standards workspace. Each directory has a clear purpose, and understanding this layout is the first step to navigating any project built on the standard.

Directory Overview

Here is a brief description of each directory and what it contains.

  • agents/ — Contains one markdown file per agent (for example, research.md, design.md, pm.md). Each file defines the agent's role, tier, phases, triggers, tool permissions, and detailed instructions. This is where the "employee profiles" live.
  • skills/ — Contains subdirectories, each with a SKILL.md file that defines a reusable workflow recipe. Skills can be loaded by any agent that needs them. Think of this as the company recipe book collection.
  • scripts/ — Automation scripts written in TypeScript (executed via bun). Includes audit tools, sync pipelines, validation checks, and other utilities that keep the workspace healthy.
  • docs/ — Documentation and context files. Includes context.md (the project's identity card), Architecture Decision Records (ADRs), user guides, and design specifications.
  • templates/ — The common template that serves as the L1 base layer (see the hierarchy section below). Contains shared agent definitions, skill templates, and configuration that all variant projects inherit.
  • presentations/ — In variant projects like co-deck, this is where individual project workspaces live. Each presentation gets its own subdirectory (for example, presentations/climate-change/) containing its lecture profile, research notes, slide deck, and output files.
  • memory/ — Session logs, meeting transcripts, and daily development notes. Every AI session writes a summary here, creating an audit trail of decisions and changes.
Tip: The agents/ and skills/ directories are the heart of the workspace. When you want to understand how a project works, start by reading the agent files in agents/ — they tell you exactly what each AI does, when it is activated, and what it produces.

Key Files

Among the many files in an ai-workspace-standards workspace, a few stand out as especially important. These are the governance files that every AI agent and every human collaborator must respect.

The Big Three

Three files form the backbone of workspace governance: AGENTS.md, CLAUDE.md, and GEMINI.md. Each serves a distinct audience, but together they create a unified set of rules.

AGENTS.md

  • Audience: All AI platforms (Claude, Gemini, and others)
  • Role: The master registry — lists every agent, its tier, phases, dispatch triggers, and the PM Gateway rules
  • Analogy: The company's org chart posted in the lobby — everyone can see who does what
  • Key content: Agent roster, PM Gateway policy, execution plan templates, 3-Tier strategy, lifecycle management rules
  • Loaded by: Claude Code automatically loads this file at the start of every session

CLAUDE.md

  • Audience: Claude Code (Anthropic's AI coding agent)
  • Role: Claude-specific behavioral instructions — how Claude should behave in this workspace
  • Analogy: The Claude employee handbook — Claude reads this on its first day and follows it throughout
  • Key content: Platform-specific dispatch rules, model tier mappings, Claude-specific tool permissions, workflow triggers
  • Loaded by: Claude Code automatically at session start

GEMINI.md

  • Audience: Gemini CLI / Antigravity (Google's AI coding agent)
  • Role: Gemini-specific behavioral instructions — how Gemini should behave in this workspace
  • Analogy: The Gemini employee handbook — Gemini reads this on its first day and follows it throughout
  • Key content: Platform-specific dispatch rules, model tier mappings, Gemini-specific tool permissions, workflow triggers
  • Loaded by: Gemini CLI automatically at session start

How the Three Files Work Together

The key insight is that AGENTS.md contains the shared rules that apply to all platforms, while CLAUDE.md and GEMINI.md add platform-specific details on top. This separation means the core governance lives in one place, and platform differences are isolated to their respective files.

Other Important Files

Beyond the big three, several other files play critical roles in the workspace.

  • context.md — The project's identity card. Declares the project type, status, architecture, key files, and documentation standards. It is marked as immutable after project creation — all project-specific changes go into a separate variant context file instead. Think of it as the company's certificate of incorporation.
  • CHANGELOG.md — A human-readable record of all changes made to the project, organized by version number. Every modification to agents, skills, scripts, or governance files is logged here so that team members can track what changed and why.
  • variant.json — The variant's metadata file. Declares the variant name, type, status, version, which agents and skills it includes, and how it inherits from the common template. We will explore this in detail in the Variants section.
  • memory/MEMORY.md — An index of all session logs. Each working session produces a dated log file (for example, memory/2026-08-10.md) with a summary of what was accomplished, what changed, what decisions were made, and what issues remain open.
File Analogy Summary: If the workspace were a city, AGENTS.md would be the city charter (the founding document everyone follows), CLAUDE.md and GEMINI.md would be department-specific rulebooks, context.md would be the city's registration certificate, CHANGELOG.md would be the public record of city council decisions, and memory/ would be the city archive where every meeting's minutes are stored.

4-Level Layer Structure

One of the most powerful design decisions in ai-workspace-standards is the 4-level layer structure. This is a hierarchical system where resources flow from the original source (L0) through common infrastructure (L1), variant templates (L2), and into actual projects (L3).

Distribution Path vs Layer Structure
"L0 → L1 → L2" describes the distribution path: the direction in which original source code is delivered to L1 and L2.
"L1 → L2 → L3" describes the layer structure: a static hierarchy where each layer serves as the foundation for the layer below it.

L0 Source (Workspace Root) — Original Source

L0 Source is the workspace root directory itself. It is the only place where edits are made, and the starting point from which changes propagate to all other layers.

  • Common agents — The PM agent and other foundational agents used by every project
  • Common skills — Reusable workflow recipes available everywhere
  • Core scripts — audit.ts, validate-templates.ts, and other essential automation tools
  • AGENTS.md — The global agent registry

L1 (Common Template) — Common Infrastructure Layer

L1 is the common infrastructure layer located at templates/common/. Built from content distributed by L0 Source, it provides templates shared by all variants, including platform-specific configurations and standardized directory structures.

  • .claude/ directory — Claude Code settings, commands, and skills
  • .gemini/ directory — Gemini CLI settings, commands, and skills
  • Platform-specific agent configurations (CLAUDE.md, GEMINI.md)
  • Common agent templates, common skills, and scripts
  • propagation-map.json — Defines L0→L1 distribution rules

Note: L1 is never edited directly. Changes are distributed automatically from L0 Source via bun run propagate:apply.

L2 (Variant Template) — Variant Template Layer

L2 is the variant template layer located at templates/co-*/. Each variant (co-deck, co-consult, etc.) is a template built on L1 that adds its own agents, skills, and configuration.

  • Variant-specific agents (for example, co-deck's image-curator, pdf-export)
  • Variant-specific skills (for example, co-deck's html-build, storyline)
  • Variant configuration (variant.json, PM agent YAML overrides)
  • Inherits the L1 common template (variant.json's inherits_common: "templates/common")

There are currently 9 variant templates: co-consult, co-deck, co-design, co-develop, co-export, co-game, co-news, co-security, and co-work.

L3 (Project) — Actual Project Layer

L3 is the actual project layer located at Projects/*/. Each L3 project is scaffolded from an L2 variant template. Projects operate independently and support local customization.

  • docs/context.md — The project's deep configuration (immutable after project creation)
  • Project-specific agents, skills, and scripts
  • variant.json — Metadata copied from L2
  • The space where actual work output is produced

Distribution Path and Layer Structure

It is important to distinguish two directions in this system.

  • Distribution path (L0 → L1 → L2): Changes from the original source (L0) are delivered via propagate:apply to the L1 common template and then to each L2 variant template. This is the direction code flows.
  • Layer structure (L1 → L2 → L3): A static hierarchical relationship where each layer builds on the template of the layer above it. L3 projects are scaffolded from L2 variant templates, and L2 inherits the L1 common template.

Override Rules

A lower layer can override settings from a higher layer, but changes never propagate in the reverse direction. This follows the same principle as class inheritance in object-oriented programming.

  • Rules set at L3 take priority over rules from L2, L1, and L0.
  • Rules set at L2 take priority over rules from L1 and L0 (unless overridden by L3).
  • Rules set at L1 take priority over rules from L0 (unless overridden by L2 or L3).
  • Rules from L0 apply to all layers when nowhere else overridden.
Everything at L0 Source is common to all projects. That means core scripts like audit.ts and validate-templates.ts work identically in every project. When you fix something at L0, the change propagates through the distribution path to L1 and L2, and ultimately reaches every L3 project. This is the core promise of the standard — define once, apply consistently everywhere.

Variant Concept

What is a Variant?

A variant is a template customized for a specific purpose, built on the L0 + L1 foundation. As explained in the 4-level layer structure section, L2 is the variant template layer, and L3 is the actual project scaffolded from an L2 template.

Variants are what make ai-workspace-standards practical. The standard provides the foundation; variants provide the specialization. Without variants, the standard would be a generic framework with no real-world application. Without the standard, variants would be isolated projects with incompatible structures.

Variant Examples

Let us look at two real variants to understand how this works in practice.

co-deck

  • Type: Lecture and presentation material production
  • Pipeline: 11-stage workflow from research to print-ready PDF
  • Agents: 11 specialized agents (PM + 10 specialists: research, source-verifier, storyline, design, image-curator, diagram-specialist, html-build, measure, pdf-export, version)
  • Output: HTML slide decks and PDF presentations
  • Unique features: Theme system (5 HTML themes), style system, image curation pipeline, SVG diagram generation, PDF layout measurement

co-consult

  • Type: Consulting analysis and advisory output
  • Pipeline: Research-driven analysis workflow for business consulting
  • Agents: Specialized consulting agents adapted from the common set
  • Output: Consulting reports, analysis documents, advisory materials
  • Unique features: Industry-specific research profiles, MECE logic frameworks, structured problem-solving workflows

Despite their different purposes, both variants share the same foundation: the PM orchestration pattern, the 3-Tier strategy, the PM Gateway, the handoff contract system, and the directory layout. This shared foundation is what makes them interoperable and maintainable.

variant.json — The Variant Identity Card

Every variant has a variant.json file at its project root that declares its identity and configuration. This file is the variant's "passport" — it tells the system what this variant is, what it includes, and how it relates to the common template.

Here are the key fields in variant.json.

  • name — The variant's identifier (for example, "co-deck" or "co-consult").
  • description — A human-readable summary of what the variant does.
  • variant_type — The category of work this variant handles (for example, "lecture" for presentation production).
  • status — The lifecycle status: "draft", "beta", or "stable".
  • version — The current version number following semantic versioning (major.minor.patch).
  • inherits_common — The path to the common template this variant inherits from (typically "templates/common").
  • agents — A list of agents this variant includes, with their file paths.
  • skills — A list of skills available in this variant.
  • lifecycle — Metadata about the variant's lifecycle transitions (when it was created, when it was promoted to beta, etc.).
{
  "name": "co-deck",
  "description": "Lecture and presentation material production variant",
  "variant_type": "lecture",
  "status": "beta",
  "version": "0.2.0",
  "inherits_common": "templates/common",
  "agents": [
    { "name": "pm",              "file": "agents/pm.md" },
    { "name": "research",         "file": "agents/research.md" },
    { "name": "storyline",       "file": "agents/storyline.md" },
    { "name": "html-build",      "file": "agents/html-build.md" }
  ]
}

Variant Lifecycle

Variants go through a defined lifecycle, tracked in variant.json under the lifecycle field.

  1. Draft — The variant is under initial development. Structure and agents are being defined. Not yet ready for use.
  2. Beta — The variant is functional but may have rough edges. Early adopters can try it and provide feedback. This is where co-deck currently stands.
  3. Stable — The variant has been thoroughly tested and is ready for production use. Breaking changes require a major version bump.

Creating a New Project From a Variant

The exercises in Chapters 6 and 7 have you clone a pre-built example project (co-consult, co-deck) to save setup time. In real day-to-day use, you don't clone anything — you scaffold a brand-new L3 project directly from an L2 variant template with a single command, run from the workspace root:

bun scripts/new-project.ts "my-market-report" --variant co-consult

This creates Projects/my-market-report/ as a fresh, independent Git repository, copying co-consult's agents, skills, and configuration into it and rendering the empty docs/context.md skeleton so you can fill in this specific project's goals. The full syntax is:

bun scripts/new-project.ts "<project-name>" --variant <variant> [--platform claude|antigravity|both] [--version X.Y.Z]
  • <project-name> — Required. Becomes the folder name under Projects/.
  • --variant <variant> — Required. Which L2 template to scaffold from (co-consult, co-deck, co-develop, etc.).
  • --platform — Optional. Restrict which platform configs (.claude/, .gemini/) get copied. Defaults to both.
  • --version — Optional. Pin the source variant's template version instead of using its current one.
Don't confuse this with creating a new variant, covered next. new-project.ts is the everyday command you'll run constantly — it scaffolds an L3 project from an L2 template that already exists. Building the L2 template itself (a brand-new variant like co-legal or co-hr) is a separate, much rarer workflow using create-l3-scaffold.ts, described in Chapter 11.
Thinking about creating your own variant? Chapter 11 of this handbook covers the process of designing and building a custom variant from scratch. You will learn how to define your own agents, skills, and workflow pipeline, and how to register your variant so it inherits all the benefits of the shared workspace standard.

Common Contracts

The final piece of the ai-workspace-standards architecture is the concept of common contracts. These are shared agreements that ensure all projects, variants, and agents speak the same language.

What Are Common Contracts?

A common contract is a formal specification that defines how different parts of the workspace interact with each other. Just as a legal contract specifies the obligations between two parties, a common contract specifies the data formats, file locations, naming conventions, and communication protocols that agents and projects must follow.

Common contracts are defined in a file called common-contract.json and serve three key roles.

1. Data Format Contract

  • Defines the structure and fields of key data files (research notes, slide decks, design specs, image manifests)
  • Ensures every agent produces output in a format the next agent can consume
  • Example: research_notes.md must include a Sources section, a Key Facts section, and a Credibility Notes section

2. Directory Layout Contract

  • Defines where each type of file lives within the workspace
  • Ensures agents can find their input files without guessing
  • Example: Research notes must be at presentations/<project>/research_notes.md

3. Naming Convention Contract

  • Defines how files, agents, skills, and variants should be named
  • Ensures consistency across the entire workspace ecosystem
  • Example: Agent files use lowercase-with-hyphens (source-verifier.md), skills use the same pattern

How Contracts Are Applied

Contracts are not just documentation — they are enforced. Here is how the contract system works in practice.

  1. Contract definition — The contract is written in common-contract.json at the L0 level. This file specifies the schemas, layouts, and naming rules that all projects must follow.
  2. Template inheritance — When an L1 common template is created, it copies the contract from L0. L2 variants inherit the contract through L1. Every project in the workspace shares the same contract foundation.
  3. Variant extension — L2 variants may add their own contract extensions for variant-specific files (for example, co-deck adds contracts for slide deck files, theme files, and PDF layout specs). These extensions are defined in the variant's own context file.
  4. Validation enforcement — The scripts/audit.ts script automatically checks every project against the contracts it inherits. If a file violates the contract (wrong format, wrong location, wrong name), the audit reports it as an error that must be fixed before the project can proceed.

Contracts and Handoff Contracts

You may recall from Chapter 4 that handoff contracts define how one agent passes its output to the next. Common contracts are the broader system that handoff contracts operate within. Think of it this way:

  • Common contracts define the overall language everyone speaks (file formats, directory layout, naming conventions)
  • Handoff contracts define the specific conversations between pairs of agents (Agent A produces file X, Agent B reads file X)

Common contracts make handoff contracts possible. If every agent agrees on the common contract (where files live and what format they use), then defining a handoff contract between two agents is straightforward — you only need to specify which file to pass.

Analogy — A Common Language: Imagine an international summit where delegates from many countries meet to collaborate. The common contract is the agreement to use English as the working language, follow parliamentary procedure, and use standardized document formats. With those ground rules in place, any two delegates (agents) can have a focused conversation (handoff contract) about their specific topic. Without the common language, every pair of delegates would need to invent their own communication protocol from scratch — inefficient and error-prone.

Contract Benefits

The contract system provides several concrete benefits for AI agent collaboration.

  • Zero configuration handoff. When Agent A finishes and Agent B starts, Agent B already knows where to find Agent A's output because the directory layout contract specifies the exact path.
  • Automatic error detection. The audit script catches contract violations before they cause runtime failures. If an agent writes a file to the wrong location or in the wrong format, the audit flags it immediately.
  • Cross-project portability. An agent that follows the common contract can work in any variant project without modification. The research agent from co-deck could, in principle, be dropped into co-consult and work correctly because both variants share the same contracts.
  • Version-controlled evolution. When the common contract needs to change (for example, adding a new required field to the slide deck format), the change is made at L0, propagated through the sync pipeline, and enforced by the audit script across all projects.
Key Takeaway: The combination of a 4-level layer structure, the variant concept, and common contracts is what makes ai-workspace-standards a true platform rather than just a collection of files. The layer structure provides organization (L0→L1→L2 distribution path, L1→L2→L3 static hierarchy), variants provide specialization, and contracts provide interoperability. Together, they enable any number of specialized AI projects to share a common foundation while remaining independently customizable.
