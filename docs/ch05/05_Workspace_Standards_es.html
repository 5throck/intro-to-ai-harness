Exploring ai-workspace-standards

Aprende la estructura y los conceptos clave del repositorio ai-workspace-standards: la estructura de 4 niveles (L0→L1→L2→L3), el concepto de variante, los archivos clave (AGENTS.md, CLAUDE.md, GEMINI.md) y los contratos comunes. Este capítulo te da un recorrido guiado por el workspace que sustenta cada proyecto multi-agente.

What is ai-workspace-standards

En el capítulo anterior exploramos los bloques de construcción conceptuales de un harness multi-agente — agents, skills, el PM Gateway y los handoff contracts. Ahora es momento de mirar el actual codebase que pone todas esas ideas en práctica. Ese código base se llama ai-workspace-standards.

Definition

ai-workspace-standards es un repositorio de código abierto en GitHub que define una estructura de workspace estandarizada para proyectos de IA multi-agente. Proporciona un conjunto compartido de convenciones, disposiciones de archivos, definiciones de agents, plantillas de skills y scripts de automatización que cualquier proyecto asistido por IA puede adoptar. Piénsalo como el foundational blueprint que hace posible el trabajo en equipo de los agents.

El repositorio está alojado en github.com/5throck/ai-workspace-standards y se mantiene como un estándar vivo que evoluciona junto con las capacidades de las herramientas de IA.

Why Standards Matter

Quizás te preguntes: ¿por qué necesitamos un workspace "estándar"? ¿No puede cada proyecto simplemente organizar sus archivos como quiera?

La respuesta se reduce a interoperability. Cuando múltiples agents de IA necesitan colaborar en el mismo proyecto, todos deben ponerse de acuerdo sobre dónde viven los archivos, qué formato usan y qué convenciones siguen. Sin un estándar compartido, cada proyecto inventaría su propia estructura, y los agents entrenados para un proyecto no podrían trabajar en otro. Los estándares hacen posible:

  • Reuse agents across projects — Un agent de investigación escrito para un proyecto puede trabajar en cualquier proyecto que siga las mismas convenciones de disposición.
  • Share skills as plugins — Las skills se empaquetan como conjuntos de instrucciones portátiles que cualquier workspace puede cargar, igual que las extensiones de navegador.
  • Automate quality checks — Los scripts de audit pueden validar cualquier workspace que siga la estructura estándar, detectando errores antes de que se propaguen.
  • Onboard new team members quickly — Ya sea humano o IA, cualquiera que se incorpore al proyecto sabe de inmediato dónde encontrar lo que necesita.

The Org Chart Analogy

Piensa en ai-workspace-standards como un "org chart and employee manual template" para una empresa. Cuando inicias un nuevo negocio, no inventas el concepto de "departamentos" desde cero — adoptas una estructura estándar (RR. HH., Finanzas, Ingeniería, Marketing) y la personalizas según tus necesidades. De la misma manera, ai-workspace-standards proporciona una plantilla organizacional probada para proyectos de IA:

Company Org Chart

  • Departments → agents/, skills/, scripts/
  • Employee handbooks → CLAUDE.md, GEMINI.md
  • Company policies → AGENTS.md
  • Project files → presentations/, docs/
  • Meeting minutes → memory/

ai-workspace-standards

  • Directories give each function its own workspace
  • Agent files define each AI's role and permissions
  • Governance files enforce consistency across the project
  • Resultado directories store the project's deliverables
  • Session logs record every decision and change
co-consult y co-deck están construidos sobre este estándar. Cada proyecto variante — ya sea que produzca presentaciones (co-deck), análisis de consultoría (co-consult) o cualquier otra cosa — hereda su estructura base de ai-workspace-standards. La variante añade sus propios agents, skills y scripts especializados sobre la base común, igual que una franquicia de restaurantes añade sus propios platos al menú sobre una cocina estándar.

Directory Structure

Hagamos un recorrido por los directorios de nivel superior en un workspace típico de ai-workspace-standards. Cada directorio tiene un propósito claro, y entender esta disposición es el primer paso para navegar cualquier proyecto construido sobre el estándar.

Directory Overview

Aquí tienes una breve descripción de cada directorio y lo que contiene.

  • agents/ — Contiene un archivo markdown por agent (por ejemplo, research.md, design.md, pm.md). Cada archivo define el rol, tier, fases, triggers, permisos de herramientas e instrucciones detalladas del agent. Aquí es donde viven los "perfiles de empleado".
  • skills/ — Contiene subdirectorios, cada uno con un archivo SKILL.md que define una receta de flujo de trabajo reutilizable. Las skills pueden ser cargadas por cualquier agent que las necesite. Piensa en esto como la colección de libros de recetas de la empresa.
  • scripts/ — Scripts de automatización escritos en TypeScript (ejecutados vía bun). Incluye herramientas de audit, pipelines de sincronización, comprobaciones de validación y otras utilidades que mantienen el workspace saludable.
  • docs/ — Documentación de gobernanza y especificaciones de diseño. Incluye Architecture Decision Records (ADRs), guías de usuario, especificaciones de diseño, VERSION_MANIFEST.md y procedimientos de ciclo de vida. Note: context.md existe solo en proyectos L2/L3, no en la raíz del workspace (L0), donde AGENTS.md es el SSOT.
  • templates/ — La plantilla común que sirve como capa base L1 (ver la sección de jerarquía más abajo). Contiene definiciones compartidas de agents, plantillas de skills y configuración que todos los proyectos variant heredan.
  • Proyectos/ — Workspaces de proyectos individuales creados a partir de plantillas variant L2. Cada proyecto es un directorio independiente (por ejemplo, Proyectos/climate-change/) con su propio contexto, agents, skills y archivos de salida. En proyectos variant como co-deck, las presentaciones individuales viven como subdirectorios dentro del proyecto.
  • memory/ — Logs de sesión, transcripciones de reuniones y notas de desarrollo diarias. Cada sesión de IA escribe un resumen aquí, creando un rastro de auditoría de decisiones y cambios.
Tip: Los directorios agents/ y skills/ son el corazón del workspace. Cuando quieras entender cómo funciona un proyecto, empieza leyendo los archivos de agent en agents/ — te dicen exactamente qué hace cada IA, cuándo se activa y qué produce.

Key Files

Entre los muchos archivos de un workspace de ai-workspace-standards, algunos destacan como especialmente importantes. Estos son los archivos de gobernanza que cada agent de IA y cada colaborador humano debe respetar.

The Big Three

Tres archivos forman la columna vertebral de la gobernanza del workspace: AGENTS.md, CLAUDE.md y GEMINI.md. Cada uno sirve a una audiencia distinta, pero juntos crean un conjunto unificado de reglas.

AGENTS.md

  • Audience: All AI platforms (Claude, Gemini, and others)
  • Role: El registro maestro — lista cada agent, su tier, fases, triggers de despacho y las reglas del PM Gateway
  • Analogía: El organigrama de la empresa publicado en el vestíbulo — todos pueden ver quién hace qué
  • Key content: Agent roster, PM Gateway policy, execution plan templates, 3-Tier strategy, lifecycle management rules
  • Loaded by: Claude Code carga automáticamente este archivo al inicio de cada sesión

CLAUDE.md

  • Audience: Claude Code (Anthropic's AI coding agent)
  • Role: Instrucciones de comportamiento específicas de Claude — cómo debe comportarse Claude en este workspace
  • Analogía: El manual del empleado de Claude — Claude lo lee su primer día y lo sigue en adelante
  • Key content: Platform-specific dispatch rules, model tier mappings, Claude-specific tool permissions, workflow triggers
  • Loaded by: Claude Code automatically at session start

GEMINI.md

  • Audience: Antigravity CLI (Google's AI coding agent)
  • Role: Instrucciones de comportamiento específicas de Antigravity — cómo debe comportarse Antigravity CLI en este workspace
  • Analogía: El manual del empleado de Antigravity CLI — Antigravity CLI lo lee su primer día y lo sigue en adelante
  • Key content: Platform-specific dispatch rules, model tier mappings, Antigravity-specific tool permissions, workflow triggers
  • Loaded by: Antigravity CLI automatically at session start

How the Three Files Work Together

La idea clave es que AGENTS.md contiene las reglas compartidas que se aplican a todas las plataformas, mientras que CLAUDE.md y GEMINI.md añaden detalles específicos de plataforma encima. Esta separación significa que la gobernanza central vive en un solo lugar, y las diferencias de plataforma se aíslan en sus respectivos archivos.

Other Important Files

Más allá de los tres grandes, varios otros archivos desempeñan roles críticos en el workspace.

  • context.md (solo L2/L3) — La tarjeta de identidad del proyecto, que se encuentra solo en plantillas variant y proyectos generados a partir de ellas. Declara el tipo de proyecto, estado, arquitectura, archivos clave y estándares de documentación. Se marca como inmutable después de la creación del proyecto — todos los cambios específicos del proyecto van en un archivo de contexto variante separado. Piénsalo como el acta constitutiva de la empresa. En la raíz del workspace (L0), AGENTS.md sirve como SSOT en su lugar.
  • CHANGELOG.md — Un registro legible por humanos de todos los cambios realizados en el proyecto, organizado por número de versión. Cada modificación a agents, skills, scripts o archivos de gobernanza se registra aquí para que los miembros del equipo puedan rastrear qué cambió y por qué.
  • variant.json — El archivo de metadatos de la variante. Declara el nombre, tipo, estado y versión de la variante, qué agents y skills incluye, y cómo hereda de la plantilla común. Exploraremos esto en detalle en la sección de Variants.
  • memory/YYYY-MM-DD.md — Logs de sesión con fecha. Cada sesión de trabajo produce un archivo de log fechado (por ejemplo, memory/2026-08-10.md) con un resumen de lo que se logró, qué cambió, qué decisiones se tomaron y qué problemas quedan abiertos.
File Analogy Summary: Si el workspace fuera una ciudad, AGENTS.md sería el acta constitutiva (el documento fundacional que todos siguen), CLAUDE.md y GEMINI.md serían los reglamentos específicos de cada departamento, context.md sería el certificado de registro de la ciudad, CHANGELOG.md sería el registro público de las decisiones del concejo, y memory/ sería el archivo de la ciudad donde se guardan las actas de cada reunión.

4-Level Layer Structure

Una de las decisiones de diseño más poderosas de ai-workspace-standards es el 4-level layer structure. Es un sistema jerárquico donde los recursos fluyen desde la fuente original (L0) a través de la infraestructura común (L1), las plantillas variant (L2) y hacia los proyectos reales (L3).

Distribution Path vs Layer Structure
"L0 → L1 → L2" describe la distribution path: la dirección en la que el código fuente original se entrega a L1 y L2.
"L1 → L2 → L3" describe la layer structure: una jerarquía estática donde cada capa sirve de fundamento para la capa inferior.

L0 Source (Workspace Root) — Original Source

L0 Source es el directorio raíz del workspace en sí. Es el único lugar donde se hacen ediciones, y el punto de partida desde el cual los cambios se propagan a todas las demás capas.

  • Common agents — El agent PM y otros agents fundamentales que usa cada proyecto
  • Common skills — Reusable workflow recipes available everywhere
  • Core scripts — audit.ts, validate-templates.ts, and other essential automation tools
  • AGENTS.md — The global agent registry

L1 (Common Template) — Common Infrastructure Layer

L1 es la capa de infraestructura común ubicada en templates/common/. Construida a partir del contenido distribuido por L0 Source, proporciona plantillas compartidas por todas las variantes, incluyendo configuraciones específicas de plataforma y estructuras de directorio estandarizadas.

  • .claude/ directory — Claude Code settings, commands, and skills
  • .gemini/ directory — Antigravity CLI settings, commands, and skills
  • Platform-specific agent configurations (CLAUDE.md, GEMINI.md)
  • Common agent templates, common skills, and scripts
  • propagation-map.json — Defines L0→L1 distribution rules

Nota: L1 nunca se edita directamente. Los cambios se distribuyen automáticamente desde L0 Source vía bun run propagate:apply.

L2 (Variant Template) — Variant Template Layer

L2 es la capa de plantillas variant ubicada en templates/co-*/. Cada variante (co-deck, co-consult, etc.) es una plantilla construida sobre L1 que añade sus propios agents, skills y configuración.

  • Variant-specific agents (for example, co-deck's image-curator, pdf-export)
  • Variant-specific skills (for example, co-deck's html-build, storyline)
  • Variant configuration (variant.json, PM agent YAML overrides)
  • Inherits the L1 common template (variant.json's inherits_common: "templates/common")

Actualmente hay 10 plantillas variant: co-abap, co-consult, co-deck, co-design, co-develop, co-export, co-game, co-news, co-security y co-work.

L3 (Project) — Actual Project Layer

L3 es la capa de proyectos reales ubicada en Proyectos/*/. Cada proyecto L3 es scaffolded a partir de una plantilla variante L2. Los proyectos operan de forma independiente y soportan personalización local.

  • docs/context.md — The project's deep configuration (immutable after project creation)
  • Project-specific agents, skills, and scripts
  • variant.json — Metadata copied from L2
  • El espacio donde se produce el resultado del trabajo real

Distribution Path and Layer Structure

Es importante distinguir dos direcciones en este sistema.

  • Distribution path (L0 → L1 → L2): Los cambios de la fuente original (L0) se entregan vía propagate:apply a la plantilla común L1 y luego a cada plantilla variante L2. Esta es la dirección code flows.
  • Layer structure (L1 → L2 → L3): Una relación jerárquica estática donde cada capa se construye sobre la plantilla de la capa superior. Los proyectos L3 se generan a partir de plantillas variant L2, y L2 hereda la plantilla común L1.

Override Rules

Una capa inferior puede override configuraciones de una capa superior, pero los cambios nunca se propagan en dirección inversa. Esto sigue el mismo principio que la herencia de clases en programación orientada a objetos.

  • Las reglas establecidas en L3 tienen prioridad sobre las reglas de L2, L1 y L0.
  • Las reglas establecidas en L2 tienen prioridad sobre las reglas de L1 y L0 (a menos que L3 las anule).
  • Las reglas establecidas en L1 tienen prioridad sobre las reglas de L0 (a menos que L2 o L3 las anulen).
  • Las reglas de L0 se aplican a todas las capas cuando ninguna otra capa las ha anulado.
Todo lo que está en L0 Source es común a todos los proyectos. Esto significa que scripts centrales como audit.ts y validate-templates.ts funcionan idénticamente en cada proyecto. Cuando corriges algo en L0, el cambio se propaga por la ruta de distribución a L1 y L2, y finalmente llega a cada proyecto L3. Esta es la promesa central del estándar — define once, apply consistently everywhere.

Variant Concept

What is a Variant?

Una variant es una plantilla personalizada para un propósito específico, construida sobre la base L0 + L1. Como se explicó en la sección de estructura de 4 niveles, L2 es la capa de plantillas variant, y L3 es el proyecto real generado a partir de una plantilla L2.

Las variantes son lo que hace práctico a ai-workspace-standards. El estándar proporciona la base; las variantes proporcionan la especialización. Sin variantes, el estándar sería un marco genérico sin aplicación real. Sin el estándar, las variantes serían proyectos aislados con estructuras incompatibles.

Variant Examples

Veamos dos variantes reales para entender cómo funciona esto en la práctica.

co-deck

  • Type: Lecture and presentation material production
  • Pipeline: 11-stage workflow from research to print-ready PDF
  • Agents: 11 specialized agents (PM + 10 specialists: research, source-verifier, storyline, design, image-curator, diagram-specialist, html-build, measure, pdf-export, version)
  • Resultado: HTML slide decks and PDF presentations
  • Unique features: Theme system (5 HTML themes), style system, image curation pipeline, SVG diagram generation, PDF layout measurement

co-consult

  • Type: Consulting analysis and advisory output
  • Pipeline: Research-driven analysis workflow for business consulting
  • Agents: Specialized consulting agents adapted from the common set
  • Resultado: Consulting reports, analysis documents, advisory materials
  • Unique features: Industry-specific research profiles, MECE logic frameworks, structured problem-solving workflows

A pesar de sus diferentes propósitos, ambas variantes comparten la misma base: el patrón de orquestación del PM, la 3-Tier strategy, el PM Gateway, el sistema de handoff contracts y la disposición de directorios. Esta base compartida es lo que las hace interoperables y mantenibles.

variant.json — The Variant Identity Card

Cada variante tiene un archivo variant.json en la raíz de su proyecto que declara su identidad y configuración. Este archivo es el "pasaporte" de la variante — le dice al sistema qué es esta variante, qué incluye y cómo se relaciona con la plantilla común.

Aquí están los campos clave en variant.json.

  • name — El identificador de la variante (por ejemplo, "co-deck" o "co-consult").
  • description — Un resumen legible por humanos de lo que hace la variante.
  • variant_type — La categoría de trabajo que maneja esta variante (por ejemplo, "lecture" para producción de presentaciones).
  • status — El estado del ciclo de vida: "draft", "beta" o "stable".
  • version — The current version number following semantic versioning (major.minor.patch).
  • inherits_common — La ruta a la plantilla común de la cual hereda esta variante (típicamente "templates/common").
  • agents — Una lista de los agents que incluye esta variante, con sus rutas de archivo.
  • skills — Una lista de las skills disponibles en esta variante.
  • lifecycle — Metadatos sobre las transiciones del ciclo de vida de la variante (cuándo fue creada, cuándo fue promovida a beta, etc.).
{
  "name": "co-deck",
  "description": "Lecture and presentation material production variant",
  "variant_type": "lecture",
  "status": "beta",
  "version": "0.2.0",
  "inherits_common": "templates/common",
  "agents": [
    { "name": "pm",              "file": "agents/pm.md" },
    { "name": "research",         "file": "agents/research.md" },
    { "name": "storyline",       "file": "agents/storyline.md" },
    { "name": "html-build",      "file": "agents/html-build.md" }
  ]
}

Variant Lifecycle

Las variantes atraviesan un ciclo de vida definido, rastreado en variant.json bajo el campo lifecycle.

  1. Draft — La variante está en desarrollo inicial. La estructura y los agents están siendo definidos. Aún no está lista para usar.
  2. Beta — La variante es funcional pero puede tener asperezas. Los primeros adoptantes pueden probarla y dar retroalimentación. Aquí es donde se encuentra co-deck actualmente.
  3. Stable — La variante ha sido probada exhaustivamente y está lista para uso en producción. Los cambios disruptivos requieren un incremento de versión mayor.

Creating a New Project From a Variant

Los ejercicios de los capítulos 6 y 7 te hacen clonar un proyecto de ejemplo preconstruido (co-consult, co-deck) para ahorrar tiempo de configuración. En el uso real del día a día, no clonas nada — scaffold un proyecto L3 completamente nuevo directamente desde una plantilla variante L2 con un solo comando, ejecutado desde la raíz del workspace:

bun scripts/new-project.ts "my-market-report" --variant co-consult

Esto crea Proyectos/my-market-report/ como un repositorio Git nuevo e independiente, copiando los agents, skills y configuración de co-consult en él y renderizando el esqueleto vacío docs/context.md para que puedas completar los objetivos de este proyecto específico. La sintaxis completa es:

bun scripts/new-project.ts "<project-name>" --variant <variant> [--platform claude|antigravity|both] [--version X.Y.Z]
  • <nombre-del-proyecto> — Requerido. Se convierte en el nombre de la carpeta dentro de Proyectos/.
  • --variant <variant> — Requerido. Desde qué plantilla L2 generar el proyecto (co-consult, co-deck, co-develop, etc.).
  • --platform — Opcional. Restringe qué configuraciones de plataforma (.claude/, .gemini/) se copian. El valor predeterminado es both.
  • --version — Opcional. Fija la versión de plantilla de la variante fuente en lugar de usar la actual.
No confundas esto con creating a new variant, que se cubre a continuación. new-project.ts es el comando cotidiano que ejecutarás constantemente — genera un proyecto L3 a partir de una plantilla L2 que ya existe. Construir la propia plantilla L2 (una variante completamente nueva como co-legal o co-hr) es un flujo de trabajo separado y mucho más raro que usa create-l3-scaffold.ts, descrito en el Capítulo 11.
¿Piensas crear tu propia variante? El Capítulo 11 de este manual cubre el proceso de diseñar y construir una variante personalizada desde cero. Aprenderás cómo definir tus propios agents, skills y pipeline de flujo de trabajo, y cómo registrar tu variante para que herede todos los beneficios del estándar de workspace compartido.

Common Contracts

La última pieza de la arquitectura de ai-workspace-standards es el concepto de common contracts. Son acuerdos compartidos que garantizan que todos los proyectos, variantes y agents hablen el mismo idioma.

What Are Common Contracts?

Un common contract es una especificación formal que define cómo interactúan entre sí las diferentes partes del workspace. Así como un contrato legal especifica las obligaciones entre dos partes, un contrato común especifica los formatos de datos, ubicaciones de archivos, convenciones de nomenclatura y protocolos de comunicación que los agents y proyectos deben seguir.

Los contratos comunes se definen en los documentos de gobernanza central del workspace — CONSTITUTION.md, AGENTS.md (SSOT de L0) y docs/context.md específico de cada variante (L2/L3) — y cumplen tres roles clave.

1. Data Format Contract

  • Define la estructura y los campos de los archivos de datos clave (notas de investigación, presentaciones, especificaciones de diseño, manifiestos de imágenes)
  • Garantiza que cada agent produzca salida en un formato que el siguiente agent pueda consumir
  • Example: research_notes.md must include a Sources section, a Key Facts section, and a Credibility Notes section

2. Directory Layout Contract

  • Define dónde vive cada tipo de archivo dentro del workspace
  • Ensures agents can find their input files without guessing
  • Example: Research notes must be at Proyectos/<project>/research_notes.md

3. Naming Convention Contract

  • Define cómo deben nombrarse los archivos, agents, skills y variantes
  • Ensures consistency across the entire workspace ecosystem
  • Ejemplo: Los archivos de agent usan minúsculas-con-guiones (source-verifier.md), las skills usan el mismo patrón

How Contracts Are Applied

Los contratos no son solo documentación — se aplican. Así es como funciona el sistema de contratos en la práctica.

  1. Contract definition — Los contratos se definen en los documentos de gobernanza central del workspace: CONSTITUTION.md (estándares compartidos), AGENTS.md (registro de agents, SSOT en L0) y docs/context.md (configuración específica del proyecto, solo L2/L3). Estos documentos especifican los esquemas, disposiciones y reglas de nomenclatura que todos los proyectos deben seguir.
  2. Template inheritance — Cuando se crea una plantilla común L1, copia el contrato de L0. Las variantes L2 heredan el contrato a través de L1. Cada proyecto del workspace comparte la misma base contractual.
  3. Variant extension — Las variantes L2 pueden añadir sus propias extensiones de contrato para archivos específicos de la variante (por ejemplo, co-deck añade contratos para archivos de presentaciones, archivos de temas y especificaciones de diseño PDF). Estas extensiones se definen en el propio archivo de contexto de la variante.
  4. Validation enforcement — El script scripts/audit.ts comprueba automáticamente cada proyecto contra los contratos que hereda. Si un archivo viola el contrato (formato incorrecto, ubicación incorrecta, nombre incorrecto), la audit lo reporta como un error que debe corregirse antes de que el proyecto pueda continuar.

Contracts and Handoff Contracts

Quizás recuerdes del Capítulo 4 que handoff contracts definen cómo un agent pasa su resultado al siguiente. Los contratos comunes son el broader system dentro del cual operan los handoff contracts. Piénsalo así:

  • Common contracts define the overall language everyone speaks (file formats, directory layout, naming conventions)
  • Handoff contracts define the specific conversations between pairs of agents (Agent A produces file X, Agent B reads file X)

Los contratos comunes hacen posibles los handoff contracts. Si cada agent acuerda el contrato común (dónde viven los archivos y qué formato usan), entonces definir un handoff contract entre dos agents es sencillo — solo necesitas especificar qué archivo pasar.

Analogy — A Common Language: Imagina una cumbre internacional donde delegados de muchos países se reúnen para colaborar. El common contract es el acuerdo de usar el inglés como idioma de trabajo, seguir el procedimiento parlamentario y usar formatos de documentos estandarizados. Con esas reglas básicas establecidas, dos delegados cualesquiera (agents) pueden mantener una conversación enfocada (handoff contract) sobre su tema específico. Sin el idioma común, cada par de delegados tendría que inventar su propio protocolo de comunicación desde cero — ineficiente y propenso a errores.

Contract Benefits

The contract system provides several concrete benefits for AI agent collaboration.

  • Zero configuration handoff. Cuando el Agent A termina y el Agent B comienza, el Agent B ya sabe dónde encontrar el resultado del Agent A porque el contrato de disposición de directorios especifica la ruta exacta.
  • Automatic error detection. El script de audit detecta las violaciones de contrato antes de que causen fallos en tiempo de ejecución. Si un agent escribe un archivo en la ubicación incorrecta o en el formato incorrecto, la audit lo marca de inmediato.
  • Cross-project portability. Un agent que sigue el contrato común puede trabajar en cualquier proyecto variante sin modificación. El agent de investigación de co-deck podría, en principio, trasladarse a co-consult y funcionar correctamente porque ambas variantes comparten los mismos contratos.
  • Version-controlled evolution. Cuando el contrato común necesita cambiar (por ejemplo, añadir un nuevo campo requerido al formato de la presentación), el cambio se hace en L0, se propaga a través del pipeline de sincronización y lo aplica el script de audit en todos los proyectos.
Key Takeaway: La combinación de la estructura de 4 niveles, el concepto de variante y los contratos comunes es lo que convierte a ai-workspace-standards en un verdadero platform y no solo una colección de archivos. La estructura de capas proporciona organización (ruta de distribución L0→L1→L2, jerarquía estática L1→L2→L3), las variantes proporcionan especialización, y los contratos proporcionan interoperabilidad. Juntos, permiten que cualquier número de proyectos de IA especializados comparta una base común manteniendo la personalización independiente.
