ai-workspace-standardsを探索する

ai-workspace-standardsリポジトリの構造とコア概念を学びます：4層レイヤー構造（L0→L1→L2→L3）、バリアント概念、主要ファイル（AGENTS.md、CLAUDE.md、GEMINI.md）、コモンコントラクト。本章では、すべてのマルチエージェントプロジェクトの基盤となるワークスペースをガイド付きで巡ります。

本章の内容
  • ai-workspace-standardsリポジトリ構造
  • 主要ファイル：AGENTS.md、CLAUDE.md、GEMINI.md
  • 4層レイヤー構造（L0 → L1 → L2 → L3）
  • バリアント概念
  • コモンコントラクトとテンプレート継承

ai-workspace-standardsとは

前章では、マルチエージェントハーネスの概念的構成要素——エージェント、スキル、PM Gateway、引き継ぎコントラクト——について学びました。次は、それらすべてのアイデアを実践に移す実際のコードベースを見ていきます。そのコードベースがai-workspace-standardsです。

定義

ai-workspace-standardsは、マルチエージェントAIプロジェクトのための標準化されたワークスペース構造を定義するオープンソースのGitHubリポジトリです。共有の一連の規約、ファイルレイアウト、エージェント定義、スキルテンプレート、自動化スクリプトを提供し、あらゆるAI支援プロジェクトが採用できます。エージェントのチームワークを可能にする基盤ブループリントと考えてください。

このリポジトリは github.com/5throck/ai-workspace-standards でホストされており、AIツールの能力と共に進化する「生きた標準」として維持されています。

なぜ標準が重要なのか

「なぜ標準ワークスペースが必要なのか？各プロジェクトが自由にファイルを整理すればいいのでは？」と思うかもしれません。

答えは相互運用性にあります。複数のAIエージェントが同じプロジェクトで協力する必要がある場合、すべてのエージェントがファイルの場所、フォーマット、規約について合意している必要があります。共有の標準がないと、各プロジェクトが独自の構造を発明し、あるプロジェクト用に訓練されたエージェントは別のプロジェクトでは動作できなくなります。標準があれば：

  • プロジェクト間でエージェントを再利用 — あるプロジェクト用に作成されたリサーチエージェントは、同じレイアウト規約に従うあらゆるプロジェクトで動作可能。
  • スキルをプラグインとして共有 — スキルはポータブルな手順書としてパッケージ化され、ブラウザの拡張機能のように任意のワークスペースが読み込める。
  • 品質チェックを自動化 — 監査スクリプトが標準構造に従うワークスペースを検証し、エラーが拡散する前に検出する。
  • 新しいチームメンバーのオンボーディングを迅速に — 人間であれAIであれ、プロジェクトに参加した直後に必要な情報のありかが分かる。

組織図の例え

ai-workspace-standardsを企業の「組織図と従業員マニュアルテンプレート」と考えてください。新しい事業を始めるとき、「部門」という概念をゼロから発明するのではなく——標準構造（人事、財務、エンジニアリング、マーケティング）を採用し、それを自分のニーズに合わせてカスタマイズします。同じように、ai-workspace-standardsはAIプロジェクトのための実績のある組織テンプレートを提供します：

企業の組織図

  • 部門 → agents/、skills/、scripts/
  • 従業員ハンドブック → CLAUDE.md、GEMINI.md
  • 会社の規程 → AGENTS.md
  • プロジェクトファイル → presentations/、docs/
  • 会議議事録 → memory/

ai-workspace-standards

  • ディレクトリが各機能に専用のワークスペースを提供
  • エージェントファイルが各AIの役割と権限を定義
  • ガバナンスファイルがプロジェクト全体の整合性を確保
  • 出力ディレクトリがプロジェクトの成果物を保管
  • セッションログがすべての決定と変更を記録
co-consultとco-deckはこの標準の上に構築されています。すべてのバリアントプロジェクト——スライドデッキ（co-deck）を作るにせよ、コンサルティング分析（co-consult）を作るにせよ、まったく別のものを作るにせよ——は、ai-workspace-standardsから基本構造を継承します。バリアントは共通基盤の上に独自の専門エージェント、スキル、スクリプトを追加します。これは、フランチャイズレストランが標準の厨房レイアウトに独自のメニューを追加するのと同じです。

ディレクトリ構造

ai-workspace-standardsワークスペースのトップレベルディレクトリを見ていきましょう。各ディレクトリには明確な目的があり、このレイアウトを理解することが、この標準に基づくプロジェクトをナビゲートする第一歩です。

ディレクトリ概要

各ディレクトリとその内容の簡単な説明です。

  • agents/ — 各エージェントごとに1つのMarkdownファイル（例：`research.md`、`design.md`、`pm.md`）を含みます。各ファイルはエージェントの役割、ティア、フェーズ、トリガー、ツール権限、詳細な指示を定義します。ここが「従業員プロファイル」の置き場所です。
  • skills/ — サブディレクトリを含み、各々に`SKILL.md`ファイルがあって再利用可能なワークフローレシピを定義します。スキルは必要とする任意のエージェントが読み込めます。会社のレシピ集と考えてください。
  • scripts/ — TypeScriptで書かれた自動化スクリプト（`bun`で実行）。監査ツール、同期パイプライン、検証チェック、その他のユーティリティが含まれます。
  • docs/ — ガバナンスドキュメントと設計仕様。Architecture Decision Records（ADR）、ユーザーガイド、設計仕様、VERSION_MANIFEST.md、ライフサイクル手順が含まれます。注： `context.md`はL2/L3プロジェクトにのみ存在し、ワークスペースルート（L0）にはありません。L0では`AGENTS.md`がSSOTです。
  • templates/ — L1ベースレイヤーとして機能する共通テンプレート（後述の階層セクション参照）。すべてのバリアントプロジェクトが継承する共有エージェント定義、スキルテンプレート、設定を含みます。
  • Projects/ — L2バリアントテンプレートからスキャフォールドされた個別プロジェクトワークスペース。各プロジェクトは独立したディレクトリ（例：`Projects/climate-change/`）で、独自のコンテキスト、エージェント、スキル、出力ファイルを持ちます。co-deckのようなバリアントプロジェクトでは、個別のプレゼンテーションがプロジェクト内のサブディレクトリとして配置されます。
  • memory/ — セッションログ、会議トランスクリプト、日次開発メモ。すべてのAIセッションがここに要約を書き込み、決定と変更の監査証跡を作成します。
ヒント： agents/とskills/ディレクトリがワークスペースの心臓部です。プロジェクトの仕組みを理解したいときは、まずagents/のエージェントファイルを読んでください。各AIが何をするのか、いつ起動するのか、何を生産するのかが正確に分かります。

主要ファイル

ai-workspace-standardsワークスペースの多くのファイルの中で、いくつかは特に重要です。これらはすべてのAIエージェントとすべての人間の協力者が尊重しなければならないガバナンスファイルです。

三つの重要ファイル

AGENTS.md、CLAUDE.md、GEMINI.mdの3つのファイルがワークスペースガバナンスの背骨を形成します。それぞれが異なる対象者に対応しますが、一緒になって統一されたルールセットを作ります。

AGENTS.md

  • 対象： すべてのAIプラットフォーム（Claude、Gemini、その他）
  • 役割： マスターレジストリ——すべてのエージェント、ティア、フェーズ、ディスパッチトリガー、PM Gatewayルールを一覧表示
  • 例え： ロビーに掲示された会社の組織図——誰が何をするか全員が分かる
  • 主な内容： エージェントロスター、PM Gatewayポリシー、実行プランテンプレート、3-Tier戦略、ライフサイクル管理ルール
  • 読込： Claude Codeが各セッション開始時に自動的に読み込み

CLAUDE.md

  • 対象： Claude Code（AnthropicのAIコーディングエージェント）
  • 役割： Claude専用の動作指示——このワークスペースでClaudeがどう振る舞うべきか
  • 例え： Claudeの従業員ハンドブック——Claudeは初日の朝にこれを読み、最後まで従う
  • 主な内容： プラットフォーム固有のディスパッチルール、モデルティアマッピング、Claude固有のツール権限、ワークフロートリガー
  • 読込： Claude Codeがセッション開始時に自動的に読み込み

GEMINI.md

  • 対象： Antigravity CLI（GoogleのAIコーディングエージェント）
  • 役割： Antigravity専用の動作指示——このワークスペースでAntigravity CLIがどう振る舞うべきか
  • 例え： Antigravity CLIの従業員ハンドブック——Antigravity CLIは初日の朝にこれを読み、最後まで従う
  • 主な内容： プラットフォーム固有のディスパッチルール、モデルティアマッピング、Antigravity固有のツール権限、ワークフロートリガー
  • 読込： Antigravity CLIがセッション開始時に自動的に読み込み

3つのファイルの連携

重要なポイントは、AGENTS.mdがすべてのプラットフォームに適用される共有ルールを含み、CLAUDE.mdとGEMINI.mdがその上にプラットフォーム固有の詳細を追加するということです。この分離により、コアガバナンスが一箇所にあり、プラットフォームの違いがそれぞれのファイルに分離されます。

その他の重要ファイル

三つの重要ファイルのほかにも、いくつかのファイルがワークスペースで重要な役割を果たします。

  • context.md（L2/L3のみ）— プロジェクトの身分証明書。バリアントテンプレートとスキャフォールドされたプロジェクトにのみ存在します。プロジェクトタイプ、ステータス、アーキテクチャ、主要ファイル、ドキュメント標準を宣言します。プロジェクト作成後に不変としてマークされ、プロジェクト固有の変更は別のバリアントコンテキストファイルに記録されます。会社の登記証明書と考えてください。ワークスペースルート（L0）では、AGENTS.mdが代わりにSSOTとして機能します。
  • CHANGELOG.md — プロジェクトに対するすべての変更の人間が読める記録。バージョン番号ごとに整理されます。エージェント、スキル、スクリプト、ガバナンスファイルへのすべての変更がここに記録され、チームメンバーが何が変わり、なぜ変わったかを追跡できます。
  • variant.json — バリアントのメタデータファイル。バリアント名、タイプ、ステータス、バージョン、含まれるエージェントとスキル、共通テンプレートからの継承方法を宣言します。バリアントセクションで詳しく説明します。
  • memory/YYYY-MM-DD.md — 日付付きセッションログ。各作業セッションが日付付きログファイル（例：`memory/2026-08-10.md`）を生成し、何が達成され、何が変わり、何が決定され、何が未解決かの要約を記録します。
ファイルの例えまとめ： ワークスペースを都市とするなら、AGENTS.mdは都市憲章（全員が従う基本文書）、CLAUDE.mdとGEMINI.mdは部門別ルールブック、context.mdは都市の登記証明書、CHANGELOG.mdは市議会の決定公開記録、memory/はすべての会議の議事録が保管される都市アーカイブとなります。

4層レイヤー構造

ai-workspace-standardsの最も強力な設計判断の一つが4層レイヤー構造です。これはオリジナルのソース（L0）から共通インフラ（L1）、バリアントテンプレート（L2）、そして実際のプロジェクト（L3）へとリソースが流れる階層システムです。

配布パス vs レイヤー構造
「L0 → L1 → L2」は配布パスを記述します：オリジナルソースコードがL1とL2に配信される方向。
「L1 → L2 → L3」はレイヤー構造を記述します：各レイヤーが下のレイヤーの基盤となる静的階層。

L0 Source（ワークスペースルート）— オリジナルソース

L0 Sourceはワークスペースルートディレクトリそのものです。唯一の編集場所であり、すべてのレイヤーに変更が伝播する出発点です。

  • 共通エージェント — すべてのプロジェクトで使用されるPMエージェントとその他の基盤エージェント
  • 共通スキル — どこでも利用可能な再利用可能ワークフローレシピ
  • コアスクリプト — audit.ts、validate-templates.ts、その他の重要な自動化ツール
  • AGENTS.md — グローバルエージェントレジストリ

L1（共通テンプレート）— 共通インフラレイヤー

L1はtemplates/common/にある共通インフラレイヤーです。L0 Sourceから配布されたコンテンツから構築され、すべてのバリアントで共有されるテンプレートを提供します。プラットフォーム固有の設定と標準化されたディレクトリ構造が含まれます。

  • .claude/ディレクトリ — Claude Code設定、コマンド、スキル
  • .gemini/ディレクトリ — Antigravity CLI設定、コマンド、スキル
  • プラットフォーム固有のエージェント設定（CLAUDE.md、GEMINI.md）
  • 共通エージェントテンプレート、共通スキル、スクリプト
  • propagation-map.json — L0→L1配布ルールを定義

注：L1は直接編集しません。変更はbun run propagate:applyでL0 Sourceから自動的に配布されます。

L2（バリアントテンプレート）— バリアントテンプレートレイヤー

L2はtemplates/co-*/にあるバリアントテンプレートレイヤーです。各バリアント（co-deck、co-consultなど）はL1上に構築されたテンプレートで、独自のエージェント、スキル、設定を追加します。

  • バリアント固有のエージェント（例：co-deckのimage-curator、pdf-export）
  • バリアント固有のスキル（例：co-deckのhtml-build、storyline）
  • バリアント設定（variant.json、PMエージェントYAMLオーバーライド）
  • L1共通テンプレートを継承（`variant.json`の`inherits_common: "templates/common"`）

現在10個のバリアントテンプレートがあります：co-abap、co-consult、co-deck、co-design、co-develop、co-export、co-game、co-news、co-security、co-work。

L3（プロジェクト）— 実際のプロジェクトレイヤー

L3はProjects/*/にある実際のプロジェクトレイヤーです。各L3プロジェクトはL2バリアントテンプレートからスキャフォールドされます。プロジェクトは独立して動作し、ローカルカスタマイズをサポートします。

  • docs/context.md — プロジェクトの詳細設定（プロジェクト作成後に不変）
  • プロジェクト固有のエージェント、スキル、スクリプト
  • variant.json — L2からコピーされたメタデータ
  • 実際の作業成果物が生成される場所

配布パスとレイヤー構造

このシステムの2つの方向を区別することが重要です。

  • 配布パス（L0 → L1 → L2）: オリジナルソース（L0）からの変更がpropagate:apply経由でL1共通テンプレートに配布され、次に各L2バリアントテンプレートに配布されます。これがコードが流れる方向です。
  • レイヤー構造（L1 → L2 → L3）: 各レイヤーが上位レイヤーのテンプレートの上に構築される静的階層関係。L3プロジェクトはL2バリアントテンプレートからスキャフォールドされ、L2はL1共通テンプレートを継承します。

オーバーライドルール

下位レイヤーは上位レイヤーの設定をオーバーライドできますが、変更は逆方向には伝播しません。これはオブジェクト指向プログラミングのクラス継承と同じ原理です。

  • L3で設定されたルールはL2、L1、L0のルールより優先。
  • L2で設定されたルールはL1、L0のルールより優先（L3でオーバーライドされない限り）。
  • L1で設定されたルールはL0のルールより優先（L2またはL3でオーバーライドされない限り）。
  • L0のルールは他の場所でオーバーライドされない限り、すべてのレイヤーに適用。
L0 Sourceのすべてがすべてのプロジェクトに共通です。つまり、audit.tsやvalidate-templates.tsのようなコアスクリプトはすべてのプロジェクトで同じように動作します。L0で修正すると、その変更は配布パスを通じてL1とL2に伝播し、最終的にすべてのL3プロジェクトに届きます。これが標準のコアプロミス——一度定義して、どこでも一貫して適用です。

バリアント概念

バリアントとは

バリアントは特定の目的に合わせてカスタマイズされたテンプレートで、L0 + L1の基盤の上に構築されます。4層レイヤー構造のセクションで説明したように、L2がバリアントテンプレートレイヤーであり、L3はL2テンプレートからスキャフォールドされた実際のプロジェクトです。

バリアントはai-workspace-standardsを実用的にするものです。標準が基盤を提供し、バリアントが専門性を提供します。バリアントがなければ、標準は実際の用途のない汎用フレームワークになります。標準がなければ、バリアントは互換性のない構造を持つ孤立したプロジェクトになります。

バリアントの例

これが実際にどのように機能するかを理解するために、2つの実際のバリアントを見てみましょう。

co-deck

  • タイプ： 講義・プレゼンテーション資料制作
  • パイプライン： リサーチから印刷用PDFまでの11ステージワークフロー
  • エージェント： 11の専門エージェント（PM + 10スペシャリスト：research, source-verifier, storyline, design, image-curator, diagram-specialist, html-build, measure, pdf-export, version）
  • 出力： HTMLスライドデッキとPDFプレゼンテーション
  • 独自機能： テーマシステム（5つのHTMLテーマ）、スタイルシステム、画像キュレーションパイプライン、SVG図生成、PDFレイアウト計測

co-consult

  • タイプ： コンサルティング分析・助言出力
  • パイプライン： ビジネスコンサルティングのためのリサーチ駆動分析ワークフロー
  • エージェント： 共通セットから適応された専門コンサルティングエージェント
  • 出力： コンサルティングレポート、分析ドキュメント、助言資料
  • 独自機能： 業界固有リサーチプロファイル、MECE論理フレームワーク、構造化問題解決ワークフロー

目的が異なっても、両バリアントは同じ基盤を共有します：PMオーケストレーションパターン、3-Tier戦略、PM Gateway、引き継ぎコントラクトシステム、ディレクトリレイアウト。この共有基盤が、相互運用性と保守性を可能にしています。

variant.json — バリアントの身分証明書

すべてのバリアントにはプロジェクトルートにvariant.jsonファイルがあり、その身元と設定を宣言します。このファイルはバリアントの「パスポート」——このバリアントが何であるか、何を含み、共通テンプレートとどう関係しているかをシステムに伝えます。

variant.jsonの主要フィールドは以下の通りです。

  • name — バリアントの識別子（例："co-deck"や"co-consult"）。
  • description — バリアントの機能の概要。
  • variant_type — このバリアントが扱う作業のカテゴリ（例："lecture"）。
  • status — ライフサイクルステータス："draft"、"beta"、"stable"。
  • version — セマンティックバージョニングに従う現在のバージョン番号。
  • inherits_common — 継承する共通テンプレートへのパス（通常"templates/common"）。
  • agents — このバリアントに含まれるエージェントのリストとファイルパス。
  • skills — このバリアントで利用可能なスキルのリスト。
  • lifecycle — バリアントのライフサイクル遷移に関するメタデータ。
{
  "name": "co-deck",
  "description": "Lecture and presentation material production variant",
  "variant_type": "lecture",
  "status": "beta",
  "version": "0.2.0",
  "inherits_common": "templates/common",
  "agents": [
    { "name": "pm",              "file": "agents/pm.md" },
    { "name": "research",         "file": "agents/research.md" },
    { "name": "storyline",       "file": "agents/storyline.md" },
    { "name": "html-build",      "file": "agents/html-build.md" }
  ]
}

バリアントのライフサイクル

バリアントは定義されたライフサイクルを経て、variant.jsonのlifecycleフィールドで追跡されます。

  1. Draft — バリアントは初期開発中。構造とエージェントが定義されています。まだ使用可能ではありません。
  2. Beta — バリアントは機能するが、荒い部分がある場合があります。アーリーアダプターが試してフィードバックを提供できます。co-deckは現在この段階にあります。
  3. Stable — バリアントは十分にテストされ、本番使用の準備ができています。破壊的変更にはメジャーバージョンの更新が必要です。

バリアントから新しいプロジェクトを作成する

第6章と第7章の演習では、セットアップ時間を節約するために既製のサンプルプロジェクト（co-consult、co-deck）をクローンします。実際の日常業務では、クローンはしません——ワークスペースルートから単一コマンドでL2バリアントテンプレートから新しいL3プロジェクトをスキャフォールドします：

bun scripts/new-project.ts "my-market-report" --variant co-consult

これでProjects/my-market-report/が新鮮な独立Gitリポジトリとして作成され、co-consultのエージェント、スキル、設定がコピーされ、空のdocs/context.mdスケルトンがレンダリングされるので、この特定のプロジェクトの目標を記入できます。完全な構文は：

bun scripts/new-project.ts "<project-name>" --variant <variant> [--platform claude|antigravity|both] [--version X.Y.Z]
  • <project-name> — 必須。Projects/の下のフォルダ名になります。
  • --variant <variant> — 必須。どのL2テンプレートからスキャフォールドするか（co-consult、co-deck、co-developなど）。
  • --platform — 任意。コピーするプラットフォーム設定（.claude/、.gemini/）を制限。デフォルトはboth。
  • --version — 任意。ソースバリアントのテンプレートバージョンを固定。
これを新しいバリアントの作成と混同しないでください。new-project.tsは日常的に頻繁に実行するコマンド——既存のL2テンプレートからL3プロジェクトをスキャフォールドします。L2テンプレート自体の構築（co-legalやco-hrのような全く新しいバリアント）は別の、はるかに稀なワークフローで、create-l3-scaffold.tsを使用します。第11章で説明します。
自分のバリアントを作りたいと考えていますか？ このハンドブックの第11章で、ゼロからカスタムバリアントを設計・構築するプロセスをカバーします。独自のエージェント、スキル、ワークフローパイプラインの定義方法と、バリアントを登録して共有ワークスペース標準のすべての恩恵を継承する方法を学びます。

コモンコントラクト

ai-workspace-standardsアーキテクチャの最後のピースがコモンコントラクトの概念です。これは、すべてのプロジェクト、バリアント、エージェントが同じ言語を話すことを保証する共有合意です。

コモンコントラクトとは

コモンコントラクトは、ワークスペースの異なる部分が互いにどう相互作用するかを定義する正式な仕様です。法的コントラクトが2者間の義務を指定するのと同様に、コモンコントラクトはエージェントとプロジェクトが従わなければならないデータ形式、ファイルの場所、命名規約、通信プロトコルを指定します。

コモンコントラクトはワークスペースのコアガバナンスドキュメント——CONSTITUTION.md、AGENTS.md（L0 SSOT）、バリアント固有のdocs/context.md（L2/L3）——で定義され、3つの主要な役割を果たします。

1. データフォーマットコントラクト

  • 主要データファイル（リサーチノート、スライドデッキ、設計仕様、画像マニフェスト）の構造とフィールドを定義
  • すべてのエージェントが次のエージェントが消費できる形式で出力を生成することを保証
  • 例：research_notes.mdには出典セクション、主要事実セクション、信頼性ノートセクションを含める必要がある

2. ディレクトリレイアウトコントラクト

  • 各ファイルタイプがワークスペース内のどこに配置されるかを定義
  • エージェントが推測なしで入力ファイルを見つけられることを保証
  • 例：リサーチノートはProjects/<project>/research_notes.mdに配置する必要がある

3. 命名規約コントラクト

  • ファイル、エージェント、スキル、バリアントの命名方法を定義
  • ワークスペースエコシステム全体の整合性を保証
  • 例：エージェントファイルは小文字＋ハイフン（source-verifier.md）、スキルも同じパターン

コントラクトの適用方法

コントラクトは単なるドキュメントではありません——強制されます。実際のコントラクトシステムの仕組みは以下の通りです。

  1. コントラクト定義 — コントラクトはワークスペースのコアガバナンスドキュメント（CONSTITUTION.md（共通標準）、AGENTS.md（エージェントレジストリ、L0のSSOT）、docs/context.md（プロジェクト固有設定、L2/L3のみ））で定義されます。これらのドキュメントがすべてのプロジェクトが従うべきスキーマ、レイアウト、命名ルールを指定します。
  2. テンプレート継承 — L1共通テンプレートが作成されると、L0からコントラクトがコピーされます。L2バリアントはL1を通じてコントラクトを継承します。ワークスペース内のすべてのプロジェクトが同じコントラクト基盤を共有します。
  3. バリアント拡張 — L2バリアントはバリアント固有ファイルに独自のコントラクト拡張を追加できます（例：co-deckはスライドデッキファイル、テーマファイル、PDFレイアウト仕様のコントラクトを追加）。これらの拡張はバリアント自身のコンテキストファイルで定義されます。
  4. 検証強制 — scripts/audit.tsスクリプトが各プロジェクトを継承したコントラクトに対して自動的にチェックします。ファイルがコントラクトに違反している場合（フォーマット、場所、名前が不正）、監査はプロジェクトが進行する前に修正すべきエラーとして報告します。

コントラクトと引き継ぎコントラクト

第4章で引き継ぎコントラクトが1つのエージェントから次のエージェントへ出力を渡す方法を定義することを覚えているかもしれません。コモンコントラクトは引き継ぎコントラクトが機能するより広いシステムです。次のように考えてください：

  • コモンコントラクトは全員が話す全体の言語を定義（ファイル形式、ディレクトリレイアウト、命名規約）
  • 引き継ぎコントラクトはエージェントのペア間の具体的な会話を定義（エージェントAがファイルXを生成、エージェントBがファイルXを読む）

コモンコントラクトが引き継ぎコントラクトを可能にします。すべてのエージェントがコモンコントラクト（ファイルの場所と形式）に合意していれば、2つのエージェント間の引き継ぎコントラクトを定義するのは簡単——渡すファイルを指定するだけで済みます。

例え — 共通言語： 多くの国の代表者が協力のために集まる国際会議を想像してください。コモンコントラクトは英語を作業言語として使用し、議事手続きに従い、標準化された文書形式を使用するという合意です。その土台があれば、任意の2人の代表者（エージェント）が特定のトピックについて集中した会話（引き継ぎコントラクト）を持てます。共通言語がなければ、すべての代表者ペアが独自の通信プロトコルをゼロから発明する必要があり——非効率でエラーが多発します。

コントラクトのメリット

コントラクトシステムはAIエージェントのコラボレーションにいくつかの具体的なメリットを提供します。

  • 設定不要の引き継ぎ。 エージェントAが終了しエージェントBが開始すると、エージェントBはディレクトリレイアウトコントラクトが正確なパスを指定しているため、エージェントAの出力の場所を既に知っています。
  • 自動エラー検出。 監査スクリプトが実行時エラーを引き起こす前にコントラクト違反を検出します。エージェントがファイルを間違った場所や形式で書き込むと、監査が直ちにフラグを立てます。
  • プロジェクト間のポータビリティ。 コモンコントラクトに従うエージェントは修正なしで任意のバリアントプロジェクトで動作できます。co-deckのリサーチエージェントは原理的にはco-consultにドロップインして正しく動作します。両方のバリアントが同じコントラクトを共有するからです。
  • バージョン管理された進化。 コモンコントラクトを変更する必要がある場合（例：スライドデッキ形式に新しい必須フィールドの追加）、変更はL0で行われ、同期パイプラインを通じて伝播され、すべてのプロジェクトで監査スクリプトによって強制されます。
重要ポイント： 4層レイヤー構造、バリアント概念、コモンコントラクトの組み合わせが、ai-workspace-standardsを単なるファイルの集まりではなく真のプラットフォームにしています。レイヤー構造が組織を提供し（L0→L1→L2配布パス、L1→L2→L3静的階層）、バリアントが専門性を提供し、コントラクトが相互運用性を提供します。これらが一緒になって、無数の専門AIプロジェクトが共通基盤を共有しながら独立してカスタマイズ可能であることを実現します。
