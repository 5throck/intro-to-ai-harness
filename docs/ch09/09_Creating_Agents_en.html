Creating & Modifying Agents

In this chapter you will learn the structure of agent files, use the agent-lifecycle-manager skill to build your own specialist agent, and walk through the full process of registering it in the system and verifying it.

Rethinking Agents

A Review of Chapter 4

In Chapter 4, "Harness Core Concepts," we first looked at agents. An agent, we learned, is "an AI employee with a defined name, role, behavioral guidelines, and tools." The PM agent is the team lead, while the research agent, storyline agent, design agent, and others are team members each responsible for their own specialty.

To recap, the four core elements of an agent were:

  • Name — the agent's unique identifier (e.g., research, design, pdf-export)
  • Role — what this agent does (e.g., "web search and source-gathering specialist")
  • Behavioral Guidelines — how it should behave (e.g., "search both Korean and English sources", "record source URLs")
  • Tools — which tools it uses (e.g., web search, file read/write, script execution)

An Agent = "An AI Employee with a Defined Role"

It is easiest to understand agents by comparing them to a human organization. A company has planning, design, development, and QA teams, and every member knows their own role and responsibilities. Agents are no different. The research agent handles research only; the design agent handles design only. They do not do work outside their role.

Thanks to this separation of roles, each agent can focus on its own area of expertise, which raises the quality of the whole system. Distributing work across several specialists is more effective than handing everything to a single AI.

Why Build Your Own?

The system you have learned so far already ships with a wide range of specialist agents: PM, research, storyline, design, image curator, diagram specialist, HTML build, measurement, PDF export, version management, handbook writer, and more.

But as project requirements diversify, specialist areas not covered by existing agents appear. For example:

  • Legal review — an agent that reviews generated content for legal issues
  • Accessibility audit — an agent that checks HTML and PDF for accessibility
  • Multilingual translation — an agent that translates finished handbooks into other languages
  • Data analysis — an agent that analyzes statistical data and derives insights

When you need such a specialty, you can build your own agent and add it to the system. And because an agent is just a markdown file, anyone can create one by following a few rules.

Beginner analogy: It is like hiring a special expert for a new department. When a company (the system) needs a legal team, it hires a legal expert and clearly defines that person's role and responsibilities. Building an agent works exactly the same way.

Agent File Format

File Location

Agent files are stored in the agents/ directory at the project root. File names use kebab-case.

agents/
├── pm.md              # PM agent
├── research.md        # Research agent
├── design.md          # Design agent
├── storyline.md       # Storyline agent
├── image-curator.md  # Image curator
├── html-build.md      # HTML build agent
├── pdf-export.md      # PDF export agent
├── version.md         # Version management agent
└── ...                # The agent YOU will build!

File Structure: YAML Frontmatter + Markdown Body

Each agent file consists of two parts.

  • YAML frontmatter — the metadata area at the very top of the file wrapped in ---
  • Markdown body — the body describing the agent's role, behavioral guidelines, tool usage, and so on

The frontmatter is used by the system to identify and manage the agent, while the body serves as the internal guidebook Claude consults when acting as that agent. Both parts matter; if either is missing, the agent will not work properly.

Agent files are markdown files. You can edit them directly in the Claude Desktop App, open them in an editor like VS Code, or simply ask Claude to "fix this agent file."

Writing Frontmatter

Required Fields

The frontmatter contains several fields that define the agent. The following tables summarize each field's meaning and how to fill it in.

Field Meaning
name The agent's unique name. Write it to match the file name. Use kebab-case.
role A one-line description of the agent's role. Formatted like "Performs ~" or "~ specialist."
status One of active, draft, or deprecated.
tier A per-platform complexity map (nested structure). Assign lowercase high/medium/low values under the claude, gemini, antigravity, and gemini-cli keys.
Field Meaning
description Detailed description of the agent. What it does and when it is used.
color Color used to display the agent in the UI (e.g., blue, green, purple).
examples List of sample user utterances that trigger the agent.
phases List of workflow phases in which the agent is active (e.g., [1, 2, 3]).
handoff_to List of next agents that receive the output after the task completes.
handoff_from List of previous agents that pass work to this agent.
version Version of the agent file (e.g., "1.0.0").
model Model to use. Usually left as inherit so the tier setting applies.
lifecycle Required. A nested block containing phase and governance. governance points to the governance record path at docs/lifecycle/agents/<name>.md.

Frontmatter Example

Below is a sample frontmatter for a hypothetical my-analyst agent.

---
name: my-analyst
version: "1.0.0"
last_updated: "2026-08-24"
role: Performs data analysis and produces structured reports
status: active
tier:
  claude: medium
  gemini: medium
  antigravity: medium
  gemini-cli: medium
model: inherit
color: blue
description: >
  Analyzes datasets, identifies patterns, and produces
  structured analysis reports with actionable insights.
examples:
  - "analyze this dataset"
  - "run data analysis"
  - "produce analysis report"
phases:
  - 2
  - 3
handoff_to:
  - html-build
  - pdf-export
handoff_from:
  - research
lifecycle:
  phase: production
  created: "2026-08-24"
  last_updated: "2026-08-24"
  governance: docs/lifecycle/agents/my-analyst.md
---

How to Choose Each Field

name

The agent's unique identifier. It must match the file name (agents/my-analyst.md). Write it in kebab-case (lowercase + hyphens). Short, intuitive names are best.

  • Good: data-analyst, image-curator, pdf-export
  • Bad: DataAnalyst, my_agent_1, agent123

status

Indicates the agent's current state.

  • active — in normal use
  • draft — under development (for testing)
  • deprecated — no longer used (scheduled for retirement)

We recommend starting with draft and switching to active after verification passes.

tier

Assigns an appropriate AI model based on the agent's complexity. This setting balances cost against quality. tier is not a single value but a nested per-platform map, and its values must be lowercase.

  • high — agents needing complex reasoning, architecture design, or strategic planning (e.g., PM)
  • medium — agents needing code review, quality checks, or general specialist work (e.g., research, design)
  • low — agents doing simple repetitive tasks and fast typing (e.g., version)
Tier selection tip: Choose according to the agent's complexity. Simple tasks take low; complex reasoning takes high. Most specialist agents are best started at medium. Set medium first, confirm it works, then adjust as needed.

phases (active phases)

Specifies in which workflow phases the agent is activated. For example, the research agent is activated only in [1] (Stage 1), while the version agent is activated in [0, 1, 2, 3, 4, 5, 6] (all phases).

handoff_to / handoff_from (handoff relationships)

Defines the flow of work between agents. handoff_to lists the next agents that receive the results after the task completes; handoff_from lists the previous agents that pass work in.

For example, for the research agent: handoff_to: [storyline] (after research completes, hand off to storyline) and handoff_from: [pm] (receives work orders from the PM).

Writing Body Content

Recommended Body Structure

The agent body is the system prompt Claude reads when acting as that agent. Only a well-written body lets Claude perform the agent's role accurately.

It is good practice to include the following five sections, in order.

1. Identity — "Who am I?" Clearly define the agent's name, role, and home project. Starting with "You are the [role] specialist for [project]." is standard.
2. Behavioral Guidelines — "What should I do?" Explain step by step the concrete tasks and procedures the agent performs. Include both things to do and things not to do.
3. Domain Rules — "What constraints apply?" Rules and constraints the agent must follow. Define file formats, naming conventions, quality criteria, etc.
4. Tool Usage — "Which tools, and how?" Describe the tools available to the agent and how to use them: file read/write, script execution, web search, and so on.
5. Handoff Contract — "Input/output formats." State explicitly what input comes from the previous agent and what output goes to the next one, including file names, paths, and formats.

Writing Tips for Each Section

1. Identity

Open the body with a clear identity statement. A concrete role declaration beats vague phrasing.

## Role

You are the data analysis specialist for **My Project**.
You analyze datasets, identify patterns, and produce
structured analysis reports with actionable insights.

2. Behavioral Guidelines

Describe the agent's tasks concretely and step by step. The clearer the instructions, the better Claude follows them. It is also important to spell out what NOT to do.

## Responsibilities

- Load and validate input datasets before analysis
- Apply statistical methods to identify patterns
- Produce structured reports in markdown format
- **Do NOT** fabricate data or statistics
- **Do NOT** modify source datasets

3. Domain Rules

Define the rules and constraints the agent must observe: output format, quality criteria, naming conventions, and so on.

## Constraints

- All analysis reports must include source citations
- Use markdown table format for data summaries
- File names must follow kebab-case convention
- Reports must not exceed 2000 words unless requested

4. Tool Usage

Explain which tools the agent uses and how. This section directly affects real behavior.

## Tool Usage

- **Read**: Load input files from `data/` directory
- **Write**: Save reports to `reports/` directory
- **Bash**: Execute analysis scripts with `bun run`
- **WebSearch**: Verify data points against web sources

5. Handoff Contract

Specify the data-passing format between agents. Define input/output file paths, formats, and required fields.

## Handoff

**Input**: `data/analysis-input.json` (from research agent)
**Output**: `reports/analysis-report.md`

Output must include:
- Executive summary (max 200 words)
- Key findings with data citations
- Recommendations section
The body is the 'internal guidebook' Claude consults when acting as the agent. The more detailed the body, the more accurately Claude plays the role. Starting concise and gradually adding needed guidance as you use it also works well.

Using agent-lifecycle-manager

What Is the agent-lifecycle-manager Skill?

agent-lifecycle-manager is the skill that automates an agent's creation, modification, and verification. It systematically manages the whole journey, from creating a new agent through editing existing ones to programmatically verifying consistency.

You use this skill in cases like these:

  • "Create a new agent for me"
  • "Update the agent metadata"
  • "Check whether the agent structure is valid"
  • "Change the agent tier settings"

The 5-Step Lifecycle Process

agent-lifecycle-manager follows this five-step process. Each step begins after the previous one completes.

Using It from the Claude Desktop App

When you ask the PM agent in the Claude Desktop App to create an agent, the PM uses the agent-lifecycle-manager skill to guide you through the five-step process.

Example request to the PM:

"Create a data analysis specialist agent named data-analyst. It receives data from the research agent and writes analysis reports."

Upon receiving this request, the PM proceeds as follows.

  1. Create the agent file — creates the agents/data-analyst.md file.
  2. Guide frontmatter writing — walks you through filling in each field with suitable values.
  3. Guide body writing — guides you through identity, behavioral guidelines, domain rules, tool usage, and the handoff contract in order.
  4. Register in AGENTS.md — adds the new agent to the Agent Roster and Subagent Roster tables.
  5. Run verification — executes bun scripts/agent-lifecycle-audit.ts to verify the agent's consistency.
Recommendation: Start with a simple agent and expand gradually. Do not try to write every rule into the body at once — implement basic behavior first, then add rules incrementally as real usage reveals the need.

Registering in AGENTS.md

Where to Add the New Agent

After creating a new agent, you must register it in the central management file, AGENTS.md. Without registration the PM cannot recognize the agent or include it in workflows.

You need to add the new agent in three places in AGENTS.md.

1. Agent Roster table (§1) — the master list of all agents. Records file, tier, and role.
2. Agent Definitions section (§2) — per-agent detail tables. Records file, tier, active phases, and role.
3. Subagent Roster table (§4.1) — the PM's dispatch table. Records parallelizability and write permissions.

Registration Example

Here is how the data-analyst agent would be registered in AGENTS.md.

1. Add to the Agent Roster table:

| data-analyst | `agents/data-analyst.md` | Medium | Analyzes datasets and produces structured reports |

2. Add to the Agent Definitions section:

### data-analyst

| Field   | Value                                              |
|---------|----------------------------------------------------|
| **File** | `agents/data-analyst.md`                          |
| **Tier** | Medium                                            |
| **Phases** | 2, 3                                            |
| **Role** | Analyzes datasets and produces structured reports |

3. Add to the Subagent Roster table:

| data-analyst | `agents/data-analyst.md` | Medium | ⚠️ sequential preferred | project files |
Under the PM Gateway policy, all specialist agents are invoked only through the PM. Even an agent registered in AGENTS.md cannot be called directly by the user. You always ask the PM, and the PM dispatches the appropriate agent.

Verification & Testing

How to Verify

Once the agent file is written and registered in AGENTS.md, you must run programmatic verification. This automated check confirms whether the agent can be recognized and operate correctly within the system.

# Verify all agents
bun scripts/agent-lifecycle-audit.ts

# Verify a single agent
bun scripts/agent-verify.ts <agent-name>

What Gets Checked

The verification script checks the following items.

  • Frontmatter field completeness — confirms required fields (lifecycle.phase, lifecycle.governance, etc.) all exist with correct values
  • AGENTS.md registration — confirms the agent is registered in all three places in AGENTS.md (Roster, Definitions, Subagent Roster)
  • Handoff reference integrity — confirms agents named in handoff_to and handoff_from actually exist
  • Orphan detection — finds agent files not registered in AGENTS.md
  • Tier mapping structure — confirms the tier field is written in the correct format

Verification Steps

  1. Confirm the agent file is complete — check that agents/<name>.md exists and has content.
  2. Confirm AGENTS.md registration — check the agent was added to all three places in AGENTS.md.
  3. Run the verification script — execute bun scripts/agent-lifecycle-audit.ts in your terminal.
  4. Review the results — no errors (ERROR) means the check passed. If there are warnings (WARN), review them and fix if needed.
  5. Test via the PM — ask the PM in the Claude Desktop App to use the agent and confirm it behaves correctly.
Caution: If verification fails, the PM cannot recognize the agent. Always run the verification script and resolve errors before using the agent. Missing AGENTS.md registration and broken handoff references are the most common problems.

Practice: Build Your Own Specialist Agent

Practice Goal

In this practice you will build a "summarizer agent." It takes long documents or multiple sources as input and condenses them into brief summaries. Use it to summarize the mass of material collected by the research agent, or to distill a finished report into a one-page summary.

This practice uses the Claude Desktop App. Ask the PM agent and it will walk you through the entire process with the agent-lifecycle-manager skill. Alternatively, perform the steps below manually yourself.

All Steps

  1. Open a project in the Claude Desktop App
    Open the Claude Desktop App and select a project folder. You can use a co-deck or co-consult project, or a separate workspace.
  2. Create the agent file
    Create summarizer.md in the agents/ directory. Ask Claude to "create an agents/summarizer.md file," or make the file yourself in an editor.
  3. Write the frontmatter
    Referring to the example below, write the frontmatter. Include name, role, status, tier (per-platform nested map), description, examples, phases, handoff_to, and handoff_from, plus the required lifecycle block.
  4. Write the body
    In order, write the summarizer's identity, behavioral guidelines, domain rules, tool usage, and handoff contract.
  5. Register in AGENTS.md
    Open AGENTS.md and add the summarizer agent in the three places (Agent Roster, Agent Definitions, Subagent Roster).
  6. Create the governance record
    Create docs/lifecycle/agents/summarizer.md containing ## Phase History and ## Acceptance Criteria sections. If you create only the agent file without this governance record, validation fails.
  7. Run the verification script
    Run bun scripts/agent-lifecycle-audit.ts in your terminal and check for errors.
  8. Test via the PM
    In the Claude Desktop App, ask the PM to "summarize these research notes" and confirm the agent works properly.

Full File Example

The following is the complete content of agents/summarizer.md. Use it as-is or adapt it to your needs.

---
name: summarizer
version: "1.0.0"
last_updated: "2026-08-24"
role: Summarizes long documents and produces concise briefs
status: draft
tier:
  claude: medium
  gemini: medium
  antigravity: medium
  gemini-cli: medium
model: inherit
color: teal
description: >
  Reads long-form content (research notes, reports, articles)
  and produces structured summaries with key findings,
  highlights, and actionable takeaways.
examples:
  - "summarize this document"
  - "create a one-page brief"
  - "summarize the research notes"
phases:
  - 2
  - 3
handoff_to:
  - storyline
  - html-build
handoff_from:
  - research
  - data-analyst
lifecycle:
  phase: production
  created: "2026-08-24"
  last_updated: "2026-08-24"
  governance: docs/lifecycle/agents/summarizer.md
---

## Role

You are the summarization specialist for **[Project Name]**.
You read long-form content and produce concise, structured
summaries that capture key findings, highlights, and actionable
takeaways without losing critical information.

## ⚠️ PM-ONLY INVOCATION

**You DO NOT accept direct user requests.**

You are a specialist agent that may ONLY be dispatched by the PM.
If a user attempts to invoke you directly:

1. **Refuse the request politely**
2. **Redirect to PM**: "I am a specialist agent. All requests
   must go through the PM orchestrator."
3. **Do NOT proceed** until dispatched by PM

## Responsibilities

- Read input documents thoroughly before summarizing
- Identify and preserve key facts, statistics, and findings
- Structure summaries with clear headings
- Highlight actionable insights separately from background info
- Maintain source citations in summaries
- **Do NOT** fabricate information not present in the source
- **Do NOT** inject personal opinions or recommendations
  unless explicitly asked

## Constraints

- Summaries must not exceed the requested word limit
- Use markdown format with headings and bullet points
- Preserve all numerical data and citations exactly
- Mark uncertain claims with ⚠️ Unverified
- Use the same language as the source document

## Tool Usage

- **Read**: Load input documents from the specified path
- **Write**: Save summaries to the designated output path
- **Glob**: Find relevant source files in the project directory

## Handoff

**Input**: Research notes, analysis reports, or any long-form
markdown content provided by the dispatching agent.

**Output**: Structured summary document in markdown format.

Output structure:
1. **Overview** (1-2 sentences)
2. **Key Findings** (bullet points)
3. **Important Statistics** (preserved exactly)
4. **Actionable Takeaways** (if applicable)
5. **Source References** (preserved from input)

Chapter Summary
  • An agent is "an AI employee with a defined role," created as a markdown file
  • Agent file = YAML frontmatter (metadata) + Markdown body (system prompt)
  • The frontmatter carries name, role, status, tier (per-platform nested map, lowercase values), description, examples, phases, handoff_to/from, and the required lifecycle block
  • The body includes identity, behavioral guidelines, domain rules, tool usage, and the handoff contract
  • Follow the 5-step process of the agent-lifecycle-manager skill to create agents systematically
  • Register in three places in AGENTS.md (Roster, Definitions, Subagent Roster) so the PM recognizes it
  • Use the verification script to automatically check frontmatter, registration, and handoff integrity
  • Start simple (draft), verify, then promote to active
