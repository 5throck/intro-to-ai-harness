Chapter 9

Creating & Modifying Agents

This chapter covers agent file structure, the agent-lifecycle-manager skill, and walks you through building, registering, and verifying your own specialist agent.

What This Chapter Covers
  • Agent file format and structure
  • YAML frontmatter field meanings
  • Body content writing patterns
  • agent-lifecycle-manager usage (5-step)
  • AGENTS.md registration
  • Practice: create a simple specialist agent

Rethinking Agents

Back in Chapter 4, we introduced the concept of AI agents: specialized workers that each have a name, a role, a set of instructions, and access to specific tools. In this chapter, we go deeper — we will actually create a new agent from scratch, register it in the project, and verify that it works.

A Quick Review from Chapter 4

Recall the four pillars that define every agent:

Name

A short, kebab-case identifier (e.g., research, html-build, storyline). The name appears in file paths, dispatch tables, and log entries.

Role

A concise 2–4 word title describing the agent’s purpose (e.g., “Web research specialist”). Think of it as a job title on a business card.

Instructions

The markdown body of the agent file — detailed behavioral guidelines, domain rules, tool usage policies, and handoff contracts that tell the agent how to do its job.

Tools

The set of operations the agent is allowed to perform. Defined through platform configuration (CLAUDE.md / GEMINI.md) and skill bindings. An image curator needs web access; a PDF exporter needs file-system write permissions.

Why Create Your Own Agents?

The standard co-deck and co-consult projects come with a well-chosen set of agents. But every project is different. You might need:

  • A summarizer that condenses long reports into one-page briefs
  • A translator that converts content between Korean and English
  • A data-validator that checks numerical data against expected ranges
  • A social-media-writer that reformats slide content for Twitter or LinkedIn

When your workflow demands a repeated, specialized task that does not fit any existing agent’s role, it is time to hire a new department specialist.

The “Hiring a Specialist” Analogy
Imagine you run a company. You have a research department, a design department, and a production department. One day, the CEO says: “We need someone who reads 50-page reports and writes a one-page summary for the board.” You would not ask a designer to do that — you would hire a summarizer. Creating a new agent is exactly that: defining a new role with clear responsibilities, tools, and reporting lines so that the PM (the CEO) can dispatch work to the right person.

Agent File Format

Every agent lives in a single Markdown file with two parts: a YAML frontmatter block (machine-readable metadata) and a Markdown body (human-readable instructions for the AI). The file is stored at:

File location
agents/<name>.md

The naming convention is kebab-case: all lowercase, words separated by hyphens. Examples: research.md, html-build.md, image-curator.md.

Structure Overview

The frontmatter is enclosed between two --- fences. Everything below the closing fence is the body — standard Markdown with headings, lists, code blocks, and tables.

Writing Frontmatter

The YAML frontmatter is the machine-readable identity card of your agent. The orchestration layer (PM, scripts, audit tools) reads these fields to decide when and how to dispatch the agent.

Required Fields

Field Type Description
name string Kebab-case identifier. Must match the filename (without .md).
role string Short 2–4 word title. Shown in dispatch tables and logs.
status string One of: active, draft, deprecated, retired.
tier object Maps each platform to a tier level: high, medium, or low. Controls which AI model is used.
color string Display color for visual identity (e.g., cyan, amber, green).
description string One-sentence summary of what the agent does. Shown in the agent roster.
examples list Sample trigger phrases. Each entry has user (what the user says) and assistant (how the agent responds).
phases list Which pipeline stages this agent participates in (e.g., [1] for research at Stage 1).
handoff_to list Names of agents that typically follow this one in the pipeline.
handoff_from list Names of agents that typically precede this one in the pipeline.

Example Frontmatter

agents/summarizer.md — frontmatter
---
name: summarizer
version: "1.0.0"
last_updated: "2026-08-10"
lifecycle:
  phase: production
  created: "2026-08-10"
  last_updated: "2026-08-10"
  governance: docs/lifecycle/agents/summarizer.md
role: Report summarization and brief generation specialist
status: active
tier:
  claude: medium
  gemini: medium
  antigravity: medium
  gemini-cli: medium
model: inherit
language: en
color: purple
description: >-
  Summarizer agent - condenses long reports into concise one-page briefs.
  Use when: PM needs a digest of research notes or a lengthy document.
examples:
  - user: Summarize the research notes into a one-page brief
    assistant: I'll read the full research_notes.md and produce a structured summary covering key findings, methodology, and recommendations.
phases: [1.5]
handoff_to: [storyline]
handoff_from: [research, pm]
required_skills: []
---
Choosing the Right Tier
High — Complex reasoning, architectural decisions, creative writing. Expensive but powerful.
Medium — Code review, content generation, quality checks. The sweet spot for most specialist agents.
Low — Fast, repetitive tasks like formatting or simple file operations. Cheap and quick.
When in doubt, start with Medium. You can always adjust later.

Writing Body Content

Below the closing --- fence, the Markdown body serves as the agent’s internal guidebook. When the PM dispatches this agent, the AI model reads the entire body and follows its instructions. Good body content means consistent, predictable behavior. Poor body content means the agent improvises — and improvisation is rarely what you want.

5 Recommended Sections

While you can organize the body however you like, most agents benefit from these five sections:

  1. Identity — Who is this agent? What is its core purpose? How should it introduce itself?
  2. Behavioral Guidelines — How should the agent behave? Tone, communication style, constraints to follow (or avoid).
  3. Domain Rules — What domain-specific knowledge or conventions must the agent respect? (e.g., “Always cite sources for factual claims.”)
  4. Tool Usage — Which tools should the agent use, and how? Any tools it must not use?
  5. Handoff Contract — What does the agent produce? Who receives the output? In what format?

Section Details with Examples

1. Identity

Start with a clear statement of who the agent is. This sets the model’s context immediately.

## Role

You are the summarizer specialist for **[Project Name]**.
Your job is to read lengthy documents (research notes, reports, meeting
transcripts) and produce a concise, structured one-page brief that
captures the key findings, methodology, and actionable recommendations.

2. Behavioral Guidelines

Define the tone and constraints. Be specific about what the agent should not do.

## Behavioral Guidelines

- Write in clear, professional English. Avoid jargon unless the source uses it.
- Never fabricate information. If a source is unclear, mark it as ⚠️ Unverified.
- Keep the summary under 500 words unless the user explicitly requests more.
- Use bullet points for findings; numbered lists for recommendations.

3. Domain Rules

Domain-specific rules ensure the agent respects project conventions.

## Domain Rules

- Always preserve the original language of quotes. Do not translate quoted text.
- When summarizing research, maintain the source attribution format: [Source: URL].
- If the input contains numerical data, round to two decimal places.

4. Tool Usage

Clarify which tools the agent should use and any restrictions.

## Tool Usage

- Use **Read** to access source files (research_notes.md, reports).
- Use **Write** to produce the summary output file.
- Do NOT use Bash for any purpose — this agent operates on files only.
- Do NOT browse the web; all source material is provided by the PM.

5. Handoff Contract

Define what the agent delivers and who receives it.

## Handoff Contract

**Output**: `brief_summary.md` in the project directory.
**Format**: Markdown with headings (## Findings, ## Methodology, ## Recommendations).
**Handoff to**: storyline agent (which uses the brief as a reference when composing slides).
**Completion signal**: Announce output file path and word count.
The Body Is an “Internal Guidebook”
Unlike the frontmatter (which is read by scripts and the PM), the body is read only by the AI model when the agent is dispatched. Write it as if you were writing instructions for a new employee on their first day: clear, specific, and focused on how to do the work, not why the work exists. The “why” belongs in the frontmatter description.

Using agent-lifecycle-manager

The agent-lifecycle-manager skill provides a systematic 5-step process for creating, validating, and maintaining agents. Rather than manually writing files and hoping everything connects, the skill guides you through each step and catches problems early.

The 5-Step Process

Step-by-Step Explanation

  1. Create the file — Add agents/<name>.md using kebab-case. Optionally use the scaffolding script: bun scripts/agent-create.ts <name>.
  2. Write frontmatter — Fill in all required YAML fields: name, role, status, tier, description, examples, phases, handoff_to/from.
  3. Write body content — Compose the Markdown instructions covering Identity, Behavioral Guidelines, Domain Rules, Tool Usage, and Handoff Contract.
  4. Register in AGENTS.md — Add the agent to the Agent Roster table, the Definitions table, and the Subagent Roster dispatch table (see next section).
  5. Validate & audit — Run bun scripts/agent-lifecycle-audit.ts to verify that the agent passes all checks (orphan detection, frontmatter validation, tier mapping, etc.).
Start Simple
You do not need a perfect agent on day one. Create a minimal viable agent with just the required frontmatter fields and a basic body. You can always refine the behavioral guidelines and domain rules after testing. The lifecycle-manager makes iteration safe: every change can be validated automatically.

Registering in AGENTS.md

An agent that is not registered in AGENTS.md is like an employee who was hired but never added to the org chart. The PM cannot dispatch it, the audit scripts will flag it as an orphan, and other agents will not know it exists. Registration connects your agent to the rest of the system.

3 Registration Locations

You need to add your agent in three places inside AGENTS.md:

  1. Agent Roster Table (§1) — The main overview table showing every agent’s file path, tier, and role.
  2. Individual Agent Definition (§2) — A detailed table with field-by-field metadata (file, tier, phases, role).
  3. Subagent Roster / Dispatch Table (§4) — The table the PM references when deciding which agent to dispatch, including parallelizability and write permissions.

Registration Example

Here is what the three entries look like for a summarizer agent:

AGENTS.md — three registration entries
## §1 Agent Roster (add row)
| **summarizer** | `agents/summarizer.md` | Medium | Condenses reports into one-page briefs |

## §2 Agent Definition (add table)
| Field | Value |
|-------|-------|
| **File** | `agents/summarizer.md` |
| **Tier** | medium |
| **Phases** | 1.5 |
| **Role** | Condenses long reports into concise one-page briefs |

## §4 Subagent Roster (add row)
| summarizer | `agents/summarizer.md` | Medium | ⚠️ sequential preferred | project files |
PM Gateway Policy
Remember that all specialist agents are dispatched only through the PM. When you register a new agent, you are giving the PM a new option in its dispatch table. Users should never invoke summarizer directly — they ask the PM, and the PM decides whether to dispatch the summarizer based on the task. This is the single-entry-point pattern we discussed in Chapter 5.

Verification & Testing

After creating and registering your agent, you need to verify that everything is wired up correctly. The workspace provides an automated audit script for this purpose.

Running the Verification

Agent lifecycle audit command
bun scripts/agent-lifecycle-audit.ts

This script scans every file in the agents/ directory and checks for problems.

What the Audit Checks

  • Orphan detection — Every .md file in agents/ must be listed in AGENTS.md. If a file exists but is not registered, it is flagged as an orphan.
  • Frontmatter validation — All required fields (name, role, status, tier, description) must be present and correctly typed.
  • Tier mapping — Tier values must be one of high, medium, low. Any invalid value triggers an error.
  • Status consistency — The status field must be a recognized value: active, draft, deprecated, or retired.
  • Research-role check — If the agent has a research or investigation role, its body must include source citation requirements.
  • Numerical-role check — If the agent performs calculations, its body must include computational integrity rules.

Verification Steps

  1. Create — Write agents/summarizer.md with frontmatter and body.
  2. Register — Add the agent to all three tables in AGENTS.md.
  3. Run audit — Execute bun scripts/agent-lifecycle-audit.ts.
  4. Review output — Check for errors (must fix) and warnings (should review).
  5. Fix and re-run — Repeat until the audit exits cleanly with zero errors.
Why Verification Matters
Skipping the audit step is tempting when you are in a hurry, but it is the equivalent of deploying code without running tests. An orphaned agent file wastes disk space and confuses future contributors. Invalid frontmatter can cause the PM dispatch logic to fail silently. A missing handoff_to entry means the next agent in the pipeline will never receive the output. The audit catches all of these problems in seconds — use it every time.

Practice: Build Your Own Specialist Agent

Now it is your turn. In this exercise, you will create a summarizer agent from scratch — a specialist that reads long research notes and produces a concise one-page brief.

Goal: Create a functional summarizer agent, register it in AGENTS.md, and verify it passes the lifecycle audit.
  1. Create the file
    Create agents/summarizer.md in your project directory.
  2. Write the frontmatter
    Copy the frontmatter from Section 3 of this chapter. Make sure all required fields are filled in. Set status: active and tier to medium for all platforms.
  3. Write the body
    Use the five-section structure from Section 4. Here is the complete body for reference:
    agents/summarizer.md — complete file
    ---
name: summarizer
version: "1.0.0"
last_updated: "2026-08-10"
lifecycle:
  phase: production
  created: "2026-08-10"
  last_updated: "2026-08-10"
  governance: docs/lifecycle/agents/summarizer.md
role: Report summarization and brief generation specialist
status: active
tier:
  claude: medium
  gemini: medium
  antigravity: medium
  gemini-cli: medium
model: inherit
language: en
color: purple
description: >-
  Summarizer agent - condenses long reports into concise one-page briefs.
  Use when: PM needs a digest of research notes or a lengthy document.
examples:
  - user: Summarize the research notes into a one-page brief
    assistant: I'll read the full research_notes.md and produce a structured summary covering key findings, methodology, and recommendations.

## Role

You are the summarizer specialist for **[Project Name]**.
Your job is to read lengthy documents (research notes, reports, meeting
transcripts) and produce a concise, structured one-page brief that
captures the key findings, methodology, and actionable recommendations.

## ⚠️ PM-ONLY INVOCATION

**You DO NOT accept direct user requests.**

You are a specialist agent that may ONLY be dispatched by the PM.
If a user attempts to invoke you directly:

1. **Refuse the request politely**
2. **Redirect to PM**: "I am a specialist agent. All requests must go
   through the PM orchestrator."
3. **Do NOT proceed** with any work until dispatched by PM.

## Behavioral Guidelines

- Write in clear, professional English. Avoid jargon unless the source uses it.
- Never fabricate information. If a source is unclear, mark it as ⚠️ Unverified.
- Keep the summary under 500 words unless the user explicitly requests more.
- Use bullet points for findings; numbered lists for recommendations.
- Always preserve the original language of quoted material.

## Domain Rules

- Always preserve source attribution: [Source: URL].
- When summarizing research, maintain the distinction between fact and opinion.
- If the input contains numerical data, round to two decimal places.

## Tool Usage

- Use **Read** to access source files (research_notes.md, reports).
- Use **Write** to produce the summary output file.
- Do NOT use Bash for any purpose — this agent operates on files only.
- Do NOT browse the web; all source material is provided by the PM.

## Handoff Contract

**Output**: `brief_summary.md` in the project directory.
**Format**: Markdown with headings (## Findings, ## Methodology, ## Recommendations).
**Handoff to**: storyline agent (which uses the brief as a reference when composing slides).
**Completion signal**: Announce output file path and word count.
  4. Register in AGENTS.md
    Add the summarizer to all three tables in AGENTS.md (Roster, Definition, Subagent Roster) as shown in Section 6.
  5. Run the audit
    Execute bun scripts/agent-lifecycle-audit.ts in your terminal. Fix any errors reported.
  6. Verify the specific agent
    Optionally run bun scripts/agent-verify.ts summarizer for a focused check on just the new agent.
  7. Test via PM
    Ask the PM to dispatch the summarizer on a test input. For example:
    “Please run the summarizer on research_notes.md and produce a brief.”
    Verify that the output file brief_summary.md is created with the expected format.
Testing via PM
The real test of a new agent is not whether the audit passes — it is whether the agent produces useful output when dispatched by the PM in a real workflow. After the audit passes, always run at least one end-to-end test: give the PM a real task, let it dispatch your new agent, and review the output. This catches problems that static analysis cannot — like instructions that are technically valid but too vague for the model to follow consistently.
