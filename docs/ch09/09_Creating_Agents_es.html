Capítulo 9

Creación y modificación de agentes

En este capítulo aprenderás la estructura de los archivos de agente, usarás la skill agent-lifecycle-manager para crear tu propio agente especialista y recorrerás todo el proceso de registrarlo en el sistema y verificarlo.

Lo que cubre este capítulo
  • Formato y estructura del archivo de agente
  • Significado de los campos YAML del frontmatter
  • Patrones de redacción del cuerpo
  • Cómo usar agent-lifecycle-manager (5 pasos)
  • Cómo registrarlo en AGENTS.md
  • Práctica: escribir un agente especialista sencillo

Repensando los agentes

Repaso del capítulo 4

En el capítulo 4, «Conceptos básicos del harness», conocimos por primera vez los agentes. Aprendimos que un agente es "un empleado de IA con nombre, rol, pautas de comportamiento y herramientas definidos". El agente PM es el jefe de equipo, mientras que el agente de investigación, el de storyline, el de diseño y otros son miembros del equipo, cada uno responsable de su especialidad.

Recordando, los cuatro elementos esenciales de un agente eran:

  • Nombre (Name) — el identificador único del agente (por ejemplo: research, design, pdf-export)
  • Rol (Role) — qué hace este agente (por ejemplo: "especialista en búsqueda web y recolección de fuentes")
  • Pautas de comportamiento (Behavioral Guidelines) — cómo debe comportarse (por ejemplo: "buscar tanto en fuentes coreanas como en inglés", "registrar las URL de origen")
  • Herramientas (Tools) — qué herramientas usa (por ejemplo: búsqueda web, lectura/escritura de archivos, ejecución de scripts)

Agente = "empleado de IA con un rol definido"

Es más fácil entender los agentes comparándolos con una organización humana. Una empresa tiene equipos de planificación, diseño, desarrollo y QA, y cada miembro conoce sus funciones y responsabilidades. Con los agentes ocurre lo mismo: el agente research solo se encarga de investigar y el agente design solo de diseñar. No hacen trabajo fuera de su rol.

Gracias a esta separación de roles, cada agente puede concentrarse en su área de experiencia y la calidad del sistema completo mejora. Repartir el trabajo entre varios especialistas es más eficaz que encargárselo todo a una sola IA.

¿Por qué crear los tuyos?

El sistema que has aprendido hasta ahora ya incluye una amplia variedad de agentes especialistas: PM, investigación, storyline, diseño, curador de imágenes, especialista en diagramas, construcción HTML, medición, exportación PDF, gestión de versiones, escritor de manuales, entre otros.

A medida que los requisitos del proyecto se diversifican, aparecen áreas especializadas no cubiertas por los agentes existentes. Por ejemplo:

  • Revisión legal — un agente que revisa los problemas legales del contenido generado
  • Auditoría de accesibilidad — un agente que comprueba la accesibilidad de HTML y PDF
  • Traducción multilingüe — un agente que traduce los manuales terminados a otros idiomas
  • Análisis de datos — un agente que analiza datos estadísticos y obtiene conclusiones

Cuando necesites una de estas especialidades, puedes crear tu propio agente y añadirlo al sistema. Y como un agente es simplemente un archivo markdown, cualquiera puede crear uno siguiendo unas pocas reglas.

Analogía para principiantes: es como contratar a un experto especial para un departamento nuevo. Cuando a una empresa (el sistema) le hace falta un equipo jurídico, contrata a un experto legal y define con claridad su rol y sus responsabilidades. Crear un agente funciona exactamente igual.

Formato del archivo de agente

Ubicación del archivo

Los archivos de agente se guardan en el directorio agents/ de la raíz del proyecto. Los nombres de archivo usan kebab-case.

agents/
├── pm.md              # Agente PM
├── research.md        # Agente de investigación
├── design.md          # Agente de diseño
├── storyline.md       # Agente de storyline
├── image-curator.md  # Curador de imágenes
├── html-build.md      # Agente de construcción HTML
├── pdf-export.md      # Agente de exportación PDF
├── version.md         # Agente de gestión de versiones
└── ...                # ¡El agente que tú vas a crear!

Estructura del archivo: frontmatter YAML + cuerpo markdown

Cada archivo de agente consta de dos partes.

  • Frontmatter YAML — el área de metadatos del inicio del archivo envuelta entre ---
  • Cuerpo markdown — el texto que describe el rol del agente, sus pautas de comportamiento, el uso de herramientas, etc.

El frontmatter lo usa el sistema para identificar y gestionar al agente, mientras que el cuerpo actúa como el manual interno que Claude consulta cuando actúa como ese agente. Ambas partes son importantes: si falta cualquiera de ellas, el agente no funcionará correctamente.

Los archivos de agente están en formato markdown. Puedes editarlos directamente desde la Claude Desktop App, abrirlos en un editor como VS Code o pedirle a Claude que "modifique este archivo de agente".

Redacción del frontmatter

Campos obligatorios

El frontmatter contiene varios campos que definen al agente. Las siguientes tablas resumen el significado de cada campo y cómo rellenarlo.

Campo Significado
name Nombre único del agente. Escríbelo igual que el nombre del archivo. Usa kebab-case.
role Describe el rol del agente en una sola línea. Con formato "Performs ~" o "especialista en ~".
status Uno de estos valores: active (activo), draft (borrador), deprecated(descartado).
tier Mapa de complejidad por plataforma (estructura anidada). Asigna valores en minúsculas high/medium/low a las claves claude, gemini, antigravityy gemini-cli.
Campo Significado
description Descripción detallada del agente. Qué hace y cuándo se usa.
color Color empleado para mostrar el agente en la interfaz (por ejemplo: blue, green, purple).
examples Lista de frases de ejemplo del usuario que activan al agente.
phases Lista de fases del flujo de trabajo en las que el agente está activo (por ejemplo: [1, 2, 3]).
handoff_to Lista de agentes siguientes que recibirán el resultado al terminar la tarea.
handoff_from Lista de agentes previos que le pasan trabajo a este agente.
version Versión del archivo de agente (por ejemplo: "1.0.0").
model Modelo a utilizar. Normalmente se deja en inherit para que aplique la configuración de tier.
lifecycle Obligatorio. Bloque anidado con los subcampos phasey governance. governance apunta a la ruta del registro de gobernanza docs/lifecycle/agents/<name>.md.

Ejemplo de frontmatter

A continuación, un frontmatter de ejemplo para un hipotético agente my-analyst.

---
name: my-analyst
version: "1.0.0"
last_updated: "2026-08-24"
role: Performs data analysis and produces structured reports
status: active
tier:
  claude: medium
  gemini: medium
  antigravity: medium
  gemini-cli: medium
model: inherit
color: blue
description: >
  Analyzes datasets, identifies patterns, and produces
  structured analysis reports with actionable insights.
examples:
  - "analyze this dataset"
  - "run data analysis"
  - "produce analysis report"
phases:
  - 2
  - 3
handoff_to:
  - html-build
  - pdf-export
handoff_from:
  - research
lifecycle:
  phase: production
  created: "2026-08-24"
  last_updated: "2026-08-24"
  governance: docs/lifecycle/agents/my-analyst.md
---

Guía para elegir cada campo

name (nombre)

Es el identificador único del agente. Debe coincidir exactamente con el nombre del archivo (agents/my-analyst.md). Escríbelo en kebab-case (minúsculas + guiones). Los nombres cortos e intuitivos son los mejores.

  • Buenos ejemplos: data-analyst, image-curator, pdf-export
  • Malos ejemplos: DataAnalyst, my_agent_1, agent123

status (estado)

Indica el estado actual del agente.

  • active — en uso normal
  • draft — en desarrollo (para pruebas)
  • deprecated — ya no se usa (previsto para retirarse)

Se recomienda empezar con drafty cambiar a active cuando la verificación pase.

tier (nivel)

Asigna el modelo de IA adecuado según la complejidad del agente. Es un ajuste para equilibrar coste y calidad. tier no es un valor único, sino un mapa anidado por plataforma, y sus valores deben escribirse siempre en minúsculas.

  • high — agentes que requieren razonamiento complejo, diseño de arquitectura o planificación estratégica (por ejemplo: PM)
  • medium — agentes que requieren revisión de código, controles de calidad o trabajo especializado general (por ejemplo: research, design)
  • low — agentes con tareas repetitivas simples y escritura rápida (por ejemplo: version)
Consejo para elegir tier: elige según la complejidad del agente. Tareas simples, low; razonamiento complejo, high. La mayoría de los agentes especialistas conviene iniciarlos en medium. Configura primero medium, comprueba que funciona y ajústalo según lo necesites.

phases (fases activas)

Especifica en qué fases del flujo de trabajo se activa el agente. Por ejemplo, el agente de investigación solo se activa en [1] (Stage 1), mientras que el agente de versiones se activa en [0, 1, 2, 3, 4, 5, 6] (todas las fases).

handoff_to / handoff_from (relaciones de entrega)

Define el flujo de trabajo entre agentes. handoff_to son los agentes siguientes que reciben los resultados al terminar la tarea; handoff_from son los agentes previos que entregan el trabajo.

Por ejemplo, para el agente de investigación: handoff_to: [storyline] (tras completar la investigación, entrega a storyline) y handoff_from: [pm] (recibe las órdenes de trabajo del PM).

Redacción del cuerpo

Estructura recomendada del cuerpo

El cuerpo del agente es el prompt de sistema que Claude consulta cuando actúa como ese agente. Solo con un cuerpo bien redactado Claude podrá desempeñar el rol del agente con precisión.

Es recomendable incluir las cinco secciones siguientes, en orden.

1. Identidad (Identity) — "¿Quién soy?". Define con claridad el nombre, el rol y el proyecto al que pertenece el agente. Es habitual empezar con "You are the [rol] specialist for [proyecto]."
2. Pautas de comportamiento (Behavioral Guidelines) — "¿Qué debo hacer?". Explica paso a paso las tareas y procedimientos concretos que realiza el agente. Incluye tanto lo que debe hacer como lo que no.
3. Reglas de dominio (Domain Rules) — "¿Qué restricciones debo respetar?". Reglas y restricciones que el agente debe cumplir obligatoriamente: formatos de archivo, convenciones de nombres, criterios de calidad, etc.
4. Uso de herramientas (Tool Usage) — "¿Qué herramientas uso y cómo?". Describe las herramientas disponibles para el agente y cómo usarlas: lectura/escritura de archivos, ejecución de scripts, búsqueda web, etc.
5. Contrato de entrega (Handoff Contract) — "Formatos de entrada/salida". Indica explícitamente qué entrada recibe del agente anterior y qué salida entrega al siguiente, incluyendo nombres de archivo, rutas y formatos.

Consejos de redacción por sección

1. Identidad (Identity)

Comienza el cuerpo con una declaración de identidad clara. Una declaración concreta del rol es mejor que expresiones vagas.

## Role

You are the data analysis specialist for **My Project**.
You analyze datasets, identify patterns, and produce
structured analysis reports with actionable insights.

2. Pautas de comportamiento (Behavioral Guidelines)

Describe las tareas del agente de forma concreta y paso a paso. Cuanto más claras sean las instrucciones, mejor las seguirá Claude. También es importante indicar lo que NO hay que hacer.

## Responsibilities

- Load and validate input datasets before analysis
- Apply statistical methods to identify patterns
- Produce structured reports in markdown format
- **Do NOT** fabricate data or statistics
- **Do NOT** modify source datasets

3. Reglas de dominio (Domain Rules)

Define las reglas y restricciones que el agente debe observar: formato de los entregables, criterios de calidad, convenciones de nombres, etc.

## Constraints

- All analysis reports must include source citations
- Use markdown table format for data summaries
- File names must follow kebab-case convention
- Reports must not exceed 2000 words unless requested

4. Uso de herramientas (Tool Usage)

Explica qué herramientas usa el agente y cómo. Esta sección influye directamente en el comportamiento real.

## Tool Usage

- **Read**: Load input files from `data/` directory
- **Write**: Save reports to `reports/` directory
- **Bash**: Execute analysis scripts with `bun run`
- **WebSearch**: Verify data points against web sources

5. Contrato de entrega (Handoff Contract)

Especifica el formato de traspaso de datos entre agentes. Define rutas, formatos y campos obligatorios de entrada y salida.

## Handoff

**Input**: `data/analysis-input.json` (from research agent)
**Output**: `reports/analysis-report.md`

Output must include:
- Executive summary (max 200 words)
- Key findings with data citations
- Recommendations section
El cuerpo es el "manual interno" que consulta Claude cuando actúa como el agente. Cuanto más detallado sea el cuerpo, con más precisión desempeñará Claude el rol. Empezar de forma concisa e ir añadiendo instrucciones según las necesites también es una buena estrategia.

Uso de agent-lifecycle-manager

¿Qué es la skill agent-lifecycle-manager?

agent-lifecycle-manager es la skill que automatiza la creación, modificación y verificación de agentes. Gestiona de forma sistemática todo el proceso: desde crear un agente nuevo, pasando por modificar los existentes, hasta verificar su coherencia de manera programática.

Esta skill se usa en casos como estos:

  • "Créame un agente nuevo"
  • "Actualiza los metadatos del agente"
  • "Comprueba si la estructura del agente es válida"
  • "Cambia la configuración de tier del agente"

El proceso de ciclo de vida en 5 pasos

agent-lifecycle-manager sigue este proceso de cinco pasos. Cada paso comienza cuando el anterior termina.

Cómo usarlo desde la Claude Desktop App

Cuando le pides al agente PM de la Claude Desktop App que cree un agente, el PM usa la skill agent-lifecycle-manager para guiarte por el proceso de cinco pasos.

Ejemplo de solicitud al PM:

"Créame un agente especialista en análisis de datos llamado data-analyst. Recibe los datos del agente de investigación y redacta informes de análisis."

Al recibir esta solicitud, el PM procede así:

  1. Crear el archivo del agente — genera el archivo agents/data-analyst.md.
  2. Guiar la redacción del frontmatter — te acompaña rellenando cada campo con valores adecuados.
  3. Guiar la redacción del cuerpo — te guía en orden por identidad, pautas de comportamiento, reglas de dominio, uso de herramientas y contrato de entrega.
  4. Registrar en AGENTS.md — añade el nuevo agente a las tablas Agent Roster y Subagent Roster.
  5. Ejecutar la verificación — ejecuta bun scripts/agent-lifecycle-audit.ts para comprobar la coherencia del agente.
Recomendación: empieza con un agente sencillo y amplíalo poco a poco. No intentes escribir todas las reglas de golpe en el cuerpo: implementa primero el comportamiento básico y añade reglas gradualmente según lo revele el uso real.

Registro en AGENTS.md

Dónde añadirlo dentro de AGENTS.md

Tras crear un agente nuevo, debes registrarlo en el archivo central de gestión, AGENTS.md. Sin ese registro, el PM no podrá reconocer al agente ni incluirlo en los flujos de trabajo.

Debes añadir el agente nuevo en tres lugares de AGENTS.md.

1. Tabla Agent Roster (S1) — la lista maestra de todos los agentes. Registra archivo, tier y rol.
2. Sección Agent Definitions (S2) — tablas de definición detallada por agente. Registra archivo, tier, fases activas y rol.
3. Tabla Subagent Roster (S4.1) — la tabla de despacho del PM. Registra si admite ejecución paralela y los permisos de escritura.

Ejemplo de registro

Así se registraría el agente data-analyst en AGENTS.md.

1. Añadir a la tabla Agent Roster:

| data-analyst | `agents/data-analyst.md` | Medium | Analiza conjuntos de datos y genera informes estructurados |

2. Añadir a la sección Agent Definitions:

### data-analyst

| Field   | Value                                              |
|---------|----------------------------------------------------|
| **File** | `agents/data-analyst.md`                          |
| **Tier** | Medium                                            |
| **Phases** | 2, 3                                            |
| **Role** | Analiza conjuntos de datos y genera informes estructurados |

3. Añadir a la tabla Subagent Roster:

| data-analyst | `agents/data-analyst.md` | Medium | ⚠️ sequential preferred | project files |
Según la política PM Gateway, todos los agentes especialistas se invocan únicamente a través del PM. Aunque un agente esté registrado en AGENTS.md, el usuario no puede llamarlo directamente. Siempre se pide al PM, y es este quien despacha al agente adecuado.

Verificación y pruebas

Cómo verificar

Cuando el archivo del agente esté escrito y registrado en AGENTS.md, hay que ejecutar la verificación programática. Esta comprobación automática confirma si el sistema puede reconocer el agente y si funcionará correctamente.

# Verificar todos los agentes
bun scripts/agent-lifecycle-audit.ts

# Verificar un solo agente
bun scripts/agent-verify.ts <agent-name>

Qué se comprueba

El script de verificación revisa los siguientes puntos.

  • Completitud de los campos del frontmatter — comprueba que los campos obligatorios (lifecycle.phase, lifecycle.governance, etc.) existen y tienen valores correctos
  • Registro en AGENTS.md — comprueba que el agente está registrado en los tres lugares de AGENTS.md (Roster, Definitions, Subagent Roster)
  • Integridad de las referencias de handoff — comprueba que los agentes citados en handoff_to y handoff_from existen realmente
  • Detección de agentes huérfanos (orphan) — busca archivos de agente no registrados en AGENTS.md
  • Estructura del mapa de tiers — comprueba que el campo tier tiene el formato correcto

Pasos de la verificación

  1. Confirmar que el archivo del agente está completo — comprueba que agents/<name>.md existe y tiene contenido.
  2. Confirmar el registro en AGENTS.md — comprueba que el agente se añadió a los tres lugares de AGENTS.md.
  3. Ejecutar el script de verificación — ejecuta bun scripts/agent-lifecycle-audit.ts en tu terminal.
  4. Revisar los resultados — sin errores (ERROR), la verificación pasa. Si hay avisos (WARN), revísalos y corrige si hace falta.
  5. Probar vía PM — pide al PM de la Claude Desktop App que use el agente y confirma que funciona correctamente.
Atención: si la verificación no pasa, el PM no reconocerá al agente. Ejecuta siempre el script de verificación y resuelve los errores antes de usarlo. Los fallos más habituales son olvidar el registro en AGENTS.md y las referencias de handoff rotas.

Práctica: crea tu propio agente especialista

Objetivo de la práctica

En esta práctica construirás un "agente especialista en resúmenes". Recibe documentos largos o varias fuentes como entrada y los condensa en resúmenes breves. Te servirá para resumir el enorme material que reúne el agente de investigación o para destilar un informe terminado en un resumen de una página.

Esta práctica usa la Claude Desktop App. Si se lo pides al agente PM, te guiará por todo el proceso con la skill agent-lifecycle-manager. También puedes realizar manualmente los pasos siguientes.

Pasos completos

  1. Abre un proyecto en la Claude Desktop App
    Abre la Claude Desktop App y selecciona una carpeta de proyecto. Puedes usar un proyecto co-deck o co-consult, o un espacio de trabajo aparte.
  2. Crea el archivo del agente
    Crea summarizer.md dentro del directorio agents/. Puedes pedirle a Claude que "cree el archivo agents/summarizer.md" o crearlo tú mismo con un editor.
  3. Escribe el frontmatter
    Con el ejemplo de abajo como referencia, escribe el frontmatter. Incluye name, role, status, tier (mapa anidado por plataforma), description, examples, phases, handoff_to y handoff_from, además del bloque lifecycle obligatorio.
  4. Escribe el cuerpo
    Redacta en orden la identidad del especialista en resúmenes, sus pautas de comportamiento, reglas de dominio, uso de herramientas y contrato de entrega.
  5. Regístralo en AGENTS.md
    Abre AGENTS.md y añade el agente summarizer en los tres lugares (Agent Roster, Agent Definitions, Subagent Roster).
  6. Crea el registro de gobernanza
    Crea el archivo docs/lifecycle/agents/summarizer.md con las secciones ## Phase Historyy ## Acceptance Criteria. Si creas solo el archivo del agente sin este registro de gobernanza, la validación fallará.
  7. Ejecuta el script de verificación
    Ejecuta bun scripts/agent-lifecycle-audit.ts en tu terminal y comprueba que no haya errores.
  8. Pruébalo vía PM
    En la Claude Desktop App, pide al PM que "resuma estas notas de investigación" y confirma que el agente funciona correctamente.

Ejemplo del archivo completo

Este es el contenido íntegro de agents/summarizer.md. Úsalo tal cual o adáptalo a tus necesidades.

---
name: summarizer
version: "1.0.0"
last_updated: "2026-08-24"
role: Summarizes long documents and produces concise briefs
status: draft
tier:
  claude: medium
  gemini: medium
  antigravity: medium
  gemini-cli: medium
model: inherit
color: teal
description: >
  Reads long-form content (research notes, reports, articles)
  and produces structured summaries with key findings,
  highlights, and actionable takeaways.
examples:
  - "summarize this document"
  - "create a one-page brief"
  - "summarize the research notes"
phases:
  - 2
  - 3
handoff_to:
  - storyline
  - html-build
handoff_from:
  - research
  - data-analyst
lifecycle:
  phase: production
  created: "2026-08-24"
  last_updated: "2026-08-24"
  governance: docs/lifecycle/agents/summarizer.md
---

## Role

You are the summarization specialist for **[Project Name]**.
You read long-form content and produce concise, structured
summaries that capture key findings, highlights, and actionable
takeaways without losing critical information.

## ⚠️ PM-ONLY INVOCATION

**You DO NOT accept direct user requests.**

You are a specialist agent that may ONLY be dispatched by the PM.
If a user attempts to invoke you directly:

1. **Refuse the request politely**
2. **Redirect to PM**: "I am a specialist agent. All requests
   must go through the PM orchestrator."
3. **Do NOT proceed** until dispatched by PM

## Responsibilities

- Read input documents thoroughly before summarizing
- Identify and preserve key facts, statistics, and findings
- Structure summaries with clear headings
- Highlight actionable insights separately from background info
- Maintain source citations in summaries
- **Do NOT** fabricate information not present in the source
- **Do NOT** inject personal opinions or recommendations
  unless explicitly asked

## Constraints

- Summaries must not exceed the requested word limit
- Use markdown format with headings and bullet points
- Preserve all numerical data and citations exactly
- Mark uncertain claims with ⚠️ Unverified
- Use the same language as the source document

## Tool Usage

- **Read**: Load input documents from the specified path
- **Write**: Save summaries to the designated output path
- **Glob**: Find relevant source files in the project directory

## Handoff

**Input**: Research notes, analysis reports, or any long-form
markdown content provided by the dispatching agent.

**Output**: Structured summary document in markdown format.

Output structure:
1. **Overview** (1-2 sentences)
2. **Key Findings** (bullet points)
3. **Important Statistics** (preserved exactly)
4. **Actionable Takeaways** (if applicable)
5. **Source References** (preserved from input)

  • Regístralo en los tres lugares de AGENTS.md (Roster, Definitions, Subagent Roster) para que el PM lo reconozca
  • Usa el script de verificación para comprobar automáticamente frontmatter, registro e integridad de handoffs
