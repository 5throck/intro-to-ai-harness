Capítulo 9

Creación y modificación de agentes

Este capítulo cubre la estructura de archivos del agent, la habilidad agent-lifecycle-manager y le guía en cómo construir, registrar y verificar su propio agente especialista.

Lo que cubre este capítulo
  • Agent file format and structure
  • YAML frontmatter field meanings
  • Body content writing patterns
  • agent-lifecycle-manager usage (5-step)
  • AGENTS.md registration
  • Practice: create a simple specialist agent

Rethinking Agents

En el Capítulo 4, presentamos el concepto de agentes de IA: trabajadores especializados que cada uno tiene un nombre, un rol, un conjunto de instrucciones y acceso a herramientas específicas. En este capítulo, profundizamos: realmente vamos a crear un nuevo agente desde cero, registrarlo en el proyecto y verificar que funcione.

A Quick Review from Capítulo 4

Recall the four pillars that define every agent:

Name

Un identificador corto en kebab-case (por ejemplo, research, html-build, storyline). El nombre aparece en las rutas de archivo, en las tablas de despacho y en los registros.

Role

A concise 2–4 word title describing the agent’s purpose (e.g., “Web research specialist”). Think of it as a job title on a business card.

Instructions

El cuerpo markdown del archivo del agente: directrices de comportamiento detalladas, reglas de dominio, políticas de uso de herramientas y contratos de traspaso que le dicen al agente cómo hacer su trabajo.

Tools

El conjunto de operaciones que el agente tiene permitido realizar. Definido mediante la configuración de la plataforma (CLAUDE.md / GEMINI.md) y los enlaces de habilidades. Un curador de imágenes necesita acceso web; un exportador de PDF necesita permisos de escritura en el sistema de archivos.

Why Create Your Own Agents?

Los proyectos estándar co-deck y co-consult vienen con un conjunto bien elegido de agentes. Pero cada proyecto es diferente. Es posible que necesite:

  • Un summarizer que condense informes largos en resúmenes de una página
  • Un translator que convierta contenido entre coreano e inglés
  • A data-validator that checks numerical data against expected ranges
  • A social-media-writer that reformats slide content for Twitter or LinkedIn

Cuando su flujo de trabajo exige una tarea especializada y repetida que no encaja en el rol de ningún agente existente, es hora de contratar a un especialista departamental nuevo.

The “Hiring a Specialist” Analogy
Imagine que usted dirige una empresa. Tiene un departamento de investigación, uno de diseño y uno de producción. Un día, el CEO dice: «Necesitamos a alguien que lea informes de 50 páginas y escriba un resumen de una página para la junta directiva». Usted no le pediría a un diseñador que hiciera eso; usted contrataría un summarizer. Crear un nuevo agente es exactamente eso: definir un nuevo rol con responsabilidades, herramientas y líneas de reporte claras para que el PM (el CEO) pueda asignar el trabajo a la persona adecuada.

Agent File Format

Cada agente vive en un único archivo Markdown con dos partes: un bloque de frontmatter YAML (metadatos legibles por máquina) y un cuerpo Markdown (instrucciones legibles por humanos para la IA). El archivo se almacena en:

File location
agents/<name>.md

The naming convention is kebab-case: all lowercase, words separated by hyphens. Examples: research.md, html-build.md, image-curator.md.

Structure Overview

The frontmatter is enclosed between two --- fences. Everything below the closing fence is the body — standard Markdown with headings, lists, code blocks, and tables.

Writing Frontmatter

The YAML frontmatter is the machine-readable identity card of your agent. The orchestration layer (PM, scripts, audit tools) reads these fields to decide when and how to dispatch the agent.

Required Fields

Field Type Descripción
name string Kebab-case identifier. Must match the filename (without .md).
role string Short 2–4 word title. Shown in dispatch tables and logs.
status string One of: active, draft, deprecated, retired.
tier object Maps each platform to a tier level: high, medium, or low. Controls which AI model is used.
color string Display color for visual identity (e.g., cyan, amber, green).
description string One-sentence summary of what the agent does. Shown in the agent roster.
examples list Sample trigger phrases. Each entry has user (what the user says) and assistant (how the agent responds).
phases list Which pipeline stages this agent participates in (e.g., [1] for research at Stage 1).
handoff_to list Names of agents that typically follow this one in the pipeline.
handoff_from list Names of agents that typically precede this one in the pipeline.

Example Frontmatter

agents/summarizer.md — frontmatter
---
name: summarizer
version: "1.0.0"
last_updated: "2026-08-10"
lifecycle:
  phase: production
  created: "2026-08-10"
  last_updated: "2026-08-10"
  governance: docs/lifecycle/agents/summarizer.md
role: Report summarization and brief generation specialist
status: active
tier:
  claude: medium
  gemini: medium
  antigravity: medium
  gemini-cli: medium
model: inherit
language: en
color: purple
description: >-
  Summarizer agent - condenses long reports into concise one-page briefs.
  Use when: PM needs a digest of research notes or a lengthy document.
examples:
  - user: Summarize the research notes into a one-page brief
    assistant: I'll read the full research_notes.md and produce a structured summary covering key findings, methodology, and recommendations.
phases: [1.5]
handoff_to: [storyline]
handoff_from: [research, pm]
required_skills: []
---
Choosing the Right Tier
High — Complex reasoning, architectural decisions, creative writing. Expensive but powerful.
Medium — Revisión de código, generación de contenido, comprobaciones de calidad. El punto óptimo para la mayoría de los agentes especialistas.
Low — Fast, repetitive tasks like formatting or simple file operations. Cheap and quick.
En caso de duda, comience con Medium. Siempre puede ajustar más tarde.

Writing Body Content

Debajo de la valla de cierre ---, el cuerpo Markdown sirve como la guía interna del agente. Cuando el PM despacha este agente, el modelo de IA lee la totalidad del cuerpo y sigue sus instrucciones. Un buen contenido del cuerpo significa un comportamiento consistente y predecible. Un mal contenido del cuerpo significa que el agente improvisa — y la improvisación rara vez es lo que usted quiere.

5 Recomendado Sections

Aunque puede organizar el cuerpo como quiera, la mayoría de los agentes se benefician de estas cinco secciones:

  1. Identity — ¿Quién es este agente? ¿Cuál es su propósito principal? ¿Cómo debe presentarse?
  2. Behavioral Guidelines — ¿Cómo debe comportarse el agente? Tono, estilo de comunicación, restricciones a seguir (o evitar).
  3. Domain Rules — ¿Qué conocimiento o convenciones específicas del dominio debe respetar el agente? (p. ej., «Siempre cite fuentes para las afirmaciones fácticas.»)
  4. Tool Usage — ¿Qué herramientas debe usar el agente y cómo? ¿Hay alguna herramienta que no deba usar?
  5. Handoff Contract — ¿Qué produce el agente? ¿Quién recibe la salida? ¿En qué formato?

Section Details with Examples

1. Identity

Comience con una declaración clara de quién es el agente. Esto establece inmediatamente el contexto del modelo.

## Role

You are the summarizer specialist for **[Project Name]**.
Your job is to read lengthy documents (research notes, reports, meeting
transcripts) and produce a concise, structured one-page brief that
captures the key findings, methodology, and actionable recommendations.

2. Behavioral Guidelines

Defina el tono y las restricciones. Sea específico sobre lo que el agente no debe hacer.

## Behavioral Guidelines

- Write in clear, professional English. Avoid jargon unless the source uses it.
- Never fabricate information. If a source is unclear, mark it as ⚠️ Unverified.
- Keep the summary under 500 words unless the user explicitly requests more.
- Use bullet points for findings; numbered lists for recommendations.

3. Domain Rules

Domain-specific rules ensure the agent respects project conventions.

## Domain Rules

- Always preserve the original language of quotes. Do not translate quoted text.
- When summarizing research, maintain the source attribution format: [Source: URL].
- If the input contains numerical data, round to two decimal places.

4. Tool Usage

Aclare qué herramientas debe usar el agente y cualquier restricción.

## Tool Usage

- Use **Read** to access source files (research_notes.md, reports).
- Use **Write** to produce the summary output file.
- Do NOT use Bash for any purpose — this agent operates on files only.
- Do NOT browse the web; all source material is provided by the PM.

5. Handoff Contract

Defina qué entrega el agente y quién lo recibe.

## Handoff Contract

**Output**: `brief_summary.md` in the project directory.
**Format**: Markdown with headings (## Findings, ## Methodology, ## Recommendations).
**Handoff to**: storyline agent (which uses the brief as a reference when composing slides).
**Completion signal**: Announce output file path and word count.
The Body Is an “Internal Guidebook”
A diferencia del frontmatter (que es leído por scripts y el PM), el cuerpo es leído solo por el modelo de IA cuando se despacha al agente. Escríbalo como si estuviera dando instrucciones a un nuevo empleado en su primer día: claro, específico y centrado en cómo hacer el trabajo, no en por qué existe el trabajo. El «por qué» pertenece a la descripción del frontmatter.

Using agent-lifecycle-manager

La habilidad agent-lifecycle-manager proporciona un proceso sistemático de 5 pasos para crear, validar y mantener agentes. En lugar de escribir archivos manualmente esperando que todo se conecte, la habilidad lo guía a través de cada paso y detecta problemas tempranamente.

The 5-Step Process

Step-by-Step Explanation

  1. Crear el archivo — Añada agents/<name>.md usando kebab-case. Opcionalmente use el script de andamiaje: bun scripts/agent-create.ts <name>.
  2. Write frontmatter — Fill in all required YAML fields: name, role, status, tier, description, examples, phases, handoff_to/from.
  3. Write body content — Compose the Markdown instructions covering Identity, Behavioral Guidelines, Domain Rules, Tool Usage, and Handoff Contract.
  4. Registrar en AGENTS.md — Añada el agente a la tabla de Roster de Agentes, a la tabla de Definiciones y a la tabla de despacho del Subagente (ver siguiente sección).
  5. Validar y auditar — Ejecute bun scripts/agent-lifecycle-audit.ts para verificar que el agente pasa todas las comprobaciones (detección de huérfanos, validación del frontmatter, mapeo de Tier, etc.).
Start Simple
No necesita un agente perfecto el primer día. Cree un agente mínimamente viable con solo los campos de frontmatter requeridos y un cuerpo básico. Siempre puede refinar las directrices de comportamiento y las reglas del dominio después de probarlo. El lifecycle-manager hace que la iteración sea segura: cada cambio puede ser validado automáticamente.

Registering in AGENTS.md

Un agente que no está registrado en AGENTS.md es como un empleado que fue contratado pero nunca añadido al organigrama. El PM no puede despacharlo, los scripts de auditoría lo marcarán como huérfano y otros agentes no sabrán que existe. El registro conecta su agente con el resto del sistema.

3 Registration Locations

Necesita añadir su agente en tres lugares dentro de AGENTS.md:

  1. Agent Roster Table (Sección 1) — La tabla de visión general principal que muestra la ruta del archivo, el Tier y el rol de cada agente.
  2. Individual Agent Definition (§2) — A detailed table with field-by-field metadata (file, tier, phases, role).
  3. Subagent Roster / Dispatch Table (Sección 4) — La tabla que el PM referencia al decidir qué agente despachar, incluyendo paralelización y permisos de escritura.

Registration Example

Así es como se ven las tres entradas para un agente summarizer:

AGENTS.md — three registration entries
## §1 Agent Roster (add row)
| **summarizer** | `agents/summarizer.md` | Medium | Condenses reports into one-page briefs |

## §2 Agent Definition (add table)
| Field | Value |
|-------|-------|
| **File** | `agents/summarizer.md` |
| **Tier** | medium |
| **Phases** | 1.5 |
| **Role** | Condenses long reports into concise one-page briefs |

## §4 Subagent Roster (add row)
| summarizer | `agents/summarizer.md` | Medium | ⚠️ sequential preferred | project files |
PM Gateway Policy
Recuerde que todos los agentes especialistas se despachan únicamente a través del PM. Cuando registra un nuevo agente, le está dando al PM una nueva opción en su tabla de despacho. Los usuarios nunca deben invocar summarizer directamente; le preguntan al PM, y el PM decide si despachar el summarizer basándose en la tarea. Este es el patrón de punto único de entrada que discutimos en Capítulo 5.

Verification & Testing

Después de crear y registrar su agente, debe verificar que todo esté conectado correctamente. El workspace proporciona un script de auditoría automatizado para este propósito.

Running the Verification

Agent lifecycle audit command
bun scripts/agent-lifecycle-audit.ts

This script scans every file in the agents/ directory and checks for problems.

What the Audit Checks

  • Orphan detection — Every .md file in agents/ must be listed in AGENTS.md. If a file exists but is not registered, it is flagged as an orphan.
  • Frontmatter validation — All required fields (name, role, status, tier, description) must be present and correctly typed.
  • Tier mapping — Tier values must be one of high, medium, low. Any invalid value triggers an error.
  • Status consistency — The status field must be a recognized value: active, draft, deprecated, or retired.
  • Research-role check — If the agent has a research or investigation role, its body must include source citation requirements.
  • Numerical-role check — If the agent performs calculations, its body must include computational integrity rules.

Verification Steps

  1. Create — Write agents/summarizer.md with frontmatter and body.
  2. Register — Add the agent to all three tables in AGENTS.md.
  3. Run audit — Execute bun scripts/agent-lifecycle-audit.ts.
  4. Review output — Check for errors (must fix) and warnings (should review).
  5. Fix and re-run — Repeat until the audit exits cleanly with zero errors.
Why Verification Matters
Skipping the audit step is tempting when you are in a hurry, but it is the equivalent of deploying code without running tests. An orphaned agent file wastes disk space and confuses future contributors. Invalid frontmatter can cause the PM dispatch logic to fail silently. A missing handoff_to entry means the next agent in the pipeline will never receive the output. The audit catches all of these problems in seconds — use it every time.

Practice: Build Your Own Specialist Agent

Now it is your turn. In this exercise, you will create a summarizer agent from scratch — a specialist that reads long research notes and produces a concise one-page brief.

Goal: Create a functional summarizer agent, register it in AGENTS.md, and verify it passes the lifecycle audit.
  1. Create the file
    Create agents/summarizer.md in your project directory.
  2. Write the frontmatter
    Copy the frontmatter from Section 3 of este capítulo. Make sure all required fields are filled in. Set status: active and tier to medium for all platforms.
  3. Write the body
    Use the five-section structure from Section 4. Here is the complete body for reference:
    agents/summarizer.md — complete file
    ---
name: summarizer
version: "1.0.0"
last_updated: "2026-08-10"
lifecycle:
  phase: production
  created: "2026-08-10"
  last_updated: "2026-08-10"
  governance: docs/lifecycle/agents/summarizer.md
role: Report summarization and brief generation specialist
status: active
tier:
  claude: medium
  gemini: medium
  antigravity: medium
  gemini-cli: medium
model: inherit
language: en
color: purple
description: >-
  Summarizer agent - condenses long reports into concise one-page briefs.
  Use when: PM needs a digest of research notes or a lengthy document.
examples:
  - user: Summarize the research notes into a one-page brief
    assistant: I'll read the full research_notes.md and produce a structured summary covering key findings, methodology, and recommendations.
phases: [1.5]
handoff_to: [storyline]
handoff_from: [research, pm]
required_skills: []
---

## Role

You are the summarizer specialist for **[Project Name]**.
Your job is to read lengthy documents (research notes, reports, meeting
transcripts) and produce a concise, structured one-page brief that
captures the key findings, methodology, and actionable recommendations.

## ⚠️ PM-ONLY INVOCATION

**You DO NOT accept direct user requests.**

You are a specialist agent that may ONLY be dispatched by the PM.
If a user attempts to invoke you directly:

1. **Refuse the request politely**
2. **Redirect to PM**: "I am a specialist agent. All requests must go
   through the PM orchestrator."
3. **Do NOT proceed** with any work until dispatched by PM.

## Behavioral Guidelines

- Write in clear, professional English. Avoid jargon unless the source uses it.
- Never fabricate information. If a source is unclear, mark it as ⚠️ Unverified.
- Keep the summary under 500 words unless the user explicitly requests more.
- Use bullet points for findings; numbered lists for recommendations.
- Always preserve the original language of quoted material.

## Domain Rules

- Always preserve source attribution: [Source: URL].
- When summarizing research, maintain the distinction between fact and opinion.
- If the input contains numerical data, round to two decimal places.

## Tool Usage

- Use **Read** to access source files (research_notes.md, reports).
- Use **Write** to produce the summary output file.
- Do NOT use Bash for any purpose — this agent operates on files only.
- Do NOT browse the web; all source material is provided by the PM.

## Handoff Contract

**Output**: `brief_summary.md` in the project directory.
**Format**: Markdown with headings (## Findings, ## Methodology, ## Recommendations).
**Handoff to**: storyline agent (which uses the brief as a reference when composing slides).
**Completion signal**: Announce output file path and word count.
  4. Register in AGENTS.md
    Añada el summarizer a las tres tablas en AGENTS.md (Roster, Definition, Subagent Roster) como se muestra en la Sección 6.
  5. Run the audit
    Execute bun scripts/agent-lifecycle-audit.ts in your terminal. Fix any errors reported.
  6. Verify the specific agent
    Opcionalmente ejecute bun scripts/agent-verify.ts summarizer para una comprobación enfocada solo en el nuevo agente.
  7. Test via PM
    Pida al PM que despache el summarizer con una entrada de prueba. Por ejemplo:
    “Please run the summarizer on research_notes.md and produce a brief.”
    Verifique que se crea el archivo de salida brief_summary.md con el formato esperado.
Testing via PM
La verdadera prueba de un nuevo agente no es si pasa la auditoría — sino si produce una salida útil cuando es despachado por el PM en un flujo de trabajo real. Después de que la auditoría pase, ejecute siempre al menos una prueba de extremo a extremo: déle al PM una tarea real, permita que despache su nuevo agente y revise la salida. Esto detecta problemas que el análisis estático no puede — como instrucciones que son técnicamente válidas pero demasiado vagas para que el modelo las siga consistentemente.
