エージェントの作成と変更

本章ではエージェントファイル構造、agent-lifecycle-managerスキルを解説し、独自のスペシャリストエージェントの構築、登録、検証を実際に体験します。

エージェントを再考する

第4章で、AIエージェントの概念を紹介しました: それぞれが名前、役割、一連の指示、特定のツールへのアクセスを持つ専門ワーカーです。本章ではさらに深く掘り下げます — 実際に新しいエージェントをゼロから作成し、プロジェクトに登録し、正しく動作することを検証します。

第4章のおさらい

すべてのエージェントを定義する4つの柱を思い出してください。

名前

短いkebab-caseの識別子（例: research、html-build、storyline）。ファイルパス、ディスパッチテーブル、ログエントリに表示されます。

役割

エージェントの目的を説明する簡潔な2〜4語のタイトル（例: 「Webリサーチスペシャリスト」）。名刺の肩書きのように考えてください。

指示

エージェントファイルのMarkdown本文 — 詳細な動作ガイドライン、ドメインルール、ツール使用ポリシー、引き継ぎコントラクトで、エージェントに作業の方法を指示します。

ツール

エージェントが実行を許可された操作のセット。プラットフォーム設定（CLAUDE.md / GEMINI.md）とスキルバインディングを通じて定義されます。画像キュレーターにはWebアクセスが必要、PDFエクスポーターにはファイルシステム書き込み権限が必要です。

独自エージェントを作成する理由

標準のco-deckやco-consultプロジェクトには適切に選ばれたエージェントセットが用意されています。しかし、プロジェクトごとに異なります。次のようなエージェントが必要になるかもしれません。

  • 長いレポートを1ページのブリーフに要約するsummarizer
  • コンテンツを韓国語と英語の間で変換するtranslator
  • 数値データを期待される範囲に対して検証するdata-validator
  • スライドコンテンツをTwitterやLinkedIn用に再フォーマットするsocial-media-writer

ワークフローが既存のエージェントの役割に合わない反復的で専門的なタスクを必要とする場合、新しい部署の専門家を採用する時です。

「専門家の採用」の例え
会社を経営していると想像してください。リサーチ部門、デザイン部門、制作部門があります。ある日、CEOがこう言います: 「50ページのレポートを読んで1ページの要約を取締役会向けに書く人が必要だ。」デザイナーにこれを頼むことはありません — 要約者を採用します。新しいエージェントの作成はまさにこれです: PM（CEO）が適切な人に仕事をディスパッチできるように、明確な責任、ツール、報告ラインを持つ新しい役割を定義することです。

エージェントファイル形式

すべてのエージェントは、YAMLフロントマターブロック（機械可読メタデータ）とMarkdownボディ（AI向けの human-readable 指示）の2つの部分を持つ単一のMarkdownファイルに存在します。ファイルは次の場所に保存されます。

ファイルの場所
agents/<name>.md

命名規則はkebab-case: すべて小文字、ハイフン区切り。例: research.md、html-build.md、image-curator.md。

構造の概要

フロントマターは2つの---フェンスで囲まれます。終了フェンスの下のすべてがボディ — 見出し、リスト、コードブロック、テーブルを持つ標準Markdownです。

フロントマターの記述

YAMLフロントマターはエージェントの機械可読なIDカードです。オーケストレーションレイヤー（PM、スクリプト、監査ツール）はこれらのフィールドを読んで、エージェントをいつどのようにディスパッチするかを決定します。

必須フィールド

フィールド 型 説明
name string kebab-case識別子。ファイル名（.mdなし）と一致する必要がある。
role string 2〜4語の短いタイトル。ディスパッチテーブルやログに表示される。
status string 次のいずれか: active、draft、deprecated、retired。
tier object 各プラットフォームをティアレベルにマッピング: high、medium、またはlow。使用するAIモデルを制御。
color string ビジュアルID用の表示色（例: cyan、amber、green）。
description string エージェントの動作を説明する1文。エージェントロスターに表示される。
examples list トリガーフレーズのサンプル。各エントリにuser（ユーザーの発言）とassistant（エージェントの応答）がある。
phases list このエージェントが参加するパイプラインステージ（例: Stage 1のリサーチなら[1]）。
handoff_to list パイプラインでこのエージェントの後に続くエージェントの名前。
handoff_from list パイプラインでこのエージェントの前に来るエージェントの名前。

フロントマターの例

agents/summarizer.md — フロントマター
---
name: summarizer
version: "1.0.0"
last_updated: "2026-08-10"
lifecycle:
  phase: production
  created: "2026-08-10"
  last_updated: "2026-08-10"
  governance: docs/lifecycle/agents/summarizer.md
role: Report summarization and brief generation specialist
status: active
tier:
  claude: medium
  gemini: medium
  antigravity: medium
  gemini-cli: medium
model: inherit
language: en
color: purple
description: >-
  Summarizer agent - condenses long reports into concise one-page briefs.
  Use when: PM needs a digest of research notes or a lengthy document.
examples:
  - user: Summarize the research notes into a one-page brief
    assistant: I'll read the full research_notes.md and produce a structured summary covering key findings, methodology, and recommendations.
phases: [1.5]
handoff_to: [storyline]
handoff_from: [research, pm]
required_skills: []
---
適切なティアの選択
High — 複雑な推論、アーキテクチャの決定、創造的な執筆。高価ですが強力。
Medium — コードレビュー、コンテンツ生成、品質チェック。大多数のスペシャリストエージェントに最適。
Low — フォーマットや簡単なファイル操作などの高速で反復的なタスク。安価で迅速。
迷った場合はMediumから始めてください。後でいつでも調整できます。

ボディコンテンツの記述

終了---フェンスの下にあるMarkdownボディは、エージェントの内部ガイドブックとして機能します。PMがこのエージェントをディスパッチすると、AIモデルがボディ全体を読み、指示に従います。良いボディコンテンツは一貫性のある予測可能な動作を意味します。悪いボディコンテンツはエージェントに即興をさせます — そして即興はめったに望ましいものではありません。

推奨される5つのセクション

ボディの構成は自由ですが、ほとんどのエージェントは次の5つのセクションで恩恵を受けます。

  1. アイデンティティ — このエージェントは誰か？コア目的は何か？どう自己紹介すべきか？
  2. 動作ガイドライン — エージェントはどう振る舞うべきか？トーン、コミュニケーションスタイル、従う（または避ける）べき制約。
  3. ドメインルール — エージェントが尊重すべきドメイン固有の知識や慣習？（例: 「事実的主張には常に情報源を引用すること。」）
  4. ツール使用 — どのツールを使用すべきか、またその方法？使用してはいけないツールは？
  5. 引き継ぎコントラクト — エージェントは何を生成するか？誰が受け取るか？どの形式で？

セクションの詳細と例

1. アイデンティティ

エージェントが誰であるかを明確な文で始めます。これによりモデルのコンテキストがすぐに設定されます。

## Role

You are the summarizer specialist for **[Project Name]**.
Your job is to read lengthy documents (research notes, reports, meeting
transcripts) and produce a concise, structured one-page brief that
captures the key findings, methodology, and actionable recommendations.

2. 動作ガイドライン

トーンと制約を定義します。エージェントがしてはいけないことを具体的にします。

## Behavioral Guidelines

- Write in clear, professional English. Avoid jargon unless the source uses it.
- Never fabricate information. If a source is unclear, mark it as ⚠️ Unverified.
- Keep the summary under 500 words unless the user explicitly requests more.
- Use bullet points for findings; numbered lists for recommendations.

3. ドメインルール

ドメイン固有のルールにより、エージェントがプロジェクトの慣習を尊重することが保証されます。

## Domain Rules

- Always preserve the original language of quotes. Do not translate quoted text.
- When summarizing research, maintain the source attribution format: [Source: URL].
- If the input contains numerical data, round to two decimal places.

4. ツール使用

エージェントが使用すべきツールと制限を明確にします。

## Tool Usage

- Use **Read** to access source files (research_notes.md, reports).
- Use **Write** to produce the summary output file.
- Do NOT use Bash for any purpose — this agent operates on files only.
- Do NOT browse the web; all source material is provided by the PM.

5. 引き継ぎコントラクト

エージェントが何を成果物として提供し、誰が受け取るかを定義します。

## Handoff Contract

**Output**: `brief_summary.md` in the project directory.
**Format**: Markdown with headings (## Findings, ## Methodology, ## Recommendations).
**Handoff to**: storyline agent (which uses the brief as a reference when composing slides).
**Completion signal**: Announce output file path and word count.
ボディは「内部ガイドブック」
フロントマター（スクリプトやPMが読み取る）とは異なり、ボディはエージェントがディスパッチされた時にAIモデルだけが読み取ります。最初の日の新しい従業員に向けた指示を書くように記述してください: 明確、具体的、仕事が存在する理由ではなく方法に焦点を当てます。「理由」はフロントマターのdescriptionに属します。

agent-lifecycle-managerの使用

agent-lifecycle-managerスキルは、エージェントの作成、検証、保守のための体系的な5ステッププロセスを提供します。手動でファイルを書いてすべてが正しく繋がっていることを祈るのではなく、スキルが各ステップをガイドし、問題を早期に発見します。

5ステッププロセス

ステップバイステップの解説

  1. ファイルを作成 — kebab-caseでagents/<name>.mdを追加。オプションでスキャフォールディングスクリプトを使用: bun scripts/agent-create.ts <name>。
  2. フロントマターを記述 — すべての必須YAMLフィールドを記入: name、role、status、tier、description、examples、phases、handoff_to/from。
  3. ボディコンテンツを記述 — アイデンティティ、動作ガイドライン、ドメインルール、ツール使用、引き継ぎコントラクトをカバーするMarkdown指示を作成。
  4. AGENTS.mdに登録 — エージェントロスターテーブル、定義テーブル、サブエージェントロスターディスパッチテーブルに追加（次のセクション参照）。
  5. 検証と監査 — bun scripts/agent-lifecycle-audit.tsを実行して、エージェントがすべてのチェック（孤立検出、フロントマター検証、ティアマッピングなど）に合格することを確認。
シンプルに始める
初日から完璧なエージェントは必要ありません。必須のフロントマーターフィールドと基本的なボディだけを持つ最小限の実行可能エージェントを作成してください。テスト後に動作ガイドラインとドメインルールを洗練できます。ライフサイクルマネージャーは反復を安全にします: すべての変更は自動的に検証できます。

AGENTS.mdへの登録

AGENTS.mdに登録されていないエージェントは、採用されたが組織図に追加されなかった従業員のようなものです。PMはディスパッチできず、監査スクリプトは孤立ファイルとしてフラグを立て、他のエージェントはその存在を知りません。登録によりエージェントはシステムの他の部分に接続されます。

3つの登録場所

AGENTS.md内の3つの場所にエージェントを追加する必要があります。

  1. エージェントロスターテーブル（§1） — すべてのエージェントのファイルパス、ティア、役割を示すメインの概要テーブル。
  2. 個別エージェント定義（§2） — フィールドごとのメタデータ（ファイル、ティア、フェーズ、役割）を持つ詳細テーブル。
  3. サブエージェントロスターディスパッチテーブル（§4） — PMがどのエージェントをディスパッチするか決定する際に参照するテーブル。並行可能性と書き込み権限を含む。

登録の例

summarizerエージェントの3つのエントリの例です。

AGENTS.md — 3つの登録エントリ
## §1 Agent Roster (行を追加)
| **summarizer** | `agents/summarizer.md` | Medium | レポートを1ページのブリーフに要約 |

## §2 Agent Definition (テーブルを追加)
| Field | Value |
|-------|-------|
| **File** | `agents/summarizer.md` |
| **Tier** | medium |
| **Phases** | 1.5 |
| **Role** | 長いレポートを簡潔な1ページのブリーフに要約 |

## §4 Subagent Roster (行を追加)
| summarizer | `agents/summarizer.md` | Medium | ⚠️ 順番優先 | プロジェクトファイル |
PM Gatewayポリシー
すべてのスペシャリストエージェントはPMを通じてのみディスパッチされることを覚えておいてください。新しいエージェントを登録すると、PMのディスパッチテーブルに新しいオプションを追加します。ユーザーはsummarizerを直接呼び出すべきではありません — PMに依頼し、PMがタスクに基づいてsummarizerをディスパッチするかどうかを決定します。これが第5章で議論した単一エントリポイントパターンです。

検証とテスト

エージェントを作成して登録した後、すべてが正しく接続されていることを検証する必要があります。ワークスペースにはこの目的のための自動監査スクリプトが用意されています。

検証の実行

エージェントライフサイクル監査コマンド
bun scripts/agent-lifecycle-audit.ts

このスクリプトはagents/ディレクトリ内のすべてのファイルをスキャンし、問題をチェックします。

監査がチェックする項目

  • 孤立検出 — agents/内のすべての.mdファイルがAGENTS.mdに記載されている必要がある。ファイルが存在するが登録されていない場合、孤立としてフラグが立てられる。
  • フロントマター検証 — すべての必須フィールド（name、role、status、tier、description）が存在し、正しく型付けられている必要がある。
  • ティアマッピング — ティア値はhigh、medium、lowのいずれかでなければならない。無効な値はエラーをトリガーする。
  • ステータス整合性 — ステータスフィールドは認識された値である必要がある: active、draft、deprecated、またはretired。
  • リサーチ役割チェック — エージェントがリサーチや調査の役割を持つ場合、ボディに情報源引用要件を含める必要がある。
  • 数値役割チェック — エージェントが計算を実行する場合、ボディに計算完全性ルールを含める必要がある。

検証ステップ

  1. 作成 — フロントマターとボディでagents/summarizer.mdを作成。
  2. 登録 — AGENTS.mdの3つのテーブルすべてにエージェントを追加。
  3. 監査を実行 — bun scripts/agent-lifecycle-audit.tsを実行。
  4. 出力をレビュー — エラー（修正必須）と警告（確認推奨）をチェック。
  5. 修正して再実行 — 監査がエラーゼロでクリーンに終了するまで繰り返す。
検証が重要な理由
急いでいると監査ステップをスキップしたくなりますが、これはテストなしでコードをデプロイするのと同じです。孤立したエージェントファイルはディスクスペースを浪費し、将来の貢献者を混乱させます。無効なフロントマターはPMのディスパッチロジックがサイレントに失敗する原因になります。handoff_toエントリの欠落はパイプラインの次のエージェントが出力を受け取れないことを意味します。監査はこれらすべての問題を数秒で発見します — 毎回必ず使用してください。

演習: 自分のスペシャリストエージェントを作る

今度はあなたの番です。この演習では、summarizerエージェントをゼロから作成します — 長いリサーチノートを読んで簡潔な1ページのブリーフを生成するスペシャリストです。

目標: 機能するsummarizerエージェントを作成し、AGENTS.mdに登録し、ライフサイクル監査に合格することを検証する。

    プロジェクトディレクトリにagents/summarizer.mdを作成。
  2. フロントマターを記述

PM経由でのテスト
新しいエージェントの本当のテストは監査に合格することではありません — PMが実際のワークフローでディスパッチした時に有用な出力を生成することです。監査が合格した後、必ず少なくとも1つのエンドツーエンドテストを実行してください: PMに実際のタスクを与え、新しいエージェントをディスパッチさせ、出力をレビューします。これにより、静的解析では検出できない問題 — 技術的には有効だがモデルが一貫して従うには曖昧すぎる指示 — を発見できます。
