스킬 만들기와 수정

이 장에서는 스킬 파일의 구조를 배우고, skill-lifecycle-manager와 skill-creator를 활용하여 나만의 커스텀 스킬을 만들고 등록하는 전체 과정을 실습합니다.

이 장에서 다루는 것
  • 스킬 파일 형식과 구조
  • YAML 프론트매터 필드 의미
  • 본문 작성 패턴 (Overview, When to Use, Steps, Outputs, Examples)
  • skill-lifecycle-manager 활용법 (6-step)
  • skill-creator (Claude Code 플러그인) 활용법
  • 실습: 간단한 커스텀 스킬 작성

스킬이란 다시 생각하기

4장에서 배운 내용 복습

4장 '멀티 에이전트 하네스 개념'에서 스킬(Skill)에 대해 처음 알아보았습니다. 스킬은 "에이전트가 수행할 수 있는 재사용 가능한 워크플로우"라고 배웠습니다. 스킬은 이름, 설명, 트리거, 단계의 네 가지 요소로 구성되며, 특정 키워드나 상황에 의해 자동으로 활성화됩니다.

복습해 보면, 스킬의 핵심 요소는 다음 네 가지였습니다.

  • 이름(Name) — 스킬을 식별하는 고유 이름 (예: research, html-build, pdf-export)
  • 설명(Description) — 이 스킬이 무엇을 하는지, 어떤 단계를 거치는지에 대한 상세 설명
  • 트리거(Trigger) — 스킬이 자동으로 활성화되는 조건 (키워드, 명령어 패턴, 파이프라인 단계)
  • 단계(Steps) — 스킬이 실행하는 구체적인 절차 (순서대로 정의)

스킬 vs 에이전트 (다시 한 번)

9장에서 에이전트 만들기를 배우셨습니다. 이제 스킬 만들기를 배우기 전에, 두 개념의 차이를 다시 한 번 확실히 정리해 봅시다.

에이전트 (Agent)

  • "누가" 작업을 수행하는가
  • 역할, 권한, 도구를 가진 AI 어시스턴트
  • 비유: 요리사 (직원)
  • 파일 위치: agents/<name>.md

스킬 (Skill)

  • "무엇을" 수행하는가
  • 재사용 가능한 워크플로우 절차
  • 비유: 요리 레시피
  • 파일 위치: skills/<name>/SKILL.md
초보자 비유: 스킬은 '요리 레시피'입니다. 에이전트(요리사)가 이 레시피를 따라 요리(작업)를 수행합니다. 한 요리사는 여러 레시피를 가질 수 있고, 같은 레시피를 여러 요리사가 공유할 수도 있습니다. 레시피가 명확하면 어떤 요리사가 요리해도 결과가 일관됩니다.

스킬의 Ownership 레이어

스킬은 에이전트와 달리 독립적으로 존재합니다. 스킬은 여러 레이어에 정의될 수 있으며, 각 레이어는 다른 범위와 영향력을 가집니다.

L0 — 워크스페이스 (Workspace)

  • 위치: skills/<name>/SKILL.md
  • 범위: 모든 프로젝트에서 사용 가능
  • 우선순위: 가장 높음 (1순위)
  • 예: sync, security-scan

L1 — 공통 템플릿 (Common Template)

  • 위치: templates/common/skills/
  • 범위: 해당 템플릿에서 파생된 프로젝트
  • 우선순위: L0 다음 (2순위)
  • 예: 템플릿 공통 검증 스킬

L2 — variant 템플릿 (Variant Template)

  • 위치: templates/co-*/skills/
  • 범위: 해당 variant에서 스캐폴딩된 모든 프로젝트
  • 우선순위: L1 다음 (3순위)
  • 예: co-deck 전용 스킬

L3 — 프로젝트 (Project)

  • 위치: .claude/skills/ 또는 .gemini/skills/
  • 범위: 해당 프로젝트만
  • 우선순위: 가장 낮음 (4순위)
  • 예: 프로젝트 전용 훅

핵심 규칙

  • 같은 스킬이 여러 위치에 있으면 1순위를 사용
  • L0 스킬은 전역적으로 공유됨
  • L2 스킬은 variant 전용, L3 스킬은 프로젝트 전용
  • 중복 정의는 피하는 것이 원칙

왜 직접 만들어야 하는가?

시스템에는 이미 다양한 스킬이 준비되어 있습니다. 하지만 프로젝트의 요구사항이 다양해질수록, 기존 스킬로 커버되지 않는 워크플로우가 생깁니다. 예를 들어:

  • 문서 품질 검토 — 생성된 문서의 일관성과 완성도를 검토하는 스킬
  • 자동 배포 — 완성된 산출물을 특정 서버에 자동 배포하는 스킬
  • 맞춤형 보고서 생성 — 프로젝트별 맞춤 형식의 보고서를 만드는 스킬
  • 정기 상태 점검 — 프로젝트의 전체 상태를 주기적으로 점검하는 스킬

이런 워크플로우가 필요할 때, 나만의 커스텀 스킬을 만들어서 시스템에 추가할 수 있습니다. 스킬은 하나의 마크다운 파일이므로, 몇 가지 규칙만 지키면 누구나 만들 수 있습니다.

스킬은 에이전트와 달리 독립적으로 존재합니다. 여러 에이전트가 같은 스킬을 참조할 수 있습니다. 예를 들어 sync 스킬은 PM 에이전트가 주로 사용하지만, 필요하다면 다른 에이전트도 참조할 수 있습니다.

스킬 파일 형식

파일 위치

스킬 파일은 프로젝트 루트의 skills/ 디렉토리에 저장됩니다. 에이전트와 달리, 스킬은 자신만의 폴더를 가집니다. 폴더 이름이 곧 스킬 이름이 되며, 그 안에 SKILL.md 파일이 들어갑니다.

skills/
├── sync/
│   └── SKILL.md              # 동기화 스킬
├── security-scan/
│   └── SKILL.md              # 보안 검사 스킬
├── meeting-facilitation/
│   └── SKILL.md              # 회의 진행 스킬
├── research/
│   └── SKILL.md              # 리서치 스킬
└── my-reviewer/              # ★ 우리가 만들 스킬
    └── SKILL.md

파일 구조: 프론트매터 + 본문

SKILL.md 파일은 두 부분으로 구성됩니다. 파일 상단에 YAML 프론트매터(메타데이터)가 오고, 그 아래에 마크다운 본문(실행 지침)이 옵니다. YAML 프론트매터는 --- 세 개로 시작하고 끝나는 블록 안에 작성됩니다.

이 구조의 핵심은 다음과 같습니다.

  1. YAML 프론트매터 — --- 구분선 사이에 스킬의 식별 정보(이름, 상태, 설명, 소유자, 버전, 메타데이터)를 작성합니다. 이 정보는 시스템이 스킬을 인식하고 관리하는 데 사용됩니다.
  2. 마크다운 본문 — 프론트매터 아래에 에이전트가 따라야 할 실행 절차를 마크다운 형식으로 작성합니다. Overview(개요), When to Use(사용 조건), Steps(실행 단계), Expected Outputs(기대 산출물), Examples(사용 예시) 등의 섹션으로 구성하는 것이 권장됩니다.
스킬은 에이전트와 달리 독립적으로 존재합니다. 여러 에이전트가 같은 스킬을 참조할 수 있습니다. 예를 들어 security-scan 스킬은 PM 에이전트가 호출할 수도 있고, 전문 에이전트가 직접 참조할 수도 있습니다.

프론트매터 작성

필수 필드와 선택 필드

YAML 프론트매터에는 스킬을 식별하고 관리하기 위한 여러 필드가 있습니다. 필수 필드와 선택 필드로 나뉩니다.

필드 필수 여부 설명 예시
name 필수 스킬의 고유 이름 my-reviewer
status 필수 active / draft / deprecated active
description 필수 스킬의 상세 설명 (PM이 디스패치할 때 참조) "Reviews document quality..."
owner 필수 유지 책임자 (에이전트 또는 역할) pm
version 필수 버전 번호 (시맨틱 버전 권장) "1.0.0"
metadata.type 선택 automation / quality / lifecycle quality
metadata.triggers 선택 자동 활성화 트리거 키워드 목록 ["review document", "check quality"]

필드 상세 설명

  1. name — 스킬의 고유 식별자입니다. 폴더 이름과 일치해야 합니다. skills/my-reviewer/SKILL.md라면 name은 my-reviewer가 됩니다. 케밥 케이스(kebab-case)를 사용하는 것이 좋습니다.
  2. status — 스킬의 현재 상태입니다. active(사용 중), draft(작성 중), deprecated(사용 중단) 중 하나입니다. 새 스킬을 처음 만들 때는 draft로 시작하고, 검증 완료 후 active로 변경하는 것이 좋습니다.
  3. description — 스킬의 상세 설명입니다. PM이 어떤 스킬을 디스패치할지 결정할 때 이 설명을 참고하므로, 명확하고 구체적으로 작성해야 합니다. "무엇을 하는지"뿐만 아니라 "어떤 단계를 거치는지"도 포함하면 좋습니다.
  4. owner — 이 스킬을 유지 관리할 책임이 있는 에이전트 또는 역할입니다. 예를 들어 PM이 관리하는 스킬이라면 pm을, 자동화 관련 스킬이라면 automation-engineer를 지정합니다.
  5. version — 스킬의 버전 번호입니다. 시맨틱 버전(Semantic Versioning) 형식(MAJOR.MINOR.PATCH)을 권장합니다. 예: "1.0.0", "1.1.0", "2.0.0".
  6. metadata.type — 스킬의 분류입니다. automation(자동화), quality(품질 관리), lifecycle(생애주기 관리) 중 하나를 선택합니다. 이 값은 스킬 목록을 필터링하거나 정리할 때 유용합니다.
  7. metadata.triggers — 스킬이 자동으로 활성화되는 트리거 키워드 목록입니다. 사용자가 이 키워드를 포함한 요청을 하면, PM이 해당 스킬을 매칭하여 디스패치합니다. 트리거는 구체적일수록 정확하게 매칭됩니다.

예시 프론트매터

다음은 실제로 사용할 수 있는 프론트매터 예시입니다.

---
name: my-reviewer
status: active
description: Reviews document quality and provides structured feedback. Checks readability, consistency, and completeness of markdown documents.
owner: pm
version: "1.0.0"
metadata:
  type: quality
  triggers:
    - "review document"
    - "check quality"
    - "quality review"
---
초보자 팁: description은 PM이 스킬을 선택할 때 참고하므로, "문서의 가독성, 일관성, 완성도를 검토하고 구조화된 피드백을 제공합니다"처럼 구체적으로 작성하세요. 짧고 모호한 설명(예: "문서를 검토함")보다 길고 구체적인 설명이 좋습니다.

본문 작성

본문 구조 권장 패턴

프론트매터 아래의 마크다운 본문은 에이전트가 실제로 따라야 할 실행 절차서입니다. 본문은 다음 다섯 가지 섹션으로 구성하는 것이 권장됩니다.

  1. Overview (개요) — 스킬의 목적과 범위를 한두 문단으로 설명합니다. "이 스킬은 무엇을 위한 것인가?", "어떤 범위까지 다루는가?"를 명확히 합니다.
  2. When to Use (사용 조건) — 이 스킬이 언제 활성화되어야 하는지 트리거 조건을 설명합니다. 어떤 상황, 어떤 요청, 어떤 파일 상태에서 실행되는지 구체적으로 적습니다.
  3. Steps (실행 단계) — 에이전트가 따라야 할 상세한 절차를 번호가 매겨진 순서로 작성합니다. 각 단계는 명확하고 모호하지 않아야 합니다. "파일을 읽고 → 검토하고 → 결과를 작성하라"식으로 구체적으로 지시합니다.
  4. Expected Outputs (기대 산출물) — 스킬 실행 완료 후 어떤 파일이나 결과물이 생성되어야 하는지 명시합니다. 파일 이름, 경로, 형식을 포함하면 다음 에이전트가 결과를 활용하기 쉽습니다.
  5. Examples (사용 예시) — 실제 사용 시나리오를 예시로 보여줍니다. 사용자가 어떤 요청을 하면 이 스킬이 어떻게 실행되는지 구체적인 예를 듭니다.

각 섹션의 작성 팁

Overview 섹션에서는 스킬의 존재 이유를 설명합니다. 독자(또는 에이전트)가 "이 스킬을 왜 사용하는가?"를 이해할 수 있도록 작성하세요.

## Overview

이 스킬은 마크다운 문서의 품질을 종합적으로 검토합니다.
가독성, 일관성, 완성도 세 가지 관점에서 문서를 평가하고,
구조화된 피드백을 제공합니다.

When to Use 섹션에서는 명확한 트리거 조건을 제시합니다.

## When to Use

사용자가 다음과 같은 요청을 할 때 활성화됩니다:
- "문서를 검토해 줘"
- "문서 품질을 확인해 줘"
- "품질 리뷰를 해 줘"

또한 다른 에이전트가 문서 완성 후 품질 검토가 필요할 때
PM이 자동으로 디스패치할 수 있습니다.

Steps 섹션은 가장 중요한 부분입니다. 에이전트가 따라야 할 절차를 명확하게 작성하세요.

## Steps

1. **대상 파일 확인** — 검토할 문서 파일의 경로를 확인합니다.
2. **문서 읽기** — 대상 파일을 읽고 내용을 분석합니다.
3. **가독성 검토** — 문장 길이, 단락 구성, 제목 계층을 검토합니다.
4. **일관성 검토** — 용어 사용, 서식 스타일, 날짜 형식을 검토합니다.
5. **완성도 검토** — 누락된 섹션, 불완전한 문장을 확인합니다.
6. **피드백 작성** — 검토 결과를 구조화된 형식으로 정리합니다.

Expected Outputs 섹션에서는 산출물을 명시합니다.

## Expected Outputs

- 검토 보고서 (stdout 또는 파일 출력)
- 문제 목록 (항목별 심각도: 경고/수정 권장/오류)
- 개선 제안 목록

Examples 섹션에서는 구체적인 사용 예시를 보여줍니다.

## Examples

**예시 1:** 사용자가 "이 문서를 검토해 줘"라고 요청
→ 대상 문서를 읽고, 5가지 항목을 점검한 뒤,
  구조화된 피드백을 제공합니다.

**예시 2:** PM이 핸드북 작성 완료 후 자동 디스패치
→ 완성된 HTML 파일의 마크다운 소스를 검토하고,
  저자 가이드라인 준수 여부를 보고합니다.
Steps 섹션은 에이전트가 따라야 할 '절차서'입니다. 명확하고 순서대로 작성하세요. 모호한 지시("문서를 잘 검토하라")보다 구체적인 지시("파일의 모든 h2 섹션을 순서대로 읽고, 각 섹션에 본문이 있는지 확인하라")가 좋습니다. 에이전트는 지시에 충실하게 따르므로, 지시가 정확할수록 결과물의 품질이 높아집니다.

skill-lifecycle-manager 활용

skill-lifecycle-manager란?

skill-lifecycle-manager는 스킬의 생성, 검증, 유지 관리를 안내하는 관리 스킬입니다. 9장에서 배운 agent-lifecycle-manager의 스킬 버전이라고 생각하시면 됩니다. 새로운 스킬을 만들 때 이 스킬의 지침을 따르면, 누락 없이 올바른 구조로 스킬을 작성할 수 있습니다.

이 스킬의 핵심 역할은 다음과 같습니다.

  • 새 스킬 생성 시 필요한 단계를 안내
  • 프론트매터 필드의 올바른 작성 확인
  • 시스템 등록(AGENTS.md, VERSION_MANIFEST.md) 절차 안내
  • 검증 스크립트 실행 지침 제공

6-step 프로세스

skill-lifecycle-manager는 스킬 생성을 6단계로 안내합니다. 각 단계를 순서대로 따르면 완성도 높은 스킬을 만들 수 있습니다.

각 단계 상세 안내

  1. 스킬 디렉토리 생성 — skills/<name>/ 폴더를 만듭니다. 이름은 케밥 케이스(소문자 + 하이픈)를 사용합니다. 예: skills/my-reviewer/. 그 안에 빈 SKILL.md 파일을 생성합니다.
  2. 프론트매터 작성 — 앞서 배운 필수 필드(name, status, description, owner, version)와 선택 필드(metadata.type, metadata.triggers)를 작성합니다. 처음에는 status를 draft로 설정합니다.
  3. 본문 작성 — Overview, When to Use, Steps, Expected Outputs, Examples 섹션을 작성합니다. Steps 섹션은 특히 명확하게, 번호가 매겨진 순서로 작성하세요.
  4. 시스템 등록 — AGENTS.md의 Skills 테이블(§6)에 스킬을 추가하고, docs/VERSION_MANIFEST.md에 버전 정보를 기록합니다. 이 단계를 거쳐야 시스템이 스킬을 인식합니다.
  5. 검증 — bun scripts/skill-lifecycle-audit.ts 스크립트를 실행하여 프론트매터 필드 누락, 파일 구조 오류, 필수 섹션 누락 등을 자동으로 검사합니다. 오류가 있으면 수정 후 재검증합니다.
  6. 활성화 테스트 — PM을 통해 실제 요청으로 스킬을 테스트합니다. 예를 들어 "문서 품질을 검토해 줘"라고 요청하여 스킬이 정상적으로 트리거되고 실행되는지 확인합니다. 모든 테스트를 통과하면 status를 active로 변경합니다.

skill-creator 플러그인

skill-creator란?

skill-creator는 Claude Code 플러그인으로 제공되는 고급 스킬 작성 도구입니다. 수동으로 SKILL.md 파일을 작성하는 것 외에도, 이 플러그인을 활용하면 더 효율적으로 스킬을 만들고 개선할 수 있습니다.

주요 기능

skill-creator는 다음 기능을 제공합니다.

  • 스킬 생성 — 대화형 안내를 통해 새로운 SKILL.md를 처음부터 작성합니다. 프론트매터 필드를 하나씩 물어보고, 본문 섹션의 구조를 제안합니다.
  • 스킬 수정 — 기존 스킬의 내용을 개선합니다. 트리거를 더 구체적으로 만들거나, Steps 섹션을 더 명확하게 다듬을 수 있습니다.
  • 트리거 개선 — 스킬의 트리거 키워드를 분석하고, 더 정확하게 매칭되도록 개선안을 제안합니다.

테스트 주도 반복 작성

skill-creator의 가장 강력한 기능은 테스트 주도 반복 작성(Test-Driven Iterative Authoring)입니다. 이 방식은 다음과 같이 진행됩니다.

1. 스킬 초안 작성 — skill-creator가 대화형으로 프론트매터와 본문의 초안을 생성합니다.
2. 트리거 테스트 — 초안을 바탕으로, 사용자가 의도한 키워드로 스킬이 정상 매칭되는지 테스트합니다.
3. 결과 분석 — 매칭 결과를 확인하고, false positive(의도치 않은 매칭)나 false negative(매칭 누락)가 있는지 분석합니다.
4. 트리거 수정 — 분석 결과를 바탕으로 트리거 키워드나 description을 수정합니다.
5. 재테스트 — 수정된 버전으로 다시 테스트합니다. 만족할 때까지 2~5단계를 반복합니다.

Claude Code CLI 환경에서 사용

skill-creator는 Claude Code CLI 환경에서 플러그인으로 동작합니다. Claude Desktop App 환경에서는 직접 파일을 편집하는 방식으로 대체할 수 있습니다.

Claude Code CLI 환경

  • skill-creator 플러그인 사용 가능
  • 대화형 스킬 생성/수정
  • 트리거 테스트 자동화
  • 반복 작성 워크플로우 지원
  • 별첨 B 참조

Claude Desktop App 환경

  • 직접 파일 편집으로 대체
  • 이 장에서 배운 수동 방식 사용
  • PM을 통해 테스트
  • 수동 검증 스크립트 실행
  • 초보자에게 권장
skill-creator는 Claude Code CLI 환경에서 사용하는 고급 도구입니다. Claude Desktop App에서는 직접 파일 편집으로 대체할 수 있습니다. 이 장에서 배운 수동 방식(프론트매터 + 본문 직접 작성)은 두 환경 모두에서 사용할 수 있는 기본 방법입니다.

등록과 배포

등록 위치

스킬 작성이 완료되면, 시스템이 스킬을 인식할 수 있도록 두 곳에 등록해야 합니다. 이 단계를 생략하면 PM이 스킬을 찾지 못해 디스패치하지 않습니다.

  1. AGENTS.md Skills 테이블 (§6) — 워크스페이스 루트의 AGENTS.md 파일에 있는 Skills 테이블에 스킬 이름, 파일 위치, 버전, 상태를 추가합니다. 이 테이블은 스킬의 레지스트리 역할을 합니다.
  2. docs/VERSION_MANIFEST.md — 스킬의 버전 정보와 상태를 기록합니다. 버전 변경 이력을 추적하고, 어떤 스킬이 활성 상태인지 한눈에 파악할 수 있습니다. VERSION_MANIFEST.md는 스킬 버전의 SSOT(Single Source of Truth)입니다.

AGENTS.md 등록 예시

AGENTS.md의 Skills 테이블에 다음과 같이 추가합니다.

| my-reviewer | `skills/my-reviewer/SKILL.md` | quality | Checks readability, consistency, completeness | active | 1.0.0 |

VERSION_MANIFEST.md 등록 예시

- **name:** my-reviewer
  **path:** skills/my-reviewer/SKILL.md
  **version:** 1.0.0
  **status:** active
  **owner:** pm
  **type:** quality

배포: sync-skills.ts

L0(워크스페이스) 스킬은 sync-skills.ts 스크립트를 통해 모든 템플릿(L1)과 프로젝트(L2)에 동기화할 수 있습니다. 이 스크립트를 실행하면 워크스페이스의 스킬이 모든 하위 프로젝트에 복제됩니다.

# 스킬 동기화 스크립트 실행
bun scripts/sync-skills.ts
L0(워크스페이스) 스킬은 모든 프로젝트에서 사용할 수 있습니다. 반면 L2(프로젝트) 스킬은 해당 프로젝트에서만 사용됩니다. 처음 스킬을 만들 때는 L0에 등록하여 모든 프로젝트에서 활용할 수 있도록 하는 것이 좋습니다.

실습: 나만의 커스텀 스킬 만들기

실습 목표

이번 실습에서는 "문서 검토 스킬(my-reviewer)"을 직접 만들어 봅니다. 앞서 배운 프론트매터 작성, 본문 작성, 시스템 등록, 검증의 전체 과정을 직접 체험합니다.

실습 단계

  1. Claude Desktop App에서 프로젝트 열기 — Claude Desktop App을 실행하고, 작업 중인 프로젝트를 엽니다. 프로젝트 루트에 skills/ 폴더가 있는지 확인합니다.
  2. 디렉토리 생성 — skills/my-reviewer/ 폴더를 만들고, 그 안에 SKILL.md 파일을 생성합니다.
  3. 프론트매터 작성 — SKILL.md 파일 상단에 YAML 프론트매터를 작성합니다. 아래 예시를 참고하세요.
  4. 본문 작성 — 프론트매터 아래에 Overview, When to Use, Steps, Expected Outputs, Examples 섹션을 작성합니다.
  5. AGENTS.md에 등록 — AGENTS.md의 Skills 테이블에 my-reviewer 스킬을 추가합니다.
  6. 검증 스크립트 실행 — bun scripts/skill-lifecycle-audit.ts를 실행하여 스킬 구조를 검증합니다. 오류가 있으면 수정하세요.
  7. PM을 통해 테스트 — Claude에게 "문서 품질을 검토해 줘"라고 요청하여 스킬이 정상 작동하는지 확인합니다.

전체 파일 내용 예시

다음은 완성된 skills/my-reviewer/SKILL.md의 전체 내용입니다. 이 예시를 그대로 사용하거나, 필요에 맞게 수정하여 활용하세요.

---
name: my-reviewer
status: active
description: >
  Reviews document quality and provides structured feedback.
  Checks readability, consistency, and completeness of
  markdown documents. Outputs a structured review report
  with severity levels and improvement suggestions.
owner: pm
version: "1.0.0"
metadata:
  type: quality
  triggers:
    - "review document"
    - "check quality"
    - "quality review"
    - "문서 검토"
    - "품질 확인"
---

## Overview

This skill performs a comprehensive quality review of
markdown documents. It evaluates documents from three
perspectives: readability, consistency, and completeness,
then provides structured feedback with actionable suggestions.

Scope: markdown (.md) files in the project workspace.

## When to Use

Activate this skill when:
- The user requests a document review
- A document has been newly created or significantly revised
- PM dispatches quality review as part of a pipeline gate
- The user asks to "check quality" or "review document"

## Steps

1. **Identify target file** — Confirm the file path of the
   document to review. If not specified, ask the user.
2. **Read the document** — Load the full content of the
   target file.
3. **Readability check** — Evaluate sentence length,
   paragraph structure, heading hierarchy, and overall
   flow. Flag sections that are hard to follow.
4. **Consistency check** — Verify terminology usage, format
   style, date format, heading capitalization, and list
   formatting across the entire document.
5. **Completeness check** — Identify missing sections,
   incomplete sentences, broken references, and unresolved
   TODO markers.
6. **Generate review report** — Compile findings into a
   structured report with severity levels:
   - INFO: minor suggestions
   - WARNING: recommended improvements
   - ERROR: issues that must be fixed

## Expected Outputs

- Structured review report (stdout)
- Issue count by severity (INFO / WARNING / ERROR)
- Prioritized improvement suggestions

## Examples

**Example 1:** User says "review document"
→ Read the specified file, run all 3 checks,
  output a structured review report.

**Example 2:** PM dispatches after handbook chapter
  completion
→ Review the chapter HTML source, check authoring
  guideline compliance, report findings.
스킬 완성 후 PM에게 "문서 품질을 검토해 줘"라고 요청해서 스킬이 정상 작동하는지 확인하세요. 만약 스킬이 트리거되지 않는다면, 프론트매터의 triggers 필드에 해당 키워드가 포함되어 있는지, AGENTS.md에 스킬이 등록되어 있는지 확인하세요. 트리거 매칭은 정확한 키워드 일치에 가까울수록 더 잘 동작합니다.

이 장의 요약
  • 스킬은 에이전트가 수행하는 재사용 가능한 워크플로우입니다. 에이전트가 "누구"라면 스킬은 "무엇을 하는지"를 정의합니다.
  • SKILL.md는 YAML 프론트매터(메타데이터)와 마크다운 본문(실행 지침) 두 부분으로 구성됩니다.
  • 프론트매터 필드에는 name, status, description, owner, version이 필수이며, metadata.type과 metadata.triggers가 선택입니다.
  • 본문은 Overview, When to Use, Steps, Expected Outputs, Examples 섹션으로 구성하는 것이 권장됩니다.
  • skill-lifecycle-manager는 디렉토리 생성 → 프론트매터 → 본문 → 등록 → 검증 → 테스트의 6-step 프로세스를 안내합니다.
  • skill-creator는 Claude Code CLI 환경에서 테스트 주도 반복 작성을 지원하는 고급 도구입니다.
  • 등록은 AGENTS.md Skills 테이블과 VERSION_MANIFEST.md 두 곳에 해야 합니다.
