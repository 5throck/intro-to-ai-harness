Chapter 10

Creating & Modifying Skills

This chapter covers skill file structure, the skill-lifecycle-manager and skill-creator tools, and walks you through building and registering your own custom skill.

What This Chapter Covers
  • Skill file format and structure
  • YAML frontmatter field meanings
  • Body content patterns (Overview, When to Use, Steps, Outputs, Examples)
  • skill-lifecycle-manager usage (6-step)
  • skill-creator (Claude Code plugin) overview
  • Practice: create a simple custom skill

Rethinking Skills

Back in Chapter 4, we introduced the concept of skills: reusable recipe books that tell agents how to perform specific types of work. In this chapter, we go one level deeper — we will actually create a new skill from scratch, register it in the project, and verify that it triggers correctly.

A Quick Review from Chapter 4

Recall the key distinction between agents and skills:

Agent

  • What: A digital employee with a fixed identity
  • Analogy: The employee themselves
  • File: agents/<name>.md
  • Scope: Persistent role across the entire project

Skill

  • What: A reusable instruction recipe
  • Analogy: The recipe book the employee follows
  • File: skills/<name>/SKILL.md
  • Scope: Invoked on demand; shared across agents

A chef (agent) uses different recipes (skills) depending on what dish the customer ordered. The chef’s identity does not change, but the recipe tells them exactly how to prepare each dish. The html-build agent always builds HTML slides, but the html-build skill tells it precisely how to read the slide deck file, apply the theme, and produce the output.

Ownership Layers (L0 / L1 / L2 / L3)

Skills live at different layers of the workspace hierarchy, and understanding which layer you are editing is critical:

  1. L0 — Workspace Root (skills/): The Single Source of Truth. All skill development happens here. When you create or edit a skill, this is the layer you modify.
  2. L1 — Common Template (templates/common/skills/): A snapshot published from L0 via bun run propagate:apply. You never edit L1 directly — changes flow downward from L0.
  3. L2 — Variant Template (templates/co-*/skills/): Variant-specific skills defined in the L2 template layer. Each variant (co-deck, co-consult, etc.) can include skills that are shared across all projects scaffolded from that variant.
  4. L3 — Project Level (Projects/<name>/skills/): A project-specific layer created when an L3 project is scaffolded from an L2 variant template. Local customizations can be added here without affecting other projects or the variant template.
The “Recipe” Analogy
If the agent is a chef, then the skill is a recipe card in the kitchen’s recipe binder. The binder is the L0 workspace (the master copy). Cookbooks printed for each restaurant chain are L1 templates. Recipe variations added for a specific cuisine (e.g., Italian, Japanese) are L2 variant skills. Notes scribbled in the margin of one restaurant’s copy are L3 project overrides. You always write new recipes at the master binder (L0), then distribute copies.

Skill File Format

Every skill lives in its own directory under skills/, with a single file named SKILL.md. The naming is important: the directory name uses kebab-case, and the file inside is always uppercase SKILL.md.

File location
skills/<name>/SKILL.md

Like agent files, a skill file has two parts: a YAML frontmatter block (machine-readable metadata) and a Markdown body (human-readable instructions). The structure is simpler than an agent file, but the same principle applies: the frontmatter is for the system, the body is for the AI model.

Structure Overview

The frontmatter is enclosed between two --- fences, just like agent files. Everything below the closing fence is the body — standard Markdown with headings, lists, code blocks, and tables.

Skill vs Agent File Naming
Agent files live at agents/<name>.md (one file per agent). Skill files live at skills/<name>/SKILL.md (one directory per skill, always with an uppercase SKILL.md inside). This extra directory layer allows skills to bundle supplementary files (examples, test fixtures) alongside the main instruction document.

Writing Frontmatter

The YAML frontmatter is the machine-readable identity card of your skill. The orchestration layer (PM, scripts, trigger matching) reads these fields to decide when and how to activate the skill.

Required and Optional Fields

Field Required? Type Description
name Required string Kebab-case identifier. Must match the directory name.
status Required string One of: active, draft, deprecated, retired.
description Required string Multi-line summary of what the skill does and when to use it. Should include Use when: trigger scenarios.
owner Required string The agent or role accountable for maintaining this skill (e.g., pm, research).
version Required string Semantic version (start at 1.0.0).
metadata.type Required string One of: process (workflow/methodology), implementation (technical), domain (domain-specific knowledge).
metadata.triggers Required list Keywords that activate this skill. Must have at least one entry.
scope Optional string Visibility scope: common (all projects) or variant (project-specific).
last_reviewed Optional string Date of last review (YYYY-MM-DD).
prerequisites Optional string Any prerequisite tools or runtime requirements (e.g., Bun runtime).

Example Frontmatter

skills/document-reviewer/SKILL.md — frontmatter
---
name: document-reviewer
status: active
scope: common
description: >
  Reviews markdown documents for clarity, consistency, and formatting
  compliance. Checks heading hierarchy, link validity, and writing style.
  Use when: "review this document", "check formatting", "proofread markdown".
owner: pm
version: 1.0.0
last_reviewed: 2026-08-10
prerequisites: none
metadata:
  type: process
  triggers:
    - review document
    - check formatting
    - proofread
    - document quality
---
Choosing the Right Type
process — Workflow and methodology skills (e.g., sync, meeting-facilitation, skill-lifecycle-manager).
implementation — Technical implementation skills (e.g., html-build, pdf-export, measure).
domain — Domain-specific knowledge skills (e.g., dart-disclosure-parser, mece-logic-auditor).
Choose the type that best describes the skill’s primary purpose. Most general-purpose workflow skills are process.

Writing Body Content

Below the closing --- fence, the Markdown body serves as the skill’s instruction manual. When the skill is loaded, the AI model reads the entire body and follows its guidance. Good body content means the agent performs the workflow consistently and correctly every time.

5 Recommended Sections

While the body can be organized in many ways, most skills benefit from these five sections, presented in order:

  1. Overview — A high-level explanation of the skill’s purpose. What problem does it solve? What value does it provide? Keep it to 2–4 sentences.
  2. When to Use This Skill — Trigger conditions and concrete use cases. List the phrases or situations that should activate this skill. This reinforces the trigger keywords in the frontmatter.
  3. Steps — Numbered, sequential instructions the agent follows to complete the task. Group them by logical phases if the workflow is complex. Each step should be actionable and include validation checkpoints where appropriate.
  4. Expected Outputs — What the skill produces. Specify file names, formats, and content structure so the next agent in the pipeline knows exactly what to expect.
  5. Examples (optional) — Concrete usage examples showing how the skill behaves in realistic scenarios. Include sample inputs and outputs.
Keep Steps Clear and Sequential
The Steps section is the heart of your skill. Write each step as a direct command in the imperative mood: “Read the input file”, “Validate the structure”, “Write the output report”. Avoid vague phrases like “Handle the data”. Include specific file paths, format requirements, and validation checks at each step. If a step has sub-steps, use numbered sub-lists (1.1, 1.2, etc.) to keep the hierarchy clear.

Section Details with Examples

1. Overview

Start with a concise statement of what the skill does and why it exists.

## Overview

Reviews markdown documents for structural clarity, formatting
consistency, and writing quality. Produces a structured review
report with categorized findings and actionable fix suggestions.

2. When to Use This Skill

List specific trigger scenarios.

## When to Use

- User says "review this document" or "check formatting"
- Before publishing a markdown file to catch issues
- After a major edit to verify the document still meets standards
- When quality-gating content before handoff to the next agent

3. Steps

Provide numbered, actionable instructions.

## Steps

### Step 1: Load and Parse
- Read the target markdown file using the Read tool
- Parse the document structure (headings, links, code blocks)

### Step 2: Structural Checks
- Verify heading hierarchy (no H3 before H2, etc.)
- Check that every internal link targets an existing file
- Validate that code blocks specify a language

### Step 3: Quality Review
- Flag passive voice overuse (more than 30% of sentences)
- Check for run-on paragraphs (more than 5 sentences)
- Verify consistent terminology usage

4. Expected Outputs

Define what the skill produces.

## Expected Outputs

- `review-report.md` in the same directory as the input file
- Sections: Structure, Links, Style, Terminology
- Each finding includes: severity (error/warning/info),
  location (line reference), and suggested fix

5. Examples (optional)

Show realistic usage scenarios.

## Examples

**Input**: User says "Review docs/ch02/02_Getting_Started.md"
**Output**: Creates `docs/ch02/review-report.md` with 3 errors
  (broken link, missing H1, code block without language) and
  5 warnings (passive voice, long paragraphs).
The Body Is an “Instruction Manual”
Unlike the frontmatter (which is read by scripts and the trigger matcher), the body is read by the AI model when the skill is loaded. Write it as if you were writing a manual for a new team member: clear, specific, and focused on how to do the work. The “why” belongs in the overview; the “when” belongs in the trigger section; the “how” belongs in the steps.

Using skill-lifecycle-manager

The skill-lifecycle-manager skill provides a systematic 6-step process for creating, validating, and maintaining skills. Rather than manually creating files and hoping everything connects, the skill guides you through each step and catches problems early.

The 6-Step Process

Step-by-Step Explanation

  1. Create the directory — Create skills/<name>/SKILL.md using kebab-case for the directory name. The file must be named exactly SKILL.md (uppercase).
  2. Write frontmatter — Fill in all required YAML fields: name, status, description, owner, version, metadata.type, and metadata.triggers. The directory name and the name field must match.
  3. Write body content — Compose the Markdown instructions covering Overview, When to Use, Steps (with validation checkpoints), Expected Outputs, and optionally Examples.
  4. Register in documentation — Add the skill to the Skills table in AGENTS.md and the Skills section in docs/context.md. Include the file path and trigger conditions.
  5. Validate — Run bun run verify-skills (or bun scripts/validate-skills.ts) to check that the skill passes all structural and content checks.
  6. Test activation — Try loading the skill via the platform tool (e.g., Skill tool in Claude Code) and verify that the frontmatter loads correctly, the content is actionable, and the triggers match expected use cases.
Start Simple, Iterate
You do not need a perfect skill on day one. Create a minimal viable skill with the required frontmatter fields and a basic Steps section. Set status: draft initially. Test it, refine the wording based on how the model interprets it, then promote to status: active once it behaves consistently. The lifecycle-manager makes iteration safe: every change can be validated automatically before promotion.

skill-creator Plugin

In addition to the manual process described above, Claude Code provides a skill-creator plugin that can assist with creating and iterating on skill files. This plugin is available in the Claude Code CLI plugin marketplace.

What skill-creator Does

The skill-creator plugin helps with three key workflows:

  1. Create from scratch — Generates a new SKILL.md file with proper frontmatter and body structure based on your description of the skill’s purpose.
  2. Edit existing skills — Refines wording, adds missing sections, or restructures an existing skill to improve trigger reliability and instruction clarity.
  3. Iterate wording — Tests different phrasings for trigger conditions and step instructions to find what works best for consistent AI behavior.

Test-Driven Iterative Authoring

The skill-creator follows a test-driven approach: write a draft, test the trigger, observe how the model behaves, then refine the wording. This cycle repeats until the skill triggers reliably and produces consistent output.

1. Describe — Tell skill-creator what you want the skill to do (purpose, trigger phrases, expected behavior).
2. Draft — skill-creator generates the initial SKILL.md with frontmatter and body.
3. Test — Load the skill in a real session and try the trigger phrases. Observe the output.
4. Refine — Based on the test results, adjust trigger keywords, clarify ambiguous steps, or add missing validation checkpoints.
5. Validate — Run the skill-lifecycle-manager validation to ensure structural compliance before registering.
Claude Desktop App Alternative
If you are using Claude Desktop App without the Claude Code CLI plugin marketplace, you can achieve the same workflow by asking Claude directly: “Create a skill that reviews markdown documents for formatting issues.” Claude will draft the SKILL.md file for you. You can then manually register and validate it using the skill-lifecycle-manager steps described in the previous section. The key difference is that the skill-creator plugin automates the iteration cycle; with Claude Desktop App, you manage the test-refine cycle manually.

Registration & Deployment

A skill that is not registered is like a recipe card that never made it into the kitchen binder. The system cannot discover it, agents cannot load it, and audit scripts will flag it as an orphan. Registration makes your skill visible to the entire workspace.

Registration Locations

You need to register your skill in two primary locations:

  1. AGENTS.md — Skills Table (§6): Add a row with the skill name, file path (skills/<name>/SKILL.md), and a brief description. This is the main registry the PM and documentation tools reference.
  2. docs/context.md — Skills Section: Add the skill name, type, and brief description to the skills section. This ensures the skill appears in developer-facing documentation.

Registration Example

AGENTS.md — Skills table entry
| document-reviewer | `skills/document-reviewer/SKILL.md` | Reviews markdown documents for clarity, consistency, and formatting compliance |
docs/context.md — Skills section entry
### document-reviewer
- **File**: `skills/document-reviewer/SKILL.md`
- **Type**: process
- **Description**: Reviews markdown documents for clarity, consistency, and formatting compliance.

Deploying with sync-skills.ts

After creating or updating a skill, run the sync script to distribute it to the platform-specific directories:

Deploy skill to all platforms
bun scripts/sync-skills.ts

This script copies the skill from skills/<name>/SKILL.md into .claude/skills/<name>/SKILL.md and .gemini/skills/<name>/SKILL.md so that both Claude Code and Gemini CLI can discover and load it. If you are in the L0 workspace and a templates/common/ directory exists, you should also propagate to the L1 template by running bun run propagate:apply.

L0 Accessibility
Workspace-level skills (skills/) have the highest priority in the skill resolution order (see Chapter 4). This means a skill you create at L0 will always take precedence over platform-level or plugin-level skills with the same name. Use this power responsibly — avoid creating skills that duplicate or shadow existing plugin functionality unless you intentionally want to override it.

Practice: Build Your Own Custom Skill

Now it is your turn. In this exercise, you will create a document-reviewer skill from scratch — a reusable recipe that reviews markdown documents for formatting, structure, and writing quality.

Goal: Create a functional document-reviewer skill, register it in AGENTS.md, deploy it with sync-skills.ts, and test that it triggers correctly.
  1. Create the directory and file
    Create the directory skills/document-reviewer/ and add a file named SKILL.md inside it.
  2. Write the frontmatter
    Add the YAML frontmatter with all required fields. Here is the complete frontmatter for reference:
    skills/document-reviewer/SKILL.md — frontmatter
    ---
name: document-reviewer
status: draft
scope: common
description: >
  Reviews markdown documents for clarity, consistency, and formatting
  compliance. Checks heading hierarchy, link validity, and writing style.
  Use when: "review this document", "check formatting", "proofread markdown".
owner: pm
version: 1.0.0
last_reviewed: 2026-08-10
prerequisites: none
metadata:
  type: process
  triggers:
    - review document
    - check formatting
    - proofread
    - document quality
---
  3. Write the body
    Use the five-section structure. Here is the complete body:
    skills/document-reviewer/SKILL.md — body
    ## Overview

Reviews markdown documents for structural clarity, formatting
consistency, and writing quality. Produces a structured review
report with categorized findings and actionable fix suggestions.

## When to Use

- User says "review this document" or "check formatting"
- Before publishing a markdown file to catch issues
- After a major edit to verify the document still meets standards
- When quality-gating content before handoff to the next agent

## Steps

### Step 1: Load and Parse
- Read the target markdown file using the Read tool
- Parse the document structure (headings, links, code blocks)
- Count total lines and estimate word count

### Step 2: Structural Checks
- Verify heading hierarchy (no H3 before H2, exactly one H1)
- Check that every internal link targets an existing file
- Validate that code blocks specify a language tag
- Ensure images have alt text

### Step 3: Style Review
- Flag passive voice overuse (more than 30% of sentences)
- Check for run-on paragraphs (more than 5 sentences)
- Verify consistent terminology (same term used throughout)
- Check for redundant phrases or wordiness

### Step 4: Generate Report
- Create `review-report.md` in the same directory as the input
- Structure the report with sections: Structure, Links, Style,
  Terminology, Summary
- Each finding includes severity (error/warning/info), location
  (line reference), and suggested fix

## Expected Outputs

- `review-report.md` in the same directory as the reviewed file
- Sections: Structure, Links, Style, Terminology, Summary
- Severity levels: error (must fix), warning (should fix),
  info (suggestion)
- Word count and line count summary at the top

## Examples

**Input**: "Review docs/ch02/02_Getting_Started.md"
**Output**: Creates `docs/ch02/review-report.md` reporting
  2 errors (broken link on line 45, missing H1), 4 warnings
  (passive voice, long paragraphs), and 3 info items
  (terminology suggestions).
  4. Register in AGENTS.md
    Add the document-reviewer to the Skills table in AGENTS.md with the file path and description. If your project has a docs/context.md, add an entry there as well.
  5. Deploy with sync-skills.ts
    Run bun scripts/sync-skills.ts in your terminal to distribute the skill to the platform-specific directories (.claude/skills/ and .gemini/skills/).
  6. Validate
    Run bun run verify-skills (or bun scripts/validate-skills.ts) to check that the skill passes all structural and content checks. Fix any errors reported.
  7. Test activation
    In Claude Code (or Claude Desktop App), try saying: “Review the README.md file for formatting issues.” Verify that the skill loads, the steps execute, and the review-report.md file is created with the expected structure.
Testing Is Essential
The real test of a new skill is not whether the validation script passes — it is whether the skill produces useful output when triggered by a real user request. After validation passes, always run at least one end-to-end test: trigger the skill with a realistic prompt, review the output, and refine the step instructions if the results are inconsistent or miss important checks. Skills are living documents; expect to iterate 2–3 times before the behavior is reliably consistent.
Key Takeaways
  • A skill is a reusable instruction recipe stored at skills/<name>/SKILL.md
  • Skill file = YAML frontmatter (metadata + triggers) + Markdown body (instructions)
  • Frontmatter requires: name, status, description, owner, version, metadata.type, metadata.triggers
  • Body sections: Overview, When to Use, Steps, Expected Outputs, Examples
  • skill-lifecycle-manager provides a 6-step creation and validation process
  • skill-creator (Claude Code plugin) assists with test-driven iterative authoring
  • Register skills in AGENTS.md and docs/context.md, then deploy with bun scripts/sync-skills.ts
  • Always test activation with a real trigger phrase after validation passes
  • Start with status: draft, promote to active after the skill behaves consistently
