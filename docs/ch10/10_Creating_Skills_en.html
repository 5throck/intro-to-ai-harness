Chapter 10

Creating & Modifying Skills

In this chapter you will learn the structure of skill files and walk through the full process of building and registering your own custom skill using skill-lifecycle-manager and skill-creator.

What This Chapter Covers
  • Skill file format and structure
  • YAML frontmatter field meanings
  • Body writing patterns (Overview, When to Use, Steps, Outputs, Examples)
  • How to use skill-lifecycle-manager (6-step)
  • How to use skill-creator (Claude Code plugin)
  • Practice: write a simple custom skill

Rethinking Skills

A Review of Chapter 4

In Chapter 4, "Multi-Agent Harness Concepts," we first looked at skills. A skill, we learned, is "a reusable workflow an agent can carry out." A skill consists of four elements — name, description, trigger, and steps — and is activated automatically by certain keywords or situations.

To recap, the four core elements of a skill were:

  • Name — the unique name identifying the skill (e.g., research, html-build, pdf-export)
  • Description — a detailed account of what the skill does and which steps it follows
  • Trigger — the conditions under which the skill activates automatically (keywords, command patterns, pipeline phases)
  • Steps — the concrete procedure the skill executes (defined in order)

Skill vs. Agent (One More Time)

In Chapter 9 you learned how to build agents. Before learning to build skills, let's firmly re-establish the difference between the two concepts.

Agent

  • "Who" performs the task
  • An AI assistant with a role, permissions, and tools
  • Analogy: a cook (an employee)
  • File location: agents/<name>.md

Skill

  • "What" gets performed
  • A reusable workflow procedure
  • Analogy: a recipe
  • File location: skills/<name>/SKILL.md
Beginner analogy: A skill is a 'cooking recipe'. The agent (the cook) follows the recipe to perform the dish (the task). One cook can own many recipes, and several cooks can share the same recipe. When the recipe is clear, any cook produces consistent results.

The Ownership Layers of a Skill

Unlike agents, skills exist independently. A skill can be defined at multiple layers, and each layer has a different scope and reach.

L0 — Workspace

  • Location: skills/<name>/SKILL.md
  • Scope: available in every project
  • Priority: highest (priority 1)
  • Examples: sync, security-scan

L1 — Common Template

  • Location: templates/common/skills/
  • Scope: projects derived from that template
  • Priority: after L0 (priority 2)
  • Examples: template-wide validation skills

L2 — Variant Template

  • Location: templates/co-*/skills/
  • Scope: all projects scaffolded from that variant
  • Priority: after L1 (priority 3)
  • Examples: co-deck-only skills

L3 — Project

  • Location: .claude/skills/ or .gemini/skills/
  • Scope: that project only
  • Priority: lowest (priority 4)
  • Examples: project-specific hooks

Core Rules

  • If the same skill exists in several locations, priority 1 wins
  • L0 skills are shared globally
  • L2 skills belong to a variant only; L3 skills to a project only
  • Avoid duplicate definitions as a principle

Why Build Your Own?

The system already ships with a variety of skills. But as project requirements diversify, workflows not covered by existing skills appear. For example:

  • Document quality review — a skill that reviews generated documents for consistency and completeness
  • Automated deployment — a skill that deploys finished deliverables to a specific server automatically
  • Custom report generation — a skill that builds reports in a project-specific format
  • Periodic health check — a skill that inspects overall project status on a schedule

When you need such a workflow, you can build your own custom skill and add it to the system. A skill is a single markdown file, so anyone can create one by following a few rules.

Unlike agents, skills exist independently. Several agents can reference the same skill. For example, the sync skill is used mainly by the PM agent, but other agents can reference it too when needed.

Skill File Format

File Location

Skill files are stored in the skills/ directory at the project root. Unlike agents, each skill gets its own folder. The folder name becomes the skill name, and inside it sits the SKILL.md file.

skills/
├── sync/
│   └── SKILL.md              # Sync skill
├── security-scan/
│   └── SKILL.md              # Security scan skill
├── meeting-facilitation/
│   └── SKILL.md              # Meeting facilitation skill
├── research/
│   └── SKILL.md              # Research skill
└── my-reviewer/              # ★ The skill we will build
    └── SKILL.md

File Structure: Frontmatter + Body

A SKILL.md file consists of two parts. At the top comes the YAML frontmatter (metadata), followed by the markdown body (execution instructions). The YAML frontmatter is written inside a block opened and closed by three dashes, ---.

The keys to this structure are:

  1. YAML frontmatter — between the --- fences you write the skill's identity information (name, status, description, owner, version, metadata). The system uses it to recognize and manage the skill.
  2. Markdown body — below the frontmatter you write, in markdown, the execution procedure the agent must follow. Recommended sections are Overview, When to Use, Steps, Expected Outputs, and Examples.
Unlike agents, skills exist independently. Several agents can reference the same skill. For example, the security-scan skill may be invoked by the PM agent or referenced directly by a specialist agent.

Writing Frontmatter

Required and Optional Fields

The YAML frontmatter carries several fields for identifying and managing the skill. They divide into required and optional fields.

Field Required Description Example
name Yes The skill's unique name my-reviewer
status Yes active / draft / deprecated active
description Yes Detailed description of the skill (consulted by the PM when dispatching) "Reviews document quality..."
owner Yes Maintainer (agent or role) pm
version Yes Version number (semantic versioning recommended) "1.0.0"
metadata.type Optional automation / quality / lifecycle quality
metadata.triggers Optional List of trigger keywords for automatic activation ["review document", "check quality"]

Field Details

  1. name — the skill's unique identifier. It must match the folder name: for skills/my-reviewer/SKILL.md the name is my-reviewer. kebab-case is recommended.
  2. status — the skill's current state: active(in use), draft(being written), or deprecated(retired). Start a new skill as draft and switch to active after validation passes.
  3. description — the skill's detailed description. The PM consults it when deciding which skill to dispatch, so it must be clear and specific. Include not just "what it does" but also "which steps it follows."
  4. owner — the agent or role responsible for maintaining this skill. For example, a PM-managed skill gets pm; an automation-related skill gets automation-engineer.
  5. version — the skill's version number. Semantic versioning (MAJOR.MINOR.PATCH) is recommended, e.g., "1.0.0", "1.1.0", "2.0.0".
  6. metadata.type — the skill's classification. Choose one of automation, quality, or lifecycle. Useful for filtering or organizing the skill list.
  7. metadata.triggers — the list of trigger keywords that automatically activate the skill. When a user request includes these keywords, the PM matches and dispatches the skill. The more specific the triggers, the more accurate the matching.

Example Frontmatter

The following is a frontmatter example you can actually use.

---
name: my-reviewer
status: active
description: Reviews document quality and provides structured feedback. Checks readability, consistency, and completeness of markdown documents.
owner: pm
version: "1.0.0"
metadata:
  type: quality
  triggers:
    - "review document"
    - "check quality"
    - "quality review"
---
Beginner tip: Because the PM consults the description when choosing a skill, write it concretely — e.g., "Reviews readability, consistency, and completeness of documents and provides structured feedback." A longer, specific description beats a short, vague one like "reviews documents."

Writing Body Content

Recommended Body Structure

The markdown body below the frontmatter is the execution procedure the agent will actually follow. Five sections are recommended.

  1. Overview — explain the skill's purpose and scope in one or two paragraphs. Make clear "what is this skill for?" and "how far does its scope reach?"
  2. When to Use — describe the trigger conditions: when should this skill activate? Write concretely which situations, requests, or file states set it off.
  3. Steps — write the detailed procedure the agent follows as a numbered sequence. Each step must be clear and unambiguous. Instruct concretely: "read the file → review it → write up the results."
  4. Expected Outputs — state which files or results must exist once the skill finishes. Including file names, paths, and formats makes it easy for the next agent to consume the results.
  5. Examples — show real usage scenarios. Give concrete examples of how this skill runs when the user makes a certain request.

Writing Tips for Each Section

In the Overview section, explain why the skill exists. Write so that the reader (or agent) understands "why would I use this skill?"

## Overview

This skill performs a comprehensive quality review of
markdown documents. It evaluates documents from three
perspectives: readability, consistency, and completeness,
then provides structured feedback.

In the When to Use section, present clear trigger conditions.

## When to Use

Activate this skill when the user makes requests like:
- "review this document"
- "check the document quality"
- "run a quality review"

It can also be dispatched automatically by the PM
when another agent needs a quality review after
finishing a document.

The Steps section is the most important part. Write the procedure clearly.

## Steps

1. **Identify the target file** — Confirm the path of the document to review.
2. **Read the document** — Load the target file and analyze its content.
3. **Readability review** — Check sentence length, paragraph structure, heading hierarchy.
4. **Consistency review** — Check terminology usage, formatting style, date formats.
5. **Completeness review** — Look for missing sections and incomplete sentences.
6. **Write the feedback** — Organize the findings into a structured format.

In the Expected Outputs section, state the deliverables.

## Expected Outputs

- Review report (stdout or file output)
- Issue list (severity per item: warning / fix recommended / error)
- List of improvement suggestions

In the Examples section, show concrete usage examples.

## Examples

**Example 1:** User asks "review this document"
→ Read the target document, run all five checks,
  then provide structured feedback.

**Example 2:** PM auto-dispatches after handbook completion
→ Review the markdown source of the finished HTML file
  and report compliance with the authoring guidelines.
The Steps section is the agent's 'procedure manual'. Write it clearly and in order. Specific instructions ("read every h2 section in order and confirm each has body text") beat vague ones ("review the document well"). Agents follow instructions faithfully, so the more precise the instruction, the higher the quality of the result.

Using skill-lifecycle-manager

What Is skill-lifecycle-manager?

skill-lifecycle-manager is a management skill that guides the creation, validation, and maintenance of skills. Think of it as the skill counterpart of the agent-lifecycle-manager you learned in Chapter 9. Following its guidance when creating a new skill lets you write it correctly, with nothing missing.

The core roles of this skill are:

  • Guiding the steps needed when creating a new skill
  • Checking that frontmatter fields are written correctly
  • Guiding system registration (AGENTS.md, VERSION_MANIFEST.md)
  • Providing instructions for running validation scripts

The 6-Step Process

skill-lifecycle-manager walks you through skill creation in six steps. Follow them in order to produce a complete, polished skill.

Step-by-Step Guidance

  1. Create the skill directory — make the skills/<name>/ folder. Use kebab-case (lowercase + hyphens), e.g., skills/my-reviewer/. Inside it, create an empty SKILL.md.
  2. Write the frontmatter — fill in the required fields covered earlier (name, status, description, owner, version) plus the optional ones (metadata.type, metadata.triggers). Set status to draft at first.
  3. Write the body — compose the Overview, When to Use, Steps, Expected Outputs, and Examples sections. Make Steps especially clear and numbered.
  4. Register in the system — add the skill to the AGENTS.md Skills table (§6) and record its version information in docs/VERSION_MANIFEST.md. Only after this step does the system recognize the skill.
  5. Validate — run bun scripts/skill-lifecycle-audit.ts to automatically check for missing frontmatter fields, file structure errors, missing required sections, etc. Fix any errors and re-validate.
  6. Activation test — test the skill via the PM with a real request. For example, ask "review this document's quality" and check that the skill triggers and runs properly. Once all tests pass, change status to active.

The skill-creator Plugin

What Is skill-creator?

skill-creator is an advanced skill authoring tool provided as a Claude Code plugin. Beyond writing SKILL.md files by hand, this plugin lets you build and improve skills more efficiently.

Main Features

skill-creator provides the following capabilities.

  • Skill creation — writes a brand-new SKILL.md through interactive guidance. It asks about each frontmatter field and proposes the structure of the body sections.
  • Skill editing — improves existing skill content. You can make triggers more specific or sharpen the Steps section.
  • Trigger improvement — analyzes a skill's trigger keywords and proposes changes so they match more accurately.

Test-Driven Iterative Authoring

The most powerful feature of skill-creator is test-driven iterative authoring. It works like this:

1. Draft the skill — skill-creator interactively generates a draft of the frontmatter and body.
2. Test triggers — based on the draft, test whether the skill matches correctly on your intended keywords.
3. Analyze results — inspect the matching results for false positives (unintended matches) or false negatives (missed matches).
4. Fix triggers — adjust trigger keywords or description based on the analysis.
5. Re-test — test again with the revised version. Repeat steps 2–5 until satisfied.

Usage in the Claude Code CLI Environment

skill-creator runs as a plugin in the Claude Code CLI environment. In the Claude Desktop App environment, direct file editing takes its place.

Claude Code CLI environment

  • skill-creator plugin available
  • Interactive skill creation/editing
  • Automated trigger testing
  • Iterative authoring workflow supported
  • See Appendix B

Claude Desktop App environment

  • Substitute with direct file editing
  • Use the manual method learned in this chapter
  • Testing via the PM
  • Run validation scripts manually
  • Recommended for beginners
skill-creator is an advanced tool for the Claude Code CLI environment. In the Claude Desktop App you can substitute direct file editing. The manual method taught in this chapter (writing frontmatter + body yourself) is the basic approach that works in both environments.

Registration & Deployment

Where to Register

Once the skill is written, you must register it in two places so the system can recognize it. Skip this and the PM will not find the skill, so it will never be dispatched.

  1. AGENTS.md Skills table (§6) — add the skill's name, file location, version, and status to the Skills table in the workspace-root AGENTS.md. This table acts as the skill registry.
  2. docs/VERSION_MANIFEST.md — record the skill's version information and status. It tracks version history and shows at a glance which skills are active. VERSION_MANIFEST.md is the SSOT (Single Source of Truth) for skill versions.

AGENTS.md Registration Example

Add a row like this to the AGENTS.md Skills table.

| my-reviewer | `skills/my-reviewer/SKILL.md` | quality | Checks readability, consistency, completeness | active | 1.0.0 |

VERSION_MANIFEST.md Registration Example

- **name:** my-reviewer
  **path:** skills/my-reviewer/SKILL.md
  **version:** 1.0.0
  **status:** active
  **owner:** pm
  **type:** quality

Deployment: sync-skills.ts

L0 (workspace) skills can be synced to every template (L1) and project (L2) via the sync-skills.ts script. Running it clones the workspace's skills into all downstream projects.

# Run the skill sync script
bun scripts/sync-skills.ts
L0 (workspace) skills are available in every project. L2 (project) skills, by contrast, are used only within their project. When you first create a skill, registering it at L0 is recommended so every project can benefit.

Practice: Build Your Own Custom Skill

Practice Goal

In this practice you will build a "document review skill (my-reviewer)" yourself. You will experience the entire process firsthand: frontmatter writing, body writing, system registration, and validation.

Practice Steps

  1. Open a project in the Claude Desktop App — launch the Claude Desktop App and open the project you are working on. Check that a skills/ folder exists at the project root.
  2. Create the directory — make the skills/my-reviewer/ folder and create a SKILL.md file inside it.
  3. Write the frontmatter — write the YAML frontmatter at the top of SKILL.md. Refer to the example below.
  4. Write the body — below the frontmatter, write the Overview, When to Use, Steps, Expected Outputs, and Examples sections.
  5. Register in AGENTS.md — add the my-reviewer skill to the AGENTS.md Skills table.
  6. Run the validation script — run bun scripts/skill-lifecycle-audit.ts to validate the skill structure. Fix any errors.
  7. Test via the PM — ask Claude to "review this document's quality" and confirm the skill works properly.

Full File Example

The following is the complete content of skills/my-reviewer/SKILL.md. Use it as-is or adapt it to your needs.

---
name: my-reviewer
status: active
description: >
  Reviews document quality and provides structured feedback.
  Checks readability, consistency, and completeness of
  markdown documents. Outputs a structured review report
  with severity levels and improvement suggestions.
owner: pm
version: "1.0.0"
metadata:
  type: quality
  triggers:
    - "review document"
    - "check quality"
    - "quality review"
    - "문서 검토"
    - "품질 확인"
---

## Overview

This skill performs a comprehensive quality review of
markdown documents. It evaluates documents from three
perspectives: readability, consistency, and completeness,
then provides structured feedback with actionable suggestions.

Scope: markdown (.md) files in the project workspace.

## When to Use

Activate this skill when:
- The user requests a document review
- A document has been newly created or significantly revised
- PM dispatches quality review as part of a pipeline gate
- The user asks to "check quality" or "review document"

## Steps

1. **Identify target file** — Confirm the file path of the
   document to review. If not specified, ask the user.
2. **Read the document** — Load the full content of the
   target file.
3. **Readability check** — Evaluate sentence length,
   paragraph structure, heading hierarchy, and overall
   flow. Flag sections that are hard to follow.
4. **Consistency check** — Verify terminology usage, format
   style, date format, heading capitalization, and list
   formatting across the entire document.
5. **Completeness check** — Identify missing sections,
   incomplete sentences, broken references, and unresolved
   TODO markers.
6. **Generate review report** — Compile findings into a
   structured report with severity levels:
   - INFO: minor suggestions
   - WARNING: recommended improvements
   - ERROR: issues that must be fixed

## Expected Outputs

- Structured review report (stdout)
- Issue count by severity (INFO / WARNING / ERROR)
- Prioritized improvement suggestions

## Examples

**Example 1:** User says "review document"
→ Read the specified file, run all 3 checks,
  output a structured review report.

**Example 2:** PM dispatches after handbook chapter
  completion
→ Review the chapter HTML source, check authoring
  guideline compliance, report findings.
After finishing the skill, ask the PM to "review this document's quality" and confirm it works properly. If the skill does not trigger, check that its keywords appear in the frontmatter triggers field and that the skill is registered in AGENTS.md. Trigger matching works best when the phrase closely matches a keyword.

Validation Checklist

After finishing the skill, do a final check with this checklist.

Check item What to verify
File location Does the file exist at skills/my-reviewer/SKILL.md?
Required fields Are name, status, description, owner, and version all filled in?
Body sections Are Overview, When to Use, Steps, Expected Outputs, and Examples present?
AGENTS.md registration Was the skill added to the Skills table?
VERSION_MANIFEST Was the version information recorded?
Behavior test Does it work correctly with trigger keywords?
Chapter Summary
  • A skill is a reusable workflow an agent performs. If the agent is "who," the skill defines "what gets done."
  • SKILL.md consists of YAML frontmatter (metadata) and a markdown body (execution instructions).
  • Frontmatter fields: name, status, description, owner, version are required; metadata.type and metadata.triggers are optional.
  • The body is recommended to consist of Overview, When to Use, Steps, Expected Outputs, and Examples sections.
  • skill-lifecycle-manager guides the 6-step process: create directory → frontmatter → body → register → validate → test.
  • skill-creator is an advanced tool supporting test-driven iterative authoring in the Claude Code CLI environment.
  • Registration happens in two places: the AGENTS.md Skills table and VERSION_MANIFEST.md.
