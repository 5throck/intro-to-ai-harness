Capítulo 10

Creación y modificación de skills

Este capítulo cubre la estructura de los archivos de habilidad, las herramientas skill-lifecycle-manager y skill-creator, y le guía en la construcción y el registro de su propia habilidad personalizada.

Lo que cubre este capítulo
  • Skill file format and structure
  • YAML frontmatter field meanings
  • Body content patterns (Overview, When to Use, Steps, Resultados, Examples)
  • skill-lifecycle-manager usage (6-step)
  • skill-creator (Claude Code plugin) overview
  • Practice: create a simple custom skill

Rethinking Skills

En el Capítulo 4, presentamos el concepto de habilidades (skills): libros de recetas reutilizables que indican a los agentes cómo realizar tipos específicos de trabajo. En este capítulo, profundizamos un nivel más — realmente crearemos una nueva habilidad desde cero, la registraremos en el proyecto y verificaremos que se active correctamente.

A Quick Review from Capítulo 4

Recordemos la distinción clave entre agentes y habilidades:

Agent

  • What: A digital employee with a fixed identity
  • Analogía: The employee themselves
  • File: agents/<name>.md
  • Scope: Persistent role across the entire project

Skill

  • What: A reusable instruction recipe
  • Analogía: The recipe book the employee follows
  • File: skills/<name>/SKILL.md
  • Scope: Invoked on demand; shared across agents

Un chef (agente) utiliza diferentes recetas (habilidades) dependiendo del plato que haya pedido el cliente. La identidad del chef no cambia, pero la receta les dice exactamente cómo preparar cada plato. El agente html-build siempre construye diapositivas HTML, pero la habilidad html-build le indica precisamente cómo leer el archivo de la presentación, aplicar el tema y producir la salida.

Ownership Layers (L0 / L1 / L2 / L3)

Las habilidades viven en diferentes capas de la jerarquía del espacio de trabajo, y comprender en qué capa está editando es fundamental:

  1. L0 — Raíz del Espacio de Trabajo (skills/): La Única Fuente de Verdad. Todo el desarrollo de habilidades ocurre aquí. Cuando crea o edita una habilidad, esta es la capa que modifica.
  2. L1 — Plantilla Común (templates/common/skills/): Una instantánea publicada desde L0 mediante bun run propagate:apply. Tú nunca editas L1 directamente — los cambios fluyen desde L0 hacia abajo.
  3. L2 — Plantilla Variante (templates/co-*/skills/): Habilidades específicas de la variante definidas en la capa de plantilla L2. Cada variante (co-deck, co-consult, etc.) puede incluir habilidades que se comparten en todos los proyectos basados en esa variante.
  4. L3 — Nivel del Proyecto (Proyectos/<name>/skills/): Una capa específica del proyecto creada cuando un proyecto L3 se basa en una plantilla variante L2. Las personalizaciones locales se pueden añadir aquí sin afectar a otros proyectos o a la plantilla variante.
La Analogía de la “Receta”
Si el agente es un chef, entonces la habilidad es una tarjeta de receta en el cuaderno de recetas de la cocina. El cuaderno es el espacio de trabajo L0 (la copia maestra). Los libros de cocina impresos para cada cadena de restaurantes son las plantillas L1. Las variaciones de recetas añadidas para una cocina específica (por ejemplo, italiana, japonesa) son las habilidades variantes L2. Las notas garabateadas en el margen de la copia de un restaurante son las anulaciones del proyecto L3. Tú siempre escribes nuevas recetas en el cuaderno maestro (L0), luego distribuyes copias.

Skill File Format

Cada habilidad vive en su propio directorio bajo skills/, con un único archivo llamado SKILL.md. El nombre es importante: el nombre del directorio utiliza kebab-case, y el archivo dentro siempre es SKILL.md en mayúsculas.

File location
skills/<name>/SKILL.md

Al igual que los archivos de agent, un archivo de skill tiene dos partes: un YAML frontmatter block (metadatos legibles por máquina) y un Markdown body (instrucciones legibles por humanos). La estructura es más simple que la de un archivo de agent, pero se aplica el mismo principio: el frontmatter es para el sistema, el cuerpo es para el modelo de IA.

Structure Overview

El frontmatter está encerrado entre dos vallas ---, igual que los archivos de agent. Todo lo que está debajo de la valla de cierre es el cuerpo — Markdown estándar con encabezados, listas, bloques de código y tablas.

Skill vs Agent File Naming
Los archivos de agent viven en agents/<name>.md (un archivo por agent). Los archivos de skill viven en skills/<name>/SKILL.md (un directorio por skill, siempre con un SKILL.md en mayúsculas dentro). Esta capa adicional de directorio permite que las skills agrupen archivos complementarios (ejemplos, fixtures de prueba) junto con el documento de instrucciones principal.

Writing Frontmatter

El frontmatter YAML es la tarjeta de identidad legible por máquina de tu skill. La capa de orquestación (PM, scripts, coincidencia de triggers) lee estos campos para decidir when y how activar la skill.

Required and Optional Fields

Field Required? Type Descripción
name Required string Kebab-case identifier. Must match the directory name.
status Required string One of: active, draft, deprecated, retired.
description Required string Resumen multilínea de lo que hace la skill y cuándo usarla. Debe incluir Use when: escenarios de trigger.
owner Required string El agent o rol responsable de mantener esta skill (p. ej., pm, research).
version Required string Semantic version (start at 1.0.0).
metadata.type Required string One of: process (workflow/methodology), implementation (technical), domain (domain-specific knowledge).
metadata.triggers Required list Palabras clave que activan esta skill. Debe tener al menos una entrada.
scope Optional string Visibility scope: common (all projects) or variant (project-specific).
last_reviewed Optional string Date of last review (YYYY-MM-DD).
prerequisites Optional string Any prerequisite tools or runtime requirements (e.g., Bun runtime).

Example Frontmatter

skills/document-reviewer/SKILL.md — frontmatter
---
name: document-reviewer
status: active
scope: common
description: >
  Reviews markdown documents for clarity, consistency, and formatting
  compliance. Checks heading hierarchy, link validity, and writing style.
  Use when: "review this document", "check formatting", "proofread markdown".
owner: pm
version: 1.0.0
last_reviewed: 2026-08-10
prerequisites: none
metadata:
  type: process
  triggers:
    - review document
    - check formatting
    - proofread
    - document quality
---
Elegir el Tipo Adecuado
process — Workflow and methodology skills (e.g., sync, meeting-facilitation, skill-lifecycle-manager).
implementation — Technical implementation skills (e.g., html-build, pdf-export, measure).
domain — Domain-specific knowledge skills (e.g., dart-disclosure-parser, mece-logic-auditor).
Elija el tipo que mejor describa el propósito principal de la habilidad. La mayoría de las habilidades de flujo de trabajo de propósito general son process.

Writing Body Content

Debajo de la valla de cierre ---, el cuerpo en Markdown sirve como el manual de instrucciones de la habilidad. Cuando se carga la habilidad, el modelo de IA lee todo el cuerpo y sigue su guía. Un buen contenido del cuerpo significa que el agente realiza el flujo de trabajo de manera consistente y correcta cada vez.

5 Secciones recomendadas

Aunque el cuerpo puede organizarse de muchas maneras, la mayoría de las habilidades se benefician de estas cinco secciones, presentadas en orden:

  1. Visión general (Overview) — Una explicación de alto nivel del propósito de la habilidad. ¿Qué problema resuelve? ¿Qué valor aporta? Manténgalo en 2–4 frases.
  2. Cuándo usar esta habilidad (When to Use This Skill) — Condiciones de activación y casos de uso concretos. Enumere las frases o situaciones que deben activar esta habilidad. Esto refuerza las palabras clave de activación en el frontmatter.
  3. Pasos (Steps) — Instrucciones numeradas y secuenciales que sigue el agente para completar la tarea. Agrúpelas por fases lógicas si el flujo de trabajo es complejo. Cada paso debe ser accionable e incluir puntos de control de validación cuando sea apropiado.
  4. Resultados esperados (Expected Results) — Lo que produce la habilidad. Especifique nombres de archivo, formatos y estructura del contenido para que el siguiente agente en la tubería sepa exactamente qué esperar.
  5. Ejemplos (Examples) (opcional) — Ejemplos de uso concretos que muestran cómo se comporta la habilidad en escenarios realistas. Incluya entradas y salidas de muestra.
Keep Steps Clear and Sequential
La sección Pasos (Steps) es el corazón de su habilidad. Escriba cada paso como un comando directo en modo imperativo: «Leer el archivo de entrada», «Validar la estructura», «Escribir el informe de salida». Evite frases vagas como «Manejar los datos». Incluya rutas de archivo específicas, requisitos de formato y comprobaciones de validación en cada paso. Si un paso tiene subpasos, utilice listas numeradas subordinadas (1.1, 1.2, etc.) para mantener la claridad de la jerarquía.

Section Details with Examples

1. Overview

Comience con una declaración concisa de lo que hace la habilidad y por qué existe.

## Overview

Reviews markdown documents for structural clarity, formatting
consistency, and writing quality. Produces a structured review
report with categorized findings and actionable fix suggestions.

2. Cuándo usar esta habilidad

List specific trigger scenarios.

## When to Use

- User says "review this document" or "check formatting"
- Before publishing a markdown file to catch issues
- After a major edit to verify the document still meets standards
- When quality-gating content before handoff to the next agent

3. Steps

Provide numbered, actionable instructions.

## Steps

### Step 1: Load and Parse
- Read the target markdown file using the Read tool
- Parse the document structure (headings, links, code blocks)

### Step 2: Structural Checks
- Verify heading hierarchy (no H3 before H2, etc.)
- Check that every internal link targets an existing file
- Validate that code blocks specify a language

### Step 3: Quality Review
- Flag passive voice overuse (more than 30% of sentences)
- Check for run-on paragraphs (more than 5 sentences)
- Verify consistent terminology usage

4. Expected Resultados

Define what the skill produces.

## Expected Outputs

- `review-report.md` in the same directory as the input file
- Sections: Structure, Links, Style, Terminology
- Each finding includes: severity (error/warning/info),
  location (line reference), and suggested fix

5. Examples (optional)

Show realistic usage scenarios.

## Examples

**Input**: User says "Review docs/ch02/02_Getting_Started.md"
**Output**: Creates `docs/ch02/review-report.md` with 3 errors
  (broken link, missing H1, code block without language) and
  5 warnings (passive voice, long paragraphs).
El Cuerpo Es un “Manual de Instrucciones”
A diferencia del frontmatter (que es leído por scripts y el comparador de activación), el cuerpo es leído por el modelo de IA cuando se carga la habilidad. Escríbalo como si estuviera escribiendo un manual para un nuevo miembro del equipo: claro, específico y centrado en cómo hacer el trabajo. El «por qué» pertenece a la visión general; el «cuándo» pertenece a la sección de activación; y el «cómo» pertenece a los pasos.

Using skill-lifecycle-manager

La habilidad skill-lifecycle-manager proporciona un proceso sistemático de 6 pasos para crear, validar y mantener habilidades. En lugar de crear archivos manualmente y esperar que todo se conecte, la habilidad lo guía a través de cada paso y detecta problemas tempranamente.

The 6-Step Process

Step-by-Step Explanation

  1. Crear el directorio — Cree skills/<name>/SKILL.md utilizando kebab-case para el nombre del directorio. El archivo debe llamarse exactamente SKILL.md (en mayúsculas).
  2. Escribir el frontmatter — Rellene todos los campos YAML requeridos: name, status, description, owner, version, metadata.type y metadata.triggers. El nombre del directorio y el campo name deben coincidir.
  3. Escribir el contenido del cuerpo — Redacte las instrucciones en Markdown cubriendo Visión general, Cuándo usar, Pasos (con puntos de control de validación), Resultados esperados y, opcionalmente, Ejemplos.
  4. Registrar en la documentación — Agregue la habilidad a la tabla de Habilidades en AGENTS.md y a la sección Skills en docs/context.md. Incluya la ruta del archivo y las condiciones de activación.
  5. Validar — Ejecute bun run verify-skills (o bun scripts/validate-skills.ts) para verificar que la habilidad pasa todas las comprobaciones estructurales y de contenido.
  6. Probar la activación — Intente cargar la habilidad a través de la herramienta de la plataforma (por ejemplo, la herramienta Skill en Claude Code) y verifique que el frontmatter se carga correctamente, que el contenido es accionable y que los activadores coinciden con los casos de uso esperados.
Start Simple, Iterate
No necesita una habilidad perfecta desde el primer día. Cree una habilidad mínima viable con los campos de frontmatter requeridos y una sección Pasos básica. Establezca inicialmente status: draft. Pruébelo, refine la redacción basándose en cómo lo interpreta el modelo y luego promuévalo a status: active una vez que se comporte de manera consistente. El lifecycle-manager hace que la iteración sea segura: cada cambio puede validarse automáticamente antes de la promoción.

skill-creator Plugin

Además del proceso manual descrito anteriormente, Claude Code proporciona un plugin skill-creator que puede ayudar con la creación e iteración de archivos de habilidad. Este plugin está disponible en el mercado de plugins de Claude Code CLI.

What skill-creator Does

The skill-creator plugin helps with three key workflows:

  1. Crear desde cero — Genera un nuevo archivo SKILL.md con el frontmatter y la estructura del cuerpo adecuados basados en su descripción del propósito de la habilidad.
  2. Edit existing skills — Refina la redacción, añade secciones faltantes o reestructura una skill existente para mejorar la fiabilidad de los triggers y la claridad de las instrucciones.
  3. Iterar redacción — Prueba diferentes frases para las condiciones de activación y las instrucciones de los pasos para encontrar lo que funciona mejor para un comportamiento consistente de la IA.

Test-Driven Iterative Authoring

El skill-creator sigue un enfoque basado en pruebas (test-driven): escriba un borrador, pruebe el activador, observe cómo se comporta el modelo y luego refine la redacción. Este ciclo se repite hasta que la habilidad se activa de manera confiable y produce una salida consistente.

1. Describir — Dígale a skill-creator qué quiere que haga la habilidad (propósito, frases activadoras, comportamiento esperado).
2. Borrador — skill-creator genera el SKILL.md inicial con frontmatter y cuerpo.
3. Probar — Cargue la habilidad en una sesión real e intente las frases activadoras. Observe la salida.
4. Refine — Basado en the test results, adjust trigger keywords, clarify ambiguous steps, or add missing validation checkpoints.
5. Validar — Ejecute la validación del skill-lifecycle-manager para asegurar el cumplimiento estructural antes de registrarla.
Claude Desktop Ap Alternative
Si está utilizando Claude Desktop App sin el mercado de plugins de Claude Code CLI, puede lograr el mismo flujo de trabajo pidiéndole directamente a Claude: «Crea una habilidad que revise documentos markdown en busca de problemas de formato». Claude redactará el archivo SKILL.md por usted. Luego puede registrarlo y validarlo manualmente utilizando los pasos del skill-lifecycle-manager descritos en la sección anterior. La diferencia clave es que el plugin skill-creator automatiza el ciclo de iteración; con Claude Desktop App, tú gestionas el ciclo probar-refinar manualmente.

Registration & Deployment

Una habilidad que no está registrada es como una tarjeta de receta que nunca llegó al cuaderno de la cocina. El sistema no puede descubrirla, los agentes no pueden cargarla y los scripts de auditoría la marcarán como huérfana. El registro hace que su habilidad sea visible para todo el espacio de trabajo.

Registration Locations

Necesita registrar su habilidad en dos ubicaciones principales:

  1. AGENTS.md — Tabla de Habilidades (§6): Agregue una fila con el nombre de la habilidad, la ruta del archivo (skills/<name>/SKILL.md) y una breve descripción. Este es el registro principal al que hacen referencia las herramientas PM y de documentación.
  2. docs/context.md — Sección de Habilidades: Agregue el nombre, tipo y breve descripción de la habilidad en la sección de habilidades. Esto asegura que la habilidad aparezca en la documentación dirigida al desarrollador.

Registration Example

AGENTS.md — Skills table entry
| document-reviewer | `skills/document-reviewer/SKILL.md` | Reviews markdown documents for clarity, consistency, and formatting compliance |
docs/context.md — Skills section entry
### document-reviewer
- **File**: `skills/document-reviewer/SKILL.md`
- **Type**: process
- **Description**: Reviews markdown documents for clarity, consistency, and formatting compliance.

Deploying with sync-skills.ts

Después de crear o actualizar una habilidad, ejecute el script de sincronización para distribuirla a los directorios específicos de la plataforma:

Deploy skill to all platforms
bun scripts/sync-skills.ts

Este script copia la skill desde skills/<name>/SKILL.md hacia .claude/skills/<name>/SKILL.md y .gemini/skills/<name>/SKILL.md para que tanto Claude Code como Antigravity CLI puedan descubrirla y cargarla. Si estás en el workspace L0 y existe un directorio templates/common/, también debes propagar a la plantilla L1 ejecutando bun run propagate:apply.

L0 Accessibility
Las skills a nivel de workspace (skills/) tienen la prioridad highest en el orden de resolución de skills (ver Capítulo 4). Esto significa que una skill que crees en L0 siempre tendrá precedencia sobre las skills a nivel de plataforma o de plugin con el mismo nombre. Usa este poder con responsabilidad — evita crear skills que dupliquen o eclipsen funcionalidades existentes de plugins, a menos que quieras anularlas intencionalmente.

Practice: Build Your Own Custom Skill

Ahora es tu turno. En este ejercicio, crearás una skill document-reviewer desde cero — una receta reutilizable que revisa documentos markdown para verificar formato, estructura y calidad de escritura.

Goal: Create a functional document-reviewer skill, register it in AGENTS.md, deploy it with sync-skills.ts, and test that it triggers correctly.
  1. Crea el directorio y el archivo
    Crea el directorio skills/document-reviewer/ y añade un archivo llamado SKILL.md dentro de él.
  2. Escribe el frontmatter
    Add the YAML frontmatter with all required fields. Here is the complete frontmatter for reference:
    skills/document-reviewer/SKILL.md — frontmatter
    ---
name: document-reviewer
status: draft
scope: common
description: >
  Reviews markdown documents for clarity, consistency, and formatting
  compliance. Checks heading hierarchy, link validity, and writing style.
  Use when: "review this document", "check formatting", "proofread markdown".
owner: pm
version: 1.0.0
last_reviewed: 2026-08-10
prerequisites: none
metadata:
  type: process
  triggers:
    - review document
    - check formatting
    - proofread
    - document quality
---
  3. Escribe el cuerpo
    Use la estructura de cinco secciones. Aquí está el cuerpo completo:
    skills/document-reviewer/SKILL.md — body
    ## Overview

Reviews markdown documents for structural clarity, formatting
consistency, and writing quality. Produces a structured review
report with categorized findings and actionable fix suggestions.

## When to Use

- User says "review this document" or "check formatting"
- Before publishing a markdown file to catch issues
- After a major edit to verify the document still meets standards
- When quality-gating content before handoff to the next agent

## Steps

### Step 1: Load and Parse
- Read the target markdown file using the Read tool
- Parse the document structure (headings, links, code blocks)
- Count total lines and estimate word count

### Step 2: Structural Checks
- Verify heading hierarchy (no H3 before H2, exactly one H1)
- Check that every internal link targets an existing file
- Validate that code blocks specify a language tag
- Ensure images have alt text

### Step 3: Style Review
- Flag passive voice overuse (more than 30% of sentences)
- Check for run-on paragraphs (more than 5 sentences)
- Verify consistent terminology (same term used throughout)
- Check for redundant phrases or wordiness

### Step 4: Generate Report
- Create `review-report.md` in the same directory as the input
- Structure the report with sections: Structure, Links, Style,
  Terminology, Summary
- Each finding includes severity (error/warning/info), location
  (line reference), and suggested fix

## Expected Outputs

- `review-report.md` in the same directory as the reviewed file
- Sections: Structure, Links, Style, Terminology, Summary
- Severity levels: error (must fix), warning (should fix),
  info (suggestion)
- Word count and line count summary at the top

## Examples

**Input**: "Review docs/ch02/02_Getting_Started.md"
**Output**: Creates `docs/ch02/review-report.md` reporting
  2 errors (broken link on line 45, missing H1), 4 warnings
  (passive voice, long paragraphs), and 3 info items
  (terminology suggestions).
  4. Register in AGENTS.md
    Agregue el document-reviewer a la tabla de Habilidades en AGENTS.md con la ruta del archivo y la descripción. Si su proyecto tiene un docs/context.md, agregue también una entrada allí.
  5. Despliega con sync-skills.ts
    Ejecute bun scripts/sync-skills.ts en su terminal para distribuir la habilidad a los directorios específicos de la plataforma (.claude/skills/ y .gemini/skills/).
  6. Validate
    Ejecute bun run verify-skills (o bun scripts/validate-skills.ts) para verificar que la habilidad pasa todas las comprobaciones estructurales y de contenido. Corrija cualquier error informado.
  7. Test activation
    En Claude Code (o Claude Desktop App), intente decir: «Revisa el archivo README.md en busca de problemas de formato». Verifique que la habilidad se cargue, que los pasos se ejecuten y que el archivo review-report.md se cree con la estructura esperada.
Probar Es Esencial
La verdadera prueba de una nueva habilidad no es si el script de validación pasa — sino si la habilidad produce una salida útil cuando se activa con una solicitud real del usuario. Después de que la validación pase, ejecute siempre al menos una prueba de extremo a extremo: active la habilidad con un prompt realista, revise la salida y refine las instrucciones del paso si los resultados son inconsistentes o pasan por alto comprobaciones importantes. Las habilidades son documentos vivos; espere iterar 2–3 veces antes de que el comportamiento sea confiablemente consistente.
Key Takeaways
  • A skill is a reusable instruction recipe stored at skills/<name>/SKILL.md
  • Skill file = YAML frontmatter (metadata + triggers) + Markdown body (instructions)
  • Frontmatter requires: name, status, description, owner, version, metadata.type, metadata.triggers
  • Body sections: Overview, When to Use, Steps, Expected Resultados, Examples
  • skill-lifecycle-manager provides a 6-step creation and validation process
  • skill-creator (Claude Code plugin) assists with test-driven iterative authoring
  • Registrar habilidades en AGENTS.md y docs/context.md, luego desplegar con bun scripts/sync-skills.ts
  • Probar siempre la activación con una frase activadora real después de que haya pasado la validación
  • Comenzar con status: draft, promover a active después de que la habilidad se comporte consistentemente
