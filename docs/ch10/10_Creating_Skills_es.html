Capítulo 10

Creación y modificación de skills

En este capítulo aprenderás la estructura de los archivos de skill y recorrerás todo el proceso de crear y registrar tu propia skill personalizada con skill-lifecycle-manager y skill-creator.

Lo que cubre este capítulo
  • Formato y estructura del archivo de skill
  • Significado de los campos YAML del frontmatter
  • Patrones de redacción del cuerpo (Overview, When to Use, Steps, Outputs, Examples)
  • Cómo usar skill-lifecycle-manager (6 pasos)
  • Cómo usar skill-creator (plugin de Claude Code)
  • Práctica: escribir una skill personalizada sencilla

Repensando las skills

Repaso del capítulo 4

En el capítulo 4, «Conceptos del harness multiagente», conocimos por primera vez las skills. Aprendimos que una skill es "un flujo de trabajo reutilizable que un agente puede ejecutar". Una skill se compone de cuatro elementos —nombre, descripción, trigger y pasos— y se activa automáticamente ante ciertas palabras clave o situaciones.

Recordando, los cuatro elementos esenciales de una skill eran:

  • Nombre (Name) — el nombre único que identifica la skill (por ejemplo: research, html-build, pdf-export)
  • Descripción (Description) — el detalle de qué hace esta skill y qué pasos sigue
  • Trigger — las condiciones bajo las que la skill se activa automáticamente (palabras clave, patrones de comandos, fases del pipeline)
  • Pasos (Steps) — el procedimiento concreto que ejecuta la skill (definido en orden)

Skill vs. agente (una vez más)

En el capítulo 9 aprendiste a crear agentes. Antes de aprender a crear skills, fijemos de nuevo con claridad la diferencia entre ambos conceptos.

Agente

  • "Quién" realiza la tarea
  • Un asistente de IA con rol, permisos y herramientas
  • Analogía: el cocinero (un empleado)
  • Ubicación del archivo: agents/<name>.md

Skill

  • "Qué" se realiza
  • Un procedimiento de flujo de trabajo reutilizable
  • Analogía: la receta
  • Ubicación del archivo: skills/<name>/SKILL.md
Analogía para principiantes: una skill es una "receta de cocina". El agente (el cocinero) sigue la receta para preparar el plato (la tarea). Un cocinero puede tener muchas recetas, y varios cocineros pueden compartir la misma receta. Cuando la receta está clara, cualquier cocinero obtiene resultados consistentes.

Las capas de propiedad (ownership) de una skill

A diferencia de los agentes, las skills existen de forma independiente. Una skill puede definirse en varias capas, y cada capa tiene un alcance y una influencia distintos.

L0 — Workspace (espacio de trabajo)

  • Ubicación: skills/<name>/SKILL.md
  • Alcance: disponible en todos los proyectos
  • Prioridad: la más alta (prioridad 1)
  • Ejemplos: sync, security-scan

L1 — Plantilla común (Common Template)

  • Ubicación: templates/common/skills/
  • Alcance: los proyectos derivados de esa plantilla
  • Prioridad: después de L0 (prioridad 2)
  • Ejemplos: skills de validación comunes de la plantilla

L2 — Plantilla variante (Variant Template)

  • Ubicación: templates/co-*/skills/
  • Alcance: todos los proyectos generados a partir de esa variante
  • Prioridad: después de L1 (prioridad 3)
  • Ejemplos: skills exclusivas de co-deck

L3 — Proyecto

  • Ubicación: .claude/skills/o .gemini/skills/
  • Alcance: solo ese proyecto
  • Prioridad: la más baja (prioridad 4)
  • Ejemplos: hooks exclusivos del proyecto

Reglas básicas

  • Si la misma skill existe en varias ubicaciones, se usa la de prioridad 1
  • Las skills L0 se comparten globalmente
  • Las skills L2 pertenecen solo a una variante; las L3, solo a un proyecto
  • Como principio, evita definiciones duplicadas

¿Por qué crear las tuyas?

El sistema ya incluye diversas skills. A medida que los requisitos del proyecto se diversifican aparecen flujos de trabajo no cubiertos por las skills existentes. Por ejemplo:

  • Revisión de calidad documental — una skill que revisa la consistencia y completitud de los documentos generados
  • Despliegue automático — una skill que publica los entregables terminados en un servidor específico automáticamente
  • Generación de informes a medida — una skill que produce informes con formato específico del proyecto
  • Revisión periódica de estado — una skill que inspecciona el estado general del proyecto con regularidad

Cuando necesites uno de estos flujos de trabajo, puedes crear tu propia skill personalizada y añadirla al sistema. Una skill es un único archivo markdown, así que cualquiera puede crearla siguiendo unas pocas reglas.

A diferencia de los agentes, las skills existen de forma independiente. Varios agentes pueden referenciar la misma skill. Por ejemplo, la skill sync la usa sobre todo el agente PM, pero otros agentes también pueden referenciarla si lo necesitan.

Formato del archivo de skill

Ubicación del archivo

Los archivos de skill se guardan en el directorio skills/ de la raíz del proyecto. A diferencia de los agentes, cada skill tiene sus propia carpeta. El nombre de la carpeta es el nombre de la skill, y dentro va el archivo SKILL.md.

skills/
├── sync/
│   └── SKILL.md              # Skill de sincronización
├── security-scan/
│   └── SKILL.md              # Skill de análisis de seguridad
├── meeting-facilitation/
│   └── SKILL.md              # Skill de facilitación de reuniones
├── research/
│   └── SKILL.md              # Skill de investigación
└── my-reviewer/              # ★ La skill que vamos a crear
    └── SKILL.md

Estructura del archivo: frontmatter + cuerpo

Un archivo SKILL.md consta de dos partes. En la parte superior va el frontmatter YAML (metadatos) y debajo el cuerpo markdown (instrucciones de ejecución). El frontmatter YAML se escribe dentro de un bloque que abre y cierra con tres guiones, ---.

Las claves de esta estructura son:

  1. Frontmatter YAML — entre las vallas --- se escribe la información de identidad de la skill (nombre, estado, descripción, propietario, versión, metadatos). El sistema la usa para reconocer y gestionar la skill.
  2. Cuerpo markdown — debajo del frontmatter se escribe, en formato markdown, el procedimiento de ejecución que el agente debe seguir. Se recomienda organizarlo en las secciones Overview (resumen), When to Use (cuándo usarlo), Steps (pasos), Expected Outputs (resultados esperados) y Examples (ejemplos).
A diferencia de los agentes, las skills existen de forma independiente. Varios agentes pueden referenciar la misma skill. Por ejemplo, la skill security-scanpuede invocarla el agente PM o referenciarla directamente un agente especialista.

Redacción del frontmatter

Campos obligatorios y opcionales

El frontmatter YAML incluye varios campos para identificar y gestionar la skill. Se dividen en obligatorios y opcionales.

Campo Obligatorio Descripción Ejemplo
name Sí Nombre único de la skill my-reviewer
status Sí active / draft / deprecated active
description Sí Descripción detallada de la skill (el PM la consulta al despachar) "Reviews document quality..."
owner Sí Responsable del mantenimiento (agente o rol) pm
version Sí Número de versión (se recomienda versionado semántico) "1.0.0"
metadata.type Opcional automation / quality / lifecycle quality
metadata.triggers Opcional Lista de palabras clave que activan la skill automáticamente ["review document", "check quality"]

Detalles de cada campo

  1. name — el identificador único de la skill. Debe coincidir con el nombre de la carpeta: para skills/my-reviewer/SKILL.md el name es my-reviewer. Se recomienda kebab-case.
  2. status — el estado actual de la skill: active(en uso), draft(en redacción) o deprecated (retirada). Empieza una skill nueva como drafty cámbiala a active cuando pase la validación.
  3. description — la descripción detallada de la skill. El PM la consulta al decidir qué skill despachar, así que debe ser clara y específica. Incluye no solo "qué hace", sino también "qué pasos sigue".
  4. owner — el agente o rol responsable del mantenimiento de esta skill. Por ejemplo, una skill gestionada por el PM lleva pm; una skill de automatización lleva automation-engineer.
  5. version — el número de versión de la skill. Se recomienda el formato de versionado semántico (MAJOR.MINOR.PATCH): por ejemplo, "1.0.0", "1.1.0", "2.0.0".
  6. metadata.type — la clasificación de la skill. Elige una de estas: automation(automatización), quality(calidad) o lifecycle(ciclo de vida). Resulta útil para filtrar u ordenar la lista de skills.
  7. metadata.triggers — la lista de palabras clave que activan automáticamente la skill. Cuando una petición del usuario contiene esas palabras, el PM empareja y despacha la skill. Cuanto más específicos sean los triggers, más precisa será la coincidencia.

Ejemplo de frontmatter

A continuación, un ejemplo de frontmatter que puedes usar tal cual.

---
name: my-reviewer
status: active
description: Reviews document quality and provides structured feedback. Checks readability, consistency, and completeness of markdown documents.
owner: pm
version: "1.0.0"
metadata:
  type: quality
  triggers:
    - "review document"
    - "check quality"
    - "quality review"
---
Consejo para principiantes: como el PM consulta la description al elegir una skill, escríbela con detalle: por ejemplo, "Revisa la legibilidad, la consistencia y la completitud de documentos y ofrece retroalimentación estructurada". Una descripción larga y específica es mejor que una breve y vaga como "revisa documentos".

Redacción del cuerpo

Estructura recomendada del cuerpo

El cuerpo markdown bajo el frontmatter es el procedimiento de ejecución que el agente seguirá realmente. Se recomienda organizarlo en cinco secciones.

  1. Overview — explica el propósito y el alcance de la skill en uno o dos párrafos. Deja claro "¿para qué sirve esta skill?" y "¿hasta dónde llega su alcance?".
  2. When to Use — describe las condiciones que activan la skill: ¿cuándo debe activarse? Escribe concretamente qué situaciones, peticiones o estados de archivo la disparan.
  3. Steps — escribe el procedimiento detallado que sigue el agente como secuencia numerada. Cada paso debe ser claro e inequívoco. Indica de forma concreta: "lee el archivo → revísalo → redacta los resultados".
  4. Expected Outputs — indica qué archivos o resultados deben existir cuando la skill termine. Incluir nombres de archivo, rutas y formatos facilita que el siguiente agente aproveche los resultados.
  5. Examples — muestra escenarios reales de uso. Da ejemplos concretos de cómo se ejecuta esta skill cuando el usuario hace cierta petición.

Consejos de redacción por sección

En la sección Overview, explica por qué existe la skill. Escribe de modo que el lector (o agente) entienda "¿por qué usaría yo esta skill?".

## Overview

Esta skill realiza una revisión integral de la calidad de
documentos markdown. Evalúa los documentos desde tres
perspectivas —legibilidad, consistencia y completitud—
y ofrece retroalimentación estructurada.

En la sección When to Use, presenta condiciones de activación claras.

## When to Use

Se activa cuando el usuario hace peticiones como:
- "revisa este documento"
- "comprueba la calidad del documento"
- "hazme una revisión de calidad"

También puede despacharla automáticamente el PM
cuando otro agente necesite una revisión de calidad
tras terminar un documento.

La sección Steps es la parte más importante. Escribe el procedimiento con claridad.

## Steps

1. **Identificar el archivo objetivo** — Confirma la ruta del documento a revisar.
2. **Leer el documento** — Carga el archivo objetivo y analiza su contenido.
3. **Revisión de legibilidad** — Comprueba longitud de frases, estructura de párrafos y jerarquía de encabezados.
4. **Revisión de consistencia** — Comprueba terminología, estilo de formato y formatos de fecha.
5. **Revisión de completitud** — Busca secciones ausentes y frases incompletas.
6. **Redactar la retroalimentación** — Organiza los hallazgos en un formato estructurado.

En la sección Expected Outputs, indica los entregables.

## Expected Outputs

- Informe de revisión (stdout o salida a archivo)
- Lista de problemas (gravedad por elemento: advertencia / corrección recomendada / error)
- Lista de sugerencias de mejora

En la sección Examples, muestra ejemplos concretos de uso.

## Examples

**Ejemplo 1:** el usuario pide "revisa este documento"
→ Lee el documento objetivo, ejecuta las cinco comprobaciones
  y entrega retroalimentación estructurada.

**Ejemplo 2:** el PM lo despacha tras completar el manual
→ Revisa el origen markdown del archivo HTML terminado y
  informa del cumplimiento de las guías de autoría.
La sección Steps es el 'manual de procedimientos' del agente. Escríbela clara y en orden. Las instrucciones concretas ("lee todas las secciones h2 en orden y comprueba que cada una tenga cuerpo") son mejores que las vagas ("revisa bien el documento"). El agente sigue las instrucciones fielmente: cuanto más precisas sean, mayor será la calidad del resultado.

Uso de skill-lifecycle-manager

¿Qué es skill-lifecycle-manager?

skill-lifecycle-manager es una skill de gestión que guía la creación, validación y mantenimiento de skills. Piensa en ella como la versión skill del agent-lifecycle-manager que aprendiste en el capítulo 9. Siguiendo sus indicaciones al crear una skill nueva, la escribirás correctamente y sin omisiones.

Las funciones centrales de esta skill son:

  • Guiar los pasos necesarios al crear una skill nueva
  • Comprobar que los campos del frontmatter están bien escritos
  • Guiar el registro en el sistema (AGENTS.md, VERSION_MANIFEST.md)
  • Proporcionar las instrucciones para ejecutar los scripts de validación

El proceso de 6 pasos

skill-lifecycle-manager guía la creación de la skill en seis pasos. Si los sigues en orden obtendrás una skill completa y pulida.

Guía detallada paso a paso

  1. Crea el directorio de la skill — haz la carpeta skills/<name>/. Usa kebab-case (minúsculas + guiones), por ejemplo: skills/my-reviewer/. Dentro crea un archivo SKILL.md vacío.
  2. Escribe el frontmatter — rellena los campos obligatorios vistos antes (name, status, description, owner, version) más los opcionales (metadata.type, metadata.triggers). Pon status en draftal principio.
  3. Escribe el cuerpo — redacta las secciones Overview, When to Use, Steps, Expected Outputs y Examples. Cuida especialmente que Steps sea claro y numerado.
  4. Regístrala en el sistema — añade la skill a la tabla Skills de AGENTS.md (§6) y anota su información de versión en docs/VERSION_MANIFEST.md. Solo tras este paso el sistema reconocerá la skill.
  5. Valida — ejecuta bun scripts/skill-lifecycle-audit.ts para comprobar automáticamente campos ausentes del frontmatter, errores de estructura de archivos o secciones obligatorias faltantes. Corrige los errores y revalida.
  6. Prueba de activación — prueba la skill vía PM con una petición real. Por ejemplo, pide "revisa la calidad de este documento" y comprueba que se dispara y se ejecuta bien. Cuando pase todas las pruebas, cambia status a active.

El plugin skill-creator

¿Qué es skill-creator?

skill-creator es una herramienta avanzada de autoría de skills que se ofrece como plugin de Claude Code. Además de escribir SKILL.md a mano, este plugin te permite crear y mejorar skills con mayor eficiencia.

Funciones principales

skill-creator ofrece estas capacidades.

  • Creación de skills — escribe un SKILL.md nuevo desde cero mediante guía interactiva. Pregunta campo a campo del frontmatter y propone la estructura de las secciones del cuerpo.
  • Edición de skills — mejora el contenido de skills existentes. Puedes hacer los triggers más específicos o afinar la sección Steps.
  • Mejora de triggers — analiza las palabras clave de una skill y propone cambios para que coincidan con más precisión.

Autoría iterativa guiada por pruebas

La función más potente de skill-creator es la autoría iterativa guiada por pruebas (Test-Driven Iterative Authoring). Funciona así:

1. Borrador de la skill — skill-creator genera de forma interactiva un borrador del frontmatter y del cuerpo.
2. Prueba de triggers — con el borrador, comprueba si la skill coincide correctamente con tus palabras clave previstas.
3. Análisis de resultados — revisa las coincidencias buscando falsos positivos (coincidencias no deseadas) o falsos negativos (coincidencias perdidas).
4. Corrección de triggers — ajusta las palabras clave o la descripción según el análisis.
5. Repetir pruebas — vuelve a probar con la versión corregida. Repite los pasos 2–5 hasta quedar satisfecho.

Uso en el entorno Claude Code CLI

skill-creator funciona como plugin en el entorno de la línea de comandos de Claude Code. En el entorno de la Claude Desktop App puedes sustituirlo editando los archivos directamente.

Entorno Claude Code CLI

  • Plugin skill-creator disponible
  • Creación/edición interactiva de skills
  • Pruebas de triggers automatizadas
  • Flujo de autoría iterativa compatible
  • Consulta el Apéndice B

Entorno Claude Desktop App

  • Sustitúyelo por edición directa de archivos
  • Usa el método manual aprendido en este capítulo
  • Pruebas vía PM
  • Ejecuta los scripts de validación manualmente
  • Recomendado para principiantes
skill-creator es una herramienta avanzada para el entorno Claude Code CLI. En la Claude Desktop App puedes sustituirla con la edición directa de archivos. El método manual enseñado en este capítulo (escribir tú mismo frontmatter + cuerpo) es la técnica básica válida en ambos entornos.

Registro y despliegue

Dónde registrar

Una vez escrita la skill, debes registrarla en dos lugares para que el sistema pueda reconocerla. Si te saltas este paso, el PM no encontrará la skill y no la despachará.

  1. Tabla Skills de AGENTS.md (§6) — añade el nombre, la ubicación del archivo, la versión y el estado de la skill a la tabla Skills del AGENTS.md de la raíz del workspace. Esta tabla actúa como registro de skills.
  2. docs/VERSION_MANIFEST.md — anota la información de versión y estado de la skill. Permite seguir el historial de versiones y ver de un vistazo qué skills están activas. VERSION_MANIFEST.md es la SSOT (Single Source of Truth) de las versiones de skills.

Ejemplo de registro en AGENTS.md

Añade una fila como esta a la tabla Skills de AGENTS.md.

| my-reviewer | `skills/my-reviewer/SKILL.md` | quality | Checks readability, consistency, completeness | active | 1.0.0 |

Ejemplo de registro en VERSION_MANIFEST.md

- **name:** my-reviewer
  **path:** skills/my-reviewer/SKILL.md
  **version:** 1.0.0
  **status:** active
  **owner:** pm
  **type:** quality

Despliegue: sync-skills.ts

Las skills L0 (workspace) pueden sincronizarse con todas las plantillas (L1) y proyectos (L2) mediante el script sync-skills.ts. Al ejecutarlo, las skills del workspace se clonan en todos los proyectos descendentes.

# Ejecutar el script de sincronización de skills
bun scripts/sync-skills.ts
Las skills L0 (workspace) están disponibles en todos los proyectos. Las skills L2 (proyecto), en cambio, solo se usan dentro de su proyecto. Cuando crees tu primera skill, conviene registrarla en L0 para que todos los proyectos puedan aprovecharla.

Práctica: crea tu propia skill personalizada

Objetivo de la práctica

En esta práctica construirás tú mismo una "skill de revisión documental (my-reviewer)". Experimentarás de primera mano todo el proceso: redacción del frontmatter, del cuerpo, registro en el sistema y validación.

Pasos de la práctica

  1. Abre un proyecto en la Claude Desktop App — inicia la Claude Desktop App y abre el proyecto en el que trabajas. Comprueba si existe una carpeta skills/ en la raíz del proyecto.
  2. Crea el directorio — crea la carpeta skills/my-reviewer/ y dentro un archivo SKILL.md.
  3. Escribe el frontmatter — escribe el frontmatter YAML al inicio del SKILL.md. Guíate por el ejemplo de abajo.
  4. Escribe el cuerpo — bajo el frontmatter, escribe las secciones Overview, When to Use, Steps, Expected Outputs y Examples.
  5. Regístrala en AGENTS.md — añade la skill my-reviewera la tabla Skills de AGENTS.md.
  6. Ejecuta el script de validación — ejecuta bun scripts/skill-lifecycle-audit.ts para validar la estructura de la skill. Corrige cualquier error.
  7. Pruébala vía PM — pide a Claude que "revisar la calidad de este documento" y confirma que la skill funciona correctamente.

Ejemplo del archivo completo

A continuación tienes el contenido íntegro de skills/my-reviewer/SKILL.md. Úsalo tal cual o adáptalo a tus necesidades.

---
name: my-reviewer
status: active
description: >
  Reviews document quality and provides structured feedback.
  Checks readability, consistency, and completeness of
  markdown documents. Outputs a structured review report
  with severity levels and improvement suggestions.
owner: pm
version: "1.0.0"
metadata:
  type: quality
  triggers:
    - "review document"
    - "check quality"
    - "quality review"
    - "문서 검토"
    - "품질 확인"
---

## Overview

This skill performs a comprehensive quality review of
markdown documents. It evaluates documents from three
perspectives: readability, consistency, and completeness,
then provides structured feedback with actionable suggestions.

Scope: markdown (.md) files in the project workspace.

## When to Use

Activate this skill when:
- The user requests a document review
- A document has been newly created or significantly revised
- PM dispatches quality review as part of a pipeline gate
- The user asks to "check quality" or "review document"

## Steps

1. **Identify target file** — Confirm the file path of the
   document to review. If not specified, ask the user.
2. **Read the document** — Load the full content of the
   target file.
3. **Readability check** — Evaluate sentence length,
   paragraph structure, heading hierarchy, and overall
   flow. Flag sections that are hard to follow.
4. **Consistency check** — Verify terminology usage, format
   style, date format, heading capitalization, and list
   formatting across the entire document.
5. **Completeness check** — Identify missing sections,
   incomplete sentences, broken references, and unresolved
   TODO markers.
6. **Generate review report** — Compile findings into a
   structured report with severity levels:
   - INFO: minor suggestions
   - WARNING: recommended improvements
   - ERROR: issues that must be fixed

## Expected Outputs

- Structured review report (stdout)
- Issue count by severity (INFO / WARNING / ERROR)
- Prioritized improvement suggestions

## Examples

**Example 1:** User says "review document"
→ Read the specified file, run all 3 checks,
  output a structured review report.

**Example 2:** PM dispatches after handbook chapter
  completion
→ Review the chapter HTML source, check authoring
  guideline compliance, report findings.
Tras terminar la skill, pide al PM que "revise la calidad de este documento" y comprueba que funciona bien. Si la skill no se dispara, revisa que sus palabras clave aparecen en el campo triggers del frontmatter y que está registrada en AGENTS.md. La coincidencia de triggers funciona mejor cuanto más se acerca a la coincidencia exacta de palabra clave.

Lista de verificación

Al terminar la skill, haz una comprobación final con esta lista.

Punto de control Qué verificar
Ubicación del archivo ¿Existe el archivo en skills/my-reviewer/SKILL.md?
Campos obligatorios ¿Están rellenados name, status, description, owner y version?
Secciones del cuerpo ¿Están Overview, When to Use, Steps, Expected Outputs y Examples?
Registro en AGENTS.md ¿Se añadió la skill a la tabla Skills?
VERSION_MANIFEST ¿Se registró la información de versión?
Prueba funcional ¿Funciona correctamente con las palabras clave?
Resumen del capítulo
  • Una skill es un flujo de trabajo reutilizable que ejecuta un agente. Si el agente es el "quién", la skill define el "qué se hace".
  • SKILL.md se compone de frontmatter YAML (metadatos) y cuerpo markdown (instrucciones de ejecución).
  • Campos del frontmatter: name, status, description, owner y version son obligatorios; metadata.type y metadata.triggers son opcionales.
  • El cuerpo debería organizarse en las secciones Overview, When to Use, Steps, Expected Outputs y Examples.
  • skill-lifecycle-manager guía el proceso de 6 pasos: crear directorio → frontmatter → cuerpo → registro → validación → prueba.
  • skill-creator es una herramienta avanzada de autoría iterativa guiada por pruebas en el entorno Claude Code CLI.
  • El registro se realiza en dos lugares: la tabla Skills de AGENTS.md y VERSION_MANIFEST.md.
