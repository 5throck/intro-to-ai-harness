第10章

スキルの作成と変更

この章では、スキルファイルの構造、skill-lifecycle-managerとskill-creatorツールについて解説し、独自のカスタムスキルを構築・登録する手順を説明します。

本章の内容
  • スキルファイルの形式と構造
  • YAMLフロントマターのフィールド解説
  • ボディコンテンツのパターン（概要、使用場面、手順、出力、例）
  • skill-lifecycle-managerの使用方法（6ステップ）
  • skill-creator（Claude Code プラグイン）の概要
  • 演習: シンプルなカスタムスキルを作成する

スキルの再考

第4章でスキルの概念を紹介しました: エージェントに特定の種類の作業をどのように実行するかを教える再利用可能なレシピブックです。この章ではさらに一歩踏み込み、実際に新しいスキルをゼロから作成し、プロジェクトに登録し、正しくトリガーされることを検証します。

第4章のおさらい

エージェントとスキルの主な違いを思い出しましょう:

エージェント

  • 対象: 固定のアイデンティティを持つデジタル従業員
  • 例え: 従業員本人
  • ファイル: agents/<name>.md
  • スコープ: プロジェクト全体で持続的な役割

スキル

  • 対象: 再利用可能な指示レシピ
  • 例え: 従業員が従うレシピブック
  • ファイル: skills/<name>/SKILL.md
  • スコープ: 必要に応じて呼び出し; エージェント間で共有

シェフ（エージェント）は、客が注文した料理に応じて異なるレシピ（スキル）を使います。シェフのアイデンティティは変わりませんが、レシピが各料理の調理方法を正確に指示します。html-buildエージェントは常にHTMLスライドを構築しますが、html-buildスキルがスライドデッキファイルの読み方、テーマの適用方法、出力の生成方法を正確に指示します。

所有権レイヤー（L0 / L1 / L2 / L3）

スキルはワークスペース階層の異なるレイヤーに存在し、どのレイヤーを編集しているかを理解することが重要です:

  1. L0 — ワークスペースルート (skills/): 単一情報源（SSOT）。すべてのスキル開発はここで行われます。スキルを作成・編集する場合、このレイヤーを変更します。
  2. L1 — コモンテンプレート (templates/common/skills/): bun run propagate:applyでL0から公開されたスナップショット。L1を直接編集することはありません — 変更はL0から下方向に流れます。
  3. L2 — バリアントテンプレート (templates/co-*/skills/): L2テンプレートレイヤーで定義されたバリアント固有のスキル。各バリアント（co-deck、co-consultなど）は、そのバリアントからスキャフォールドされたすべてのプロジェクトで共有されるスキルを含めることができます。
  4. L3 — プロジェクトレベル (Projects/<name>/skills/): L2バリアントテンプレートからL3プロジェクトをスキャフォールドした時に作成されるプロジェクト固有のレイヤー。他のプロジェクトやバリアントテンプレートに影響を与えずに、ローカルカスタマイズをここに追加できます。
「レシピ」の例え
エージェントがシェフなら、スキルはキッチンのレシピバインダーにあるレシピカードです。バインダーがL0ワークスペース（マスター原稿）。各レストランチェーン用に印刷された料理本がL1テンプレート。特定の料理（イタリアン、日本料理など）用に追加されたレシピバリエーションがL2バリアントスキル。あるレストランのコピーの余白に書き込まれたメモがL3プロジェクトオーバーライド。常にマスターバインダー（L0）で新しいレシピを書き、コピーを配布します。

スキルファイルの形式

すべてのスキルはskills/の下に独自のディレクトリを持ち、SKILL.mdという名前の単一ファイルを格納します。命名規則が重要です: ディレクトリ名はケバブケースを使用し、内部のファイルは常に大文字のSKILL.mdです。

ファイルの場所
skills/<name>/SKILL.md

エージェントファイルと同様に、スキルファイルは2つの部分で構成されます: YAMLフロントマターブロック（機械可読メタデータ）とMarkdownボディ（人間可読の指示）。構造はエージェントファイルよりシンプルですが、同じ原則が適用されます: フロントマターはシステム用、ボディはAIモデル用です。

構造の概要

フロントマターは2つの---フェンスで囲まれ、エージェントファイルと同じです。閉じフェンスの下のすべてがボディ — 見出し、リスト、コードブロック、テーブルを持つ標準的なMarkdownです。

スキルとエージェントの命名規則の違い
エージェントファイルはagents/<name>.md（エージェントごとに1ファイル）に配置されます。スキルファイルはskills/<name>/SKILL.md（スキルごとに1ディレクトリ、内部に常に大文字のSKILL.md）に配置されます。この余分なディレクトリレイヤーにより、スキルはメインの指示ドキュメントと一緒に補助ファイル（例、テストフィクスチャ）をバンドルできます。

フロントマターの記述

YAMLフロントマターはスキルの機械可読な身分証明書です。オーケストレーションレイヤー（PM、スクリプト、トリガーマッチング）はこれらのフィールドを読み取り、スキルをいつ、どのようにアクティブにするかを決定します。

必須フィールドとオプションフィールド

フィールド 必須? 型 説明
name 必須 string ケバブケース識別子。ディレクトリ名と一致する必要があります。
status 必須 string 次のいずれか: active、draft、deprecated、retired。
description 必須 string スキルの機能と使用場面を説明する複数行の概要。Use when:トリガーシナリオを含める必要があります。
owner 必須 string このスキルの保守責任を持つエージェントまたはロール（例: pm、research）。
version 必須 string セマンティックバージョン（1.0.0から開始）。
metadata.type 必須 string 次のいずれか: process（ワークフロー/方法論）、implementation（技術）、domain（ドメイン固有の知識）。
metadata.triggers 必須 list このスキルをアクティブにするキーワード。少なくとも1つのエントリが必要です。
scope オプション string 可視性スコープ: common（すべてのプロジェクト）またはvariant（プロジェクト固有）。
last_reviewed オプション string 最終レビュー日（YYYY-MM-DD）。
prerequisites オプション string 前提となるツールやランタイム要件（例: Bun runtime）。

フロントマターの例

skills/document-reviewer/SKILL.md — フロントマター
---
name: document-reviewer
status: active
scope: common
description: >
  Reviews markdown documents for clarity, consistency, and formatting
  compliance. Checks heading hierarchy, link validity, and writing style.
  Use when: "review this document", "check formatting", "proofread markdown".
owner: pm
version: 1.0.0
last_reviewed: 2026-08-10
prerequisites: none
metadata:
  type: process
  triggers:
    - review document
    - check formatting
    - proofread
    - document quality
---
適切なタイプの選択
process — ワークフローと方法論のスキル（例: sync、meeting-facilitation、skill-lifecycle-manager）。
implementation — 技術実装のスキル（例: html-build、pdf-export、measure）。
domain — ドメイン固有の知識スキル（例: dart-disclosure-parser、mece-logic-auditor）。
スキルの主な目的を最もよく表すタイプを選択してください。汎用ワークフローのスキルはほとんどがprocessです。

ボディコンテンツの記述

閉じ---フェンスの下にあるMarkdownボディは、スキルの取扱説明書です。スキルがロードされると、AIモデルはボディ全体を読み、その指示に従います。良いボディコンテンツは、エージェントが毎回一貫して正確にワークフローを実行することを保証します。

推奨される5つのセクション

ボディの構成方法は多岐にわたりますが、ほとんどのスキルは以下の5つのセクション（順序通り）で恩恵を受けます:

  1. 概要（Overview） — スキルの目的に関する高位の説明。どのような問題を解決するのか？どんな価値を提供するのか？2〜4文に収めてください。
  2. 使用場面（When to Use） — トリガー条件と具体的なユースケース。このスキルをアクティブにするフレーズや状況をリストします。フロントマターのトリガーキーワードを補強します。
  3. 手順（Steps） — エージェントがタスクを完了するために従う番号付きの順次指示。ワークフローが複雑な場合は、論理フェーズごとにグループ化します。各ステップは実行可能であり、適宜検証チェックポイントを含める必要があります。
  4. 期待される出力（Expected Outputs） — スキルが生成するもの。ファイル名、形式、コンテンツ構造を指定し、パイプラインの次のエージェントが正確に何を期待できるかを把握できるようにします。
  5. 例（Examples）（オプション） — スキルが現実的なシナリオでどのように機能するかを示す具体的な使用例。サンプル入力と出力を含めます。
手順を明確かつ順次的に保つ
手順セクションはスキルの心臓部です。各ステップを命令形の直接命令として書いてください:「入力ファイルを読む」「構造を検証する」「出力レポートを書く」。「データを処理する」のような曖昧なフレーズを避けてください。各ステップで具体的なファイルパス、形式要件、検証チェックを含めてください。サブステップがある場合は、番号付きサブリスト（1.1、1.2など）を使って階層を明確にします。

セクションの詳細と例

1. 概要（Overview）

スキルの機能と存在理由を簡潔な文で始めます。

## Overview

Reviews markdown documents for structural clarity, formatting
consistency, and writing quality. Produces a structured review
report with categorized findings and actionable fix suggestions.

2. 使用場面（When to Use）

具体的なトリガーシナリオをリストします。

## When to Use

- User says "review this document" or "check formatting"
- Before publishing a markdown file to catch issues
- After a major edit to verify the document still meets standards
- When quality-gating content before handoff to the next agent

3. 手順（Steps）

番号付きの実行可能な指示を提供します。

## Steps

### Step 1: Load and Parse
- Read the target markdown file using the Read tool
- Parse the document structure (headings, links, code blocks)

### Step 2: Structural Checks
- Verify heading hierarchy (no H3 before H2, etc.)
- Check that every internal link targets an existing file
- Validate that code blocks specify a language

### Step 3: Quality Review
- Flag passive voice overuse (more than 30% of sentences)
- Check for run-on paragraphs (more than 5 sentences)
- Verify consistent terminology usage

4. 期待される出力（Expected Outputs）

スキルが生成するものを定義します。

## Expected Outputs

- `review-report.md` in the same directory as the input file
- Sections: Structure, Links, Style, Terminology
- Each finding includes: severity (error/warning/info),
  location (line reference), and suggested fix

5. 例（Examples）（オプション）

現実的な使用シナリオを示します。

## Examples

**Input**: User says "Review docs/ch02/02_Getting_Started.md"
**Output**: Creates `docs/ch02/review-report.md` with 3 errors
  (broken link, missing H1, code block without language) and
  5 warnings (passive voice, long paragraphs).
ボディは「取扱説明書」
フロントマター（スクリプトとトリガーマッチャーが読み取る）とは異なり、ボディはスキルがロードされた時にAIモデルによって読み取られます。新しいチームメンバー向けのマニュアルを書くように書いてください: 明確で具体的、そしてどのように作業を行うかに焦点を当てます。「なぜ」は概要に、「いつ」はトリガーセクションに、「どのように」は手順に属します。

skill-lifecycle-managerの利用

skill-lifecycle-managerスキルは、スキルの作成、検証、保守のための体系的な6ステッププロセスを提供します。手動でファイルを作成してすべてが正しく接続されることを期待するのではなく、このスキルが各ステップをガイドし、問題を早期に検出します。

6ステッププロセス

ステップバイステップの解説

  1. ディレクトリを作成する — ディレクトリ名にケバブケースを使用してskills/<name>/SKILL.mdを作成します。ファイル名は正確にSKILL.md（大文字）である必要があります。
  2. フロントマターを記述する — すべての必須YAMLフィールド（name、status、description、owner、version、metadata.type、metadata.triggers）を入力します。ディレクトリ名とnameフィールドは一致する必要があります。
  3. ボディコンテンツを記述する — 概要、使用場面、手順（検証チェックポイント付き）、期待される出力、オプションで例を含むMarkdown指示を作成します。
  4. ドキュメントに登録する — AGENTS.mdのスキルテーブルとdocs/context.mdのスキルセクションにスキルを追加します。ファイルパスとトリガー条件を含めます。
  5. 検証する — bun run verify-skills（またはbun scripts/validate-skills.ts）を実行して、スキルがすべての構造・コンテンツチェックに合格するか確認します。
  6. アクティブ化テスト — プラットフォームツール（Claude CodeのSkillツールなど）でスキルをロードしてみて、フロントマターが正しく読み込まれること、コンテンツが実行可能であること、トリガーが期待されるユースケースに一致することを確認します。
シンプルに始めて反復する
初日から完璧なスキルを作る必要はありません。必須フロントマターフィールドと基本的な手順セクションを持つ最小限の実行可能なスキルを作成してください。最初はstatus: draftに設定します。テストし、モデルがどのように解釈するかに基づいて文言を調整し、一貫した動作になったらstatus: activeに昇格させます。ライフサイクルマネージャーは反復を安全にします: すべての変更は昇格前に自動的に検証できます。

skill-creator プラグイン

上記で説明した手動プロセスに加えて、Claude Codeにはskill-creatorプラグインが用意されており、スキルファイルの作成と反復を支援できます。このプラグインはClaude Code CLIプラグインマーケットプレイスで利用可能です。

skill-creatorができること

skill-creatorプラグインは3つの主要なワークフローを支援します:

  1. ゼロから作成 — スキルの目的を説明するだけで、適切なフロントマターとボディ構造を持つ新しいSKILL.mdファイルを生成します。
  2. 既存スキルの編集 — 既存のスキルの文言を調整し、欠落しているセクションを追加するか、構造を再編成してトリガーの信頼性と指示の明確さを向上させます。
  3. 文言の反復 — トリガー条件や手順指示の異なる言い回しをテストし、一貫したAI動作に最適なものを見つけます。

テスト駆動の反復的オーサリング

skill-creatorはテスト駆動アプローチを採用しています: ドラフトを書き、トリガーをテストし、モデルの動作を観察し、文言を調整します。このサイクルは、スキルが確実にトリガーされ、一貫した出力を生成するまで繰り返されます。

1. 説明 — スキルに何をしてほしいか（目的、トリガーフレーズ、期待される動作）をskill-creatorに伝えます。
2. ドラフト — skill-creatorがフロントマターとボディを持つ初期のSKILL.mdを生成します。
3. テスト — 実際のセッションでスキルをロードし、トリガーフレーズを試します。出力を観察します。
4. 調整 — テスト結果に基づいて、トリガーキーワードを調整し、曖昧な手順を明確にし、欠落している検証チェックポイントを追加します。
5. 検証 — 登録前に構造的コンプライアンスを確認するため、skill-lifecycle-managerの検証を実行します。
Claude Desktop Appでの代替方法
Claude Code CLIプラグインマーケットプレイスなしのClaude Desktop Appを使用している場合、Claudeに直接依頼することで同じワークフローを実現できます:「Markdownドキュメントの書式問題をレビューするスキルを作成して」。ClaudeがSKILL.mdファイルのドラフトを作成します。その後、前述のskill-lifecycle-managerの手順を使用して手動で登録・検証できます。主な違いは、skill-creatorプラグインが反復サイクルを自動化する点です。Claude Desktop Appでは、テスト・調整サイクルを手動で管理します。

登録とデプロイ

登録されていないスキルは、キッチンのバインダーに入れられなかったレシピカードと同じです。システムはそれを発見できず、エージェントはロードできず、監査スクリプトはそれを孤立したものとしてフラグします。登録により、スキルはワークスペース全体から可視になります。

登録先

2つの主要な場所にスキルを登録する必要があります:

  1. AGENTS.md — スキルテーブル（§6）: スキル名、ファイルパス（skills/<name>/SKILL.md）、簡単な説明を含む行を追加します。これはPMとドキュメントツールが参照するメインレジストリです。
  2. docs/context.md — スキルセクション: スキル名、タイプ、簡単な説明をスキルセクションに追加します。これにより、開発者向けドキュメントにスキルが表示されます。

登録の例

AGENTS.md — スキルテーブルのエントリ
| document-reviewer | `skills/document-reviewer/SKILL.md` | Reviews markdown documents for clarity, consistency, and formatting compliance |
docs/context.md — スキルセクションのエントリ
### document-reviewer
- **File**: `skills/document-reviewer/SKILL.md`
- **Type**: process
- **Description**: Reviews markdown documents for clarity, consistency, and formatting compliance.

sync-skills.tsによるデプロイ

スキルの作成または更新後、同期スクリプトを実行してプラットフォーム固有のディレクトリに配布します:

すべてのプラットフォームにスキルをデプロイ
bun scripts/sync-skills.ts

このスクリプトは、skills/<name>/SKILL.mdから.claude/skills/<name>/SKILL.mdと.gemini/skills/<name>/SKILL.mdにコピーし、Claude CodeとAntigravity CLIの両方が発見・ロードできるようにします。L0ワークスペースにいてtemplates/common/ディレクトリが存在する場合、bun run propagate:applyを実行してL1テンプレートにも伝播させる必要があります。

L0の優先度
ワークスペースレベルのスキル（skills/）はスキル解決順序で最も高い優先度を持ちます（第4章参照）。つまり、L0で作成したスキルは、同じ名前のプラットフォームレベルやプラグインレベルのスキルより常に優先されます。この力を責任を持って使ってください — 既存のプラグイン機能を意図的にオーバーライドしたい場合を除き、重複やシャドウイングを行うスキルの作成は避けてください。

演習: 独自のカスタムスキルを構築する

さあ、あなたの番です。この演習では、Markdownドキュメントの書式、構造、執筆品質をレビューする再利用可能なレシピであるdocument-reviewerスキルをゼロから作成します。

目標: 機能するdocument-reviewerスキルを作成し、AGENTS.mdに登録し、sync-skills.tsでデプロイし、正しくトリガーされることをテストする。
  1. ディレクトリとファイルを作成する
    skills/document-reviewer/ディレクトリを作成し、その中にSKILL.mdという名前のファイルを追加します。
  2. フロントマターを記述する
    すべての必須フィールドを含むYAMLフロントマターを追加します。参考用の完全なフロントマター:
    skills/document-reviewer/SKILL.md — フロントマター
    ---
name: document-reviewer
status: draft
scope: common
description: >
  Reviews markdown documents for clarity, consistency, and formatting
  compliance. Checks heading hierarchy, link validity, and writing style.
  Use when: "review this document", "check formatting", "proofread markdown".
owner: pm
version: 1.0.0
last_reviewed: 2026-08-10
prerequisites: none
metadata:
  type: process
  triggers:
    - review document
    - check formatting
    - proofread
    - document quality
---
  3. ボディを記述する
    5セクション構造を使用します。完全なボディ:
    skills/document-reviewer/SKILL.md — ボディ
    ## Overview

Reviews markdown documents for structural clarity, formatting
consistency, and writing quality. Produces a structured review
report with categorized findings and actionable fix suggestions.

## When to Use

- User says "review this document" or "check formatting"
- Before publishing a markdown file to catch issues
- After a major edit to verify the document still meets standards
- When quality-gating content before handoff to the next agent

## Steps

### Step 1: Load and Parse
- Read the target markdown file using the Read tool
- Parse the document structure (headings, links, code blocks)
- Count total lines and estimate word count

### Step 2: Structural Checks
- Verify heading hierarchy (no H3 before H2, exactly one H1)
- Check that every internal link targets an existing file
- Validate that code blocks specify a language tag
- Ensure images have alt text

### Step 3: Style Review
- Flag passive voice overuse (more than 30% of sentences)
- Check for run-on paragraphs (more than 5 sentences)
- Verify consistent terminology (same term used throughout)
- Check for redundant phrases or wordiness

### Step 4: Generate Report
- Create `review-report.md` in the same directory as the input
- Structure the report with sections: Structure, Links, Style,
  Terminology, Summary
- Each finding includes severity (error/warning/info), location
  (line reference), and suggested fix

## Expected Outputs

- `review-report.md` in the same directory as the reviewed file
- Sections: Structure, Links, Style, Terminology, Summary
- Severity levels: error (must fix), warning (should fix),
  info (suggestion)
- Word count and line count summary at the top

## Examples

**Input**: "Review docs/ch02/02_Getting_Started.md"
**Output**: Creates `docs/ch02/review-report.md` reporting
  2 errors (broken link on line 45, missing H1), 4 warnings
  (passive voice, long paragraphs), and 3 info items
  (terminology suggestions).
  4. AGENTS.mdに登録する
    AGENTS.mdのスキルテーブルにdocument-reviewerをファイルパスと説明とともに追加します。プロジェクトにdocs/context.mdがあれば、そこにもエントリを追加します。
  5. sync-skills.tsでデプロイする
    ターミナルでbun scripts/sync-skills.tsを実行し、スキルをプラットフォーム固有のディレクトリ（.claude/skills/と.gemini/skills/）に配布します。
  6. 検証する
    bun run verify-skills（またはbun scripts/validate-skills.ts）を実行し、スキルがすべての構造・コンテンツチェックに合格するか確認します。報告されたエラーを修正します。
  7. アクティブ化テスト
    Claude Code（またはClaude Desktop App）で、「README.mdファイルの書式問題をレビューして」と言ってみてください。スキルがロードされ、手順が実行され、review-report.mdファイルが期待される構造で作成されることを確認します。
テストは必須
新しいスキルの本当のテストは、検証スクリプトが通過することではなく、実際のユーザーリクエストでトリガーされたときに有用な出力を生成することです。検証に合格した後は、必ず少なくとも1回のエンドツーエンドテストを実行してください: リアルなプロンプトでスキルをトリガーし、出力をレビューし、結果が不安定だったり重要なチェックが漏れたりしている場合は手順指示を調整します。スキルは生きたドキュメントであり、動作が確実に一貫するまで2〜3回の反復を想定してください。
重要ポイント
  • スキルはskills/<name>/SKILL.mdに保存される再利用可能な指示レシピ
  • スキルファイル = YAMLフロントマター（メタデータ + トリガー）+ Markdownボディ（指示）
  • フロントマターの必須フィールド: name、status、description、owner、version、metadata.type、metadata.triggers
  • ボディセクション: 概要、使用場面、手順、期待される出力、例
  • skill-lifecycle-managerは6ステップの作成・検証プロセスを提供
  • skill-creator（Claude Code プラグイン）はテスト駆動の反復的オーサリングを支援
  • AGENTS.mdとdocs/context.mdにスキルを登録し、bun scripts/sync-skills.tsでデプロイ
  • 検証通過後、必ず実際のトリガーフレーズでアクティブ化テストを実行
  • status: draftで開始し、スキルが一貫して動作したらactiveに昇格
