独自のエージェントチームを構築する

これまで個別のエージェントとスキルの作成方法を学んできました。この章では、複数のエージェントを協調チームに組み合わせる方法を学び、team-builderスキルを使って要件インタビューから完全に登録されたエージェントロスターまでの全プロセスを自動化します。

本章で学ぶこと
  • エージェントチーム編成の重要性
  • team-builderスキル: AIレイヤーとスクリプトレイヤー
  • 5ステップワークフロー: インタビュー → ベンチマーク → 診断 → 提案 → 承認
  • 提案JSONの構造とフィールドの意味
  • ハンズオン: 独自のカスタムエージェントチームを構築する

エージェントチームを構築する理由

単一のAIアシスタントは強力ですが、現実の仕事はめったに1つの役割に収まりません。マーケティングチームには、戦略家、コピーライター、データアナリスト、デザイナーが協力して作業する必要があります。研究ラボには、文献レビュアー、仮説テスター、レポートライターが必要です。いずれの場合も、チーム編成 — 誰が何をどの順序で行うか — が最終的な出力の品質を決定します。

現実のシナリオ

専門特化されたエージェントチームが単一のジェネラリストより優れる3つのシナリオを考えてみましょう:

マーケティングチーム

  • 戦略アナリスト — 市場調査、競合分析
  • コンテンツライター — ブログ記事、広告コピー、ソーシャルメディア
  • データアナリスト — キャンペーン指標、A/Bテスト結果

研究ラボ

  • 文献レビュアー — 論文検索と総合
  • 実験デザイナー — 方法論とプロトコル
  • レポートライター — 研究成果と出版原稿

教育機関

  • カリキュラムデザイナー — コース構造と学習目標
  • コンテンツ作成者 — 講義資料と教科書
  • 評価作成者 — 小テスト、試験、ルーブリック
  • QAレビュアー — 品質チェックとアクセシビリティコンプライアンス

チーム編成のメリット

  • 各エージェントがフォーカスされたコンテキストを保持 — 情報過負荷なし
  • 関心事項の分離 — ライターは自分の仕事をレビューしない
  • 並列実行 — 独立したエージェントが同時に実行
  • 拡張が容易 — 他に触れずに新しいスペシャリストを追加
  • 一貫した品質 — 各役割でのスペシャリストの深み

単一AIの限界

すべてを単一のAIエージェントに頼ると、いくつかの問題に直面します:

  • コンテキスト過負荷 — 1つのエージェントがすべてのドメイン知識、指示、中間結果を同時に保持する必要があります。
  • 関心事項の分離なし — 同じエージェントがコードを書き、レビューし、テストするため、品質が低下します。
  • スケールが困難 — 新しい機能を追加するにはエージェント定義全体を書き直す必要があります。
  • 専門化なし — ジェネラリストエージェントは、1つのタスクに特化したスペシャリストの深みに及びません。

単一AI vs. エージェントチーム

重要なインサイト

実際の組織と同様に、エージェントチームは各AIに明確な役割、定義されたスキルセット、他のエージェントとの明示的な引き継ぎ関係を割り当てます。この関心事項の分離により、保守・拡張が容易で、より高品質な出力が得られます。

team-builder スキルの紹介

team-builderスキルは、新しいエージェントチームの設計とデプロイの全プロセスを自動化します。2層アーキテクチャを採用しています: AI駆動の計画レイヤーと自動化されたスクリプト実行レイヤーです。

AIレイヤー + スクリプトレイヤー

  • AIレイヤー（ステップ1〜5） — AIが要件インタビューを実施し、業界のチーム構造とベンチマークし、現在のエージェント設定を診断し、提案を生成して承認を待ちます。
  • スクリプトレイヤー（ステップ6〜14） — 提案を承認した後、bun scripts/team-builder.tsがすべての変更を自動的に実行します: エージェントファイルの作成、AGENTS.mdへの登録、スキルのインストール、ガバナンスドキュメントの更新。
重要: スクリプトレイヤーはステップ5での明示的な承認なしには絶対に実行されません。これは必須の安全ゲートです。AIが技術的にスクリプトを実行できたとしても、ワークフローはあなたが自分でターミナルコマンドを実行するように設計されています。

なぜ2層なのか?

「なぜAIに全部やらせないのか」と思うかもしれません。その答えは信頼性とアカウンタビリティにあります。

  • AIが得意なこと: 意図の理解、リサーチ、トレードオフの評価、創造的な提案の生成。ステップ1〜4はまさにこれらの強みを活用します。
  • スクリプトが得意なこと: 決定的なファイル操作: ディレクトリの作成、正確な書式でのファイル書き込み、複数の相互参照ドキュメントの同時更新、毎回一貫した出力の生成。ステップ6〜14にはこの信頼性が必要です。
  • あなたがゲートを提供するのはステップ5で、情報に基づいた同意なしに変更が行われないことを保証します。これにより、AIが誤ってエージェントを削除したり、引き継ぎチェーンを壊したり、不整合なガバナンスドキュメントを作成したりすることを防ぎます。

既存のシステム: co-consult

co-consultプロジェクトは、コンサルティング・エンゲージメント用に構築されたエージェントチームの実例です。エンゲージメントリーダー、戦略アナリスト、業界エキスパート、ソリューションアーキテクトなど、11人のスペシャリストエージェントが4つの定義済み編成パターンに組織されています:

  • クイック評価 — 迅速でフォーカスされた評価用に3つのエージェント
  • スタンダード — 典型的なコンサルティング・エンゲージメント用に5つのエージェント
  • 複雑な変革 — 大規模な組織変革用に8つのエージェント
  • 専門特化 — 深いドメインの技術的作業用に4つのエージェント

レイヤーアーキテクチャ図

AIレイヤー 5ステップワークフロー

AIレイヤーは、提案されたチームが適切に設計され、現実世界の標準とベンチマークされ、あなたの特定のニーズに合わせて調整されることを保証するため、厳密な5ステッププロセスに従います。各ステップを詳しく見ていきましょう。

ステップ1: 要件インタビュー

AIは他のことをする前に、6つの必須質問をあなたに尋ねます。あなたの回答がチーム設計全体を定義します。

6つの必須質問

  1. ドメイン/目的 — 新しいチームの主なドメインまたは目的は何か？（例: コンサルティング、教育、ソフトウェア開発）
  2. チーム規模 — チームにいくつのエージェントを予定しているか？（3、5、8+）
  3. 主要タスク — このチームはどのような種類のプロジェクトを担当するか？
  4. 技術スタック — チームが使用するツール、プラットフォーム、フレームワークは？
  5. 協業スタイル — 順次引き継ぎ、並列実行、それとも混合？
  6. 成功指標 — チームが満たすべき品質や納品基準は？

6つすべてが重要な理由

  • ドメインがスペシャリストの役割を決定
  • 規模が予算とティア計画に影響
  • タスクが必要なスキルを形成
  • 技術スタックがツール設定に反映
  • 協業が引き継ぎチェーンを定義
  • 指標が品質ゲートを設定
AIはあなたの回答を要約して確認を求めます。確認するまでベンチマークは開始されません。

ステップ2: ベンチマーク

AIはウェブ検索を使用して、要件に類似した現実世界のチーム構造を見つけます。McKinsey、BCG、Gartner、Forrester、または査読付き研究などの権威ある情報源を参照します。

AIは各参照チームについて以下を文書化します:

  • チーム名と情報源
  • 役割と責任
  • 階層と報告構造
  • 典型的なプロジェクトタイプ
  • 既知の長所と短所
  • 要件に対する適合スコア（基準ごとに1〜5）

最高スコアの参照が提案の設計テンプレートになります。この証拠に基づくアプローチにより、チームは純粋な想像から設計されるのではなく、実証済みの現実世界の組織パターンに基づいていることが保証されます。

情報源の品質が重要

AIは各ベンチマーク情報源を3つの基準で検証します: (1) 過去5年以内に発行、(2) 公式な組織ドメインまたは査読付きジャーナル、(3) 可能な限り一次情報源。情報源がいずれかのチェックに不合格の場合、AIは明示的に記録し、代替を探します。

ステップ3: 現在のチーム診断

変更を提案する前に、AIは既存のエージェントとスキルの状況をマッピングします:

  1. エージェントインベントリ — すべてのagents/*.mdファイルを名前、ティア、フェーズ、スキルとともにリスト化。
  2. スキルインベントリ — すべてのskills/*/SKILL.mdファイルをオーナーとステータスとともにリスト化。
  3. 依存関係マップ — 削除される可能性のある各エージェントについて、所有するスキルと引き継ぎ関係を特定。
  4. 事前のスキル移譲計画 — 削除が行われる前に、孤立したスキルを有効な残存または新規エージェントに割り当て。

ステップ4: 提案生成

AIは以下を含む構造化された提案を生成します:

  • チーム比較テーブル — 現在と提案のエージェントを変更タイプ（作成 / 変換 / 削除 / 保持）とともに
  • エージェント変更の詳細 — 各変更の名前、ティア、フェーズ、スキル、理由
  • スキル変更計画 — 新規スキル、変更スキル、スキルオーナーの再割り当て
  • ワークフロー設計 — フェーズ定義、ディスパッチ順序、引き継ぎチェーン
  • ベンチマーク証拠 — 使用された情報源と適合理由

ステップ5: ユーザー承認（必須ゲート）

必須停止

これはハードゲートです。AIは完全な提案を提示し、あなたの明示的な返信を待ちます。独自にスクリプト実行に進むことはありません。

  • 「承認」と返信 — 提案JSONをmemory/に保存し、スクリプトの実行を指示
  • 変更要求を返信 — 提案を修正し、レビューに戻る
  • 「キャンセル」と返信 — プロセス全体を停止

5ステップワークフロー図

提案の形式

ステップ5で、AIは提案JSONファイルをmemory/team-builder-proposal-YYYY-MM-DD.jsonに保存します。このJSONは、スクリプトレイヤー（bun scripts/team-builder.ts）がすべての変更を実行するために読み込む入力です。構造を分解して見てみましょう。

トップレベルフィールド

メタデータフィールド

  • version — スキーマバージョン（例: "1.0.0"）
  • timestamp — 提案の生成日時
  • teamName — 人間が読めるチーム名
  • benchmarkSources — 使用されたURLまたは引用
  • changeHistoryEntry — 1段落の要約
  • approvedBy / approvedAt — 誰がいつ承認したか

変更配列（changes内）

  • agentsToCreate[] — 追加する新規エージェント
  • agentsToConvert[] — 名前変更/目的変更する既存エージェント
  • agentsToDelete[] — 削除するエージェント
  • skillsToCreate[] — 作成する新規スキル
  • skillsToModify[] — 更新する既存スキル
  • skillsToReassign[] — スキル所有権の移譲
  • workflowPhases[] — フェーズ定義とディスパッチ順序

例: エージェント作成エントリ

{
  "name": "strategy-analyst",
  "formalName": "Strategy Analyst",
  "tier": { "claude": "medium" },
  "color": "blue",
  "description": "Market analysis and competitive research",
  "phases": ["1", "2"],
  "handoffTo": ["communications-lead"],
  "handoffFrom": ["engagement-leader"],
  "requiredSkills": ["research", "insight-synthesis"],
  "rationale": "Benchmarking shows McKinsey teams include a dedicated strategy role"
}

各フィールドは第9章で学んだエージェントのフロントマタープロパティに直接マップされます。rationaleフィールドは特に重要です — すべての設計決定をステップ2のベンチマーク証拠にリンクします。

ワークフローフェーズエントリ

workflowPhases配列はエージェントがプロジェクトライフサイクル全体でどのように連携するかを定義します:

{
  "phase": 0,
  "name": "Project Initiation",
  "lead": "engagement-leader",
  "supporting": ["strategy-analyst"]
}

各フェーズはリードエージェント（オーケストレーター）とオプションのサポートエージェント（貢献者）を指定します。この構造はAGENTS.mdのディスパッチテーブルに直接対応します。

スキル再割り当てエントリ

エージェントが削除される場合、そのスキルは残存エージェントに移譲される必要があります。提案は次のように記録します:

{
  "skill": "research",
  "fromOwner": "old-analyst",
  "toOwner": "strategy-analyst"
}

これにより、エージェント削除時にスキルが孤立しないことが保証されます。ステップ3の事前スキル移譲計画により、削除前にすべてのスキルが有効なオーナーを持つことが保証されます。

スクリプトレイヤー

提案を承認すると、実行はAIからTypeScriptスクリプトに移ります。これは意図的なものです: 複雑なファイル操作（作成、名前変更、削除、ガバナンスドキュメントの更新）は、AI生成よりも決定的なコードで処理する方が信頼性が高くなります。

スクリプトの動作

ターミナルからスクリプトを実行します:

bun scripts/team-builder.ts memory/team-builder-proposal-2026-08-10.json

スクリプトは提案JSONを読み込み、各ステップでチェックポイントロギングを行いながら固定された安全な順序で変更を実行します:

  1. ドライラン検証 — JSONをパースし、すべての必須フィールドをチェック（変更なし）
  2. エージェント削除 — 削除対象のエージェントファイルを削除（スキル移譲後）
  3. エージェント変換 — 既存エージェントの名前変更と目的変更
  4. エージェント作成 — テンプレートから新しいagents/<name>.mdファイルを生成
  5. スキル作成 — 新しいskills/<name>/SKILL.mdスタブファイルを生成
  6. スキル変更 — 既存スキルファイルに指定された変更を適用
  7. スキル再割り当て — スキルフロントマターのownerフィールドを更新
  8. AGENTS.mdに登録 — エージェントロスターとサブエージェントロスターブルに新規エージェントを追加
  9. フェーズテーブル更新 — ディスパッチトリガーとフェーズゲートマッピングを調整
  10. 変更履歴を記録 — 要約をmemory/YYYY-MM-DD.mdに書き込み

AIレイヤー → スクリプトレイヤーの流れ

まずはドライラン

--dry-runフラグを追加すると、変更を行わずにスクリプトが何をするかをプレビューできます: bun scripts/team-builder.ts proposal.json --dry-run。初回の実際の実行前に強く推奨されます。

問題が発生した場合は?

スクリプトは各ステップでチェックポイントロギングを含みます。途中でエラーが発生した場合（例: ファイルが既に存在する、権限が拒否された）、スクリプトはどのステップで失敗したか、何が既に完了したかを正確に報告します。問題を修正してスクリプトを再実行できます — 既に正常に完了したステップはスキップされます。

実行前にバックアップ

スクリプトは安全に設計されていますが、team-builder.tsを実行する前に現在のプロジェクト状態をGitにコミットすることをお勧めします。予期しないことが起きた場合のクリーンなロールバックポイントになります。

既存のチーム編成パターン

co-consultプロジェクトには4つの定義済み編成パターンが付属しており、そのまま使用することもカスタマイズすることもできます。各パターンは異なるエンゲージメントタイプと複雑さレベルに最適化されています。

クイック評価

エージェント: 3  |  最適用途: 迅速でフォーカスされた評価

  • エンゲージメントリーダー（オーケストレーター）
  • 業界エキスパート（ドメイン知識）
  • 戦略アナリスト（リサーチと分析）

使用場面: 1セッション内で迅速な市場スキャン、競合概要、または初期評価が必要な場合。

スタンダード

エージェント: 5  |  最適用途: 典型的なコンサルティング・エンゲージメント

  • エンゲージメントリーダー（オーケストレーター）
  • 戦略アナリスト（リサーチ）
  • 業界エキスパート（ドメイン）
  • コミュニケーションリード（納品物）
  • デリバリーマネージャー（運用）

使用場面: リサーチ、納品物作成、プロジェクト調整を必要とするほとんどの標準的なエンゲージメント。

複雑な変革

エージェント: 8  |  最適用途: 大規模な組織変革

  • エンゲージメントリーダー（オーケストレーター）
  • チェンジマネジメントパートナー（変革）
  • 戦略アナリスト（リサーチ）
  • 業界エキスパート（ドメイン）
  • ソリューションアーキテクト（技術設計）
  • コミュニケーションリード（納品物）
  • ワークストリームリード（調整）
  • デリバリーマネージャー（運用）

使用場面: 技術、人、プロセスの変革を伴う多段階の変革プログラム。

専門特化

エージェント: 4  |  最適用途: 深いドメインの技術的作業

  • エンゲージメントリーダー（オーケストレーター）
  • サブジェクトマターエキスパート（機能的深み）
  • テクノロジースペシャリスト（ツールと自動化）
  • データアナリスト（指標とモデリング）

使用場面: 財務モデリング、HR分析、技術スタック評価などの高度に専門化されたタスク。

カスタマイズ: これら4つのパターンに限定されません。team-builderスキルは独自の要件に基づいてチームをゼロから設計できます。上記のパターンは出発点とベンチマーク参照として機能します。ベンチマークステップ（ステップ2）で、AIはこれらのパターンをあなたの特定のニーズと照らし合わせて評価し、最適な適合またはハイブリッドアプローチを推奨します。

パターン選択ガイド

状況に応じたパターン選択のクイックガイド:

小規模スコープ

  • 単一のリサーチ質問
  • 一回限りの分析タスク
  • 厳しい期限（同セッション内）
  • → クイック評価

中規模スコープ

  • 数週間のエンゲージメント
  • クライアント納品物が期待される
  • リサーチ + 執筆 + 調整
  • → スタンダード

大規模スコープ

  • 多段階プログラム
  • ステークホルダー管理が必要
  • 技術 + 人 + プロセス
  • → 複雑な変革

深いドメイン

  • 高度なデータ分析
  • 専門的なツール
  • 機能的専門知識が必要
  • → 専門特化

ハンズオン: 独自のエージェントチームを構築する

さあ、すべてを組み合わせましょう。この演習では、Claude Desktop Appで/team-builderコマンドを使用して、選択したドメイン向けのカスタムエージェントチームを設計・デプロイします。

  1. ドメインを選択する — 実際のプロジェクトまたはユースケースを選んでください: 教育、ソフトウェア開発、コンテンツ制作、法律研究、医療管理、またはその他。チームが何をするかを1文で書き留めます。
  2. 要件を準備する — Claudeを開始する前に6つの必須質問に紙で回答します。これによりインタビューステップがはるかに速くなります:
    • チームのドメイン/目的
    • 予定チーム規模（エージェント数）
    • 主要タスクとプロジェクトタイプ
    • 技術スタック（ツールとプラットフォーム）
    • 協業スタイル（順次、並列、混合）
    • 成功指標と品質基準
  3. Claudeにチーム構築を依頼する — Claude Desktop Appを開き、team-builderスキルを呼び出します。準備した回答を提供します。Claudeがステップ1〜4を自動的に実行します。
  4. 提案をレビューする — ステップ5で、Claudeが完全な提案を提示します。すべてのセクション: エージェント変更、スキル計画、ワークフローフェーズ、ベンチマーク証拠を読んでください。理由があなたのドメインで意味をなすか確認します。
  5. 承認または修正 — 提案が良ければ「承認」と返信します。変更が必要なら、何を修正したいかを説明するとClaudeが再生成します。必要な回数だけ反復できます。
  6. 結果を確認する — 承認後、Claudeが提案JSONを保存します。ターミナルからスクリプトを実行します: bun scripts/team-builder.ts memory/team-builder-proposal-YYYY-MM-DD.json 新しいエージェントファイル、スキルファイル、更新されたAGENTS.mdがすべて正しいことを確認します。

プロンプトの例

/team-builder

I need an agent team for a university course production workflow.

Domain: Higher education — creating online course materials (lecture slides, 
handbook chapters, quiz questions, and assessment rubrics)

Team size: 5 agents

Primary tasks: Research topics, write lecture content, generate assessment materials,
produce HTML output, and review quality.

Tech stack: Markdown, HTML/CSS, Bun/TypeScript scripts

Collaboration style: Sequential with a quality review gate before final output

Success metrics: All content must pass a quality checklist; HTML output must be 
accessible (WCAG 2.1 AA compliant)

ヒント: 小さく始める

初めての場合は、クイック評価パターン（3エージェント）から始め、少し変更してみてください。比較するための動作する参照が得られます。完全なサイクルを理解したら、大規模なチームをゼロから設計してみてください。

まとめ

重要ポイント
  • エージェントチームは各AIにフォーカスされた役割、明確なスキル、明示的な引き継ぎ関係を割り当て、単一のジェネラリストエージェントより高品質な出力を生成します。
  • team-builderスキルは2層アーキテクチャを採用: インテリジェント計画のためのAIレイヤー（ステップ1〜5）と、信頼性の高い自動実行のためのスクリプトレイヤー（ステップ6〜14）。
  • AIレイヤーは厳密な5ステップワークフローに従う: 要件インタビュー → ベンチマーク → 現在のチーム診断 → 提案生成 → ユーザー承認。
  • ステップ5は必須ゲート — スクリプトレイヤーはあなたの明示的な承認なしには実行されません。
  • 提案JSONはAIレイヤーとスクリプトレイヤーの間のコントラクトです。すべてのエージェント変更、スキル計画、ワークフローフェーズ、ベンチマーク証拠が含まれます。
  • co-consultプロジェクトは出発点とベンチマーク参照として機能する4つの定義済みパターン（クイック評価、スタンダード、複雑な変革、専門特化）を提供します。
  • プロジェクトへの変更をコミットする前に、必ず--dry-runを使用してスクリプト実行をプレビューしてください。

次の章では、ワークフローと自動化を探ります — エージェントをチェーンして反復可能で効率的な本番パイプラインにする多段階プロセスの定義方法です。
