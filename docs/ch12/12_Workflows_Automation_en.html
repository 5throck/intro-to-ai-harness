Chapter 12

Understanding Workflows & Automation

This chapter covers workflow automation in the AI harness — the /sync command, Git/GitHub PRs, hooks, CI/CD basics, and how dev-sync.ts works.

What This Chapter Covers
  • Why automation matters
  • How /sync works
  • Git and GitHub PR basics
  • Hook concepts
  • CI/CD basics
  • dev-sync.ts internals
  • Practice: walk through a full workflow

What Is Automation

Imagine you had to wash every piece of clothing by hand — scrubbing, rinsing, and wringing each item individually. It would take hours every week. Then someone invented the washing machine: you load the clothes, press a button, and the machine handles the entire cycle automatically. That is automation — replacing repetitive manual steps with a system that runs them for you.

The same principle applies to software development and AI agent workflows. In the previous chapters, you learned how agents collaborate to produce research, slide decks, and handbooks. But what happens after an agent finishes its work? How do changes get saved, verified, and shared? That is where workflow automation comes in.

Manual vs. Automated

Let us compare what a typical workflow looks like with and without automation.

Without Automation (Manual)

  • Run audit checks yourself
  • Update version files by hand
  • Commit changes with git commands
  • Push to GitHub manually
  • Create a Pull Request through the web UI
  • Copy shared changes to every variant project
  • Risk: forgetting a step, typos, inconsistent versions

With Automation (/sync)

  • Audit runs automatically
  • Version files update automatically
  • Commit message generated for you
  • Push happens as part of the pipeline
  • PR created with a single command
  • L0 changes propagate to all variants
  • Result: consistent, reliable, repeatable

The Washing Machine Analogy

Think of the /sync command as the washing machine for your project. Instead of doing each step of the post-work workflow manually (audit, version update, commit, push, create PR), you run one command and the system handles the entire cycle. You load the "clothes" (your changed files), press the button (/sync), and the machine takes care of the rest.

This analogy extends further: just as a washing machine has different cycles (delicate, heavy duty), the automation pipeline can be configured for different scenarios. And just as a washing machine ensures your clothes are consistently clean, the automation ensures your project is consistently maintained.

Automation does not replace thinking — it replaces repetition. You still decide what changes to make and when to run the sync. Automation simply ensures that once you make that decision, all the routine steps that follow are executed correctly and consistently every time.

Understanding the /sync Command

The /sync command is the central automation command in the AI harness. It encapsulates the entire post-work workflow into a single invocation. Whenever you finish a task that modified files — adding an agent, updating a skill, changing a script — you run /sync to finalize the work properly.

The 5-Step Sync Pipeline

When you invoke /sync, the system runs five steps in sequence. Each step depends on the previous one completing successfully.

  1. Lifecycle Update — The system checks whether any lifecycle-tracked artifacts changed (agents, skills, scripts, governance files). If they did, it updates the relevant lifecycle records and CHANGELOG.md to reflect the changes.
  2. Audit — The scripts/audit.ts script runs a comprehensive check on the workspace. It validates file structure, naming conventions, frontmatter completeness, cross-references, and contract compliance. Any errors are reported and must be fixed before proceeding.
  3. Publish (L0→L1) — If changes were made at the L0 workspace root level, those changes are published downward to the L1 common template. This ensures all variants inherit the latest standards.
  4. Commit — All changes are committed to git with a conventional commit message. The message includes a type prefix (feat, fix, docs, etc.), a scope, and a description of what changed.
  5. Push + PR — The commit is pushed to the remote repository, and a Pull Request is automatically created (or an existing one is updated) for review.
Tip: The /sync command takes a conventional commit message as its argument, for example: /sync "feat(pm): add meeting facilitation skill". The system uses this message for the git commit, so writing a clear, descriptive message is important. The format follows the pattern type(scope): description.

When to Run /sync

You should run /sync at the end of any work session that modified project files. Specifically:

  • After adding, modifying, or deprecating an agent
  • After creating, updating, or removing a skill
  • After changing a script or its status in SCRIPTS.md
  • After modifying governance files (AGENTS.md, CLAUDE.md, GEMINI.md)
  • After any change to common-contract.json or template files
You do not need to run /sync for every tiny change. For documentation-only changes (body text updates, memory log entries) that do not affect lifecycle-tracked artifacts, you can simply commit and push manually. The /sync pipeline is designed for changes that affect the project's structural integrity.

Git & GitHub PR

To understand how the automation pipeline works, you need a basic understanding of Git and GitHub Pull Requests. These are the tools that underpin every step of the sync pipeline after the audit.

Git Basics

Git is a version control system that tracks every change made to files in a project. Think of it as a detailed diary of your project's history. Every time you save a set of changes, Git records who made the change, when it was made, and what exactly changed.

Here are the essential Git commands you will encounter in the AI harness workflow.

Essential Git Commands
# Check what files have changed
git status

# See the actual differences in changed files
git diff

# Save changes to a "staging area" (preparing to commit)
git add <filename>

# Record the staged changes with a message
git commit -m "type(scope): description"

# Send commits to the remote repository (GitHub)
git push

# Download the latest changes from the remote
git pull

# Create a new branch (a parallel line of work)
git checkout -b feature/my-new-feature

# See the commit history
git log --oneline

GitHub Basics

GitHub is a web platform that hosts Git repositories. It adds collaboration features on top of Git: team access management, code review tools, issue tracking, and Pull Requests. Your AI workspace lives on GitHub, and the sync pipeline interacts with it to push changes and create PRs.

Pull Requests (PRs)

A Pull Request (PR) is a proposal to merge changes from one branch into another. It is the standard mechanism for code review in collaborative projects. Here is how it works:

  1. Create a branch — You create a new branch (a parallel copy of the code) where you make your changes. This keeps the main branch stable while you work.
  2. Make changes and commit — You edit files, add new agents or skills, and commit those changes on your branch.
  3. Open a PR — You create a Pull Request that says "please review these changes and merge them into the main branch."
  4. Review — Team members (or automated checks) review the changes, leave comments, and request modifications if needed.
  5. Merge — Once approved, the PR is merged into the main branch, and your changes become part of the official project.
In the AI harness, Git operations are mostly handled for you. When you run /sync, the pipeline takes care of staging, committing, pushing, and creating the PR. You do not need to memorize every Git command. However, understanding the concepts — what a commit is, what a branch is, what a PR does — helps you understand what the automation is doing behind the scenes.

Hooks

A hook is a script that runs automatically when a specific event occurs. The word "hook" comes from fishing: just as a fishhook catches a fish when it swims by, a code hook catches an event and runs a script in response.

How Hooks Work

In the AI harness, hooks are used to enforce rules and automate checks at key moments. Instead of relying on developers to remember to run checks manually, hooks ensure that the checks happen automatically every time the relevant event fires.

The most common type of hooks are Git hooks, which are scripts that Git runs automatically before or after certain Git operations.

Common Git Hook Events
# pre-commit  — Runs BEFORE each commit is finalized
#               Use: check for secrets, lint code, format files

# commit-msg   — Runs AFTER the commit message is written
#               Use: validate commit message format

# pre-push     — Runs BEFORE pushing to a remote repository
#               Use: run tests, verify build passes

# post-merge   — Runs AFTER a branch is merged
#               Use: install dependencies, update lock files

The Alarm System Analogy

Think of hooks like an alarm system in a building. You do not have to remember to lock every door and window each night — the alarm system monitors them automatically. If a door is opened without authorization, the alarm triggers instantly. In the same way, hooks monitor your workflow automatically:

Analogy: A pre-commit hook is like a security guard who checks your bags before you leave the building. A pre-push hook is like a final inspection before goods are shipped to the customer. You could do these checks yourself every time, but hooks ensure they never get skipped — even when you are in a hurry or forget.

In the AI harness, hooks can also be defined at the tool level. For example, Claude Code hooks can trigger scripts when an AI agent attempts to edit a file, providing an additional layer of enforcement beyond what Git hooks offer.

CI/CD Basics

CI/CD stands for Continuous Integration / Continuous Delivery. These are practices that automate the process of testing and deploying code changes. While CI/CD is a broad topic in software engineering, understanding the basic concepts will help you understand how the AI harness ensures quality.

Continuous Integration (CI)

Continuous Integration means automatically building and testing code every time someone pushes changes. Instead of waiting for a designated "testing day," every change is tested immediately. This catches bugs and issues early, when they are easiest to fix.

In the AI harness context, CI means running audit scripts, validation checks, and tests automatically whenever a Pull Request is created or updated.

Continuous Delivery (CD)

Continuous Delivery means automatically preparing code changes for release. After tests pass, the system can deploy the changes to production with minimal manual intervention. The key word is "delivery" — the changes are prepared and ready to ship, but a human still approves the final release.

In the AI harness, CD means that once a PR is approved and merged, the updated workspace is automatically available to all team members and variants.

GitHub Actions Example

The most common CI/CD tool used with GitHub is GitHub Actions. Here is what a simple CI workflow looks like in concept:

Conceptual GitHub Actions Workflow
# This runs automatically when a PR is created
on: pull_request

jobs:
  audit:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: bun install
      - run: bun scripts/audit.ts        # Validate workspace
      - run: bun scripts/validate-skills.ts  # Check skills

  security:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: gitleaks detect              # Scan for secrets
This is a conceptual overview. As a beginner, you do not need to configure CI/CD pipelines yourself. The AI harness comes with pre-configured automation. Understanding these concepts helps you read error messages, understand why a PR might be blocked, and appreciate how automation keeps the project healthy. When you are ready to dive deeper, GitHub has excellent documentation on GitHub Actions.

How dev-sync.ts Works

The scripts/dev-sync.ts script is the TypeScript implementation that powers the sync pipeline. It is the engine behind the /sync command. Let us look at what it does internally.

Purpose

dev-sync.ts synchronizes changes across the 3-level inheritance hierarchy. When you modify files at the L0 workspace root or the L1 common template, dev-sync.ts ensures those changes propagate correctly to all downstream variant projects (L2). This is critical because the L2 variants inherit their base structure from L0 and L1 — without sync, changes at the top would never reach the variants that depend on them.

The 4-Step Process

  1. Detect changes — The script compares the current state of L0 and L1 files against the last known state. It identifies which files were added, modified, or deleted since the last sync.
  2. Validate contracts — Before propagating anything, the script checks that the changes comply with the common contracts. If a change would break a contract (for example, renaming a file that other projects depend on), the script reports the violation and halts.
  3. Publish changes — Validated changes are copied from L0 to L1 (or from L1 to L2 variants). The script preserves variant-specific customizations while applying shared updates.
  4. Verify integrity — After publishing, the script runs a final verification to ensure every downstream project is in a valid state. This includes checking that all inherited files are present and that no conflicts exist.
Think of it like headquarters sending updates to branch offices. When the corporate headquarters (L0) updates its employee handbook, it does not expect every branch office (L1, L2) to manually copy the new handbook. Instead, the update is published through a distribution system (dev-sync.ts) that sends the changes to every branch automatically. Each branch receives the updates while keeping its own local customizations intact.
Always commit your work before running dev-sync.ts. The sync script operates on the committed state of the repository. If you have uncommitted changes, the script may produce unexpected results or fail to detect the correct diff. Run git status first to confirm your working directory is clean, or commit all pending changes before starting the sync.

Running dev-sync.ts Manually

While /sync runs the full pipeline automatically, you can also run dev-sync.ts directly when you need more control.

Running dev-sync.ts
# Run the sync script directly
bun scripts/dev-sync.ts

# The script will:
# 1. Detect changes at L0 and L1
# 2. Validate against common contracts
# 3. Publish changes to downstream variants
# 4. Verify integrity of all projects

# Check for help and available options
bun scripts/dev-sync.ts --help
Warning: The dev-sync.ts script is a core synchronization tool — it must remain standardized and identical across all templates and variants. Direct modification of this core script in L3 projects is strictly forbidden. If a variant needs custom verification checks, it should implement them in a separate pluggable hook script at scripts/audit-variant.ts instead.

Practice: Walk Through a Workflow

Now let us put everything together by walking through a realistic workflow from start to finish. The goal: make a file change, commit it, and run /sync to complete the full automation pipeline.

Before you start: Always check which branch you are on with git branch. Make sure you are on a feature branch (not directly on main) before making changes. Working directly on main bypasses the PR review process, which can introduce instability.
  1. Create a feature branch. Start by creating a new branch for your work. This isolates your changes from the main branch and allows for review before merging. 
    git checkout -b feature/update-agent-tier
  2. Make your changes. Edit the files you need to modify. For example, you might update an agent's tier in its markdown file, add a new skill, or fix a documentation error. Use the Version Agent to snapshot files before editing.
  3. Review your changes. Before committing, review what you changed to make sure everything looks correct. 
    git status          # See which files changed
git diff            # See the actual differences
  4. Commit your changes. Stage and commit with a clear conventional commit message. 
    git add agents/my-agent.md
git commit -m "feat(agent): update tier from low to medium"
  5. Run /sync. Execute the sync command with a descriptive message. The pipeline will run the audit, update lifecycle records, push the commit, and create a PR. 
    /sync "feat(agent): update tier from low to medium"
  6. Review and merge the PR. Once the PR is created, review it on GitHub. If automated checks pass and the changes look correct, merge the PR into the main branch.

What Happens Behind the Scenes

When you follow this workflow, here is what the system does at each step:

You: Create branch → Edit files → Review → Commit → /sync
System (Step 1 — Lifecycle): Detects that an agent file changed → Updates the agent lifecycle record in docs/lifecycle/agents/
System (Step 2 — Audit): Runs audit.ts → Validates file structure, frontmatter, naming conventions → All checks pass
System (Step 3 — Publish): Checks if the change affects L0 shared files → If so, propagates to L1 template
System (Step 4 — Commit): Your commit is already recorded → Lifecycle files are committed with the sync message
System (Step 5 — Push + PR): Pushes to GitHub → Creates a PR titled "feat(agent): update tier from low to medium" → CI runs automatically on the PR
Result: Your change is reviewed, tested, and ready to merge — all from a single /sync command
Practice makes perfect. Try this workflow with a small, low-risk change first — like updating a typo in documentation. Once you are comfortable with the full cycle (branch, edit, commit, /sync, review PR), you can tackle larger changes like adding new agents or creating new skills with confidence. The automation handles the routine steps; you focus on the creative work.
