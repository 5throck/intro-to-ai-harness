Capítulo 12

Comprendiendo flujos de trabajo y automatización

Este capítulo cubre la automatización de flujos de trabajo en el harness de IA — el comando /sync, los PRs de Git/GitHub, los hooks, lo básico de CI/CD y cómo funciona dev-sync.ts.

Lo que cubre este capítulo
  • Why automation matters
  • How /sync works
  • Git and GitHub PR basics
  • Hook concepts
  • CI/CD basics
  • dev-sync.ts internals
  • Practice: walk through a full workflow

What Is Automation

Imagina que tuvieras que lavar cada prenda a mano — frotando, enjuagando y escurriendo cada artículo individualmente. Tomaría horas cada semana. Luego alguien inventó la lavadora: cargas la ropa, presionas un botón y la máquina maneja el ciclo completo automáticamente. Eso es la automatización — reemplazar los pasos manuales repetitivos con un sistema que los ejecuta por ti.

El mismo principio se aplica al desarrollo de software y a los flujos de trabajo de agentes de IA. En los capítulos anteriores, aprendiste cómo colaboran los agentes para producir investigaciones, presentaciones y manuales. Pero, ¿qué sucede después de que un agente termina su trabajo? ¿Cómo se guardan, verifican y comparten los cambios? Ahí es donde entra en juego la automatización del flujo de trabajo.

Manual vs. Automated

Comparemos cómo se ve un flujo de trabajo típico con y sin automatización.

Without Automation (Manual)

  • Run audit checks yourself
  • Update version files by hand
  • Commit changes with git commands
  • Push to GitHub manually
  • Create a Pull Request through the web UI
  • Copy shared changes to every variant project
  • Risk: forgetting a step, typos, inconsistent versions

With Automation (/sync)

  • Audit runs automatically
  • Version files update automatically
  • Commit message generated for you
  • El push ocurre como parte del pipeline
  • PR created with a single command
  • L0 changes propagate to all variants
  • Result: consistent, reliable, repeatable

The Washing Machine Analogy

Piensa en el comando /sync como la lavadora de tu proyecto. En lugar de hacer manualmente cada paso del flujo de trabajo posterior (auditoría, actualización de versión, commit, push, creación de PR), ejecutas un solo comando y el sistema maneja todo el ciclo. Cargas la "ropa" (tus archivos modificados), presionas el botón (/sync) y la máquina se encarga del resto.

Esta analogía se extiende más allá: al igual que una lavadora tiene diferentes ciclos (delicado, ciclo pesado), la tubería de automatización se puede configurar para diferentes escenarios. Y al igual que una lavadora asegura que tu ropa esté consistentemente limpia, la automatización asegura que tu proyecto se mantenga consistentemente.

La automatización no reemplaza el pensamiento — reemplaza la repetición. Todavía decides qué cambios hacer y cuándo ejecutar el sync. La automatización simplemente asegura que una vez que tomas esa decisión, todos los pasos rutinarios que siguen se ejecuten correctamente y de manera consistente cada vez.

Understanding the /sync Command

El comando /sync es el comando central de automatización en el harness de IA. Encapsula el flujo de trabajo posterior completo en una única invocación. Cada vez que terminas una tarea que modificó archivos — añadir un agente, actualizar una habilidad, cambiar un script — ejecutas /sync para finalizar el trabajo correctamente.

The 5-Step Sync Pipeline

Cuando invocas /sync, el sistema ejecuta cinco pasos en secuencia. Cada paso depende de que el anterior haya finalizado con éxito.

  1. Actualización del Ciclo de Vida (Lifecycle Update) — El sistema comprueba si algún artefacto rastreado por el ciclo de vida ha cambiado (agentes, habilidades, scripts, archivos de gobernanza). Si es así, actualiza los registros relevantes del ciclo de vida y CHANGELOG.md para reflejar los cambios.
  2. Auditoría (Audit) — El script scripts/audit.ts ejecuta una verificación exhaustiva del workspace. Valida la estructura de archivos, las convenciones de nomenclatura, la integridad del frontmatter, las referencias cruzadas y el cumplimiento contractual. Cualquier error se informa y debe corregirse antes de continuar.
  3. Publicar (L0→L1) — Si se realizaron cambios en la raíz del workspace L0, esos cambios se publican hacia abajo en la plantilla común L1. Esto asegura que todas las variantes hereden los últimos estándares.
  4. Commit — Todos los cambios se confirman en git con un mensaje de commit convencional. El mensaje incluye un prefijo de tipo (feat, fix, docs, etc.), un alcance y una descripción de lo que cambió.
  5. Push + PR — El commit se envía al repositorio remoto y se crea automáticamente un Pull Request (o se actualiza uno existente) para revisión.
Consejo: El comando /sync toma un mensaje de commit convencional como argumento, por ejemplo: /sync "feat(pm): add meeting facilitation skill". El sistema utiliza este mensaje para el commit de git, por lo que escribir un mensaje claro y descriptivo es importante. El formato sigue el patrón type(scope): description.

When to Run /sync

Debes ejecutar /sync al final de cualquier sesión de trabajo que haya modificado los archivos del proyecto. Específicamente:

  • After adding, modifying, or deprecating an agent
  • After creating, updating, or removing a skill
  • Después de cambiar un script o su estado en SCRIPTS.md
  • After modifying governance files (AGENTS.md, CLAUDE.md, GEMINI.md)
  • Después de cualquier cambio en common-contract.json o en archivos de plantilla
No necesitas ejecutar /sync por cada pequeño cambio. Para los cambios solo de documentación (actualizaciones del cuerpo del texto, entradas de registro de memoria) que no afectan a los artefactos rastreados por el ciclo de vida, simplemente puedes hacer commit y push manualmente. La tubería /sync está diseñada para cambios que afectan la integridad estructural del proyecto.

Git & GitHub PR

Para comprender cómo funciona la tubería de automatización, necesitas una comprensión básica de Git y de los Pull Requests de GitHub. Estas son las herramientas que sustentan cada paso del flujo de sync después de la auditoría.

Git Basics

Git es un sistema de control de versiones que rastrea cada cambio realizado en los archivos de un proyecto. Piénsalo como un diario detallado de la historia de tu proyecto. Cada vez que guardas un conjunto de cambios, Git registra quién hizo el cambio, cuándo se hizo y qué cambió exactamente.

Aquí están los comandos esenciales de Git que encontrarás en el flujo de trabajo del harness de IA.

Essential Git Commands
# Check what files have changed
git status

# See the actual differences in changed files
git diff

# Save changes to a "staging area" (preparing to commit)
git add <filename>

# Record the staged changes with a message
git commit -m "type(scope): description"

# Send commits to the remote repository (GitHub)
git push

# Download the latest changes from the remote
git pull

# Create a new branch (a parallel line of work)
git checkout -b feature/my-new-feature

# See the commit history
git log --oneline

GitHub Basics

GitHub es una plataforma web que aloja repositorios Git. Añade funciones de colaboración sobre Git: gestión de acceso al equipo, herramientas de revisión de código, seguimiento de problemas y Pull Requests. Tu workspace de IA vive en GitHub, y la tubería sync interactúa con él para enviar cambios y crear PRs.

Pull Requests (PRs)

Un Pull Request (PR) es una propuesta para fusionar cambios de una rama en otra. Es el mecanismo estándar para la revisión de código en proyectos colaborativos.

  1. Crear una rama — Creas una nueva rama (una copia paralela del código) donde realizas tus cambios. Esto mantiene la rama principal estable mientras trabajas.
  2. Hacer cambios y hacer commit — Editas archivos, añades nuevos agentes o habilidades y haces commit de esos cambios en tu rama.
  3. Abrir un PR — Creas un Pull Request que dice: "por favor, revisen estos cambios y fusionen en la rama principal."
  4. Review — Los miembros del equipo (o las comprobaciones automatizadas) revisan los cambios, dejan comentarios y solicitan modificaciones si es necesario.
  5. Fusionar (Merge) — Una vez aprobado, el PR se fusiona en la rama principal y tus cambios forman parte del proyecto oficial.
En el harness de IA, las operaciones de Git son manejadas en gran medida por ti. Cuando ejecutas /sync, la tubería se encarga de staging, committing, pushing y creación del PR. No necesitas memorizar cada comando de Git. Sin embargo, comprender los conceptos te ayuda a entender lo que la automatización está haciendo detrás de escena.

Hooks

Un hook es un script que se ejecuta automáticamente cuando ocurre un evento específico. La palabra "hook" proviene de la pesca: al igual que un anzuelo atrapa a un pez cuando pasa, un hook de código captura un evento y ejecuta un script en respuesta.

How Hooks Work

En el harness de IA, los hooks se utilizan para hacer cumplir reglas y automatizar verificaciones en momentos clave. En lugar de depender de que los desarrolladores recuerden ejecutar las comprobaciones manualmente, los hooks aseguran que estas verificaciones ocurran automáticamente cada vez que se dispara el evento relevante.

El tipo más común de hooks son los Git hooks, que son scripts que Git ejecuta automáticamente antes o después de ciertas operaciones de Git.

Common Git Hook Events
# pre-commit  — Runs BEFORE each commit is finalized
#               Use: check for secrets, lint code, format files

# commit-msg   — Runs AFTER the commit message is written
#               Use: validate commit message format

# pre-push     — Runs BEFORE pushing to a remote repository
#               Use: run tests, verify build passes

# post-merge   — Runs AFTER a branch is merged
#               Use: install dependencies, update lock files

The Alarm System Analogy

Piensa en los hooks como un sistema de alarma en un edificio. No tienes que recordar cerrar cada puerta y ventana por la noche — el sistema de alarma los monitorea automáticamente. Si se abre una puerta sin autorización, la alarma se activa instantáneamente. De la misma manera, los hooks monitorean tu flujo de trabajo automáticamente:

Analogía: Un hook pre-commit es como un guardia de seguridad que revisa tus maletas antes de salir del edificio. Un hook pre-push es como una inspección final antes de que la mercancía se envíe al cliente. Podrías hacer estas comprobaciones tú mismo cada vez, pero los hooks aseguran que nunca se omitan — incluso cuando tienes prisa o lo olvidas.

En el harness de IA, también se pueden definir hooks a nivel de herramienta. Por ejemplo, los Claude Code hooks pueden activar scripts cuando un agente de IA intenta editar un archivo, proporcionando una capa adicional de cumplimiento más allá de lo que ofrecen los Git hooks.

CI/CD Basics

CI/CD significa Integración Continua / Entrega Continua. Estas son prácticas que automatizan el proceso de prueba y despliegue de cambios de código.

Continuous Integration (CI)

Integración Continua significa construir y probar el código automáticamente cada vez que alguien envía cambios. En lugar de esperar un "día de pruebas" designado, cada cambio se prueba inmediatamente. Esto detecta errores y problemas temprano, cuando son más fáciles de arreglar.

En el contexto del harness de IA, CI significa ejecutar scripts de audit, comprobaciones de validación y pruebas automáticamente cada vez que se crea o actualiza un Pull Request.

Continuous Delivery (CD)

Entrega Continua significa preparar automáticamente los cambios de código para su lanzamiento. Después de que las pruebas pasan, el sistema puede implementar los cambios en producción con una mínima intervención manual. La palabra clave es "entrega" — los cambios están preparados y listos para ser enviados, pero un humano aún aprueba el lanzamiento final.

En el harness de IA, CD significa que una vez que un PR es aprobado y fusionado, el workspace actualizado está automáticamente disponible para todos los miembros del equipo y variantes.

GitHub Actions Example

La herramienta CI/CD más común utilizada con GitHub es GitHub Actions.

Conceptual GitHub Actions Workflow
# This runs automatically when a PR is created
on: pull_request

jobs:
  audit:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: bun install
      - run: bun scripts/audit.ts        # Validate workspace
      - run: bun scripts/validate-skills.ts  # Check skills

  security:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: gitleaks detect              # Scan for secrets
Esta es una visión conceptual. Como principiante, no necesitas configurar tú mismo las tuberías CI/CD. El harness de IA viene con automatización preconfigurada. Comprender estos conceptos te ayuda a leer los mensajes de error, entender por qué un PR podría estar bloqueado y apreciar cómo la automatización mantiene el proyecto saludable.

How dev-sync.ts Works

El script scripts/dev-sync.ts es la implementación en TypeScript que impulsa la tubería sync. Es el motor detrás del comando /sync.

Purpose

dev-sync.ts sincroniza los cambios a través de la jerarquía de herencia de 3 niveles. Cuando modificas archivos en la raíz del workspace L0 o en la plantilla común L1, dev-sync.ts asegura que esos cambios se propaguen correctamente a todos los proyectos variante descendientes (L2). Esto es crítico porque las variantes L2 heredan su estructura base de L0 y L1.

The 4-Step Process

  1. Detectar cambios — El script compara el estado actual de los archivos L0 y L1 con el último estado conocido. Identifica qué archivos se agregaron, modificaron o eliminaron desde la última sincronización.
  2. Validar contratos — Antes de propagar cualquier cosa, el script comprueba que los cambios cumplan con los contratos comunes.
  3. Publicar cambios — Los cambios validados se copian de L0 a L1 (o de L1 a las variantes L2). El script preserva las personalizaciones específicas de la variante mientras aplica las actualizaciones compartidas.
  4. Verificar integridad — Después de publicar, el script ejecuta una verificación final para asegurar que cada proyecto descendiente esté en un estado válido.
Piénsalo como la oficina central enviando actualizaciones a las oficinas sucursales. Cuando la sede corporativa (L0) actualiza su manual del empleado, la actualización se publica a través de un sistema de distribución (dev-sync.ts) que envía los cambios a cada sucursal automáticamente.
Siempre haz commit de tu trabajo antes de ejecutar dev-sync.ts. El script sync opera sobre el estado confirmado del repositorio. Si tienes cambios sin confirmar, el script puede producir resultados inesperados.

Running dev-sync.ts Manually

Si bien /sync ejecuta la tubería completa automáticamente, también puedes ejecutar dev-sync.ts directamente cuando necesitas más control.

Running dev-sync.ts
# Run the sync script directly
bun scripts/dev-sync.ts

# The script will:
# 1. Detect changes at L0 and L1
# 2. Validate against common contracts
# 3. Publish changes to downstream variants
# 4. Verify integrity of all projects

# Check for help and available options
bun scripts/dev-sync.ts --help
Advertencia: El script dev-sync.ts es una herramienta de sincronización central — debe permanecer estandarizado e idéntico en todas las plantillas y variantes. La modificación directa de este script central en proyectos L3 está estrictamente prohibida.

Practice: Walk Through a Workflow

Ahora pongamos todo junto recorriendo un flujo de trabajo realista de principio a fin. El objetivo: hacer un cambio en un archivo, hacerlo commit y ejecutar /sync para completar la tubería de automatización completa.

Antes de comenzar: Siempre comprueba en qué rama estás con git branch. Asegúrate de estar en una rama de característica (no directamente en main) antes de hacer cambios.
  1. Crea una rama de característica. Comienza creando una nueva rama para tu trabajo. Esto aísla tus cambios de la rama principal y permite la revisión antes de fusionar. 
    git checkout -b feature/update-agent-tier
  2. Haz tus cambios. Edita los archivos que necesitas modificar. Por ejemplo, puedes actualizar el tier de un agent en su archivo markdown, añadir una nueva skill o corregir un error de documentación. Usa el Version Agent para tomar instantáneas de los archivos antes de editarlos.
  3. Revisa tus cambios. Before committing, review what you changed to make sure everything looks correct. 
    git status          # See which files changed
git diff            # See the actual differences
  4. Haz commit de tus cambios. Etiqueta y haz commit con un mensaje de commit convencional claro. 
    git add agents/my-agent.md
git commit -m "feat(agent): update tier from low to medium"
  5. Ejecuta /sync. Ejecuta el comando sync con un mensaje descriptivo. La tubería ejecutará la auditoría, actualizará los registros del ciclo de vida, enviará el commit y creará un PR. 
    /sync "feat(agent): update tier from low to medium"
  6. Revisa y fusiona el PR. Una vez creado el PR, revísalo en GitHub. Si las comprobaciones automatizadas pasan y los cambios se ven correctos, fusiona el PR en la rama main.

What Happens Behind the Scenes

Cuando sigues este flujo de trabajo, esto es lo que el sistema hace en cada paso:

You: Create branch → Edit files → Review → Commit → /sync
System (Step 1 — Lifecycle): Detecta que cambió un archivo de agent → Actualiza el registro del ciclo de vida del agent en docs/lifecycle/agents/
System (Step 2 — Audit): Runs audit.ts → Validates file structure, frontmatter, naming conventions → All checks pass
System (Step 3 — Publish): Comprueba si el cambio afecta a los archivos compartidos de L0 → Si es así, propaga a la plantilla L1
System (Step 4 — Commit): Tu commit ya está registrado → Los archivos del ciclo de vida se confirman con el mensaje de sync
System (Step 5 — Push + PR): Sube los cambios a GitHub → Crea un PR titulado "feat(agent): update tier from low to medium" → CI se ejecuta automáticamente en el PR
Result: Tu cambio queda revisado, probado y listo para fusionar — todo con un solo comando /sync
Practice makes perfect. Prueba este flujo de trabajo primero con un cambio pequeño y de bajo riesgo — como corregir una errata en la documentación. Una vez que te sientas cómodo con el ciclo completo (branch, editar, commit, /sync, revisar PR), podrás abordar con confianza cambios mayores como añadir nuevos agents o crear nuevas skills. La automatización maneja los pasos rutinarios; tú te concentras en el trabajo creativo.
